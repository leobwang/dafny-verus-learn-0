## 1. Rationale

### 1.1 The gateway exposure and the two network routes

A container on a `--internal` network has one on-link route, to its subnet, and the subnet's gateway address is a host interface. Traffic to it is host input, not forwarded traffic, so Docker's isolation rules for internal networks (which drop forwarding into and out of the bridge) do not cover it. Any host service bound to all addresses then answers the container: sshd on 22, the firecrawl API on 3002 (a web-fetching service, which would be an egress route around every network rule and a contamination route for benchmark answers), and whatever runs on 902, on IPv4 and, if the container's interface has IPv6, on IPv6 too (§0.1 item 17: all three listen on `[::]`). The gate itself, bound to one bridge's gateway address, is also host input for containers on every other bridge (the firecrawl stack's included). This is the expected kernel behaviour, **not observed**: step 2c must show it before any filter is built, and the containment controls test it on every run.

- **Route B (plan of record):** `--network none`; the gate listens on a Unix socket `state/ollama.sock` in the run directory (mode 0600, owner uid 1000), bind-mounted at `/run/dvl/ollama.sock`; the image's entry starts a 30-line standard-library relay on `127.0.0.1:11434` → the socket before it execs the agent. The agent can kill the relay and gain nothing; a connection straight to the socket meets the same gate. Route B removes DNS, every host port, IPv6, other bridges and the per-run network objects at once, and needs no capability. In Claude agent mode the egress proxy uses a second socket and relay (`127.0.0.1:3128`, `HTTPS_PROXY=http://127.0.0.1:3128`). The probe: a bind-mounted Unix socket accepts connections under the docker-default AppArmor profile with `--cap-drop ALL` (the Docker socket's common use suggests it does; not observed here).
- **Route A (fallback):** a holder container on the internal network with `--sysctl net.ipv6.conf.all.disable_ipv6=1`; a `dvl-netfilter` container `--network container:<holder> --cap-add NET_ADMIN`, which sets the namespace's IPv4 and IPv6 OUTPUT policies to DROP and admits `-o lo` and `-d <gateway> -p tcp --dport <gate port>`, then exits; the agent `--network container:<holder>` with `--cap-drop ALL` (it cannot set sysctls itself: they belong to the holder's namespace). The gate checks each connection's peer address against the holder's. Docker's embedded DNS at 127.0.0.11 is loopback traffic in that namespace, so name resolution for external names must be checked separately (control C8); passing `--dns` with an unreachable resolver is the candidate fix.

### 1.2 Why the forwarder must speak HTTP

Ollama's API on the same port serves `/api/pull` (fetches from the public registry: an egress channel), `/api/push`, `/api/create`, `/api/copy` and `/api/delete` (removes the user's 17–112 GB models). Δ61's TCP forwarder passes all of them. The gate's endpoint allowlist, model allowlist and option pinning close this and make Δ65's request pins enforceable whatever the client sends. The OpenAI-compatible endpoint that opencode's provider uses (`/v1/chat/completions`) reports token usage but not Ollama's durations, so the gate times each request itself; with one request in flight per run, busy seconds approximate GPU occupancy. A partly offloaded model (flash-next) is recorded with `/api/ps`'s `size_vram` so its GPU-seconds are not compared with a fully resident model's. Ollama cuts an over-long prompt to `num_ctx` without an error, so a run whose context saturates is measuring a different task; the gate's `ctx-saturated` flag makes that visible, and setting opencode's model context limit to `num_ctx` lets opencode compact first.

### 1.3 Credentials

**Why strip the refresh token (host policy mode).**

- The CLI rewrites `.credentials.json` when it refreshes (§0.1 item 9: expiry exactly 8.00 h after the last write). A process given a full copy in another `CLAUDE_CONFIG_DIR` would refresh into its copy when its access token nears expiry. OAuth refresh-token rotation is common practice; if the provider rotates refresh tokens, the copy's refresh invalidates the user's stored refresh token and logs the user's own sessions out the next time they refresh. Not observed; the derived snapshot avoids the question.
- With a snapshot that holds only the access token, a call can never refresh, so nothing writes to it and a leaked copy dies with the access token. Rebuilding it before each call picks up any refresh the user's own sessions made in between.
- `setup-token` (a long-lived token in `CLAUDE_CODE_OAUTH_TOKEN`) was considered and rejected: its lifetime is unknown and long by name, it travels in the environment (visible to every process in the container), and revoking it is a manual step.

**Why agent mode needs more than a read-only snapshot (the review's finding).** In Claude agent mode the CLI's own tool processes (Bash and whatever it starts) run as the same uid, in the same network namespace, with `HTTPS_PROXY` set. A read-only snapshot is readable by them. A pass-through `CONNECT` proxy sees only `api.anthropic.com:443` for both the CLI and a tool process, so a tool process could (a) make model calls outside the CLI's stream, which `fvh`'s budget would never count, and (b) send requests that ask the API for server-side tools (web search and the like), a route to public benchmark answers (X17) through the one allowed host. Two layers close this:

1. **TLS termination with a request policy.** The proxy sees every request: it admits only the inference endpoint (and whatever the probe shows the CLI needs at start-up), refuses any request whose `tools` contain a server-side type (an allowlist: only client tool definitions, which carry an input schema and no server type) or that names remote MCP servers, and counts calls and tokens itself. A call by a tool process is then counted and policed like any other, and the mismatch with the CLI's stream is a run finding. The per-run CA is made by the host's `openssl` (the standard library cannot make certificates); its key never enters the container.
2. **No usable token in the container (preferred).** If the CLI accepts a placeholder credential, the proxy injects the real access token per request from the user's own file. A tool process then has nothing to exfiltrate, the proxy never refreshes (so the user's refresh token is untouched), and a refresh by the user's sessions mid-run is absorbed. Risks the probe must rule out: the CLI validates the token by calling an endpoint first (the proxy can inject there too, if the endpoint is admitted); the CLI pins certificates (then `NODE_EXTRA_CA_CERTS` is not enough, and the preferred form fails); the CLI tries to refresh because it distrusts the placeholder's expiry.

If (2) fails, the fallback keeps the read-only snapshot and confines tool processes with Claude Code's command sandbox (bubblewrap on Linux per the binary's strings): reads of the credentials path denied and no network for commands. Design §13.3's opening found bubblewrap's network unsharing failing inside a Claude session on this host (AppArmor's restriction on unprivileged user namespaces); inside a container with the default seccomp profile, user namespaces are usually refused too, which is why the binary's `enableWeakerNestedSandbox` exists. Whether the weaker mode still denies the credentials read and the network is the probe. If neither (2) nor the confined fallback works, harness-executed runs are the only Claude route, which design D6 already allows.

**The D6 probe protocol (step 4c), with the user present.** Every step records the init event, the result's `is_error`, `api_error_status` and `num_turns`, the proxy log, and `claude auth status --json` on the host (identifying fields redacted) before and after; no token value is ever printed or stored.

1. Build the derived snapshot: load the host file, drop `refreshToken` and `refreshTokenExpiresAt`, write it 0600 under `$XDG_RUNTIME_DIR/dvl-runs/<random>/state/config/.credentials.json`.
2. Host policy call with that `CLAUDE_CONFIG_DIR` (one call): does it run? Is the host file's mtime unchanged afterwards?

Which hosts, paths and methods did the CLI request (with and without the four switches: two runs)? Did any authenticated request bypass injection (a 401 the proxy logged)?
4. Controls C21–C25 in that run (§2.2).
5. **Only if step 3 fails:** the read-only snapshot, `chmod 0400`, bind-mounted, with the command sandbox enabled in `agent-settings.json` (and `enableWeakerNestedSandbox` if needed): one short run, then C21 and C22 in the snapshot form.

Outcome: step 2 passes and step 3 passes → Claude agent mode in the preferred form; step 3 fails and step 5 passes → agent mode in the fallback form, runs bounded by the token's remaining life (and by C23's answer); otherwise harness-executed runs only. Step 2 fails → host policy mode uses a link to the user's own credentials file (probe whether a refresh writes through the link or replaces it).

### 1.4 The self-test's study-mode limits (an oracle the plan avoids)

A membership test over the twins' answer fingerprints, run in a study checkout, would answer "does this file share a window with the reference?" for any file the learner (or Claude) puts into a manifest, which is an answer oracle for every hole (put a candidate line into an editable file, run `--selftest-only`, read the verdict). `contract_local.sh` mounts the learner's own work, which may legitimately match the reference. So study-mode runs check only closure, canaries, attestation and public answers, and the reference fingerprints and leak patterns run only under `--author` (rule 1b keeps a study session from calling it). Design §13.3 item 2 asks for the scan on every run; the plan records the departure as P6.

- **Canaries without a secret.** A canary token `DVLCANARY-<suffix>` is detected by its public prefix, so a study-mode run needs no secret and reads no reference tree. The hash list attributes a hit to its tree. A planted prefix in a learner's own file would only make their own run refuse.
- **Attested task cards.** Lab task cards are static course files whose stripped forms the author can scan once against the reference in the author's context; a study-mode run then needs only the hash. This keeps design §13.3 item 2's intent for the lab material, the place where a mis-stripped card would leak most.
- **The public-answer window.** Seven tokens matched idioms such as `forall i :: 0 <= i <` (the review's example) and would fail legitimate runs as infrastructure failures. Long windows, a count of distinct windows per answer file, and the exclusion of text that the given layers, the shipped task form and the public task file already contain make the check measure copying, not shared vocabulary. Step 1b calibrates on Q01–Q06's shipped files and the sets' task forms (no false positive allowed there).

### 1.5 Why a curated minimal course root in the container

The contract acceptance lines name `scripts/vcheck --gate <file>`, `scripts/vaudit <file>` and `scripts/specfreeze --against <snapshot> <file>`; the verification container must give the same verdict as the host, and the agent must be able to run its own acceptance. Copying the real `scripts/vcheck`, `scripts/vaudit`, `scripts/specfreeze`, `scripts/dvl/`, `scripts/course_items.py`, `MODULES.toml`, the module's generated unit files, its `expected/<ID>.counts` and `.freeze` and the `.audit` pins a CONTRACT names (all learner-visible, none reference) keeps one gate implementation. `expected/` is on the *Predictions first* list, but the agent under test is not a learner and these pins answer nothing a contract asks. The snapshot is the learner's own committed file, read from git, never the working tree. The parity acceptance (§5.9) proves the copy behaves like the host.

### 1.6 Containers and the memory rules

`systemd-run --user --scope … docker run` puts the Docker client in the scope, not the container: the container's processes are children of `containerd-shim` under the daemon's cgroup. Only `--memory` (with `--memory-swap` equal, so no swap is used) caps them, and `docker inspect --format '{{.State.OOMKilled}}'` tells a memory kill apart from a crash, which is better evidence than an exit code of 137. tmpfs pages are charged to the container's memory cgroup, so the `/work`, `/tmp` and home tmpfs caps are part of `--memory`.

The first draft required `memory.max` ≤ cap + 1 GB in every container, while agent containers got cap + 4 GB: every in-container verification in an agent container would have been refused, and the Qwen agent would have had no feedback (the review's finding). The two modes fix the contradiction. In `container-agent` mode the agent and one solver job share the container; a cross-pool `flock` keeps the course tools from starting a second solver beside it, and the container cap stays the hard bound for anything the agent starts by other means. When a solver inside is OOM-killed, the container usually survives (the kernel picks the largest process), so the job's `killed(memory)` comes from the cgroup's `memory.events` `oom_kill` count, not from `docker inspect`. The modes' limits come from the read-only pins; an agent that changes `DVL_CAP` gains nothing, because both bounds are checked against the container's own `memory.max`.

### 1.7 The pinned version file and auto-update

The versions directory keeps old builds (2.1.287 still present), so pinning the absolute version file survives an update of the `claude` link; the apparatus check refuses when the pinned file's sha256 changes or the file disappears. This does not need H3, but H3 keeps the user's interactive sessions on the same version as the harness, which keeps `guard_doors.py`'s results meaningful. Writing the path relative to `HOME` in the apparatus file is what makes the CI tripwire hold: under CI's empty `HOME` the binary does not exist.

### 1.8 opencode's provider package and extra calls

The DV0 config names `"npm": "@ai-sdk/openai-compatible"`. If opencode installs provider packages on first use into its cache, every isolated run would fetch from the npm registry (a network dependency in host policy mode, and a failure inside a network-less container). Step 3a checks with an empty cache and the network blocked; if a fetch is needed, the package is pinned (tarball sha256) and pre-seeded into each run's `XDG_CACHE_HOME`, and baked into `dvl-agent`. opencode may also send requests that are not agent turns (session titles, context compaction); the gate counts them, so Q07's 40-call cap and its turn cap can disagree. Step 3a measures requests per turn before the replay is armed; the run config disables title generation or uses a small-model setting only if opencode's config allows, otherwise the turn cap drops.

### 1.9 Why the single-route rule is a CI step, not a hook change

`scan_file` returns early for every 2f and 2g file (`trusted`), so the 1f words in `scripts/` and `harness/fvh/` are never scanned when such a file is named on a shell line. Narrowing that early return to the entry points would make the hook refuse `bash scripts/test_hooks.sh` and `scripts/ci.sh` (their fixtures and the tripwire shims name `docker` and `opencode` on purpose), `scripts/gen_hook_fixtures.py`, and `tests/acceptance/guard_doors.py` (doors f and g). A build-time allowlist check catches the real risk (a later script that starts a container or an agent outside `mksandbox-run`, or calls `sudo`) without those false refusals, and it runs in every `ci.sh` before a merge.

### 1.10 The provenance rule: why the default is `agent`

The review found that QPLAN's `fvh.tools.run` (a host subprocess) and DV4's executor runners were two designs, so a later gate (Q18's gate v2, a lab gate) written against `fvh.tools.run` would verify agent deliveries on the host. Verification can run agent-written code (Dafny `--target py` tests, Verus `--compile` tests, Python acceptance tests), and even a plain verification of a crate parses a project file an agent may have written; N2 forbids it. One interface with a fail-closed provenance rule settles it: only paths the course itself declares can run on the host; everything else, including files a learner copies out of `research/`, defaults to `agent`. The cost is that Docker is needed to gate anything that is not a course file, which every such use case needs anyway.

`get_bench.sh --validate` stays on the host: it verifies public answers, not agent output, through the course wrappers (which refuse skip options and build scripts), and it runs no test. If a set ever needs its tests run, that part goes through the verification container.

### 1.11 Ledger anchors and the truncation outcome

A hash chain detects an edited line but not a missing file. `research/runs/` may be gitignored (§14 Q12), a learner's `git clean -fdx` removes it, and a fresh clone lacks it; any of these silently returns `qwen_runs` or a lab's attempt plan to zero, and a restart then becomes best-of-n. Anchoring each batch's head in a tracked file makes a reset an explicit, visible act. An `open` anchor without its `close` means a batch died mid-way; requiring `fvh resume` there keeps a crash from becoming a fresh draw.

The first draft scored every attempt with model output as the agent's outcome, whatever cut it short. A rate limit, a token expiry or a CLI crash after the first token is not the agent's doing, and it hits arms unevenly (Claude arms meet window limits, Qwen arms do not), so counting it as failure biases the comparison, and re-issuing it would make it best-of-n. `truncated:<cause>` is the middle path: never re-issued, always visible, analysed both ways.

### 1.12 Staging the replay from the snapshot's commit

The first draft staged "the allowed files as the learner has them now", which after the `/contract` run is Claude's refactor: Qwen would have been handed Claude's answer to its own task, and `COMPARISON` would compare different tasks. The snapshot the learner commits before the run marks the starting state, and its commit holds every allowed file as it was then. Staging from `git show <snapshot commit>:<path>` rather than from the snapshot file's content keeps working if the DV3b lane makes the snapshot hold only the `FROZEN` section (the review's rung-7 finding): the snapshot is then only a marker for the acceptance line, and the files come from the commit. A contract with no snapshot and no `--from` is refused rather than guessed.

### 1.13 The return path as a stream

Reading a host directory that a container wrote invites symlink and FIFO tricks: a scanner that opens a path before checking its type can be made to read a host file or block forever. The first draft's bind-mounted `work/` also could not enforce `disk_mb` (a subdirectory of the shared 13 GB `XDG_RUNTIME_DIR` tmpfs) and left the given and tool copies writable, so an agent could tamper with its own in-container verifier and waste the run. With `/work` a size-capped tmpfs inside the container, read-only binds for every non-editable input, and a tar stream parsed member by member without extraction, the host never opens a path the container made, and the size cap is the kernel's. Whether `docker cp` (the review's suggestion) reaches a tmpfs mount on 29.1.3 is uncertain (the lane recalls reports that it does not; not tried here), and it would extract onto the host before any check; `docker exec … tar` avoids both. The container is kept alive after the agent exits only to be read; its entry process then exits on the host's signal.

### 1.14 The CI tripwire

The first draft's tripwire was `FVH_NO_MODEL` plus PATH shims. The backends run pinned binaries by absolute path, which PATH shims never see, and the job ran with the real `HOME`, where the credentials live; nothing stopped a test from reaching the live Ollama on `127.0.0.1:11434`. The revision layers: the apparatus file is the only source of binaries and addresses, CI points it at shims and fakes; `HOME` and the config directories are empty, so neither the real binaries (resolved relative to `HOME`) nor the credentials exist; the socket guard refuses any connection a fake has not registered; the shims include `sudo`. uv's cache path is resolved before `HOME` is swapped, so the offline sync still finds pytest.

### 13.2 The rule as built (`scripts/dvl/sandbox.py`: `ScanIndex`, `scan_index`, `author_scan`, `attest_data`)

- **Spans** as DV5d: every minimal run of whole consecutive answer lines of a twin (lines the twin holds and its learner file does not) with at least `SPAN_TOKENS` = 10 tokens; the lab cards' references in `Solutions/bench/local/` are twins.
- **Two ways to hit.** *Whole*: every 7-token shingle of the span is in the file (DV5d's test). *Renamed* (new): the span's renamed form (`renamed_form`: each identifier that is not a Dafny, Rust/Verus or Python keyword or builtin becomes the index of its first occurrence, `$0`, `$1`, …) occurs as a contiguous run of the file's tokens, in either of two variants: every identifier renamed, or the names the given layers declare (`dafny/given/**`, `verus/given/**`, 96 at db398e4) kept literal, since a copy that calls the layers keeps them. Whitespace, line breaks and comments never matter.
- **Generic structure never counts.** (1) Text a learner-visible course code file shows (as DV5d; for the renamed test, a form any such file shows): the definitions a card copies from the course. (2) Shapes common to the public pools (new): an exact shingle, or a renamed form, found in at least `POOL_COMMON` = 2 installed public benchmark files (`bench/public/<set>/{tasks,answers}/**`, 10,325 `.dfy`/`.rs` files at db398e4); a span with no other shingle has no whole test, a form so found has no renamed test. (3) Language structure (new, for the renamed test): a span all of whose lines are declaration headers (a signature, a module, an import), brackets and separators, or comments has no renamed test; an exact copy of a twin's own header still counts when (1) and (2) leave it a shingle.
- **Attestation records its rule.** Each `sandbox/attested.toml` entry gains `scan = "DV5e"` (`SCAN_RULE`) and `pools = "<n> files, sha256 <16 hex>"` (the installed pool files the rule read). Attesting a card whose entry names an earlier rule scans it again: a pass rewrites the entry in place (date, rule, pools; an earlier `source` kept), a failure withdraws it. A study-mode self-test still checks the hash only (unchanged). With no pool installed the scan is stricter, and a renamed hit's message says so.
- **Cost.** The index (5,155 spans; 4,730 count whole, 3,628 and 3,755 renamed) builds in about 15 s over the course and the pools and is kept for the process while no input file changes (`scan_index`); `mksandbox-run --author --attest` takes about 15 s a card, `--author --selftest-only` as much more.
