### K1 [predict] — the hypothesis about the wrong call
**viva:** yes (verifier-refereed predict) · **strand:** S4 · **tags:** `invariant-generalization`, `induction-as-recursion` · **backward-edge:** Q13 (an accumulator generalized into an invariant)

`Pile(s)` sums a sequence; `Hoard(s, acc)` sums it with an accumulator, adding each entry to `acc` as it goes (Verus: `pile`, `hoard`). A lemma claims `Hoard(s, 0) == Pile(s)` and recurs on `s[1..]` (`decreases |s|`, its body one recursive call). Predict `scripts/vcheck --module Q16`'s verdict in each language (`D:<v> V:<v>`, each `ok` or `fail`). Then: which statement would the induction go through for, and how is the plain one its instance?

**Target insights**
- Both fail. The recursive call gives `Hoard(s[1..], 0) == Pile(s[1..])`, but unfolding the goal gives `Hoard(s[1..], s[0])`: the accumulator is not 0 any more, so the hypothesis is about another call.
- The statement to prove by induction leaves the accumulator free and says what it contributes (`Hoard(s, acc) == acc + Pile(s)`); its recursive instance is exactly the call the recursion makes, at `acc + s[0]`.
- The plain statement is then one call of the general lemma at `acc = 0`: generalize first, instantiate last.

**Misconceptions & counter-moves**
- *"It is a one-line induction; the recursive call closes it."* → Ask: after one unfolding of `Hoard(s, 0)`, what is the second argument?
- *"Dafny proves it by automatic induction."* → Point at the unit's options: automatic lemma induction is off in this tier, and it would induct on the same plain statement anyway.

**Verifier probe**

### K2 [predict] — a 128-bit step that fits
**viva:** yes (verifier-refereed predict) · **strand:** S1 · **tags:** `exec-overflow`, `nat-vs-machine-int`, `nonlinear-arith` · **backward-edge:** Q02 (machine integers and their overflow)

One step of a schoolbook row in Verus: `x as u128 * y as u128 + c as u128 + r as u128` for four `u64`s, with no proof. In Dafny, the same sum `x * y + c + r` of four naturals below `2^64`, converted to a 128-bit newtype `W128` in a module with nonlinear arithmetic off. The sum is at most `(2^64 - 1)^2 + 2 * (2^64 - 1) = 2^128 - 1`, so it always fits. Predict each verdict (`D:<v> V:<v>`). Then: what does each tool need to see that it fits?

**Target insights**
- Both fail: Verus reports possible overflow (three times, one per operation it cannot bound), Dafny a possible violation of the newtype's constraint. The arithmetic fact is true; the solver does not know it.
- With nonlinear arithmetic off, a product of two variables has no bound until a lemma gives one: `lemma_mul_upper_bound(x, 2^64 - 1, y, 2^64 - 1)` bounds the product, after which the two additions are linear and the solver adds them up itself.
- In schoolbook code this is the step's first proof obligation, before any value equation: it is why the step's carry fits in a `u64` again.

**Misconceptions & counter-moves**
- *"u128 is twice as wide, so a product of two u64s obviously fits."* → Ask: who checks "obviously"? Probe: the Verus file.
- *"Dafny has no overflow."* → Ask: what is the newtype's constraint, and what must the solver prove at the conversion?

### K3 [connect] — the same value, a different sequence
**viva:** yes · **strand:** S2 · **tags:** `spec-strength` · **backward-edge:** Q10 (specifications of given code)

Two methods append a zero limb to `s`. [a] promises the result's value is `s`'s; [b] promises the result *is* `s`, limb for limb. Each body is the same append plus the layer lemma that a trailing zero keeps the value (Dafny `ToNatAppendZero`; Verus `lemma_seq_to_nat_push_zero`). Which verify, and what does that say about a specification such as `r == Times(a, b)` against `ToNat(r) == ToNat(a) * ToNat(b)`? Connect it to Q10's specifications of given code: which of them was the stronger kind?

**Target insights**
- [a] verifies and [b] fails in both languages: two sequences with one value can differ in their limbs, so a value specification allows results that an exact one refuses.
- A specification that names the exact sequence pins the algorithm's representation: a result that is right by value (for instance one built through a different route, or with a trailing zero) does not meet it.
- The connection: Q10's specification items asked how much a postcondition must say for a client's use; here the stronger one is chosen on purpose, because a later client (the capstone's Dafny mirror) states against the definition itself.

**Misconceptions & counter-moves**
- *"Equal values mean equal numbers, so both are the same specification."* → Ask: are `[5]` and `[5, 0]` equal sequences?
- *"[b] fails because the lemma is not called."* → Point at the bodies: they are the same; the lemma is about the value only.

### K4 [why] — refused before any proof
**viva:** yes · **strand:** S2 · **tags:** `ghost-and-modes`, `erasure` · **backward-edge:** Q03 (modes: what ghost and spec code may do)

A ghost function `Rungs(n)` defines a number, and a compiled method returns it by calling it, with an `ensures` that names it (Verus: a spec fn `rungs_low`, over the spec fn `rungs`, called by an exec fn). Both runs fail, and at which stage? Why does the tool refuse the call before it tries any proof, when the `ensures` may name the same function?

**Target insights**
- Dafny stops at resolution ("a call to a ghost function is allowed only in specification contexts"); Verus at resolution too ("cannot call function … with mode spec"). No verification condition is generated.
- Ghost and spec code is erased from the compiled program: a compiled call of it would have nothing to run. The mode check is static, so it comes before the solver.
- A specification may still name the function: an `ensures`, an invariant and a proof are erased too. So a compiled loop can be specified against a ghost definition and proved equal to it, and it must compute the value itself.

**Misconceptions & counter-moves**
- *"It fails because the function is recursive."* → Probe: the stage is resolve; ask what a resolver checks.
- *"Then the ensures must not name it either."* → Ask: which parts of the method survive compilation?

### K5 [predict] — what the inner loop forgets
**viva:** yes (verifier-refereed predict) · **strand:** S1 · **tags:** `loop-invariant`, `false-friends` · **backward-edge:** Q05 (what a loop may change, and what it keeps)

Two nested loops visit an `n`-by-`m` grid. The outer loop's invariant is `j <= n`; the inner loop's is `i <= m`; the inner body asserts `j < n`, which the outer guard established and the inner loop never changes. Predict each verdict (`D:<v> V:<v>`). Then: what must the inner invariant say in the language that fails?

**Target insights**
- Dafny verifies: a loop forgets only what it may modify, and the inner loop does not modify `j` or `n`, so `j < n` survives into its body.
- Verus fails at the assertion: a Verus loop body starts from its invariant alone (loop isolation), so a fact from before the loop, even about variables the loop never touches, must be restated in the inner invariant.
- With `j < n` added to the inner invariant, Verus verifies. In a nested Verus loop, every fact the inner body needs from outside (lengths, bounds, the outer index's range) is written again.

**Misconceptions & counter-moves**
- *"j is not assigned in the inner loop, so every tool keeps its facts."* → Probe: the Verus file; ask what the inner body is allowed to assume.
- *"Then Dafny loses facts too."* → Probe: the Dafny file; ask which variables Dafny's inner loop may change.

### K7 [reconstruct] — the identity a prefix needs
**viva:** yes · **strand:** S3 · **tags:** `sequences-and-views`, `false-friends` · **backward-edge:** none

**Target insights**

### K8 [transfer] — a loop from the top, and its measure
**viva:** yes · **strand:** S4 · **tags:** `termination-measure`, `false-friends` · **backward-edge:** Q14 (a measure you choose)

A loop counts the zero entries at the top of a sequence: `i` starts at its length and steps down while `i > 0` and the entry below `i` is zero. In Dafny it has an invariant and no `decreases`; in Verus the same. Transfer what you know about Dafny's measures to Verus: which run fails, at which stage, and what one clause fixes it?

**Target insights**
- Dafny verifies: for a loop with no `decreases`, it guesses one from the guard (here `i` counts down to the bound in `i > 0`).
- Verus stops before verification ("loop must have a decreases clause"): an exec loop in Verus states its measure, always. `decreases i` fixes it.
- For a loop that steps its counter down at the top of its body, the measure is the counter itself; for one that steps up to a bound, the bound minus the counter. Write it in both languages: the guess is Dafny's convenience, not a proof you read.

**Misconceptions & counter-moves**
- *"A loop that obviously stops needs no measure."* → Probe: the Verus file; ask what stage the error comes from.
- *"Dafny proved termination with no measure."* → Ask: which measure did it guess, and from where?
