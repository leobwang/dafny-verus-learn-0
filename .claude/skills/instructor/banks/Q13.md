### K1 [predict] — one borrow step
**viva:** yes (verifier-refereed predict) · **strand:** S1 · **tags:** `nat-vs-machine-int`, `limb-arithmetic` · **backward-edge:** Q02 (`nat` against machine integers)

One step of a subtraction with a borrow: `x - y - borrow`, under `requires borrow <= 1` and `x >= y`. In Dafny the result is a `nat` (`Debit`), in Verus a `u64` (`debit`). Predict `scripts/vcheck --module Q13`'s verdict in each language (`D:<v> V:<v>`, each `ok`, `fail` or `err:<stage>`). Then: which inputs break it, and what must the guard say instead?

**Target insights**
- The guard `x >= y` makes `x - y` non-negative, not `x - y - borrow`: at `x == y` with `borrow == 1` the result would be `-1`. Both fail, at the same point, for the same reason.
- Dafny reports it as a value outside `nat` (a subset constraint); Verus as a possible arithmetic underflow of `u64`. One concept, two messages.
- The fix makes the guard cover the whole subtraction (`x >= y + borrow`), or branches on it: the guard must describe the expression actually computed, not a part of it.

**Misconceptions & counter-moves**
- *"`borrow` is at most 1 and `x >= y`, so the result is fine."* → Ask: what is `x - y - borrow` at `x = y = 3`, `borrow = 1`?
- *"Dafny's `nat` is unbounded, so nothing can go wrong there."* → Probe: the Dafny file; ask: what does unbounded above say about below zero?

**Verifier probe**

### K2 [predict] — a lemma that proves anything
**viva:** yes (verifier-refereed predict) · **strand:** S2 · **tags:** `vacuity`, `witnesses` · **backward-edge:** Q03 (contradictory premises; the witness call)

A lemma requires `x > 5` and `x < 3` and ensures `x == 42`, with an empty body; a second declaration calls it at `x = 4`. Predict the verdict of the lemma and of the call, in each language. Then: what does the lemma's green verdict tell a caller, and what would a witness have shown?

**Target insights**
- The lemma verifies: no `x` meets its `requires`, so its `ensures` is never at stake. A green verdict on it proves nothing about any value.
- The call fails at its precondition: the witness is the instrument that exposes the contradiction, because a non-vacuous statement must have at least one call whose `requires` hold.

### K3 [why] — the use site that refuses a statement
**viva:** yes · **strand:** S2 · **tags:** `prose-to-spec`, `spec-strength` · **backward-edge:** none

Prose: *the larger of two integers is at least each of them.* A learner states it as `BigAbove(x, y)` with `requires x >= y` and the two inequalities as its `ensures`, and proves it. A use site calls it on two arbitrary integers `p`, `q` and asserts `Big(p, q) >= q`. The lemma verifies; the use site does not. Why, and what does that say about the statement, not the proof?

**Target insights**
- The `requires x >= y` is an assumption the prose does not make: the statement is narrower than the prose, so the use site, whose arguments may be in either order, cannot call it (the precondition fails at the call).
- The lemma's own green verdict cannot see this: a statement with more `requires` is easier to prove. Only a client that needs the full prose exposes it; the same statement without the extra `requires` verifies with the same empty proof and serves the use site.
- The three instruments of a prose item each catch a different mistake: the use site a statement too narrow or too weak for a real caller, the witness a statement no call can meet, the equivalence check a statement that says something else.

**Misconceptions & counter-moves**
- *"The proof is wrong."* → Probe: the file; ask: which declaration does the error point at?
- *"An extra `requires` only makes the lemma safer."* → Ask: safer for whom: the prover of the lemma, or its caller?

### K4 [connect] — the accumulator the induction needs
**viva:** yes · **strand:** S4 · **tags:** `invariant-generalization`, `induction-as-recursion` · **backward-edge:** Q10 (an invariant written from the exit backwards)

`Gather(s)` sums a sequence from its front; `GatherAcc(s, acc)` sums it into an accumulator. `GatherZero(s)` states `GatherAcc(s, 0) == Gather(s)` and recurs on `s[1..]`. It fails. Why does the recursive call not help, what statement does, and how is this the loop rule you used in Q10?

**Target insights**
- `GatherAcc(s, 0)` unfolds to `GatherAcc(s[1..], s[0])`, an accumulator that is not 0: the hypothesis `GatherAcc(s[1..], 0) == Gather(s[1..])` is about another term, so the step has nothing to use.
- The generalized statement `GatherAcc(s, acc) == acc + Gather(s)`, for every `acc`, is its own induction hypothesis at `acc + s[0]`; the original is its instance at 0.
- The same move is a loop invariant: Q10 wrote invariants from the exit backwards, and here the exit's statement says nothing about the value carried, so the statement true at every step must mention it (what is accumulated plus what is still to come).

**Misconceptions & counter-moves**
- *"It needs more fuel or an assertion."* → Probe: the failing file; ask: what does the recursive call's postcondition say, and what does the goal need after one unfolding?
- *"Generalizing makes it harder to prove."* → Probe: the generalized file; ask: why does the stronger statement go through when the weaker did not?

**Verifier probe**

### K5 [predict] — which argument shrinks
**viva:** yes (verifier-refereed predict) · **strand:** S4 · **tags:** `induction-as-recursion`, `termination-measure` · **backward-edge:** none

`Flip(s)` reverses a sequence by peeling its **first** element. Two proofs of `Flip(a + b) == Flip(b) + Flip(a)`: `FlipConcatA` recurs on `a[1..]` (`decreases |a|`), `FlipConcatB` on `b[1..]` (`decreases |b|`). The Q13 unit has manual lemma induction. Predict which verify (`A:<v> B:<v>`). Then: what decides the right argument?

**Target insights**
- `Flip` peels the front, and the front of `a + b` is `a`'s (when `a` is not empty): unfolding `Flip(a + b)` produces `Flip((a + b)[1..])`, which is `Flip(a[1..] + b)`, the hypothesis of the call on `a[1..]`. A verifies.
- B's hypothesis is about `a + b[1..]`, a term the unfolding never produces: B fails at its postcondition.
- The rule: recur on the argument the unfolded definition shrinks. A definition that peels the last element would make the other argument the right one; read the definition before choosing.

**Misconceptions & counter-moves**
- *"Both terminate, so both prove it."* → Probe: the file; ask: the measure makes the call legal, but does its conclusion match what the unfolding needs?
- *"The right side mentions `Flip(b)` first, so recur on `b`."* → Ask: which side does `Flip` unfold, and what does it unfold to?

**Verifier probe**
```dafny
module ProbeK5 {
  function Flip(s: seq<nat>): seq<nat>
  {
    if |s| == 0 then [] else Flip(s[1..]) + [s[0]]
  }

  lemma FlipConcatA(a: seq<nat>, b: seq<nat>)
    ensures Flip(a + b) == Flip(b) + Flip(a)
    decreases |a|
  {
    if |a| > 0 {
      assert (a + b)[1..] == a[1..] + b;
      FlipConcatA(a[1..], b);
    } else {
      assert a + b == b;
    }
  }

  lemma FlipConcatB(a: seq<nat>, b: seq<nat>)
    ensures Flip(a + b) == Flip(b) + Flip(a)
    decreases |b|
  {
    if |b| > 0 {
      FlipConcatB(a, b[1..]);
    } else {
      assert a + b == a;
    }
  }
}
```

### K7 [reconstruct] — what an `assert … by` leaves behind
**viva:** yes · **strand:** S3 · **tags:** `assert-by`, `lemma-call` · **backward-edge:** Q02 (what survives an `assert … by`)

`Pw(n)` doubles `n` times from 1; `PwPos(n)` proves `Pw(n) > 0` by induction. A method asserts `Pw(n) > 0 by { PwPos(n); }` and then, outside the block, `Pw(n + 5) > 0`. Reconstruct what the verifier knows after the block, and say why the second assertion fails. Then: two different one-line repairs.

**Target insights**
- After the block, only the asserted fact `Pw(n) > 0` is in context. The lemma call's conclusion is scoped to the block, and it was about `n` in any case.
- `Pw(n + 5)` unfolds only so far on a symbolic argument: it is not reduced to `Pw(n)`, and the general fact `forall k :: Pw(k) > 0` was never in context, so the assertion fails.
- Repairs: call the lemma at the instance needed (`PwPos(n + 5)`), or assert the needed fact `by` that call. The point of `assert … by` is to keep a proof step's facts local; the price is that nothing else leaks out.

**Misconceptions & counter-moves**
- *"The lemma proved `Pw` positive everywhere, so it is known everywhere."* → Ask: which instance does a call put in context, and where?
- *"`Pw(n + 5)` is just `32 * Pw(n)`."* → Probe: the file; ask: how far does the verifier unfold a recursive function on a symbolic argument?

### K8 [transfer] — a ghost record and the code beside it
**viva:** yes · **strand:** S1 · **tags:** `ghost-and-modes`, `false-friends`, `limb-arithmetic` · **backward-edge:** none

A countdown loop keeps a ghost sequence `trail` of the values it has seen, with an invariant on its length, as a borrow chain keeps its borrows. After the loop, compiled code reads its length into a variable. Predict where each language stops (`D:<v> V:<v>`, each `ok`, `fail` or `err:<stage>`), and say what a ghost record may and may not be used for in a loop like H1v's.

**Target insights**
- A ghost value exists only for the proof, and compiled code cannot read it. Verus refuses the `let` at resolution: `trail.len()` is a spec function, and an exec `let` cannot call it. Dafny accepts the same lines: it infers that `total` is ghost too, because it is initialized from a ghost value and no compiled code uses it. Once compiled code does use it (a `print`), Dafny refuses at resolution as well, naming the inference.
- A false friend: the same lines are refused by one verifier and accepted by the other, for one rule (ghost values never flow into compiled code) applied at different points.
- Inside invariants, assertions and ghost or proof updates it is free: that is where a record of every step's borrow belongs, so that one invariant can speak about all the limbs written so far.
- The compiled loop must carry its own state in compiled variables; a ghost record only mirrors what the code did, for the proof's sake, and is erased from the program that runs.

**Misconceptions & counter-moves**
- *"Ghost state is just a variable the verifier also tracks."* → Probe: the files; ask: does the compiled program still have it?
- *"Dafny accepted it, so the read is legal."* → Probe: the `print` variant; ask: what did Dafny decide about `total`, and when does that decision stop being possible?

**Verifier probe**

        r == 0,

            trail.len() == n - i,
        decreases i,
    {
        proof {
            trail = trail.push(i);
        }
        i = i - 1;
    }

    i
}

} // verus!
