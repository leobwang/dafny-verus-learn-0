### K1 [predict] — a view that no state can meet
**viva:** yes (verifier-refereed predict) · **strand:** S6 · **tags:** `traits-and-interfaces`, `vacuity` · **backward-edge:** Q03 (vacuity: a contradictory precondition proves anything)

A trait `Valve` describes its state only through a ghost view `Mark` (Verus: `spec fn mark`), and its method `Nudge` requires the mark to be below 10 and ensures it goes up by one. The implementation `Jammed` defines the view as the constant 50 and gives `Nudge` an empty body. Predict `scripts/vcheck --module Q14`'s verdict for the implementation in each language (`D:<v> V:<v>`, each `ok`, `fail` or `err:<stage>`). Then: what happens to the first client that calls `Nudge` on a `Jammed`, and what in H2v rules this trick out?

**Target insights**
- Both verify. The view is the implementation's choice, and with `Mark() == 50` the trait's precondition `Mark() < 10` is false in every state, so the empty body meets the `ensures` vacuously: nothing is ever checked against it.
- The vacuity surfaces only at a call: a client that calls `Nudge` on a `Jammed` must prove `Mark() < 10`, and cannot. A green implementation is not a usable one.
- A contract stated through a view is only as strong as the view. In H2v the view `lo + BASE * hi` ships with the trait's other parts: you implement the methods, never the meaning of `total`, so you cannot choose a view that makes the `requires` unsatisfiable.
- The general rule from Q03: a precondition no state meets proves anything. A view is one more way to write such a precondition without seeing it.

**Misconceptions & counter-moves**
- *"An empty body cannot meet an `ensures` that says the mark went up."* → Probe: the implementation file; ask: in which state does the verifier check that `ensures`?
- *"If it verifies, a client can use it."* → Probe: the file with the client appended; ask: which obligation does the call create?

### K2 [predict] — an implementation's own contract
**viva:** yes (verifier-refereed predict) · **strand:** S6 · **tags:** `traits-and-interfaces`, `requires-ensures`, `false-friends` · **backward-edge:** none

A trait `Raiser` declares `Lift(x) returns (y)` (Verus `fn lift(&self, x: u64) -> (y: u64)`) with `requires 0 <= x <= 10` (Verus `x <= 10`) and `ensures y > x`. The implementation `Brace` writes a contract of its own: [a] a **weaker** precondition (Dafny `requires 0 <= x`; Verus `requires x <= 100`) with the trait's postcondition, and a direct client that calls it at 40; [b] the trait's precondition with a **stronger** postcondition, `ensures y == x + 1`, and a direct client that asserts `y == 5` after a call at 4. Predict the verdict of each of the four files. Answer form: `D:<a> <b> V:<a> <b>`.

**Target insights**
- `D:ok ok V:err:resolve ok`.
- Dafny checks an overriding method against the trait it extends: the trait's precondition must imply the override's, and the override's postcondition must give the trait's. A weaker `requires` and a stronger `ensures` both pass, and a client that holds a `Brace` (not a `Raiser`) uses the class's own contract: the call at 40 is legal.
- Verus refuses any `requires` on a trait method implementation, at resolve, before verification: preconditions are inherited only. A weaker one is refused as firmly as the stronger one of the chapter's `ticker_req.rs`.
- Verus does accept an extra `ensures` on an implementation; it is one more obligation for the body, and a caller that knows the concrete type may use it. A generic client sees only the trait's.
- The rule both tools enforce in their own way: a substitute may ask less and promise more, never ask more or promise less. H2v's implementation cannot ask for more than the trait's `requires` give it.

**Misconceptions & counter-moves**
- *"Verus refuses only a requires that is stronger than the trait's."* → Probe: [a]'s Verus file; ask: what does the message say a `requires` can only be?
- *"An implementation must repeat the trait's contract exactly."* → Probe: [b] in both languages; ask: who can use the extra `ensures`?

### K3 [why] — a validity predicate the refinement chooses
**viva:** yes · **strand:** S6 · **tags:** `refinement`, `vacuity`, `traits-and-interfaces` · **backward-edge:** Q08 (a client of a frozen statement)

An abstract module `RollSpec` leaves its validity predicate `Fine` to each refinement, as `QG_L4_Spec` leaves `Wf` to `Q14_Cached`. The refinement `RollNone` defines `Fine` as `false`. One of its two inherited lemmas, `HeadsBound`, requires `Fine(t)`; the other, `BeginCorrect`, ensures `Fine(Begin(n))`. Why does `RollNone`'s `HeadsBound` verify with an empty body while its `BeginCorrect` fails, and what does that say about who may choose `Wf` in H1d and what keeps the choice honest? The Verus file asks the same of a trait whose constructor `begin` ensures `fine()`.

**Target insights**
- With `Fine` false, `HeadsBound`'s precondition is never met, so its empty body is vacuously correct, exactly as K1's `Nudge` was.
- `BeginCorrect` ensures `Fine(Begin(n))`, so a refinement that makes `Fine` false cannot prove it: the statements that *establish* validity are what keep a chosen predicate honest. A spec whose lemmas only *assume* validity could be met by `false`.
- `RollHonest` (`Fine(t)` is `t < 1000`) proves both lemmas with empty bodies: an honest predicate is one that the constructors establish and the other lemmas can use.
- In H1d, `Wf` (canonical limbs and a correct cached length) is given, and the shipped `ZeroCorrect`, `FromNatCorrect` and `AddCorrect` establish it for every value the operations build. So `CmpCorrect`'s precondition `Wf(a) && Wf(b)` is a real assumption you may use, not a vacuous one.
- Q08's lesson stands: a client of the abstract module knows only the statements. A refinement's freedom is inside the statements, and the statements that produce valid values bound it.

**Misconceptions & counter-moves**
- *"If every lemma verifies, the refinement is right."* → Probe: `RollNone` with `BeginCorrect` removed (or read the file: which lemma would then fail?); ask: what would a client of `RollSpec` be able to build?
- *"A validity predicate is a free choice of the implementer."* → Ask: which lemma would `Fine == true` break, and why is that one the guard?

### K4 [predict] — a shorter sequence that is not a slice
**viva:** yes (verifier-refereed predict) · **strand:** S7 · **tags:** `termination-measure`, `false-friends` · **backward-edge:** Q05 (termination measures and Dafny's default)

`Squash(s)` replaces the first two elements of a sequence by their sum and recurs, so each call's argument is one element shorter. The Dafny function has no `decreases` clause (its default measure is its parameter, `s`); the Verus `spec fn` says `decreases s`. Predict each verdict (`D:<v> V:<v>`). Then: what does each tool accept instead, and how does this differ from a recursion on `s[2..]`?

**Target insights**
- `D:fail V:fail`, both at the recursive call ("cannot prove termination"; "could not prove termination").
- A sequence as a measure is not compared by its length. The rebuilt sequence `[s[0] + s[1]] + s[2..]` is shorter, but it is a new sequence, not a part of `s`, and neither tool counts it as smaller. A call on the slice `s[2..]` passes with the same Dafny default (`k4slice.dfy`).
- Writing the measure as the length (`decreases |s|`; Verus `decreases s.len()`) makes both verify: a `nat` that drops by one at every call.
- The lesson of P1dv in another form: the default is a guess about a particular order; when the call's argument is not smaller in that order, the measure is yours to write, and the simplest quantity that drops at every call is the one to name.

**Misconceptions & counter-moves**
- *"A shorter sequence is always smaller."* → Probe: the files as shipped; ask: which order is the default comparing?
- *"Verus's `decreases s` measures the length."* → Probe: `k4len.rs`; ask: what changed between the two Verus files?

### K5 [predict] — a ghost argument is still checked
**viva:** yes (verifier-refereed predict) · **strand:** S7 · **tags:** `ghost-and-modes`, `erasure` · **backward-edge:** none

`PickLow(a, b, roof)` returns the smaller of two numbers; its third parameter `roof` is ghost (Verus `Ghost(roof): Ghost<nat>`), and its `requires` says both numbers are at most `roof`. Two callers pass `3` and `8`: `CallFair` with the ghost argument `8`, `CallLow` with `5`. Predict, per language, which caller (if any) the verifier refuses. Answer form: `D:<fair> <low> V:<fair> <low>`, each `ok` or `fail`.

**Target insights**
- `D:ok fail V:ok fail`: the low caller fails at its call ("a precondition for this call could not be proved"; "precondition not satisfied"), the fair one verifies.
- A ghost argument is erased from the compiled call but not from the proof: the `requires` that mentions it is the caller's obligation, checked like any other. Erasure removes the run-time cost, not the logical one.
- Information flows from exec to ghost freely (the caller may pass any value it can describe, including one the code could never compute); the other direction is refused (the chapter's `first_or_zero_read.rs`). In H3v the caller's ghost bound is what makes `v.len() * bound <= u128::MAX` a fact the body may use.
- Choosing a ghost parameter is a design decision: the bound costs nothing at run time and still lets the specification and the proof speak of it.

**Misconceptions & counter-moves**
- *"A ghost argument is never checked, since it is erased."* → Probe: the files; ask: which line carries the error, and what does it say?
- *"A ghost parameter must be computed by ghost code."* → Ask: where do the literals `8` and `5` come from, and in which mode does the call run?

**Verifier probe**

### K7 [connect] — what a run that never ends promises
**viva:** yes · **strand:** S8 · **tags:** `hoare-logic`, `verified-metatheory`, `induction-as-recursion` · **backward-edge:** Q08 (the loop rule on paper and its side conditions)

Q08 wrote the loop rule on paper and asked which side condition makes it total. Connect that to H4d's statement, which speaks only of runs that end `Done`. In the probe, `SpinF` from an odd `x` never ends; `OddEndsAt42` claims that every run of it that ends returns 42. Why does that verify, and what would a soundness theorem for `Exec` have to add to rule out a loop that never ends? Why does `OddNeverEnds` need a body when automatic induction is off?

**Target insights**
- A statement of the form "if the run ends, it ends where `q` holds" is true of every run that never ends: there is nothing to check. `OddNeverEnds` shows `SpinF` from an odd `x` is always `OutOfFuel`, and `OddEndsAt42` follows with any value in place of 42.
- That is partial correctness, the meaning of a Hoare triple with the plain loop rule: H4d proves it for `While`, from the invariant and the loop's two side conditions. Total correctness needs a variant, a measure the body decreases and that is bounded below, which is the extra side condition Q08's paper rule named.
- `OddNeverEnds` is an induction on the fuel, written as a recursive call with one unit less; with automatic induction off (this unit's option) the empty body fails. The same shape, recursion on the fuel, is the one H4d's shipped `decreases fuel` announces.
- A green soundness proof is about the theorem it states: reading which runs the statement quantifies over is part of reading the proof.

**Misconceptions & counter-moves**
- *"A soundness theorem that verifies rules out wrong programs."* → Probe: `OddEndsAt42`; ask: what would it claim with 42 replaced by 7?
- *"The fuel makes every run end."* → Ask: what does `OutOfFuel` say about the loop, and what does it say about the fuel?
