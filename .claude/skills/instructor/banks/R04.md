## Questions

### K1 [reconstruct] — an arbitrary value, not a sample
**viva:** yes · **tags:** `quantifiers`, `witnesses` · **backward-edge:** R01 (an assertion is an obligation for every admitted value)

Reconstruct what a proof of `forall s :: P(s) ==> Q(s)` must do, in each language, and what the variable it introduces stands for. Then read the probe. Both files state the same claim: every string matched by `Cat(Chr('z'), Star(Chr('y')))` is non-empty and starts with `'z'`. Proof [all] introduces an arbitrary `s` and reasons about its split; proof [sample] checks one string, "zy". What does each language report for each proof, and why does the Dafny result not mean that a sample proves a universal claim?

```dafny
module R04_BankZed {
  import opened RG_A1_Re

  // [all] the claim for an arbitrary s: take the split and read its sides
  lemma ZedPairAll()
    ensures forall s :: Matches(Cat(Chr('z'), Star(Chr('y'))), s) ==> |s| >= 1 && s[0] == 'z'
  {
    forall s | Matches(Cat(Chr('z'), Star(Chr('y'))), s)
      ensures |s| >= 1 && s[0] == 'z'
    {
      var i :| 0 <= i <= |s| && Matches(Chr('z'), s[..i]) && Matches(Star(Chr('y')), s[i..]);
      assert s[..i] == ['z'];
    }
  }

  // [sample] the claim checked on one string only
  lemma ZedPairSample()
    ensures forall s :: Matches(Cat(Chr('z'), Star(Chr('y'))), s) ==> |s| >= 1 && s[0] == 'z'
  {
    assert "zy"[..1] == "z";
    assert "zy"[1..] == "y";
  }
}
```
```rust
use vstd::prelude::*;
use rg_re_a1::*;

verus! {

spec fn zy() -> Re {
    Re::Cat(Box::new(Re::Chr('z')), Box::new(Re::Star(Box::new(Re::Chr('y')))))
}

// [all] the claim for an arbitrary s: take the split and read its sides
proof fn lemma_zed_pair_all()
    ensures
        forall|s: Seq<char>| matches(zy(), s) ==> s.len() >= 1 && s[0] == 'z',
{
    assert forall|s: Seq<char>| #[trigger] matches(zy(), s) implies s.len() >= 1 && s[0] == 'z' by {
        let i = choose|i: int|
            0 <= i <= s.len() && matches(Re::Chr('z'), #[trigger] s.subrange(0, i)) && matches(
                Re::Star(Box::new(Re::Chr('y'))),
                s.subrange(i, s.len() as int),
            );
        assert(s.subrange(0, i).len() == 1);
        assert(s.subrange(0, i)[0] == s[0]);
    }
}

// [sample] the claim checked on one string only
proof fn lemma_zed_pair_sample()
    ensures
        forall|s: Seq<char>| matches(zy(), s) ==> s.len() >= 1 && s[0] == 'z',
{
    let s = seq!['z', 'y'];
    assert(s.subrange(0, 1) =~= seq!['z']);
    assert(s.subrange(1, 2) =~= seq!['y']);
}

} // verus!
```

**Target insights**
- A universal claim is introduced by fixing an arbitrary value that satisfies the antecedent and proving the conclusion for it: Dafny's `forall s | P(s) ensures Q(s) { … }`, Verus's `assert forall|s| P(s) implies Q(s) by { … }`. Inside the body, `s` is any string the range admits, so every step must hold for all of them; with `implies`, Verus puts the antecedent in scope.
- Inside [all], `:|` / `choose` takes the split that `Matches` of a `Cat` guarantees, and the slice fact `s[..i] == ['z']` gives the first character: elimination inside introduction.
- Dafny verifies both lemmas: its solver proves this postcondition by itself (the `Cat` existential of a single-character head unfolds automatically), so the sample's two assertions are simply unused. The sample did not prove anything; the automation did. Verus verifies [all] and refuses [sample]: facts about "zy" say nothing about the other strings.

**Misconceptions & counter-moves**
- *"The Dafny [sample] verified, so checking a sample is a proof."* → Ask: delete the sample's two assertions; what does Dafny report then, and what does that say about where the proof came from?
- *"The variable in a `forall` statement is a chosen example."* → Ask: which property of `s` may the body use, and where is it written?
- *"`==>` in the `ensures` and `implies` in the proof are the same thing."* → Ask: in the Verus proof, which fact is available inside the `by` block, and what would change with `==>` there?

**Verifier probe**
(Dafny 4.11.0:)
```

```
(Verus 0.2026.09.27; line 29 is [sample]'s postcondition:)
```

instructor/scratch/probe.rs:29:9: error: postcondition not satisfied
```
Follow-up: in Verus, which single line of [all] carries the claim's content, and what would the proof lose if `choose` kept only the first conjunct? (K2 shows that case.)

**Reread:** §2.1 "Introducing a `forall`: an arbitrary value", §2.2 "Eliminating an `exists`: a justified witness"

### K2 [predict] — what a pick owes and what it keeps
**viva:** yes (verifier-refereed predict) · **tags:** `witnesses`, `verdict-reading` · **backward-edge:** R02 (`choose` and `:|` take a split out of an existential)

Three proofs take a split out of `Matches(Cat(Chr('m'), Chr('n')), s)`. [a] has that match as a premise and picks a split with all three conjuncts; [b] has no premise at all; [c] has the premise but picks with the first conjunct only. Predict which labels fail in each language, and where. Answer form `D:FAILS <labels> V:FAILS <labels>` (or `none`).

```dafny
module R04_BankPick {
  import opened RG_A1_Re

  // [a] the premise guarantees the split
  lemma PickedSplitA(s: seq<char>)
    requires Matches(Cat(Chr('m'), Chr('n')), s)
    ensures |s| == 2
  {
    var i :| 0 <= i <= |s| && Matches(Chr('m'), s[..i]) && Matches(Chr('n'), s[i..]);
    assert |s[..i]| == 1;
  }

  // [b] no premise: nothing guarantees a split exists
  lemma PickedSplitB(s: seq<char>)
  {
    var i :| 0 <= i <= |s| && Matches(Chr('m'), s[..i]) && Matches(Chr('n'), s[i..]);
    assert |s| == 2;
  }

  // [c] the premise is there, but the pick keeps only one conjunct
  lemma PickedSplitC(s: seq<char>)
    requires Matches(Cat(Chr('m'), Chr('n')), s)
    ensures |s| == 2
  {
    var i :| 0 <= i <= |s| && Matches(Chr('m'), s[..i]);
    assert |s[..i]| == 1;
  }
}
```
```rust
use vstd::prelude::*;
use rg_re_a1::*;

verus! {

spec fn mn_pattern() -> Re {
    Re::Cat(Box::new(Re::Chr('m')), Box::new(Re::Chr('n')))
}

// [a] the premise guarantees the split
proof fn lemma_picked_split_a(s: Seq<char>)
    requires
        matches(mn_pattern(), s),
    ensures
        s.len() == 2,
{
    let i = choose|i: int|
        0 <= i <= s.len() && matches(Re::Chr('m'), #[trigger] s.subrange(0, i)) && matches(
            Re::Chr('n'),
            s.subrange(i, s.len() as int),
        );
    assert(s.subrange(0, i).len() == 1);
}

// [b] no premise: nothing guarantees a split exists
proof fn lemma_picked_split_b(s: Seq<char>) {
    let i = choose|i: int|
        0 <= i <= s.len() && matches(Re::Chr('m'), #[trigger] s.subrange(0, i)) && matches(
            Re::Chr('n'),
            s.subrange(i, s.len() as int),
        );
    assert(s.len() == 2);
}

// [c] the premise is there, but the pick keeps only one conjunct
proof fn lemma_picked_split_c(s: Seq<char>)
    requires
        matches(mn_pattern(), s),
    ensures
        s.len() == 2,
{
    let i = choose|i: int| 0 <= i <= s.len() && matches(Re::Chr('m'), #[trigger] s.subrange(0, i));
    assert(s.subrange(0, i).len() == 1);
}

} // verus!
```

**Target insights**
- Dafny's `:|` owes a proof that some value satisfies its predicate: with no premise, [b] fails at the pick itself ("cannot establish the existence of LHS values"), and the assertion after it fails too.
- Verus's `choose` is total: it always returns a value, and its predicate is known only when some value satisfies it. In [b] nothing is known, so the failure is at the assertion after the pick, not at the pick.
- [c] keeps the prefix fact only. Verus loses the suffix fact, so the postcondition `s.len() == 2` fails; Dafny still verifies, because its solver derives the length from the premise directly. The pick's predicate is what the rest of a Verus proof may use.
- The answer: `D:FAILS b V:FAILS b c`.

**Misconceptions & counter-moves**
- *"A pick creates the witness."* → Ask: in [b], which fact would make the Dafny pick legal, and where would it come from?
- *"Keeping one conjunct is harmless: the others are still true."* → Ask: in Verus [c], which fact does the postcondition need, and which line states it?
- *"Both languages fail in the same place."* → Probe [b]: compare the two error lines and name what each tool was checking there.

### K3 [predict] — three negative claims, empty bodies
**viva:** yes (verifier-refereed predict) · **tags:** `quantifiers`, `verdict-reading`, `anchoring` · **backward-edge:** R02 (`Matches` by splits)

Three claims that a regex does **not** match a whole string, each with an empty body: [a] `Cat(Chr('q'), Chr('q'))` on "q"; [b] `Star(Chr('q'))` on "qr"; [c] `Alt(Chr('q'), Eps)` on "r". Predict which labels fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>`.

```dafny
module R04_BankShort {
  import opened RG_A1_Re

  // [a] too short for the pattern
  lemma QqNotQ()
    ensures !Matches(Cat(Chr('q'), Chr('q')), "q")
  {
  }

  // [b] a character the star cannot take
  lemma StarQNotQr()
    ensures !Matches(Star(Chr('q')), "qr")
  {
  }

  // [c] an alternative that misses both sides
  lemma AltNotR()
    ensures !Matches(Alt(Chr('q'), Eps), "r")
  {
  }
}
```
```rust

use rg_re_a1::*;

verus! {

// [a] too short for the pattern
proof fn lemma_qq_not_q()
    ensures
        !matches(Re::Cat(Box::new(Re::Chr('q')), Box::new(Re::Chr('q'))), seq!['q']),
{
}

// [b] a character the star cannot take
proof fn lemma_star_q_not_qr()
    ensures
        !matches(Re::Star(Box::new(Re::Chr('q'))), seq!['q', 'r']),
{
}

// [c] an alternative that misses both sides
proof fn lemma_alt_not_r()
    ensures
        !matches(Re::Alt(Box::new(Re::Chr('q')), Box::new(Re::Eps)), seq!['r']),
{
}

} // verus!
```

**Target insights**
- A negative claim about `Matches` is a claim about every candidate: every split of a `Cat`, every first chunk of a `Star`, both sides of an `Alt`.
- Dafny settles [a] and [c] with no help: the candidates are few and its sequence reasoning evaluates each. [b] needs the `Star`'s recursion on the rest of "qr", which the solver does not unfold far enough, so it fails.
- Verus unfolds a recursive spec fn one level per mention and needs the subranges stated, so all three fail with empty bodies.
- The answer: `D:FAILS b V:FAILS a b c`. An empty-body success in one language is a fact about that tool's automation, not about the claim's difficulty; a written proof must cover every candidate the tool does not.

**Misconceptions & counter-moves**
- *"If Dafny proves it with no body, there is nothing to prove."* → Ask: which candidates did Dafny have to rule out in [a], and what would you write in Verus to rule them out yourself?
- *"Showing that one split fails proves the negative claim."* → Ask: for [b], list every first chunk the `Star` could take of "qr".
- *"A failed negative claim means the regex matches."* → Ask: what does the error say failed, the claim or its proof?

### K4 [predict] — four contracts, one body
**viva:** yes (verifier-refereed predict) · **tags:** `spec-strength`, `verdict-reading` · **backward-edge:** none

Four methods share the body `b := true` (Verus: `true`) and differ only in their postcondition about whether `s` is non-empty: [a] `b ==> |s| > 0`; [b] `|s| > 0 ==> b`; [c] `b <==> |s| > 0`; [d] `b || !b`. Predict which fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>`.

```dafny
module R04_BankNonEmpty {
  // Four contracts for one question: is s non-empty? Each body returns true.

  // [a] true only for non-empty strings
  method NonEmptyA(s: seq<char>) returns (b: bool)
    ensures b ==> |s| > 0
  {
    b := true;
  }

  // [b] true for every non-empty string
  method NonEmptyB(s: seq<char>) returns (b: bool)
    ensures |s| > 0 ==> b
  {
    b := true;
  }

  // [c] true exactly for non-empty strings
  method NonEmptyC(s: seq<char>) returns (b: bool)
    ensures b <==> |s| > 0
  {
    b := true;
  }

  // [d] a postcondition that says nothing
  method NonEmptyD(s: seq<char>) returns (b: bool)
    ensures b || !b
  {
    b := true;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// Four contracts for one question: is s non-empty? Each body returns true.

// [a] true only for non-empty vectors
fn non_empty_a(s: &Vec<char>) -> (b: bool)
    ensures
        b ==> s.len() > 0,
{
    true
}

// [b] true for every non-empty vector
fn non_empty_b(s: &Vec<char>) -> (b: bool)
    ensures
        s.len() > 0 ==> b,
{
    true
}

// [c] true exactly for non-empty vectors
fn non_empty_c(s: &Vec<char>) -> (b: bool)
    ensures
        b <==> s.len() > 0,
{
    true
}

// [d] a postcondition that says nothing
fn non_empty_d(s: &Vec<char>) -> (b: bool)
    ensures
        b || !b,
{
    true
}

} // verus!
```

**Target insights**
- A one-way implication constrains one Boolean value: [a] says "true only for non-empty" (a constant `true` breaks it on the empty string); [b] says "true for every non-empty" (a constant `true` meets it).
- [c], the equivalence, constrains both values and rejects the constant. [d] is a tautology: every body meets it, so it specifies nothing.
- The answer: `D:FAILS a c V:FAILS a c`. A trivial body is a probe of a contract's strength: whatever trivial bodies a contract admits, a faithful implementation must be distinguishable from them by the contract or by nothing.

**Misconceptions & counter-moves**
- *"`==>` and `<==>` differ only in strictness."* → Ask: for each of [a] and [b], which Boolean value does the contract leave unconstrained?
- *"A contract that verifies is a good contract."* → Ask: what does [d] promise a caller?
- *"Either direction expresses 'b is true when s is non-empty'."* → Ask: which of [a] and [b] does the constant `true` satisfy, and which would the constant `false` satisfy?

### K6 [why] — why a search API needs an anchor decision
**viva:** yes · **tags:** `anchoring`, `witnesses` · **backward-edge:** none

```dafny

    assert "cat"[2..3] == "t";

  lemma TeeNotCat()
    ensures !Matches(Chr('t'), "cat")
  {
  }
}
```

**viva:** yes · **tags:** `prose-to-spec`, `verdict-reading` · **backward-edge:** none

Prose: "`EndsWithDot(s)` is true exactly when the last character of `s` is a dot." Three readings: [x] `|s| > 0 && s[|s| - 1] == '.'`; [y] "a dot occurs in `s`"; [z] `s[|s| - 1] == '.'` with no length guard. Three use-site checks are given: a positive case, a negative case and the empty string. Transfer H4's move to this sentence: which reading passes the checks, and how do the other two fail, in each language?

```dafny
module R04_BankDotX {
  // [x] Prose: "true exactly when the last character of s is a dot".
  predicate EndsWithDot(s: seq<char>)
  {
    |s| > 0 && s[|s| - 1] == '.'
  }

  lemma DotChecksX()
  {
    assert EndsWithDot("a.");
    assert !EndsWithDot(".a");
    assert !EndsWithDot([]);
  }
}

module R04_BankDotY {
  // [y] the same prose, read as "a dot occurs in s"
  predicate EndsWithDot(s: seq<char>)
  {
    '.' in s
  }

  lemma DotChecksY()
  {
    assert EndsWithDot("a.");
    assert !EndsWithDot(".a");
    assert !EndsWithDot([]);
  }
}

module R04_BankDotZ {
  // [z] the last character, with no length guard
  predicate EndsWithDot(s: seq<char>)
  {
    s[|s| - 1] == '.'
  }
}
```

// [x] Prose: "true exactly when the last character of s is a dot".

}

    assert(!ends_with_dot_x(seq!['.', 'a']));

    s.contains('.')
}

    assert(ends_with_dot_y(seq!['a', '.']));

}

} // verus!

**Target insights**
- [x] verifies all three checks. [y] passes the positive check and fails the negative one (".a" holds a dot that is not last): a reading that agrees with one example can answer a different question.
- [z] is rejected differently in each language. Dafny refuses the definition itself (`index out of range`: the body is not well-formed on `[]`). Verus accepts it, because spec indexing out of range is not an error but an unspecified value, and the empty-string check then fails: nothing is known about `s[-1]`.
- Use-site checks are how prose meets a formula: a positive, a negative and a boundary case. They constrain the definition; they do not prove it faithful on inputs no check names.

**Misconceptions & counter-moves**
- *"If the positive check passes, the definition is right."* → Ask: which check separates [x] from [y]?

- *"Three checks prove the definition."* → Ask: write a fourth reading that passes all three checks and still misreads the prose. (For example one that also accepts a final '!'.)

### K12 [transfer] — a delivered statement that is false
**viva:** yes · **tags:** `frozen-statements`, `witnesses` · **backward-edge:** R01 (the contract, not the intent, and the contractor's evidence)

A contractor is asked to prove `StarIsOnce`: every string matched by `Star(r)` is matched by `r`. Transfer the audited-prover discipline: what should a faithful contractor deliver, and what does the probe show? [claim] is the statement with an empty body; [refute] proves a counterexample.

```dafny
module R04_BankOnce {
  import opened RG_A1_Re

  // [claim] as delivered: every star match is a match of the body
  lemma StarIsOnce(r: Re, s: seq<char>)
    requires Matches(Star(r), s)
    ensures Matches(r, s)
  {
  }

  // [refute] a counterexample, proved: the empty string
  lemma StarIsOnceRefuted()
    ensures Matches(Star(Chr('m')), []) && !Matches(Chr('m'), [])
  {
  }
}
```
```rust
use vstd::prelude::*;
use rg_re_a1::*;

verus! {

// [claim] as delivered: every star match is a match of the body
proof fn lemma_star_is_once(r: Re, s: Seq<char>)
    requires
        matches(Re::Star(Box::new(r)), s),
    ensures
        matches(r, s),
{
}

// [refute] a counterexample, proved: the empty string
proof fn lemma_star_is_once_refuted()
    ensures
        matches(Re::Star(Box::new(Re::Chr('m'))), Seq::<char>::empty()) && !matches(Re::Chr('m'), Seq::<char>::empty()),
{
}

} // verus!
```

**Target insights**
- The statement is false, and the cheapest counterexample is the empty string: `Star(Chr('m'))` matches `[]` and `Chr('m')` does not, so both [refute] bodies are empty. A two-chunk string such as "mm" refutes it too, at the price of a witness proof. A proved counterexample settles the question; no proof of [claim] exists, whatever the effort.
- A faithful delivery reports the unchanged statement, the counterexample and its proof, and leaves [claim]'s hole open. It never adds `requires |s| <= 1`, weakens the `ensures`, or closes the hole with an `assume`: those deliver a different, green statement, which the statement freeze and the audit are there to catch.
- Dafny reports [claim]'s failure once per case of `Matches` it could not establish (five related lines into A1); that is the shape of a false universal claim, not a missing hint.

**Misconceptions & counter-moves**
- *"A good contractor always ends green."* → Ask: what would a green [claim] have to contain, given [refute]?
- *"Adding a precondition is a small repair."* → Ask: which statement would then be proved, and who asked for it?
- *"The failure means the proof needs induction."* → Ask: does [refute] verify? What does that say about every possible proof of [claim]?
