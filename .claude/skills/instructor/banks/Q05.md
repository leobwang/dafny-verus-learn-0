### K1 [reconstruct] — what a routine may write
**viva:** yes · **strand:** S6 · **tags:** `frames`, `ownership-and-mut-ref`, `pipeline-stages` · **backward-edge:** Q02 (`modifies` and `old` on arrays: what a caller knows after a call)

Reconstruct, in each language, the rule that decides which locations a routine may write: Dafny's `modifies` clause, and Verus's `&` and `&mut` parameters. Say who checks each rule, at which stage, and what a caller may assume, after a call, about a location the rule does not let the callee write. Then read the two probes' errors and give the one-line repair of each.

**Target insights**
- Dafny: a method may assign the fields and elements of the objects its `modifies` clause names (and of objects it allocates itself); the verifier checks every heap write against that frame ("assignment might update an object not in the enclosing context's modifies clause", stage verify). At a call, the caller forgets exactly the callee's frame and keeps every other location.
- Verus: there is no `modifies` clause; the types decide. A `&mut` parameter lends the whole value for writing, a `&` parameter only for reading, and writing through `&` is a borrow-check error reported before verification (stage resolve). A caller knows a `&` argument unchanged; what became of a `&mut` argument it knows only through the `final(…)` clauses of the callee's `ensures`.
- Either way, "what changed" is a fact of the contract or the types, never of the body: a caller never reads the callee's body.
- The repairs: name `h` in the frame (`modifies g, h`, and say in `ensures` what a caller needs about it), or pass `h` as `&mut`.

**Misconceptions & counter-moves**
- *"`modifies` is documentation; the verifier works out from the body what changes."* → Probe: the Dafny `Fill` below; ask: which line is rejected, and what would a caller assume about `h` after the call if the write were allowed?
- *"In Verus a write through `&` is a verification error like any other."* → Probe: the Verus `fill`; ask: which stage reports it, and what does the verifier ever see of this file?
- *"Once `h` is in the frame, a caller knows `h.level == 5`."* → Ask: what does a caller know about `h` after the call when the `ensures` says nothing about it? Then point at the repaired versions' `ensures`.

**Verifier probe**

{

### K2 [predict] — two arguments, one object?
**viva:** yes (verifier-refereed predict) · **strand:** S6 · **tags:** `frames`, `ownership-and-mut-ref`, `pipeline-stages` · **backward-edge:** none

Each caller reads one cell of a second argument, makes a call that may write the first argument, and asserts that the cell is unchanged. Predict, per routine, its verdict: verified, or an error (the stage, and the line).

```dafny
method ClearFirst(a: array<int>)
  requires a.Length > 0
  modifies a
  ensures a[0] == 0
{
  a[0] := 0;
}

method KeepA(a: array<int>, b: array<int>)
  requires a.Length > 0 && b.Length > 0 && a != b
  modifies a
{
  var b0 := b[0];
  ClearFirst(a);
  assert b[0] == b0;
}

method KeepB(a: array<int>, b: array<int>)
  requires a.Length > 0 && b.Length > 0
  modifies a
{
  var b0 := b[0];
  ClearFirst(a);
  assert b[0] == b0;
}
```
```rust
use vstd::prelude::*;

verus! {

fn clear_first(v: &mut Vec<i64>)
    requires
        old(v).len() > 0,
    ensures
        final(v).len() == old(v).len(),
        final(v)@[0] == 0,
{
    v.set(0, 0);
}

fn keep(v: &mut Vec<i64>, w: &Vec<i64>)
    requires
        old(v).len() > 0,
        w.len() > 0,
{
    let w0 = w[0];
    clear_first(v);
    assert(w@[0] == w0);
}

fn lend_twice(u: &mut Vec<i64>)
    requires
        old(u).len() > 0,
{
    keep(u, u);
}

} // verus!
```
The Verus probe runs twice: first without `lend_twice` (the file down to `keep`), then whole. Answer form, per routine: `verified` or `error at line <n> (<stage>)`.

**Target insights**
- Dafny: `KeepA` verifies and `KeepB` fails at its `assert` (line 24). A caller forgets the callee's frame, here the array `a`; when nothing says `a != b`, `b` may be the same array, so `b[0]` is forgotten too. The `requires a != b` is what lets the frame rule keep `b`.
- Verus: `keep` verifies with no distinctness clause: a `&mut` and a `&` argument can never be the same value, because the borrow checker refuses any call that would make them so. `lend_twice`, which tries, is rejected before verification (stage resolve), so the whole file never reaches the verifier.
- So aliasing is a proof obligation in Dafny (a `requires`, or a `Repr` disjointness such as `!!`) and a type error in Verus.

**Misconceptions & counter-moves**
- *"`ClearFirst` only writes `a[0]`, so `b[0]` is untouched in both callers."* → Ask: what does `KeepB`'s proof know about `b` when `b` is `a`? Then run the Dafny probe.
- *"Verus must be missing the aliasing case: `keep` needs a distinctness `requires` too."* → Probe: the whole Verus file; ask: which stage rejects `lend_twice`, and why does `keep` never meet an aliased call?

### K3 [predict] — the early return
**viva:** yes (verifier-refereed predict) · **strand:** S6 · **tags:** `requires-ensures`, `verdict-reading` · **backward-edge:** none

Each file has a helper that halves an even number and fails on an odd one, and two callers that take the half with one `:-` (Dafny) or `?` (Verus) step and return it plus one. Predict, per caller, whether it verifies; for a caller that fails, the line the error names.

```dafny
import opened Std.Wrappers

function EvenHalf(n: nat): Result<nat, string>
{
  if n % 2 == 0 then Success(n / 2) else Failure("odd")
}

method EvenHalfPlusOne(n: nat) returns (r: Result<nat, string>)
  ensures r.Success? ==> r.value * 2 == n + 2
{
  var h :- EvenHalf(n);
  return Success(h + 1);
}

method EvenHalfPlusOneAlways(n: nat) returns (r: Result<nat, string>)
  ensures r.Success?
{
  var h :- EvenHalf(n);
  return Success(h + 1);
}
```
```rust
use vstd::prelude::*;

verus! {

pub struct OddInput;

fn even_half(n: u64) -> (r: Result<u64, OddInput>)
    ensures
        r is Ok <==> n % 2 == 0,
        r is Ok ==> r->Ok_0 * 2 == n,
{
    if n % 2 == 0 {
        Ok(n / 2)
    } else {
        Err(OddInput)
    }
}

fn even_half_plus_one(n: u64) -> (r: Result<u64, OddInput>)
    ensures
        r is Ok ==> r->Ok_0 * 2 == n + 2,
{
    let h = even_half(n)?;
    Ok(h + 1)
}

fn even_half_plus_one_always(n: u64) -> (r: Result<u64, OddInput>)
    ensures
        r is Ok,
{
    let h = even_half(n)?;
    Ok(h + 1)
}

} // verus!
```
Answer form, per caller: `verified` or `error at line <n>`.

**Target insights**
- `:-` and `?` are early returns: on a failure the caller returns at once, with the failure as its own result. That is a second return path, and every postcondition must hold on it too.
- The first caller verifies in both languages: its postcondition is guarded by "success implies …", which holds on the failure path, and on the success path the helper's postcondition (Dafny: its transparent body) gives `h * 2 == n`.
- The second caller fails in both: "the result is a success" is false on the failure path, for every odd `n`. Dafny names the return path, the `:-` line (18), with the `ensures` as the related location (16); Verus names the clause, line 29.
- The message names the obligation and the path, not the fix: the repair is a weaker postcondition (or a stronger `requires`, such as an even `n`), never a change of the step.

**Misconceptions & counter-moves**
- *"The `:-` step cannot fail when the code after it returns a success."* → Ask: what does the caller return when `n` is 3? Then run the probe.
- *"Dafny points at line 18, so the `:-` line is wrong."* → Ask: which line is the related location, and what does each line of the message name?

### K4 [predict] — a measure for swapped arguments
**viva:** yes (verifier-refereed predict) · **strand:** S7 · **tags:** `termination-measure`, `verdict-reading` · **backward-edge:** Q02 (termination measures: strictly smaller at each call, bounded below)

The recursive call swaps the two arguments. The Dafny function has no `decreases` clause; the Verus one says `decreases a, b`. Predict each verdict, then name a measure that both tools accept.

```dafny
function Interleave(a: nat, b: nat): nat
{
  if a == 0 then b else 1 + Interleave(b, a - 1)
}
```
```rust
use vstd::prelude::*;

verus! {

spec fn interleave(a: nat, b: nat) -> nat
    decreases a, b,
{
    if a == 0 {
        b
    } else {
        1 + interleave(b, (a - 1) as nat)
    }
}

} // verus!
```
Answer form: `D:<v> V:<v>`, with `v` in the module's verdict vocabulary (`ok`, `fail`, `timeout`, `err:<stage>`).

**Target insights**
- Both fail: `D:fail V:fail`. Dafny's default measure is the parameters in order, `a, b`, the same tuple Verus is given; a lexicographic tuple goes down when its first component goes down, or stays while the second goes down.
- The call maps `(a, b)` to `(b, a - 1)`: when `b >= a` the new first component is no smaller, so the tuple need not go down (`(1, 5)` to `(5, 0)`).
- `a + b` goes down by one at every call and is bounded below: with `decreases a + b` both verify. The right measure follows what the call does to the arguments, not their order in the signature.

**Misconceptions & counter-moves**
- *"Two arguments: a lexicographic `decreases a, b` is always the answer."* → Probe: the Verus run; ask: what is the tuple before and after the call at `a = 1, b = 5`?
- *"Dafny guesses a measure, so it must find one that works."* → Ask: which measure does Dafny guess, and what does its message suggest you do?

### K5 [why] — one name, two bodies
**viva:** yes · **strand:** S7 · **tags:** `function-by-method`, `spec-vs-exec`, `loop-invariant` · **backward-edge:** Q03 (what runs is the compiled, executable part; specifications are erased)

`Fib` below has two bodies. Which one does a caller's proof reason with, and which one does the compiled program run? Why must the verifier prove that the method body returns the function body's value, and what would go wrong without that proof? In Verus, which two declarations play the same roles? (Dafny only: `function … by method` has no Verus form.)

```dafny
function Fib(n: nat): nat
  decreases n
{
  if n < 2 then n else Fib(n - 1) + Fib(n - 2)
} by method {
  var a, b := 0, 1;
  var k := 0;
  while k < n
    invariant 0 <= k <= n && a == Fib(k) && b == Fib(k + 1)
    decreases n - k
  {
    a, b := b, a + b;
    k := k + 1;
  }
  return a;
}

@Test
method FibSixty()
{
  expect Fib(60) == 1548008755920;
}
```

**Target insights**
- The function body is the specification: every proof that mentions `Fib(n)` reasons with the recursive definition, unfolding it.
- The compiled program runs the method body, the loop. `FibSixty` passes; the recursive definition, run as written, would make about 5 × 10^12 calls for `Fib(60)`.
- The by-method obligation (the method's result equals the function body's value) is what makes the swap sound: without it, the proofs would be about one function and the program would run another. A fast body that is wrong, or unproved, cannot ship: the probe without `b == Fib(k + 1)` fails.
- In Verus there are two names: a `spec fn` that proofs use, and an exec `fn` whose `ensures` says its result equals the spec fn's value; callers' proofs use the first, compiled code calls the second.

**Misconceptions & counter-moves**
- *"The verifier uses the loop, since that is the code."* → Ask: what does a caller's proof of `Fib(5) == 5` unfold? Then point at the method body's obligation.
- *"The method body is checked by running the test."* → Probe: the variant without `b == Fib(k + 1)`; ask: which stage rejects it, and what would the test have shown?

- A ghost field, like a ghost variable, exists for the verifier only: specifications, ghost functions and other ghost code may read it, and it is erased from the compiled program. ### K8 [transfer] — a proposer and a checker
**viva:** yes · **strand:** S8 · **tags:** `wp-vc`, `hoare-logic`, `loop-invariant`, `exec-overflow`, `paper-cards` · **backward-edge:** Q03 (the verification conditions of a loop by hand; an invariant one conjunct short)

A language model proposes, one at a time, three invariants for the loop below: I1 `y >= 0`; I2 `y <= 2 * n`; I3 `0 <= x <= n && y == 2 * (n - x)` (Verus: `x <= n` and `y == 2 * (n - x)`, the bound coming from `u32`). For each, which verification conditions of the loop fail (entry, maintenance, use at exit; in Verus also the overflow check of `y + 2`)? Is the candidate false on some run, true but too weak, or good? What may the checker conclude about the program from a failed check? Relate this to card 03.12, where the model proposes and the verifier decides.

```dafny
method DoubleUp(n: nat) returns (y: nat)
  ensures y == 2 * n
{
  var x := n;
  y := 0;
  while x > 0
    invariant y >= 0
    decreases x
  {
    x := x - 1;
    y := y + 2;
  }
}
```
```rust

fn double_up(n: u32) -> (y: u64)
    ensures
        y == 2 * n,
{
    let mut x: u32 = n;
    let mut y: u64 = 0;
    while x > 0
        invariant
            y >= 0,
        decreases x,
    {
        x = x - 1;
        y = y + 2;
    }
    y
}

} // verus!
```
(The probe above carries I1; I2 and I3 replace its invariant line.)

**Target insights**
- I1 holds on every run and is inductive, but at exit it says nothing about `y`: use at exit fails (the postcondition). In Verus it is also too weak to bound `y` for `y + 2`, so the overflow check fails too. Too weak.
- I2 holds on every run (`y = 2(n - x) <= 2n`) but is not inductive: from the unreachable state `n = 1, x = 1, y = 2` one pass gives `y = 4 > 2`. Maintenance fails, and so does use at exit. True on runs, still not an invariant the checker can use.
- I3 verifies in both languages: it ties `y` to the work done and bounds `x`, and with the exit's `x == 0` gives `y == 2n`.
- A failed check refutes the candidate as a proof, never the program: the same loop verifies under I3. An error alone is not a counterexample (the course's asymmetry rule); the counterexample to I2's maintenance is the state above, run one pass.
- Card 03.12's boundary: the proposer only produces assumptions and the checker alone decides; a candidate the checker cannot prove goes back for repair (the card's Repair rules) and is never accepted on the proposer's word.

**Misconceptions & counter-moves**
- *"I2 is true of every run, so it is an invariant."* → Ask: which state does maintenance range over? Then give the state `n = 1, x = 1, y = 2` and one pass.
- *"The verifier rejected I1, so the program is wrong."* → Probe: I3; ask: what did the failed check refute?
