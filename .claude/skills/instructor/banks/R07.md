### K1 [reconstruct] — a call owes its requires
**viva:** yes · **tags:** `standard-library`, `requires-ensures` · **backward-edge:** R04 (a contract: the caller proves `requires` and receives `ensures`)

A library lemma is a contract like any other: calling it hands you its `ensures` only where its `requires` holds. Reconstruct what the verifier checks at the call. `DistinctCount` / `lemma_distinct_count` call the library's no-duplicates cardinality lemma on an arbitrary sample. What fails, and where does Dafny's related line point?

```dafny
module R07_BankPre {
  import S = Std.Collections.Seq

  // The library lemma's requires is the caller's to discharge.
  lemma DistinctCount(xs: seq<char>)
    ensures |S.ToSet(xs)| == |xs|
  {
    S.LemmaCardinalityOfSetNoDuplicates(xs);
  }
}
```
```rust
use vstd::prelude::*;
use vstd::seq_lib::*;

verus! {

// The library lemma's requires is the caller's to discharge.
proof fn lemma_distinct_count(xs: Seq<char>)
    ensures
        xs.to_set().len() == xs.len(),
{
    xs.unique_seq_to_set();
}

} // verus!
```

**Target insights**
- At a call the verifier proves the callee's `requires` at the arguments, then assumes its `ensures`. `LemmaCardinalityOfSetNoDuplicates` requires `HasNoDuplicates(xs)`, which an arbitrary sample does not have.
- Dafny reports "a precondition for this call could not be proved" and points its related lines into the standard library's source: the precondition and the proposition inside it. Verus says "precondition not satisfied" at the call.
- The repair is a hypothesis that supplies the precondition (`requires S.HasNoDuplicates(xs)`), or a different lemma; the claim as stated is false for samples with repeats.

**Misconceptions & counter-moves**
- *"The library is broken."* → Ask: which proposition does the related line point at, and who owes it?
- *"A call always helps."* → Ask: what does the call contribute when its `requires` fails?
- *"Add an assume."* → Ask: is the claim true for `"aa"`?

### K2 [predict] — one claim, two libraries
**viva:** yes (verifier-refereed predict) · **tags:** `standard-library`, `sequences-and-views` · **backward-edge:** R02 (a sequence and the set of its elements are different objects)

Both files claim that the alphabet of a joined sample is the union of the two alphabets, with an empty body: Dafny's `S.ToSet(a + b) == S.ToSet(a) + S.ToSet(b)`, Verus's `(a + b).to_set() == a.to_set().union(b.to_set())`. Predict each verdict, `D:<ok|fail> V:<ok|fail>`.

```dafny
module R07_BankUnion {
  import S = Std.Collections.Seq

  // The alphabet of a joined sample, with no call.
  lemma JoinedAlphabet(a: seq<char>, b: seq<char>)
    ensures S.ToSet(a + b) == S.ToSet(a) + S.ToSet(b)
  {
  }
}
```

```rust
use vstd::seq_lib::*;

// The alphabet of a joined sample, with no call.

    ensures
        (a + b).to_set() == a.to_set().union(b.to_set()),

}
```

**Target insights**

### K3 [predict] — a broadcast has a scope
**viva:** yes (verifier-refereed predict) · **tags:** `broadcast-use`, `standard-library` · **backward-edge:** none

The file declares its own `broadcast proof fn lemma_double_even`, then two proofs of the same quantified claim. The first has `broadcast use lemma_double_even;` in its body; the second has an empty body. Predict which verify: `evens_here`, `evens_there`, both, or neither.

```rust
use vstd::prelude::*;

verus! {

#[verifier::opaque]
spec fn double(n: int) -> int {
    n + n
}

// An opaque function, and a broadcast lemma of this file's own about it.
broadcast proof fn lemma_double_even(n: int)
    ensures
        #[trigger] double(n) % 2 == 0,
{
    reveal(double);
}

// The broadcast, inside one proof's body.
proof fn evens_here(xs: Seq<int>)
    ensures
        forall|i: int| 0 <= i < xs.len() ==> #[trigger] double(xs[i]) % 2 == 0,
{
    broadcast use lemma_double_even;
}

// The same claim in another proof, with no broadcast of its own.
proof fn evens_there(xs: Seq<int>)
    ensures
        forall|i: int| 0 <= i < xs.len() ==> #[trigger] double(xs[i]) % 2 == 0,
{
}

} // verus!
```

**Target insights**
- `evens_here` verifies and `evens_there` fails: a `broadcast use` inside a proof body is scoped to that body. The second proof never sees the lemma.
- Scope is the point. A broadcast lets the solver use a lemma wherever its trigger matches, inside the scope you chose; here the trigger `double(n) % 2 == 0` matches at every `xs[i]` the goal mentions, which one named call could not cover.
- A module-level `broadcast use` would reach both proofs, and every other proof in the module. The hand-first rule asks for the named call first and the smallest scope after.

**Misconceptions & counter-moves**
- *"A broadcast is global."* → Ask: where in the file is the `broadcast use` line?
- *"The second proof should see the first proof's facts."* → Ask: does any proof's body export its facts to another proof?
- *"Broadcast more to be safe."* → Ask: which other proofs would then pay for the instances?

**Verifier probe**
Answer: only `evens_here`.

### K5 [reconstruct] — what a found-by note is
**viva:** yes · **tags:** `search-then-name`, `standard-library` · **backward-edge:** none

Reconstruct the role of a `// found-by:` note. The two lemmas below are identical except for the note on the call. Both verify. What does the note record, what does the verifier do with it, and why does the named-call gate (D90) require it?

```dafny
module R07_BankNote {
  import S = Std.Collections.Seq

  // The found-by note is provenance, not a premise: the call is the step.
  lemma EmptyAlphabetNoted(xs: seq<char>)
    ensures |S.ToSet(xs)| == 0 <==> |xs| == 0
  {
    S.LemmaCardinalityOfEmptySetIs0(xs);  // found-by: grep
  }

  lemma EmptyAlphabetUnnoted(xs: seq<char>)
    ensures |S.ToSet(xs)| == 0 <==> |xs| == 0
  {
    S.LemmaCardinalityOfEmptySetIs0(xs);
  }
}
```

**Target insights**
- The note is provenance: the rung of the search ladder that found the symbol (`ide`, `grep`, `docs`, `source`, `llm`, `memory`). The verifier ignores it; it is a comment.
- It matters for review and for experiments: a reader can repeat the search, and the retriever race compares arms by how symbols were found. A remembered name and a grep hit are different evidence.
- The proof is the call. Removing the note changes no verdict; removing the call does (the gate checks that).

**Misconceptions & counter-moves**
- *"The note helps the solver."* → Ask: does either lemma's verdict change?
- *"Any rung label will do."* → Ask: what would a reviewer do with `found-by: grep` that they cannot do with `found-by: memory`?
- *"A note can replace a precondition proof."* → Ask: which part of the proof does the note justify?

### K6 [why] — a called lemma and an axiom
**viva:** yes · **tags:** `tcb`, `standard-library` · **backward-edge:** R04 (the audit sees what the gate does not)

Why is a named library call not an assumption, and an `{:axiom}` lemma is? Both lemmas below state the same bound; both verify in the learner loop. Run the audit and explain the difference.

```dafny
module R07_BankTrust {
  import S = Std.Collections.Seq

  // A named library call: proved in the library, checked here.
  lemma AlphabetBoundCalled(xs: seq<char>)
    ensures |S.ToSet(xs)| <= |xs|
  {
    S.LemmaCardinalityOfSet(xs);
  }

  // The same claim stated as an axiom: no proof anywhere.
  lemma {:axiom} AlphabetBoundAssumed(xs: seq<char>)
    ensures |S.ToSet(xs)| <= |xs|
}
```

**Target insights**
- `AlphabetBoundCalled` uses a lemma whose body the library proved under the same toolchain: the call is a checked step, and it trusts only what the library's proof trusts.
- `AlphabetBoundAssumed` has no proof at all. Verify is silent about it; the audit reports it as an axiom, an unproved assumption.
- A clean verify is not a clean audit, and a library is not an axiom: the trust surface is the toolchain and the library's own external specifications, not every lemma you call.

- *"Library lemmas are axioms."* → Ask: which of the two did the audit flag?

```dafny
module R07_BankVacuous {
```

```python
try:
    pass_at_k(5, 2, 6)
except ValueError as e:
    print("k > n:", e)
```

**Target insights**
- Per task: pass@1 is 0.4 and 0.8, pass@2 0.7 and 1.0, so the task-level mean pass@2 is 0.85.
- Pooling the ten attempts as one task gives 0.8667: a different number, because pass@k is nonlinear in c and pooling weights attempts, not tasks.
- The estimator refuses `k > n`; a report must say what it does for tasks with too few attempts, rather than clip k or drop tasks silently.

**Misconceptions & counter-moves**
- *"Pooling is just more data."* → Ask: which unit does the claim talk about: attempts, or tasks?
- *"The difference is rounding."* → Ask: which step is nonlinear?
- *"Use k = n when n is small."* → Ask: what metric would that report?

### K10 [connect] — an interval for a pass rate
**viva:** yes · **tags:** `statistics`, `variance` · **backward-edge:** R05 (a bootstrap interval of a mean, and what it licenses)

Connect R05's bootstrap interval to the race's numbers. Five tasks with n=5 attempts each have per-task pass@1 values; what is their mean, and what does a 95 % bootstrap interval of that mean license?

```python
import statistics
from fvh.stats import pass_at_k, bootstrap_ci
per_task = [pass_at_k(5, c, 1) for c in (2, 4, 1, 5, 3)]
print("per-task pass@1", per_task)
print("mean", statistics.fmean(per_task))
print("95% bootstrap interval of the mean", bootstrap_ci(per_task, statistics.fmean, seed=7))
```

**Target insights**
- The mean pass@1 is 0.6, and the 95 % bootstrap interval of the mean is (0.36, 0.84): a statement about the mean over these five tasks' population, under the assumption that the tasks are independent draws.
- It is not an interval for one task's success, nor for the next attempt, and five tasks give a wide interval. R05's cautions carry over.
- The interval resamples tasks, the unit of the claim; resampling attempts would answer a different question.

**Misconceptions & counter-moves**
- *"60 % of attempts succeed."* → Ask: what was averaged: attempts, or tasks?
- *"The interval is narrow enough."* → Ask: how many tasks?

### K12 [transfer] — read the function's own contract
**viva:** yes · **tags:** `standard-library`, `requires-ensures` · **backward-edge:** none

Transfer the search to a new fact: the alphabet of a filtered sample is no larger than the sample. It looks like two facts (filtering shrinks; a set is no larger than its sequence). Read the probe: one named call suffices. Where did the other fact come from?

```dafny
module R07_BankCompose {
  import S = Std.Collections.Seq

  // Only the cardinality fact.
  lemma FilteredAlphabetBound(p: char -> bool, xs: seq<char>)

}
```

**Target insights**

- Under the named-call gate this body is one call, and removing it fails.

- *"Two facts need two calls."* → Ask: which of the two facts is in `Filter`'s signature?
