### K3 [why] — a green caller of a red callee
**viva:** yes · **tags:** `fast-channel`, `requires-ensures`, `tcb` · **backward-edge:** R08 (a client of an interface knows only its contract)

`UseDoubleBankR13` proves `2 + 2 == 6` from a callee whose own proof fails. Why does a run selected to the caller verify, and why is that not a contradiction in the verifier? What exactly does the selected green establish, and what does it depend on?

```dafny
module R13_BankModular {
  // A false claim: n + n == n * 3 holds only at n == 0.
  lemma DoubleBankR13(n: nat)
    ensures n + n == n * 3
  {
  }

  // The caller uses only the callee's contract.
  lemma UseDoubleBankR13()
    ensures 2 + 2 == 6
  {
    DoubleBankR13(2);
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// A false claim: n + n == n * 3 holds only at n == 0.
pub proof fn double_bank_r13(n: nat)
    ensures
        n + n == n * 3,
{
}

// The caller uses only the callee's contract.
pub proof fn use_double_bank_r13()
    ensures
        2 + 2 == 6,
{
    double_bank_r13(2);
}

} // verus!
```

**Target insights**
- Verification is modular: a call is checked against the callee's `requires` and then the callee's `ensures` is assumed. The caller's obligation is "if `DoubleBankR13`'s contract holds, then `2 + 2 == 6`", and from `2 + 2 == 2 * 3` that implication is valid.
- A per-symbol run checks the selected declaration's obligations only. The callee's own obligation, that its body establishes its `ensures`, is a different symbol and is not run. The selected green is therefore a conditional result: it holds relative to every contract the caller uses.
- The full run is what discharges the callee, and it fails at the callee's postcondition. Until it passes, every caller's green inherits the callee's unproved claim. This is R08's interface discipline seen from the trust side: a client knows only the contract, and so does the verifier.
- Selection cannot be widened afterwards. A ledger row for a selected run names the symbol, and the claim "the file verifies" needs the full target with zero holes.

**Misconceptions & counter-moves**
- *"The caller verified, so the arithmetic must be right."* → Ask: which fact did the caller use, and where was that fact proved?
- *"The fast channel is a faster gate."* → Ask: which declarations' obligations did the selected run generate, and which did it never ask about?
- *"The verifier is unsound here."* → Ask: write down the implication the caller actually proved; is it valid?

### K4 [predict] — a runtime check the verifier believes
**viva:** yes (verifier-refereed predict) · **tags:** `running-verified-code`, `tcb`, `fake-green`, `verdict-reading` · **backward-edge:** R04 (`expect` is a runtime check that the verifier assumes)

Predict the learner loop's verdict on each Dafny file [a] and [b], and on the Verus file (verdict and hole count). Commit all three before any run.

```dafny
module R13_BankExpectA {
  method GuardBankR13()
  {
    var x := 3;
    expect x == 4;
    assert x == 4;
  }
}
```
```dafny
module R13_BankExpectB {
  method NoGuardBankR13()
  {
    var x := 3;
    assert x == 4;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// A trusted helper: its body is never checked against its ensures.
#[verifier::external_body]
pub fn three_bank_r13() -> (x: u32)
    ensures
        x == 4,
{
    3
}

pub fn use_three_bank_r13() {
    let x = three_bank_r13();
    assert(x == 4);
}

} // verus!

#[test]
fn trial_three_bank_r13() {
    assert_eq!(three_bank_r13(), 4);
}
```

**Target insights**
- Dafny [a] verifies: after `expect x == 4`, the verifier assumes `x == 4`. With `x == 3` already known, the state after the `expect` is contradictory, and the `assert` is proved vacuously. Dafny [b], without the `expect`, fails at the assertion.
- `expect` is R04's runtime check: it is compiled, it halts the program when false, and in exchange the verifier may assume it. That makes it a trusted statement: correct only if the run reaches it and it holds. A verified file that contains an `expect` has a proof that depends on a runtime event.
- Verus: `three_bank_r13` is `external_body`, so its `ensures x == 4` is believed and its body `3` is never checked; the caller's assertion is proved from the trusted contract. The wrapper counts the `external_body` as a hole, so the learner loop says `verified` with `1 hole`.
- In both languages the compiled test is the instrument that sees the gap: it runs the code that the proof trusted and finds it false.

**Misconceptions & counter-moves**
- *"`expect` is just a runtime `assert`; the verifier ignores it."* → Ask: why does [a] verify while [b] fails, when they differ only in the `expect` line?
- *"`verified` with `1 hole` is a pass with a note."* → Ask: which declaration's body did the verifier read, and which `ensures` did it take on trust?
- *"The test failing means the proof is wrong."* → Ask: what did the proof assume, and is that assumption false or the proof's reasoning?

### K8 [connect] — a small checker, checked once
**viva:** yes · **tags:** `verified-metatheory`, `tcb`, `running-verified-code` · **backward-edge:** R11 (a certificate is checked by a small verified checker)

`ConfirmFactorBankR13` accepts a factor as a certificate that `n` is composite. Connect it to R11's derivation checker: what is proved once, what is run per certificate, and which parts of the trusted base does the design shrink, and which does it leave?

```dafny
module R13_BankFactor {
  ghost predicate CompositeBankR13(n: nat)
  {
    exists d: nat :: 1 < d < n && n % d == 0
  }

  // A small checker: a true answer comes with its own proof obligation, discharged once.
  method ConfirmFactorBankR13(n: nat, d: nat) returns (ok: bool)
    ensures ok ==> CompositeBankR13(n)
  {
    ok := 1 < d < n && n % d == 0;
  }

  method {:test} FactorTrialBankR13()
  {
    var good := ConfirmFactorBankR13(91, 7);
    expect good;
    var bad := ConfirmFactorBankR13(91, 6);
    expect !bad;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

pub open spec fn composite_bank_r13(n: nat) -> bool {
    exists|d: nat| #![trigger n % d] 1 < d < n && n % d == 0
}

// A small checker: a true answer comes with its own proof obligation, discharged once.
pub fn confirm_factor_bank_r13(n: u64, d: u64) -> (ok: bool)
    ensures
        ok ==> composite_bank_r13(n as nat),
{
    if 1 < d && d < n && n % d == 0 {
        assert((n as nat) % (d as nat) == 0);
        true
    } else {
        false
    }
}

} // verus!

#[test]
fn factor_trial_bank_r13() {
    assert!(confirm_factor_bank_r13(91, 7));
    assert!(!confirm_factor_bank_r13(91, 6));
}
```

**Target insights**
- The checker's soundness (`ok ==> CompositeBankR13(n)`) is proved once, by the verifier and solver. Each certificate is then checked by running the compiled checker, a few arithmetic operations, with no solver call. This is R11's shape: an untrusted producer, a small verified checker, a cheap check per answer.
- The design moves trust: a `true` answer no longer depends on whoever produced the factor (an agent, a search, a guess). It still depends on the checker's proof (verifier, translation, solver, once), on the compiler and runtime that execute it, and on the predicate meaning "composite" (fidelity, as in R11's rule binding).
- A `false` answer refutes the certificate, not the claim: `91` is composite and `6` is simply not a factor. Soundness and completeness are separate promises (R11 §1.2).
- Unlike a proof-assistant kernel, the checker is a program in the same toolchain; R13's "no small kernel" still holds for the checker itself.

**Misconceptions & counter-moves**
- *"With a verified checker nothing is trusted any more."* → Ask: which tools ran when the checker was proved, and which run each time it executes?
- *"`ConfirmFactorBankR13(91, 6)` returning false proves 91 is prime."* → Ask: which direction does the `ensures` state?
- *"The test passing is what makes the checker trustworthy."* → Ask: which of the two observations (verified, passed) covers every `n` and `d`?

```rust
// Meant: every earlier element is at most every later one.
pub open spec fn ascending_bank_r13(s: Seq<int>) -> bool {
    forall|i: int, j: int| 0 <= i < j < s.len() && j < i ==> s[i] <= s[j]
}

pub proof fn ascending_witness_bank_r13() {
    assert(ascending_bank_r13(seq![3int, 1, 2]));
}

} // verus!
```

**Target insights**
- L1 (validity): the derivation is correct relative to its formal inputs. The lemma verifies in both languages, and nothing is wrong with the proof.
- L2 (fidelity): the predicate does not represent "ascending". Its guard `i < j && j < i` is unsatisfiable, so the `forall` holds of every sequence. The witness `[3, 1, 2]`, which the intended predicate rejects, is accepted: a vacuous specification, found by a concrete value, not by the verifier.
- L3 (significance): whether a verified ascending check matters for its use is a further question, answered by the purpose, not by a proof. The card's point is that cheap checking (L1 abundant) moves the scarce work to deciding L2 and L3.
- Keep numbers attached to their objects: the card's byte ratio of proof to statement is a size ratio, not an error rate, and two cases do not estimate a population rate.

**Misconceptions & counter-moves**
- *"It verified, so the predicate is right."* → Ask: which level does a verified lemma speak to, and which sequence should the intended predicate reject?
- *"A vacuous predicate is a verifier bug."* → Ask: what would the verifier have to know about your intent to reject it?
- *"L3 is the same as L2 with more tests."* → Ask: can any amount of fidelity evidence say whether the result was worth proving?

`SumCatBankR13` (Verus `lemma_sum_cat_bank_r13`) states that the sum of a concatenation is the sum of its parts. A trusted version would be `{:axiom}` or `external_body`; prove it instead. module R13_PP2 {
```dafny
  function SumBankR13(s: seq<nat>): nat
    decreases |s|
```
