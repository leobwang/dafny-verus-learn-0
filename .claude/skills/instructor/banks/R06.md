### K1 [reconstruct] — what a measure establishes
**viva:** yes · **tags:** `termination-measure`, `induction-as-recursion` · **backward-edge:** R02 (the termination pair of `Matches`: a measure that decreases at every recursive use)

A recursive lemma is accepted only if a declared measure decreases at each recursive call. Reconstruct what the verifier checks at a call, and what it does not check. Then read the probe: `HalveStepsBound` / `lemma_halve_steps_bound` calls itself on `n / 2`, and `HalveStepsStuck` / `lemma_halve_steps_stuck` on `n` itself, both under `decreases n`. Which call is refused, and with what message?

```dafny
module R06_BankHalve {
  // A sum of halvings: the recursive call is on n / 2.
  function HalveSteps(n: nat): nat
    decreases n
  {
    if n <= 1 then 0 else 1 + HalveSteps(n / 2)
  }

  lemma HalveStepsBound(n: nat)
    ensures HalveSteps(n) <= n
    decreases n
  {
    if n > 1 {
      HalveStepsBound(n / 2);
    }
  }

  lemma HalveStepsStuck(n: nat)
    ensures HalveSteps(n) <= n
    decreases n
  {
    if n > 1 {
      HalveStepsStuck(n);
    }
  }
}
```
```rust
use vstd::prelude::*;

verus! {

spec fn halve_steps(n: nat) -> nat
    decreases n,
{
    if n <= 1 { 0 } else { 1 + halve_steps(n / 2) }
}

proof fn lemma_halve_steps_bound(n: nat)
    ensures
        halve_steps(n) <= n,
    decreases n,
{
    if n > 1 {
        lemma_halve_steps_bound(n / 2);
    }
}

proof fn lemma_halve_steps_stuck(n: nat)
    ensures
        halve_steps(n) <= n,
    decreases n,
{
    if n > 1 {
        lemma_halve_steps_stuck(n);
    }
}

} // verus!
```

**Target insights**
- At each recursive call the verifier proves that the measure of the call's arguments is smaller than the measure at entry (for `nat`, strictly smaller; for a datatype, a sub-term), and that it is bounded below. That is the whole termination obligation.
- It does not check that the call is useful: a call that terminates can still give a useless hypothesis, and a call that does not decrease is refused even if the claim is true.
- `n / 2 < n` holds for `n > 1`, which the `if` guard supplies; `n < n` never holds, so `HalveStepsStuck`'s call is refused at the call site, in both languages.

**Misconceptions & counter-moves**
- *"The lemma is true, so the call is fine."* → Ask: what would the call's postcondition give you that you did not already have?
- *"The measure is about the function, not the lemma."* → Ask: whose `decreases` clause does the error point at, and which call?
- *"`decreases n` means n must reach 0."* → Ask: what is compared at each call: the value at the call, or the final value?

### K2 [predict] — Dafny's default measure
**viva:** yes (verifier-refereed predict) · **tags:** `termination-measure`, `auto-induction` · **backward-edge:** R02 (a measure is part of the claim about recursion)

`Climb(k, n)` calls itself on `k + 1` while `k < n`, and has no `decreases` clause. Predict: does Dafny accept it as written, and does Verus accept `lemma_climb` with no `decreases`? Answer `D:<ok|fail> V:<ok|fail>` before running.

```dafny
module R06_BankClimb {
  // Counts up from k to n; the call raises k.
  lemma {:induction false} Climb(k: nat, n: nat)
    requires k <= n
    ensures k <= n
  {
    if k < n {
      Climb(k + 1, n);
    }
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// Counts up from k to n; the call raises k.
proof fn lemma_climb(k: nat, n: nat)
    requires
        k <= n,
    ensures
        k <= n,
{
    if k < n {
        lemma_climb(k + 1, n);
    }
}

} // verus!
```

**Target insights**
- Dafny's default measure is the parameters in order, compared lexicographically: here `(k, n)`. The call raises `k` and keeps `n`, so the default does not decrease: `fail`, with "cannot prove termination; try supplying a decreases clause".
- Verus has no default for a recursive proof function: it refuses at resolution, before any proof, with "recursive function must have a decreases clause": `fail`.
- The measure that works is the distance still to go, `n - k`, in both languages. A default is a guess about the recursion; when the call does not shrink the first parameter, the guess is wrong.

**Misconceptions & counter-moves**
- *"Dafny infers termination."* → Ask: what does it infer, and what does that guess compare at this call?
- *"k gets closer to n, so it decreases."* → Ask: which expression gets smaller? Is it `k`?
- *"Verus failed for the same reason."* → Ask: at which stage did each fail, and did either reach the call?

### K3 [predict] — which invariant obligation fails
**viva:** yes (verifier-refereed predict) · **tags:** `loop-invariant`, `verdict-reading` · **backward-edge:** none

`EvenTally` / `even_tally` counts the even numbers of `s` with the invariant `n < i` (and the bounds). The invariant has three obligations: on entry, preserved by the body, and enough at exit for `n <= |s|`. Predict which one fails, in each language, before running.

```dafny
module R06_BankTally {
  // Counts the even numbers of s.
  method EvenTally(s: seq<int>) returns (n: nat)
    ensures n <= |s|
  {
    n := 0;
    var i := 0;
    while i < |s|
      invariant 0 <= i <= |s|
      invariant n < i
      decreases |s| - i
    {
      if s[i] % 2 == 0 {
        n := n + 1;
      }
      i := i + 1;
    }
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// Counts the even numbers of s.
fn even_tally(s: &Vec<i64>) -> (n: usize)
    ensures
        n <= s.len(),
{
    let mut n: usize = 0;
    let mut i: usize = 0;
    while i < s.len()
        invariant
            i <= s.len(),
            n < i,
        decreases s.len() - i,
    {
        if s[i] % 2 == 0 {
            n = n + 1;
        }
        i = i + 1;
    }
    n
}

} // verus!
```

**Target insights**
- On entry `n` and `i` are both 0, and `0 < 0` is false: the invariant fails on entry. Dafny says "this loop invariant could not be proved on entry"; Verus "invariant not satisfied before loop".
- Preservation would hold: if `n < i`, then after the body `n` grows by at most 1 and `i` by exactly 1. Exit would hold too: `n < i == |s|` gives `n <= |s|`. Neither is reported, because the verifier stops at the failure it found, but only entry is false.
- The repair is `n <= i`: true on entry, preserved, and enough at exit. A strict invariant that is false at the start is the classic off-by-one of loops.

**Misconceptions & counter-moves**
- *"It fails at the end, because the postcondition is about n."* → Ask: what are `n` and `i` before the first iteration?
- *"An invariant only has to hold inside the loop."* → Ask: which state is the base case of the induction on `i`?
- *"Only one error means only one obligation was checked."* → Ask: is preservation true? Check it by hand.

**Verifier probe**

### K5 [reconstruct] — the invariant as an induction hypothesis
**viva:** yes · **tags:** `loop-invariant`, `induction-as-recursion` · **backward-edge:** none

Reconstruct why a loop needs an invariant to establish a postcondition about all of its input, using `AllPositive`. As shipped it has only the bounds as its invariant. What does the verifier know at exit, and which invariant is the induction hypothesis the postcondition needs?

```dafny
module R06_BankPositive {
  // Is every element of s positive?
  method AllPositive(s: seq<int>) returns (b: bool)
    ensures b <==> forall j :: 0 <= j < |s| ==> s[j] > 0
  {
    b := true;
    var i := 0;
    while i < |s|
      invariant 0 <= i <= |s|
      decreases |s| - i
    {
      b := b && s[i] > 0;
      i := i + 1;
    }
  }
}
```

**Target insights**
- At exit the verifier knows the invariant and the negated guard, nothing else: here `0 <= i <= |s|` and `i >= |s|`, so `i == |s|`. It knows nothing about `b`, so the postcondition fails.
- The invariant the proof needs is the postcondition with `|s|` replaced by `i`: `b <==> forall j :: 0 <= j < i ==> s[j] > 0`. It holds on entry (an empty range), each iteration extends it by one index, and at `i == |s|` it is the postcondition.
- This is induction on `i`: the invariant is the statement, the body the step, the initial values the base case.

**Misconceptions & counter-moves**
- *"The loop computes the right thing, so the postcondition follows."* → Ask: what does the verifier know about `b` after the loop, and from where?
- *"The invariant should be the postcondition."* → Ask: is the postcondition true when `i` is 0 and `s` has a negative element?
- *"A bigger invariant is safer."* → Ask: which extra conjunct would you have to prove preserved?

### K6 [why] — why the theorem must quantify
**viva:** yes · **tags:** `invariant-generalization`, `induction-as-recursion` · **backward-edge:** R02 (the hypothesis must cover the arguments you pass)

Why does an induction proof need its claim stated for every argument, rather than for the one value you care about? Use the probe: `TwiceThree` proves the length fact for `[1, 2, 3]` by hand, and `TwiceLength` for every `s` by a call on `s[1..]`. Both verify. Which one could a later proof use for a word it does not know?

```dafny
module R06_BankGeneral {
  function Twice(s: seq<int>): seq<int>
    decreases |s|
  {
    if s == [] then [] else [s[0], s[0]] + Twice(s[1..])
  }

  // Only the three-element case, by hand.
  lemma {:induction false} TwiceThree()
    ensures |Twice([1, 2, 3])| == 6
  {
    assert [1, 2, 3][1..] == [2, 3];
    assert [2, 3][1..] == [3];
    assert [3][1..] == [];
  }

  // Every case, by induction: the call is on a shorter s.
  lemma {:induction false} TwiceLength(s: seq<int>)
    ensures |Twice(s)| == 2 * |s|
    decreases |s|
  {
    if s != [] {
      TwiceLength(s[1..]);
    }
  }
}
```

**Target insights**
- `TwiceThree` is a fact about one sequence; it cannot be called on `s[1..]` for an unknown `s`, so it can never be the induction hypothesis of anything.
- `TwiceLength` quantifies over `s`, so its own body can call it on `s[1..]`, and any other proof can call it on any sequence. The generality is what makes the recursive call available.
- The same holds for H1: its hypothesis is used on a prefix of the word, so the claim must quantify over the word; a version for one fixed word would leave you no call to make.

**Misconceptions & counter-moves**
- *"A specific case is a smaller proof, so it is better."* → Ask: what can a caller with an unknown sequence do with `TwiceThree`?
- *"Induction needs a natural number."* → Ask: what decreases in `TwiceLength`'s call?
- *"Generalizing makes the proof harder."* → Ask: which call does the general statement give you that the specific one does not?

**Verifier probe**
(Dafny 4.11.0:)
```
vcheck: instructor/scratch/probe.dfy [dafny, learner loop]: verified — 14 verified, 0 holes, 0 errors
```
Follow-up: which argument of H1 is used at a value other than its own in the recursive calls? (The word: the hypothesis is used at a prefix of `s`.)

### K9 [why] — why the weakest repair
**viva:** yes · **tags:** `refute-repair-prove`, `spec-strength` · **backward-edge:** R04 (spec strength: a stronger precondition is a weaker theorem)

K7's claim fails because `b` may match. Two repairs both verify: `AltLeftWeak` requires `!Matches(b, s)`, `AltLeftStrong` requires `b == Empty`. Why is the weak one the repair, when the verifier accepts both?

```dafny
module R06_BankRepair {
  import opened RG_A1_Re

  // Two repairs of AltLeft; both verify.
  lemma AltLeftWeak(a: Re, b: Re, s: seq<char>)
    requires !Matches(b, s)
    ensures Matches(Alt(a, b), s) ==> Matches(a, s)
  {
    assert Matches(Alt(a, b), s) == (Matches(a, s) || Matches(b, s));
  }

  lemma AltLeftStrong(a: Re, b: Re, s: seq<char>)
    requires b == Empty
    ensures Matches(Alt(a, b), s) ==> Matches(a, s)
  {
    assert !Matches(Empty, s);
  }
}
```

**Target insights**
- A precondition narrows the theorem: `AltLeftStrong` says nothing about any `b` other than `Empty`, so it is a weaker theorem, true on fewer inputs. `AltLeftWeak` excludes exactly the inputs where the claim fails (a `b` that matches `s`).
- The verifier checks sufficiency only: the conclusion follows from the hypothesis. Necessity (every excluded input is a counterexample) is an argument you write: if `b` matches `s` and `a` does not, the claim fails.
- An over-strong repair is the R04 lattice in reverse: the statement verifies and describes less than it could. `requires false` would verify too.

**Misconceptions & counter-moves**
- *"Both verify, so both are correct."* → Ask: for `b = Eps` and `s = ['x']`, which of the two theorems tells you anything?
- *"The strongest hypothesis is the safest."* → Ask: which inputs does each repair give up on?
- *"The verifier would reject a non-weakest repair."* → Ask: which obligation would express "no stronger than needed"?

### K10 [connect] — bisecting a loop body
**viva:** yes · **tags:** `assertion-repair`, `loop-invariant` · **backward-edge:** R05 (bisection: an inserted assertion moves the failure to the first unproved fact)

Connect R05's bisection to a loop. `Triangle` sums 1 to n with the invariant `2 * t == i * (i + 1)`, and asserts the invariant at the end of the body. The second probe swaps the body's two updates. Which line fails, and what does the inserted assertion tell you that the bare preservation error would not?

```dafny
module R06_BankStep {
  // Sums 1 + 2 + ... + n, checked against a closed form.
  method Triangle(n: nat) returns (t: nat)
    ensures 2 * t == n * (n + 1)
  {
    t := 0;
    var i := 0;
    while i < n
      invariant 0 <= i <= n
      invariant 2 * t == i * (i + 1)
      decreases n - i
    {
      i := i + 1;
      t := t + i;
      assert 2 * t == i * (i + 1);
    }
  }
}
```
```dafny
module R06_BankStep {
  // The same loop with its two updates swapped.
  method Triangle(n: nat) returns (t: nat)
    ensures 2 * t == n * (n + 1)
  {
    t := 0;
    var i := 0;
    while i < n
      invariant 0 <= i <= n
      invariant 2 * t == i * (i + 1)
      decreases n - i
    {
      t := t + i;
      i := i + 1;
      assert 2 * t == i * (i + 1);
    }

}
```

**Target insights**

- *"The invariant is wrong."* → Ask: is it true of the correct loop? Which line differs between the two probes?
- *"Asserting the invariant is redundant."* → Ask: where does the failure point with and without it?

  function Deriv(r: Re, c: char): Re
    decreases r
  {
    match r

    case Eps => Empty
    case Chr(d) => if c == d then Eps else Empty
    case Alt(a, b) => Alt(Deriv(a, c), Deriv(b, c))
    case Cat(a, b) =>
      if Nullable(a) then Alt(Cat(Deriv(a, c), b), Deriv(b, c)) else Cat(Deriv(a, c), b)
    case Star(a) => Cat(Deriv(a, c), Star(a))

  lemma XThenY()
  {
    var r := Alt(Chr('x'), Cat(Chr('x'), Chr('y')));
    assert Deriv(r, 'x') == Alt(Eps, Cat(Eps, Chr('y')));
    assert Nullable(Deriv(r, 'x'));

### K12 [transfer] — a chain and its assertions
**viva:** yes · **tags:** `calc-chains`, `assert-by` · **backward-edge:** R05 (`assert … by`: a step proved from a local block)

Transfer §4: the same fact proved as a `calc` chain and as two assertions. Both verify. What does each chain step correspond to in the assertion form, and what does the chain's hint block correspond to?

```dafny
module R06_BankChain {
  // The same fact as a chain and as assertions.
  lemma ChainForm(x: int, y: int)
    requires y == x + 1
    ensures 2 * y == 2 * x + 2
  {
    calc {
      2 * y;
      == { assert y == x + 1; }
      2 * (x + 1);
      ==
      2 * x + 2;
    }
  }

  lemma AssertForm(x: int, y: int)
    requires y == x + 1
    ensures 2 * y == 2 * x + 2
  {
    assert 2 * y == 2 * (x + 1);
    assert 2 * (x + 1) == 2 * x + 2;
  }
}
```

**Target insights**
- Each `==` step of the chain is one assertion (`2 * y == 2 * (x + 1)`, then `2 * (x + 1) == 2 * x + 2`); the chain also proves their composition, which the assertion form gets from transitivity.
- The hint block `{ assert y == x + 1; }` is a local proof of one step, like R05's `assert … by`: its facts belong to that step.
- A chain is a presentation; it is never required. Write one when the intermediate expressions are what a reader needs to follow; a one-step chain with the whole proof in its block shows nothing.

**Misconceptions & counter-moves**
- *"calc is a different kind of proof."* → Ask: which assertions does the chain check?
- *"The hint block is a comment."* → Ask: what happens if its assertion is false? (C1, §4.)
- *"A longer chain is a stronger proof."* → Ask: what does each extra step add to what is proved?
