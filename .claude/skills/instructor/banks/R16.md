### K1 [reconstruct] — eight steps for two characters
**viva:** yes · **tags:** `opacity`, `lemma-call` · **backward-edge:** R08 (an opaque definition used through its lemmas)

Reconstruct, without the chapter, A5's machine: the four instructions, what one unit of fuel buys, and the five facts A5 gives you about the opaque `Accepts` (Verus `accepts`). Then work the probe by hand. `LoopBR16` / `loop_b_r16` is the program for `b*` written out: a split at 0 into the body (1) or past it (3), the body `IChar('b')`, a jump back to the split, and `IMatch`. How much fuel does the shortest accepting run on `"bb"` from address 0 need? Which one-step lemma does each instruction of that run call, and at which address, word and fuel? What happens to the proof if every fuel in it is one lower?

```dafny
module R16_FuelCountProbe {
  import opened RG_A1_Re
  import opened RG_A5_VM

  // b*, by hand: a split into the loop or past it, the body, a jump back, the end.
  function LoopBR16(): Prog
  {
    [ISplit(1, 3), IChar('b'), IJmp(0), IMatch]
  }

  // The word "bb" from address 0, one one-step lemma per instruction passed.
  lemma TwoBsR16()
    ensures Accepts(LoopBR16(), 0, ['b', 'b'], 8)
  {
    var p := LoopBR16();
    AcceptsMatch(p, 3, [], 1);
    AcceptsSplit(p, 0, [], 2);
    AcceptsJmp(p, 2, [], 3);
    assert ['b'][1..] == [];
    AcceptsChar(p, 1, ['b'], 4);
    AcceptsSplit(p, 0, ['b'], 5);
    AcceptsJmp(p, 2, ['b'], 6);
    assert ['b', 'b'][1..] == ['b'];
    AcceptsChar(p, 1, ['b', 'b'], 7);
    AcceptsSplit(p, 0, ['b', 'b'], 8);
  }
}
```
```rust
use vstd::prelude::*;
use rg_re_a1::*;
use rg_re_a5::*;

verus! {

// b*, by hand: a split into the loop or past it, the body, a jump back, the end.
pub open spec fn loop_b_r16() -> Seq<Inst> {
    seq![Inst::Split(1, 3), Inst::Char('b'), Inst::Jmp(0), Inst::Match]
}

// The word "bb" from address 0, one one-step lemma per instruction passed.
proof fn two_bs_r16()
    ensures
        accepts(loop_b_r16(), 0, seq!['b', 'b'], 8),
{
    let p = loop_b_r16();
    let e = Seq::<char>::empty();
    lemma_accepts_match(p, 3, e, 1);
    lemma_accepts_split(p, 0, e, 2);
    lemma_accepts_jmp(p, 2, e, 3);
    assert(seq!['b'].drop_first() =~= e);
    lemma_accepts_char(p, 1, seq!['b'], 4);
    lemma_accepts_split(p, 0, seq!['b'], 5);
    lemma_accepts_jmp(p, 2, seq!['b'], 6);
    assert(seq!['b', 'b'].drop_first() =~= seq!['b']);
    lemma_accepts_char(p, 1, seq!['b', 'b'], 7);
    lemma_accepts_split(p, 0, seq!['b', 'b'], 8);
}

} // verus!
```

**Target insights**
- The machine: `IChar(c)` consumes one matching character and moves to `pc + 1`; `ISplit(x, y)` continues at either target; `IJmp(x)` continues at `x`; `IMatch` accepts exactly when the word is used up. Every instruction executed costs one unit of fuel, `IMatch` included (it needs `fuel > 0`), and a thread outside the program dies. `AcceptsFrom(p, pc, w)` is "some fuel suffices": the frozen statements are about it, never about a fuel number.
- The run on `"bb"`: split → `b` → jump, twice (six steps), then split → `IMatch` (two steps). Eight steps, so fuel 8 and not 7: the last `IMatch` needs a unit of its own. The proof is written backwards from the end of the run: `IMatch` at 3 with `[]` and fuel 1, then each earlier instruction with one more unit. Each call is an `<==>` at one address, one word and one fuel; it relates that triple to the next one, and nothing else.
- `Accepts` is opaque, so the solver knows nothing about it except what those calls state: `AcceptsChar`, `AcceptsSplit`, `AcceptsJmp`, `AcceptsMatch` (each one step) and `AcceptsInside` (an accepting thread has fuel and an in-range address). A `reveal` would hand the solver the whole recursive definition at every term; the one-step lemmas hand it exactly one step at a chosen term. R08 hid a definition behind its lemmas so that clients could not depend on its body; A5 hides `Accepts` so that a proof states each step it takes.
- The two sequence equations (`['b'][1..] == []`, `['b', 'b'][1..] == ['b']`; Verus `drop_first`) are not about the machine: they put the word `AcceptsChar` produces in the same form as the word the next call names, so the two `<==>` facts meet.

**Misconceptions & counter-moves**
- *"Seven steps: the match is free."* → Ask what `AcceptsMatch` says when the fuel is 0.
- *"The order of the calls matters to the solver."* → It does not; each call adds one fact. Ask which call's right-hand side is another call's left-hand side.
- *"Opaque means the verifier cannot reason about `Accepts` at all."* → It reasons about every fact a lemma states. Ask what an empty body proves here, and what `AcceptsInside` adds that the four one-step lemmas do not.

### K2 [predict] — a hypothesis no program meets
**viva:** yes (verifier-refereed predict) · **tags:** `vacuity`, `opacity`, `witnesses` · **backward-edge:** R04 (a vacuous `requires` and the witness that tests it)

`NoRoomR16` / `no_room_r16` assumes a three-instruction program that holds two instructions at address 2, and concludes that address 0 accepts every word. The body is empty. Predict each verdict: `D:<verified|failed> V:<verified|failed>`. Then say what each verdict tells a reviewer about the statement, and what check would have told the reviewer more.

```dafny
module R16_NoRoomProbe {
  import opened RG_A1_Re
  import opened RG_A5_VM

  // Two instructions placed at address 2 of a three-instruction program,
  // and a claim about every word, with an empty proof.
  lemma NoRoomR16(p: Prog, w: seq<char>)
    requires |p| == 3
    requires CodeAt(p, 2, [IMatch, IMatch])
    ensures AcceptsFrom(p, 0, w)
  {
  }
}
```
```rust

use rg_re_a1::*;
use rg_re_a5::*;

verus! {

// Two instructions placed at address 2 of a three-instruction program,
// and a claim about every word, with an empty proof.
proof fn no_room_r16(p: Seq<Inst>, w: Seq<char>)
    requires
        p.len() == 3,
        code_at(p, 2, seq![Inst::Match, Inst::Match]),
    ensures
        accepts_from(p, 0, w),
{
}

} // verus!
```

**Target insights**
- The conclusion is false for most programs, so a green verdict can only come from the hypotheses: two instructions at address 2 need `2 + 2 <= |p|`, and `|p| == 3`. No program meets both, so the lemma is vacuous, and it is true.
- Dafny proves it with nothing: `CodeAt` is a transparent (non-opaque) predicate, so its first conjunct `0 <= pc && pc + |code| <= |p|` is in the solver's hands, and `4 <= 3` closes the goal. Verus fails the same body: A5's `code_at` is opaque, so the contradiction is invisible without `reveal(code_at)` (the follow-up) or a layout lemma.
- Neither verdict says anything about the statement's quality. The Dafny green is a proof of an empty claim; the Verus red is a missing step, not a refuted claim. P1dv is the same split verdict on a candidate statement about `Emit`'s code running past its program. The two verdicts differ for a reason that has nothing to do with what the statement means.
- H1's statements are built so that this cannot happen by accident: `CodeAt(p, pc, Emit(r, pc))` is their only constraint on the program, and every concrete program that holds `r`'s code meets it, `EmitProg(r)` at address 0 first among them (A5's `LayoutProg`). A candidate that adds a second constraint on `p`, `pc` or the lengths (the code runs past the program, the program ends right after the code, `pc` is 0) has to be checked against `CodeAt` itself, because `CodeAt` already says how long `p` is at least.
- R04's move is the one that informs: before trusting a statement, exhibit an input that meets its hypotheses. Here no such input exists, and Dafny cannot prove one does (the second run). A statement-only review of H1 asks the same question of each frozen statement: name a program, an address and a word for which the hypotheses hold.

**Misconceptions & counter-moves**
- *"Then make every predicate opaque, so nothing vacuous slips through."* → The Verus run did not refute the claim either. Ask which check actually separates a vacuous statement from a strong one.
- *"Both verifiers see the same definitions, so they agree."* → Ask which of A5's definitions are opaque in which language.
- *"Verus failed, so the statement is wrong."* → Run the follow-up: one `reveal` and it is proved. Ask what changed: the claim, or what the solver could see?
- *"Dafny proved it, so address 0 accepts every word."* → Ask for a program that meets the two `requires`.
- *"A vacuous lemma is harmless: nobody can use it."* → Ask what a frozen statement that is vacuous lets every later proof, agent and trust-report claim, and what Lab γ's gate would then certify.

### K3 [connect] — the accumulator and the continuation
**viva:** yes · **tags:** `invariant-generalization`, `induction-as-recursion` · **backward-edge:** R06 (strengthen the statement until the induction goes through)

`TallyFromR16` / `tally_from_r16` totals a sequence with an accumulator, the shape a loop computes. `TallyStartR16` states the fact for the start value 0 only and calls itself on the tail; `TallyAnyR16` states it for every accumulator. Which of the two verifies, and why does the other fail although it is true? Then connect: what plays the accumulator's role in R16's completeness statement, and which whole-program proof in R16 fails for the reason `TallyStartR16` does?

```dafny
module R16_TallyProbe {
  // The total of a sequence, from its head.
  function TallyR16(s: seq<int>): int
  {
    if s == [] then 0 else s[0] + TallyR16(s[1..])
  }

  // The same total with a running accumulator: a loop's shape.
  function TallyFromR16(s: seq<int>, acc: int): int
  {
    if s == [] then acc else TallyFromR16(s[1..], acc + s[0])
  }

  // Stated for the start only, proved by calling itself on the tail.
  lemma TallyStartR16(s: seq<int>)
    ensures TallyFromR16(s, 0) == TallyR16(s)
  {
    if s != [] {
      TallyStartR16(s[1..]);
    }
  }

  // Stated for every accumulator, proved the same way.
  lemma TallyAnyR16(s: seq<int>, acc: int)
    ensures TallyFromR16(s, acc) == acc + TallyR16(s)
  {
    if s != [] {
      TallyAnyR16(s[1..], acc + s[0]);
    }
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// The total of a sequence, from its head.
pub open spec fn tally_r16(s: Seq<int>) -> int
    decreases s.len(),
{
    if s.len() == 0 {
        0
    } else {
        s[0] + tally_r16(s.drop_first())
    }
}

// The same total with a running accumulator: a loop's shape.
pub open spec fn tally_from_r16(s: Seq<int>, acc: int) -> int
    decreases s.len(),
{
    if s.len() == 0 {
        acc
    } else {
        tally_from_r16(s.drop_first(), acc + s[0])
    }
}

// Stated for the start only, proved by calling itself on the tail.
proof fn lemma_tally_start_r16(s: Seq<int>)
    ensures
        tally_from_r16(s, 0) == tally_r16(s),
    decreases s.len(),
{
    if s.len() > 0 {
        lemma_tally_start_r16(s.drop_first());
    }
}

// Stated for every accumulator, proved the same way.
proof fn lemma_tally_any_r16(s: Seq<int>, acc: int)
    ensures
        tally_from_r16(s, acc) == acc + tally_r16(s),
    decreases s.len(),
{
    if s.len() > 0 {
        lemma_tally_any_r16(s.drop_first(), acc + s[0]);
    }
}

} // verus!
```

**Target insights**
- `TallyFromR16(s, 0)` unfolds to `TallyFromR16(s[1..], s[0])`: the accumulator is no longer 0. The recursive call gives `TallyFromR16(s[1..], 0) == TallyR16(s[1..])`, a fact about a term the goal does not contain. The induction hypothesis is about the wrong object; no extra assertion repairs that.
- `TallyAnyR16` quantifies over the accumulator, so its recursive call can be made at `acc + s[0]`, the exact term the unfolded goal holds. The stronger statement is the easier proof. The start fact is then one call (the follow-up).
- In R16 the accumulator is the continuation. `EmitProg(a)` stops with `IMatch`; inside `EmitProg(Cat(a, b))` the code of `a` falls through into the code of `b`. A whole-program hypothesis for `a` speaks about a program the goal does not contain, exactly as `TallyStartR16`'s does. P2dv's specimen fails for this reason in both languages. The repair is the same move: make "what follows" a parameter (any program `p` that holds `r`'s code at `pc`, with whatever starts at the first address after it) and recurse at the continuation the case needs.
- R06 met this as a loop invariant that must mention the partial result, and as lemmas strengthened until the induction goes through. The capstone is that skill at the scale of a compiler: the strengthening is found on paper (§2's blueprint), before any proof.

### K4 [predict] — one call doubles the regex
**viva:** yes (verifier-refereed predict) · **tags:** `termination-measure` · **backward-edge:** R02 (a lexicographic measure on `Matches`)

`TwiceR16` / `twice_r16` has the shape of the second engine: on an alternation it recurses into both branches with `n` unchanged; otherwise it spends one unit of `n` and recurses on `Cat(r, r)`, a regex with more than twice the nodes. As shipped it has no `decreases` clause. Predict, for the shipped file and for the file with `decreases n + NodeCount(r)` (Verus `n + node_count(r)`), each verdict: `D:<verified|failed> V:<verified|failed>`, and which recursive call each failure names. Then give a measure that works and say why no sum of `n` and `NodeCount(r)`, weighted or not, does.

```dafny
module R16_GrowProbe {
  import opened RG_A1_Re

  // Splits an alternation with n unchanged; otherwise doubles the regex
  // (more than twice its nodes) and spends one unit of n.
  ghost function TwiceR16(r: Re, n: nat): nat
  {
    if n == 0 then 0
    else match r
      case Alt(a, b) => TwiceR16(a, n) + TwiceR16(b, n)
      case _ => 1 + TwiceR16(Cat(r, r), n - 1)
  }
}
```
```rust

// (more than twice its nodes) and spends one unit of n.

{
    if n == 0 {
        0
    } else {
        match r {
            Re::Alt(a, b) => twice_r16(*a, n) + twice_r16(*b, n),
            _ => 1 + twice_r16(Re::Cat(Box::new(r), Box::new(r)), (n - 1) as nat),

    }
}

} // verus!
```

**Target insights**
- Two calls, two different things that shrink. The `Alt` call keeps `n` and moves to a structurally smaller regex; the other call lowers `n` and moves to a larger regex. A measure has to go down at both.
- Without a clause, Dafny guesses one from the parameters, in order: `decreases r, n`. The `Cat(r, r)` call fails it, because `Cat(r, r)` is not smaller than `r`. Verus does not guess a measure for a recursive spec function: without `decreases` it reports an error before any proof is attempted.
- The sum `n + NodeCount(r)` fails at the same call: `n - 1 + 2·NodeCount(r) + 1` is larger than `n + NodeCount(r)` as soon as the regex has a node. A weighted sum `α·n + β·NodeCount(r)` decreases there only while `β·(NodeCount(r) + 1) < α`, which a large enough regex breaks: the growth is proportional to the regex, and no fixed weight on `n` pays for it. The second engine is in the same position: `Deriv(Star(a), c) = Cat(Deriv(a, c), Star(a))` copies `a`, and §8's specimen shows two nodes becoming four on one character.
- The pair `n, r` is compared lexicographically: the `Alt` call ties on `n` and decreases `r`; the other call decreases `n`, and then `r` may grow without limit. That is H6's and H7's measure in its plain form, `|w|, r`: the word first, the regex second. R02 already wrote `decreases r, |s|` for `Matches`, whose `Star` case recurses on the same `Star(a)` with a shorter word; there the regex comes first because it never grows.

### K5 [predict] — a split with no range on its point
**viva:** yes (verifier-refereed predict) · **tags:** `spec-wellformedness`, `spec-strength`, `quantifiers` · **backward-edge:** R04 (a specification expression is itself checked)

`OpenSplitR16` / `open_split_r16` says that a word splits at some `k` into an all-`'a'` part and nothing; the split point has no range. The consumer `OpenSplitUseR16` takes the split and concludes the whole word is all `'a'`, which is what a whole-program theorem does with a soundness split whose continuation accepts only the empty word.
```dafny
module R16_OpenSplitProbe {
  // Only the letter 'a'.
  ghost predicate AllAR16(s: seq<char>)
  {
    forall i | 0 <= i < |s| :: s[i] == 'a'
  }

  // A split with no range on its point: an all-'a' part, then nothing left.
  ghost predicate OpenSplitR16(w: seq<char>)
  {
    exists k: int :: AllAR16(w[..k]) && w[k..] == []
  }

  // The consumer: nothing is left, so the whole word is all 'a'.
  lemma OpenSplitUseR16(w: seq<char>)
    requires OpenSplitR16(w)
    ensures AllAR16(w)
  {
    var k: int :| AllAR16(w[..k]) && w[k..] == [];
    assert w[..k] == w;
  }
}
```

### K6 [why] — why the frozen statements hide the fuel
**viva:** yes · **tags:** `frozen-statements`, `spec-strength` · **backward-edge:** R10 (a human statement fixed before a contractor's body)

`FoldR16` / `fold_r16` is a small optimizer, not R16's: a jump whose target holds `IMatch` becomes `IMatch` itself. It is correct: every address accepts the same words before and after. The probe computes one program before and after and counts the fuel each needs for the empty word. Why do R16's frozen statements (H1's two, and the optimizer's) speak only of `AcceptsFrom`, never of `Accepts` at a given fuel?
```dafny
module R16_FoldCostProbe {
  import opened RG_A1_Re
  import opened RG_A5_VM

  // An optimizer: a jump whose target holds IMatch becomes IMatch itself.
  function FoldR16(p: Prog, ins: Inst): Inst
  {
    if ins.IJmp? && 0 <= ins.x < |p| && p[ins.x] == IMatch then IMatch else ins
  }

  function FoldAllR16(p: Prog): Prog
  {
    seq(|p|, i requires 0 <= i < |p| => FoldR16(p, p[i]))
  }

  // One program before and after: the same word, at different costs.
  lemma FoldCostR16()
    ensures FoldAllR16([IJmp(1), IMatch]) == [IMatch, IMatch]
    ensures Accepts([IMatch, IMatch], 0, [], 1)
    ensures !Accepts([IJmp(1), IMatch], 0, [], 1)
    ensures Accepts([IJmp(1), IMatch], 0, [], 2)
  {
    var p: Prog := [IJmp(1), IMatch];
    AcceptsMatch([IMatch, IMatch], 0, [], 1);
    AcceptsJmp(p, 0, [], 1);
    AcceptsMatch(p, 1, [], 0);
    AcceptsJmp(p, 0, [], 2);
    AcceptsMatch(p, 1, [], 1);
  }
}
```

- The optimized program accepts `[]` from address 0 with fuel 1; the original needs fuel 2 (the jump, then the match). - The fuel-free statement is not weaker for the user of `rexc`: `AcceptsFrom` is what `pike_run` decides and what the whole-program theorem relates to `Matches`.

### K8 [reconstruct] — a loop that never ends accepts nothing
**viva:** yes · **tags:** `induction-as-recursion`, `termination-measure`, `quantifiers` · **backward-edge:** R06 (manual lemma induction)

```dafny
module R16_SpinProbe {
  import opened RG_A1_Re
  import opened RG_A5_VM

  // A jump to itself accepts no word, for any fuel.
  lemma SpinNeverR16(p: Prog, pc: int, w: seq<char>)
    requires 0 <= pc < |p| && p[pc] == IJmp(pc)
    ensures !AcceptsFrom(p, pc, w)
  {
    forall f: nat
      ensures !Accepts(p, pc, w, f)
    {
      SpinFuelR16(p, pc, w, f);
    }
  }

  // The same for one fuel, by induction on the fuel.
  lemma SpinFuelR16(p: Prog, pc: int, w: seq<char>, f: nat)
    requires 0 <= pc < |p| && p[pc] == IJmp(pc)
    ensures !Accepts(p, pc, w, f)
    decreases f
  {
    AcceptsJmp(p, pc, w, f);
```

**Target insights**
- A run that takes the self-jump comes back to the same address, with the same word, in the same program. The only thing that changed is the fuel, one unit less. An induction has to run on something that shrinks along the run, so it runs on the fuel. H3 has the same situation twice: `Empty`'s self-jump and `Star`'s jump back to its own split, where the regex at the address is `Star(a)` again; the lemma's measure therefore puts the fuel first.
- `AcceptsJmp` alone restates the goal one unit down: `Accepts(p, pc, w, f) <==> f > 0 && Accepts(p, pc, w, f - 1)`. Without the recursive call that is all the helper knows (the follow-up), and the goal does not follow. The recursive call is the induction hypothesis at `f - 1`; `decreases f` is the measure, and `f > 0` guards the call.
- `AcceptsFrom` is `exists fuel :: Accepts(...)`, so its negation is a statement for every fuel. Dafny's `forall f: nat ensures … { helper call }` and Verus's `assert forall|f: nat| … by { helper call }` prove it one fuel at a time. Completeness goes the other way: from `AcceptsFrom`, take a fuel with `:|` / `choose`, call the helper, and the returned fuel is the witness for the conclusion.
- R06's manual inductions recursed on the structure of a regex or a word; this one recurses on a number that the definition of `Accepts` already decreases (`decreases fuel` in A5). The lemma follows the definition it reasons about, as R06's lemmas followed theirs.

- *"Recurse on `pc` or on the program."* → Ask what the address is after the jump.
- *"`AcceptsJmp` is the whole proof."* → Run the follow-up. Ask what the call states about `f - 1`.

### K9 [transfer] — a delivered optimizer and its witness
**viva:** yes · **tags:** `agent-roles`, `witnesses`, `frozen-statements`, `contract-allowlist` · **backward-edge:** R15 (the red-teamed contractor and the statement snapshot)

A contractor delivers a second optimizer for A5's VM, not the agent file's: `EndR16` turns a split whose second target holds `IMatch` into `IMatch`. The frozen statement is both directions from every address, `AcceptsFrom(EndAllR16(p), pc, w) <==> AcceptsFrom(p, pc, w)`. The delivery proves one direction and, for the other, narrows the statement to `==>`. Review it as the capstone's adversary round asks: which direction is true, which is false, what is the smallest witness, and what do `specfreeze`, the contract and your trust-report say about the delivery?

```dafny
module R16_SplitEndProbe {
  import opened RG_A1_Re
  import opened RG_A5_VM

  // A delivered optimizer: a split whose second target holds IMatch becomes
  // IMatch itself.
  function EndR16(p: Prog, ins: Inst): Inst
  {
    if ins.ISplit? && 0 <= ins.y < |p| && p[ins.y] == IMatch then IMatch else ins
  }

  function EndAllR16(p: Prog): Prog
  {
    seq(|p|, i requires 0 <= i < |p| => EndR16(p, p[i]))
  }

  function MaybeAR16(): Prog

    [ISplit(2, 1), IMatch, IChar('a'), IJmp(1)]
```

### K10 [why] — two gates that read a missing check
**viva:** yes · **tags:** `gate-design`, `unavailable-not-zero` · **backward-edge:** R13 (two instruments and UNKNOWN)

Each check of a delivery reads `Held`, `Broke` or `Unrun` (the instrument did not run: it was killed, it errored, it was not wired in). - *"Unrun checks are rare; treat them as passes."* → Ask what Lab γ's naive graders are, and how a cheat would arrange to be unrun.

- It verifies in both languages: the only `ensures` is guarded by `res.Answer?` / `res is Some`, and a body that never answers meets every guarded clause. The contract is weak in exactly R15's sense: a constant body satisfies it.
- `rexc_match` also states when it may decline: `res is None ==> clen(*r) + 1 >= usize::MAX`. A refusal must name its reason, and the reason must be something the caller can check. - *"The use-site check is redundant once the contract is strong."* → Ask what the use site proves that a contract read alone does not: that the function is callable and answers on real inputs.

### K12 [connect] — what a naive grader's pass is worth
**viva:** yes · **tags:** `grader-inflation`, `pre-registration`, `statistics` · **backward-edge:** R12 (the unit of uncertainty is the cluster)

```dafny
module R16_InflationProbe {
  // One delivery: what two naive graders said (exit code, a "verified"
  // substring) and what the gate said.
  datatype Graded = Graded(byExit: bool, byText: bool, byGate: bool)

  // Grader g passed d: g = 0 the exit code, 1 the substring, 2 either one.
  predicate NaivePassR16(d: Graded, g: nat)
  {
    if g == 0 then d.byExit else if g == 1 then d.byText else d.byExit || d.byText
  }

  // How many deliveries grader g passed, and how many of those the gate passed.
  function PassedR16(ds: seq<Graded>, g: nat): nat
  {
    if ds == [] then 0 else (if NaivePassR16(ds[0], g) then 1 else 0) + PassedR16(ds[1..], g)
  }
```

**Target insights**
- Exit code: 5 passes, 3 survive the gate, `I_exit = 1 − 3/5 = 2/5`. Substring: 5 and 3, `I_text = 2/5`. Either: 7 passes, 4 survive, `I = 3/7`. The pooled ratio is taken over the union of passes, so a delivery both graders pass counts once, and one that only one grader passes still counts; it is a ratio of two counts over a different set, not an average of the two inflations. Here it is larger than both.
- The cluster is the task: a task's deliveries (2 Claude runs and 3 Qwen runs on each crate task, plus the re-graded α and β successes) share a statement, a cheat surface and an author, so they are correlated. The interval is a cluster bootstrap over tasks (10,000 resamples), as R12's Lab α kept repeats inside their cluster and R15's Lab β resampled cards. With about 40 to 80 naive successes over a few dozen tasks there is no test worth powering; the pre-registration fixes a simulated interval half-width at `I ∈ {0.1, 0.3, 0.5}` instead of a minimum detectable effect.
- On an impossible task every naive pass is a cheat by construction, so the gate's PASS rate there measures the gate, not the grader: pooled with the possible tasks it would move `I` by the mix of task kinds the author chose. Those four are reported separately.
- What makes a gate PASS meaningful is the order of the lab: the statement pin (`statements` no longer `PENDING`) comes before `fvh` unpacks any crate task, and the trust-report's rules are in `TRUST.md` before any delivery is graded. An undefined ratio (a grader that passes nothing) is a missing value with a pre-registered rule, never 0.

**Misconceptions & counter-moves**
- *"Pooled inflation is the average of the per-grader inflations."* → Compute both from the table.
- *"Eighty deliveries give eighty independent observations."* → Ask what the five runs on one task share.
- *"Impossible tasks are free data: every naive pass there is a cheat."* → Ask what including them does to the estimate when the task mix changes.

### PP2 — parallel to R16.H3d and R16.H3v (soundness by induction on fuel; a split by cases; an existential split)
