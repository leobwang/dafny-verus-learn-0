### K1 [reconstruct] — what makes a recursive call a proof
**viva:** yes · **strand:** S4 · **tags:** `induction-as-recursion`, `termination-measure`, `auto-induction` · **backward-edge:** Q03 (manual lemma induction: the recursive call you write)

In each language, reconstruct what turns a lemma that calls itself into a proof by induction: what the call contributes, where the base case is, what `decreases` is for, and what the verifier checks at the call. Then read the probe: three proofs of one bound, with no call, with the call on the tail, and with the call on the same argument. Which fail, and why? Why does the Dafny verdict of [a] change when the file is run without `--module Q04`?

**Target insights**
- The call's postcondition, at the smaller argument, is the induction hypothesis; the branch with no call is the base case; the step proves the statement from that hypothesis and one unfolding of the definition.
- At the call the verifier checks the callee's `requires` and that the `decreases` measure goes down. A call on the same argument would assume the goal itself; the measure check refuses it (Dafny: "decreases clause might not decrease"; Verus: "could not prove termination"), which is what makes the hypothesis sound.
- With no call there is no hypothesis: under Q04's units (manual lemma induction) and in Verus, which never inducts, the postcondition fails.
- Under Dafny's default options the tool attempts the induction itself, and [a] verifies with an empty body: a found induction that no file shows. The course turns the attempt off so that every hypothesis is a call someone wrote.

**Misconceptions & counter-moves**
- *"A lemma calling itself is circular, so it proves nothing."* → Probe: [b] against [c]; ask: which check accepts the one and refuses the other, and what does it compare?
- *"If the empty body verifies, the lemma needed no induction."* → Probe: [a] in the plain run against the `--module Q04` run; ask: what did the tool do in the plain run that Q04's units do not let it do?
- *"`decreases` is documentation."* → Probe: [c]; ask: which error would vanish if the measure were not checked, and what would that let you prove?

```dafny
module ProbeK1 {
  // How many times x occurs in s.
  function Occurrences(s: seq<int>, x: int): nat
    decreases |s|
  {
    if |s| == 0 then 0 else (if s[0] == x then 1 else 0) + Occurrences(s[1..], x)
  }

  // [a] no call
  lemma OccurrencesAtMostA(s: seq<int>, x: int)
    ensures Occurrences(s, x) <= |s|
    decreases |s|
  {
  }

  // [b] the call at the argument Occurrences recurses on
  lemma OccurrencesAtMostB(s: seq<int>, x: int)
    ensures Occurrences(s, x) <= |s|
    decreases |s|
  {
    if |s| > 0 {
      OccurrencesAtMostB(s[1..], x);
    }
  }

  // [c] the call at the same argument
  lemma OccurrencesAtMostC(s: seq<int>, x: int)
    ensures Occurrences(s, x) <= |s|
    decreases |s|
  {
    OccurrencesAtMostC(s, x);
  }
}
```

### K2 [predict] — which step a hint serves
**viva:** yes (verifier-refereed predict) · **strand:** S3 · **tags:** `calc-chains`, `lemma-call` · **backward-edge:** none

`Hop` is opaque, and `HopStep`, given and proved, is its one equation. Each of the three lemmas proves the same two-step chain; they differ only in where the two calls of `HopStep` sit: [a] each call is the hint of the step that needs it; [b] both calls are the hint of the first step; [c] the second call is made before the chain. Before running anything, predict which of [a], [b], [c] fail, in each language.

```dafny
module ProbeK2 {
  // Three ahead: opaque, so the solver knows it only through HopStep.
  opaque function Hop(n: nat): nat
  {
    n + 3
  }

  // Given, proved: Hop's one equation.
  lemma HopStep(n: nat)
    ensures Hop(n) == n + 3
  {
    reveal Hop();
  }

  // [a] each call is the hint of the step that needs it
  lemma TwoHopsA(x: nat)
    ensures Hop(Hop(x)) == x + 6
  {
    calc {
      Hop(Hop(x));
    ==  { HopStep(Hop(x)); }
      Hop(x) + 3;
    ==  { HopStep(x); }
      x + 6;
    }
  }

  // [b] both calls are the hint of the first step
  lemma TwoHopsB(x: nat)
    ensures Hop(Hop(x)) == x + 6
  {
    calc {
      Hop(Hop(x));
    ==  { HopStep(Hop(x)); HopStep(x); }
      Hop(x) + 3;
    ==
      x + 6;
    }
  }

  // [c] the second call before the chain
  lemma TwoHopsC(x: nat)
    ensures Hop(Hop(x)) == x + 6
  {
    HopStep(x);
    calc {
      Hop(Hop(x));
    ==  { HopStep(Hop(x)); }
      Hop(x) + 3;
    ==
      x + 6;
    }
  }
}
```

```rust
use vstd::calc;

verus! {

// Three ahead: opaque, so the solver knows it only through lemma_hop.
#[verifier::opaque]
pub open spec fn hop(n: nat) -> nat {
    n + 3
}

// Given, proved: hop's one equation.
pub proof fn lemma_hop(n: nat)
    ensures
        hop(n) == n + 3,
{
    reveal(hop);
}

// [a] each call is the hint of the step that needs it
proof fn two_hops_a(x: nat)
    ensures
        hop(hop(x)) == x + 6,
{
    calc! {
        (==)
        hop(hop(x)); { lemma_hop(hop(x)); }
        hop(x) + 3; { lemma_hop(x); }
        x + 6;
    }
}

// [b] both calls are the hint of the first step
proof fn two_hops_b(x: nat)
    ensures
        hop(hop(x)) == x + 6,
{
    calc! {
        (==)
        hop(hop(x)); {
            lemma_hop(hop(x));
            lemma_hop(x);
        }
        hop(x) + 3; {}
        x + 6;
    }
}

// [c] the second call before the chain
proof fn two_hops_c(x: nat)
    ensures
        hop(hop(x)) == x + 6,
{
    lemma_hop(x);
    calc! {
        (==)
        hop(hop(x)); { lemma_hop(hop(x)); }
        hop(x) + 3; {}
        x + 6;
    }
}

} // verus!
```

**Target insights**
- Each step of a chain is checked on its own: it sees its own hint and every fact established before the chain, never another step's hint. So [b]'s second step lacks the fact its first step's hint proved, and [b] fails there, in both languages.
- A call made before the chain puts its conclusion in scope for every step ([c] verifies); a hint attached to the step that needs it does the same for that step alone ([a] verifies) and tells the reader which step needs it.
- Where the failure is reported differs: Dafny names the failing step's line; Verus's `calc!` reports inside the macro, so attributing it takes one run per function (`--symbol`) or a split chain (K8).

**Misconceptions & counter-moves**
- *"Facts flow down a chain: what one step's hint proves stays known below it."* → Probe: [b]; ask: which line does Dafny name, and what did that step have in scope?
- *"Then every fact belongs before the chain."* → Probe: [a] and [c] both verify; ask: which version tells a reader why each step holds?

### K3 [predict] — how far a lemma group reaches
**viva:** yes (verifier-refereed predict) · **strand:** S5 · **tags:** `broadcast-use`, `lemma-call` · **backward-edge:** none

`ladder` is opaque: the solver knows it only through `lemma_ladder_mono`, a broadcast lemma in the group `group_ladder`. Three proof fns state the same order: [a] with `broadcast use group_ladder;` as its body, [b] right below it with an empty body, [c] calling the lemma by name. Predict which verify. The Dafny half has no lemma groups (every lemma applies only where it is called): predict [b] and [c] there too.

```rust
use vstd::prelude::*;

verus! {

// Two units per step: opaque, so the solver knows it only through lemmas.
#[verifier::opaque]
pub open spec fn ladder(n: nat) -> nat
    decreases n,
{
    if n == 0 {
        0
    } else {
        2 + ladder((n - 1) as nat)
    }
}

pub broadcast proof fn lemma_ladder_mono(m: nat, n: nat)
    requires
        m <= n,
    ensures
        #[trigger] ladder(m) <= #[trigger] ladder(n),
    decreases n,
{
    reveal(ladder);
    if m < n {
        lemma_ladder_mono(m, (n - 1) as nat);
    }
}

pub broadcast group group_ladder {
    lemma_ladder_mono,
}

// [a] the group, in this body
proof fn order_a(k: nat)
    ensures
        ladder(k) <= ladder(k + 3),
{
    broadcast use group_ladder;
}

// [b] no group line, right below [a]
proof fn order_b(k: nat)
    ensures
        ladder(k) <= ladder(k + 3),
{
}

// [c] the lemma, called by name
proof fn order_c(k: nat)
    ensures
        ladder(k) <= ladder(k + 3),
{
    lemma_ladder_mono(k, k + 3);
}

} // verus!
```

```dafny
  opaque function Ladder(n: nat): nat
    decreases n
  {
    if n == 0 then 0 else 2 + Ladder(n - 1)

    requires m <= n
    ensures Ladder(m) <= Ladder(n)

    }
```

**Target insights**
- `broadcast use` inside a body brings the group's lemmas into that body only; a function below it gets nothing from it, so [b] fails in Verus as it does in Dafny.
- With the group in scope, a member's conclusion holds wherever its trigger terms appear (`ladder(k)` and `ladder(k + 3)` here), so [a]'s body names no instance; a named call ([c]) supplies exactly one instance, visible in the text.
- A group puts every member's quantified fact into the solver's context for the whole body: cheap while the goal is easy, costly when the solver must search (chapter §5.2). Scope it to the function that needs it.

**Misconceptions & counter-moves**
- *"Once a group is used in a file, its facts hold below that line."* → Probe: [b]; ask: what is the scope of a `broadcast use` written inside a body?
- *"A group is just an import of names."* → Probe: [a] against [b]; ask: what does the solver have in [a] that it lacks in [b], and which terms make it use it?

### K4 [why] — why a product needs another prover
**viva:** yes · **strand:** S5 · **tags:** `nonlinear-arith`, `prover-choice` · **backward-edge:** none

In Verus, why does the empty body of `area_le_a` fail, why does `by (nonlinear_arith)` fail with no `requires`, and why does it verify with them? In Dafny, why does a one-sided product bound verify under the default options and fail in a module that turns nonlinear arithmetic off, and why would a course, or an agent benchmark, turn it off?

**Target insights**
- Verus's default query treats a product of two variables as an uninterpreted term: it cannot use `w <= wb` to bound `w * h`.
- `by (nonlinear_arith)` sends that one assertion to a separate query with nonlinear reasoning on, and that query sees the assertion and its own `requires` only, not the function's preconditions: so [b] fails and [c] verifies.
- Dafny's defaults let the solver attempt nonlinear arithmetic in the main query: it proves some products (here the one-sided bound) and is incomplete on others, failing or spending the resource limit. `{:disableNonlinearArithmetic}` turns the attempt off, so the fact needs a library lemma or an explicit argument, and its absence fails at once. The race's Dafny file turns it off so that no goal falls to arithmetic automation and every proof is the calls the contract asks for.

**Misconceptions & counter-moves**
- *"`nonlinear_arith` knows everything the function knows."* → Probe: [b]; ask: which facts did that query have?
- *"Dafny is simply better at arithmetic than Verus."* → Probe: `ProbeK4` against `ProbeK4Off`; ask: what changed between the two modules, and which behaviour would you want inside a benchmark of proof agents?

**Verifier probe**
```rust

verus! {

// [a] no help
proof fn area_le_a(w: nat, h: nat, wb: nat, hb: nat)
    requires
        w <= wb,
        h <= hb,
    ensures
        w * h <= wb * hb,
```
