### K2 [reconstruct] — the doors to a verdict
**viva:** yes · **strand:** S10 · **tags:** `exit-codes-and-doors`, `lsp`, `hole-contract` · **backward-edge:** Q03 (a learner-loop `verified` that still holds a hole; done = verified and zero tool-counted holes)

Then say which door decides "done", and why the editor's green tick is not that door. The probe runs one file through the learner loop and the gate in each language.

**Target insights**
- The plain binaries verify under the flags you pass; the editor's door (a language server: `dafny server`, verus-analyzer) verifies under the project's options, keeps state between edits, and prints no document anyone else can re-run. It is the fastest loop and no grader.
- `scripts/vcheck` pins the toolchain, the options and the resource limit: its learner loop is a measurement, `--json` the machine record of the same run (§1), `--gate` the verdict. Each prints the command or the document that lets a third party re-run it.
- The learner loop says `verified` with a hole in it; the gate fails the same file, because done means verified and zero tool-counted holes (Dafny: the hole's warning fails the gate; Verus: the gate refuses a run whose output lacks its success fields). Same file, same solver, two doors, two answers.
- Ranking: an editor's tick is a hint, `scripts/vcheck` a measurement, `scripts/vcheck --gate` the verdict (§2).

**Misconceptions & counter-moves**
- *"The editor showed no error, so the file is done."* → Ask: under which options did the editor verify, and what would you hand a reviewer to re-run it?

### K4 [predict] — which trigger reaches the goal
**viva:** yes (verifier-refereed predict) · **strand:** S11 · **tags:** `triggers`, `matching-loop` · **backward-edge:** Q06 (the terms that switch a quantified fact on)

`Storey` is opaque: only the hypothesis says anything about it. Four lemmas take the same hypothesis, "every storey is below the next", with its trigger on `Storey(k)` ([a], [c]) or on `Storey(k + 1)` ([b], [d]); [a] and [b] state a goal the hypothesis entails, [c] and [d] one it does not. The Dafny module turns nonlinear arithmetic off for itself.

```dafny
module {:disableNonlinearArithmetic} K4 {
  // A storey per floor; opaque, so only the hypotheses below say anything about it.
  opaque function Storey(k: nat): nat
  {
    k
  }

  // [a] trigger on Storey(k); a goal the hypothesis entails.
  lemma ClimbOld(n: nat)
    requires forall k: nat {:trigger Storey(k)} :: Storey(k) < Storey(k + 1)
    ensures Storey(0) < Storey(3)
  {
  }
```

### PP2 — parallel to Q09.T1d and Q09.T1v (a quantified step with a trigger you choose)
**Isolates:** `triggers`, `matching-loop`

The sums `1 + 2 + … + n` grow faster than their index. Prove it with a quantified step whose trigger you choose and write explicitly, so that the quantified step carries the proof; the proof must be stable and carry no resource attribute. Work in a scratch file and check it with `scripts/vcheck --module Q09 <file>`, then measure it with the sweep as in PP1.

```dafny
module {:disableNonlinearArithmetic} PP2 {
  // The sum 1 + 2 + ... + n.
  function Ramp(n: nat): nat
  {
    if n == 0 then 0 else n + Ramp(n - 1)
  }

  // PP2: the sums grow faster than their index. Prove it with a quantified step whose
  // trigger you choose and write explicitly; the proof must be stable under
  // scripts/vcheck --brittleness --solvers and carry no resource attribute.
  lemma RampOutgrows(m: nat, n: nat)
    requires m < n
    ensures Ramp(m) + m < Ramp(n)
    decreases n - m
}
```
