### K1 [reconstruct] — three laws make a loop
**viva:** yes · **tags:** `traits-and-interfaces`, `refinement`, `verdict-reading` · **backward-edge:** R06 (the derivative matcher's loop invariant)

Reconstruct, without the file, the invariant of the interface's run loop (`MatchWord` in Dafny, `match_word` in Verus) and say which of the three laws establishes it, which keeps it, and which turns it into the answer. Then read the probe: an engine whose `Final` is the negation of `Nullable`. Where does each verifier report the failure, and why there rather than in the engine?

```dafny
module R08_FlipEngine refines RG_A2_StepMatcher {
  import opened RG_A1_Re
  import B = RG_A1b_Facts
  import A2 = RG_A2_Deriv

  type Pattern = Re
  type Config = Re

  ghost predicate Lang(p: Pattern, w: seq<char>) { Matches(p, w) }
  ghost predicate Res(st: Config, w: seq<char>) { Matches(st, w) }

  function Feed(st: Config, c: char): Config { A2.Deriv(st, c) }
```

### K2 [predict] — a true promise the inherited body cannot keep
**viva:** yes (verifier-refereed predict) · **tags:** `refinement`, `requires-ensures` · **backward-edge:** none

The derivative engine again, with one extra promise. In Dafny the refinement adds to `MatchWord` the postcondition `w == [] ==> b == Nullable(p)`; in Verus the implementation adds to `is_final` the postcondition `b == matches(*st, Seq::<char>::empty())`. Both promises are true. Predict each verdict: `D:<verified|failed> V:<verified|failed>`.

```dafny
module R08_PromiseEngine refines RG_A2_StepMatcher {
  import opened RG_A1_Re
  import B = RG_A1b_Facts
  import A2 = RG_A2_Deriv

  type Pattern = Re
  type Config = Re

  ghost predicate Lang(p: Pattern, w: seq<char>) { Matches(p, w) }
  ghost predicate Res(st: Config, w: seq<char>) { Matches(st, w) }
  function Start(p: Pattern): Config { p }
  function Feed(st: Config, c: char): Config { A2.Deriv(st, c) }
  predicate Final(st: Config) { Nullable(st) }
  lemma StartLaw(p: Pattern, w: seq<char>) { }
  lemma FeedLaw(st: Config, c: char, w: seq<char>) { A2.DerivCorrect(st, c, w); }
  lemma FinalLaw(st: Config) { B.NullableCorrect(st); }

    ensures w == [] ==> b == Nullable(p)
}
```

**Target insights**
- A refinement may add an `ensures`, and it is checked against the body. Dafny re-verifies the *inherited* body of `MatchWord`, which the refinement cannot change; that body never mentions `NullableCorrect`, so the true promise is not provable from it. - Truth is not enough: a postcondition is proved from the body as written. The difference between the two languages is where a fix can go. In Verus the implementation owns the body: add `proof { lemma_nullable_correct(*st); }` and it verifies. In Dafny the body is the interface's; the refinement can add declarations but not proof steps inside `MatchWord`.

- *"The promise is false for some pattern."* → Ask for a pattern and the empty word where it fails; when none comes, ask which lemma says it holds.

### K3 [why] — when a refining lemma may recurse
**viva:** yes · **tags:** `termination-measure`, `refinement`, `induction-as-recursion` · **backward-edge:** R06 (decreases clauses and the induction hypothesis)

The Dafny probe's `StartLaw` calls itself on `p - 1` and `w[1..]`, with no `decreases` clause; the Verus probe's implementation recurses with no `decreases` either. Explain both verdicts, and why the hand file's alternative-set engine proves its step law in a lemma of its own instead of in `FeedLaw`.

```dafny
module R08_CountEngine refines RG_A2_StepMatcher {
  type Pattern = nat
  type Config = int

  ghost predicate Within(n: nat, w: seq<char>)
  {
    if n == 0 then w == [] else w == [] || Within(n - 1, w[1..])
  }

  ghost predicate Lang(p: Pattern, w: seq<char>) { Within(p, w) }
  ghost predicate Res(st: Config, w: seq<char>) { |w| <= st }
  function Start(p: Pattern): Config { p }
  function Feed(st: Config, c: char): Config { st - 1 }
  predicate Final(st: Config) { st >= 0 }

  lemma StartLaw(p: Pattern, w: seq<char>)
  {
    if p > 0 && w != [] {
      StartLaw(p - 1, w[1..]);
    }
  }

  lemma FeedLaw(st: Config, c: char, w: seq<char>) { }
  lemma FinalLaw(st: Config) { }
}
```
```rust
use vstd::prelude::*;

verus! {

pub trait CountLaw {
    spec fn within(n: nat, w: Seq<char>) -> bool;

    proof fn lemma_within(n: nat, w: Seq<char>)
        ensures
            Self::within(n, w) == (w.len() <= n),
    ;
}

pub open spec fn within_r(n: nat, w: Seq<char>) -> bool
    decreases n,
{
    if n == 0 {
        w.len() == 0
    } else {
        w.len() == 0 || within_r((n - 1) as nat, w.drop_first())
    }
}

pub struct CountList;

impl CountLaw for CountList {
    open spec fn within(n: nat, w: Seq<char>) -> bool {
        within_r(n, w)
    }

    proof fn lemma_within(n: nat, w: Seq<char>) {
        if n > 0 && w.len() > 0 {
            Self::lemma_within((n - 1) as nat, w.drop_first());
        }
    }
}

} // verus!
```

**Target insights**
- A refining lemma may not state a decreases clause; it inherits the interface's default, the tuple of its parameters. Parameters of the abstract types (`Pattern`, `Config`) carry no order there, so only a concrete-typed parameter can decrease: here the word `w` shrinks, and the Dafny probe verifies.
- A law that recurses on the state with the word unchanged (`FeedLaw(st[1..], c, w)`) has no decreasing component and fails its termination check; hence the engine's own `AltFeedLaw`, an ordinary lemma with `decreases |st|`, and a one-call law.
- Verus checks termination per function and requires an explicit `decreases` on every recursive function, implementation fns included; with one (as P3's specimen has) the recursion is accepted.

**Misconceptions & counter-moves**
- *"Dafny never allows recursion in a refinement."* → Point at the Dafny probe's verdict; ask which argument got smaller.
- *"Adding `decreases |st|` fixes the alternative-set law."* → Ask what P3's Dafny specimen reported for a `decreases` clause on a refining lemma.
- *"Verus infers the measure."* → Point at the Verus probe's stage and message.

### K4 [predict] — what a revealing lemma exports
**viva:** yes (verifier-refereed predict) · **tags:** `opacity` · **backward-edge:** none

`Doubled` is opaque. `RevealOne` reveals it to prove `Doubled(2 * k)`. Lemma [a] uses `RevealOne` to prove `Doubled(2 * k + 2)`; lemma [b] uses it to prove `Doubled(n) ==> n % 2 == 0`. Neither [a] nor [b] reveals anything. Predict, per language, which of [a] and [b] verify: `D:a:<v>,b:<v> V:a:<v>,b:<v>`.

```dafny
module R08_ScopeProbe {
  opaque ghost predicate Doubled(n: int)
  {
    n % 2 == 0
  }

  lemma RevealOne(k: int)
    ensures Doubled(2 * k)
  {
    reveal Doubled();
  }

  // [a]
  lemma UseFact(k: int)
    ensures Doubled(2 * k + 2)
  {
    RevealOne(k + 1);
  }

  // [b]
  lemma UseBody(n: int)
    ensures Doubled(n) ==> n % 2 == 0
  {
    RevealOne(n / 2);
  }
}
```

**Target insights**
- A revealing lemma exports its `ensures`, not the definition: the reveal ends with the proof that contains it. [a] needs only an instance of `RevealOne`'s statement (at `k + 1`, where `2 * (k + 1) == 2 * k + 2`), so it verifies.
- [b] needs the definition itself, read the other way (from `Doubled(n)` to a fact about `n`); `RevealOne` states only that even arguments are `Doubled`, never the converse, so [b] fails in both languages until it reveals `Doubled` itself.
- This is why H4 reveals the engine's model in its own proofs (`AltFinalLaw`, and the start law, whose goal is about `AltRes` while H2 speaks of `AnyMatches`): the facts H3 proved about `AltRes` do not give them the definition they need.

- *"Once revealed, a definition stays revealed for the module."* → Ask: where does [b]'s proof see the body of `Doubled`?
- *"[a] fails too: it never reveals."* → Ask what `RevealOne(k + 1)` puts in [a]'s context.

### K5 [why] — a body a client cannot see
**viva:** yes · **tags:** `module-visibility`, `opacity` · **backward-edge:** R03 (export sets: an API that hides its representation)

In the Dafny probe, `R08_Gate` exports `Hidden` with `provides` and `Shown` with `reveals`; in the Verus probe, `hidden` is a `closed spec fn` and `shown` an `open` one, inside `mod gate`. A client outside proves both from `x > 0`. Why does exactly one obligation fail in each language, and how does this relate to P4's sealed engine?

```dafny
module R08_Gate {
  export
    provides Hidden
    reveals Shown

  ghost predicate Hidden(x: int) { x > 0 }
  ghost predicate Shown(x: int) { x > 0 }
}

module R08_GateClient {
  import G = R08_Gate

  lemma BothHold(x: int)
    requires x > 0
    ensures G.Shown(x)
    ensures G.Hidden(x)
  {
  }
}
```

**Target insights**
- `provides` exports a name and its signature; `reveals` also exports the body. A client sees `Shown`'s body and proves it, but `Hidden` is a name with no definition outside its module. Verus's `closed` is the same boundary: the body is visible inside `mod gate` only.
- This is visibility, not opacity: no `reveal` statement can open a `provides`d or `closed` body from outside; only the module that owns the body can prove things about it and export them as lemmas.
- P4's sealed engine is the same situation: outside its module, `res` has no body, so a client learns only what the laws' instances state.

**Misconceptions & counter-moves**
- *"Add `reveal Hidden();` to the client."* → Ask which declarations a client may reveal, and where `Hidden`'s body is visible.
- *"Both fail: the client cannot see anything of the gate."* → Point at `Shown`'s verdict line.
