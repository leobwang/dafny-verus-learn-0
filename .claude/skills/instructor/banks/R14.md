### K1 [reconstruct] — the term an existential waits for
**viva:** yes · **tags:** `triggers`, `quantifiers` · **backward-edge:** R04 (an existential and its witness)

Reconstruct, without the file, why `CatIntroV` needs its two sequence equations: what the trigger of `MatchesV`'s Cat case is, which term the solver has, and which it lacks. Then read the probe. `PrefixHits(s, t)` says some prefix of `s` sums to `t`, with the trigger `Total(s[..i])`. Three bodies for the same lemma: empty; a value fact `Total([3]) == 3`; the value fact and the equation `[3, 4][..1] == [3]`. Which verify, and why does the value fact alone not?

```dafny
module R14_SplitProbe {
  function Total(s: seq<int>): int
    decreases |s|
  {
    if s == [] then 0 else s[0] + Total(s[1..])
  }

  ghost predicate PrefixHits(s: seq<int>, t: int)
  {
    exists i {:trigger Total(s[..i])} | 0 <= i <= |s| :: Total(s[..i]) == t
  }

  lemma ThreeFirst()
    ensures PrefixHits([3, 4], 3)
  {
    assert [3, 4][..1] == [3];
    assert Total([3]) == 3;
  }
}
```

**Target insights**
- The existential is instantiated only at a term `Total([3, 4][..k])` for some `k`. The goal mentions no such term; the solver does not search the integers for a witness.
- `Total([3]) == 3` is true and useful, but `Total([3])` is not of the trigger's shape: no slice of `[3, 4]` appears in it. The equation `[3, 4][..1] == [3]` puts the slice `[3, 4][..1]` into the proof and into the same equivalence class as `[3]`, so the known `Total([3])` now *is* a `Total([3, 4][..1])` term.
- That is H1's move exactly: `s[..|u|] == u` makes the known `MatchesV(a, u)` a trigger term. A witness in R04's sense (`i = 1`) is the content; the term is how the solver is told.

**Misconceptions & counter-moves**
- *"The value fact is the missing step."* → Show the middle probe: it fails. Ask which term of the trigger's shape it adds.
- *"The equation is something the solver already knows."* → It knows it once asked; it never asks, because no `[3, 4][..1]` term exists. Ask what "knows" means for a fact about a term not in the proof.

### K2 [predict] — a chain with no end and a goal that is false
**viva:** yes (verifier-refereed predict) · **tags:** `matching-loop`, `resource-limits`, `verdict-reading` · **backward-edge:** R05 (a resource limit as the end of a search)

The hypothesis `forall n :: reach(n) ==> reach(n + 1)`, triggered by `reach(n)`, feeds its own trigger: from `reach(0)` it gives `reach(1)`, which matches again, and so on. The goal `k < 0` does not follow. Predict each verdict: `D:<verified|failed|inconclusive> V:<verified|failed|inconclusive>`.

```dafny
module R14_ChainProbe {
  lemma Far(reach: int -> bool, k: int)
    requires reach(0)
    requires forall n {:trigger reach(n)} :: reach(n) ==> reach(n + 1)
    ensures k < 0
  {
  }
}
```
```rust
use vstd::prelude::*;

verus! {

proof fn lemma_far(reach: spec_fn(int) -> bool, k: int)
    requires
        reach(0),
        forall|n: int| #[trigger] reach(n) ==> reach(n + 1),
    ensures
        k < 0,
{
}

} // verus!
```

**Target insights**
- No verdict here is `verified`: the goal is false (take `k = 0`), so no instantiation proves it.
- The interesting part is `failed` versus `inconclusive`. Both report `failed` here: the solvers' instantiation limits (Z3 bounds how deep a chain of instances may grow from the original terms) end this chain before the resource limit. P1's quantifier, over `MatchesV` and `s + s`, behaved differently in Dafny (`inconclusive`). The verdict alone does not tell whether a loop exists; the source and the patterns do (§2, §3).
- `inconclusive` is the run ending at the pinned budget (R05's deterministic resource limit), never a refutation; `failed` with zero holes says the obligation was not proved, never that it is false.

**Misconceptions & counter-moves**
- *"A matching loop always runs out of resources."* → Show this probe and P1's: same shape of hypothesis, different verdicts. Ask what the verdict measures.
- *"`failed` means the solver found a counterexample."* → Ask for the counterexample from the output; there is none. The goal happens to be false, but the verdict would read the same for a true goal the solver could not reach.

### K3 [why] — fuel reaches three, not every n
**viva:** yes · **tags:** `fuel`, `induction-as-recursion` · **backward-edge:** R06 (manual lemma induction)

`Ones(n)` is `n` copies of `1`. With `{:fuel Ones, 4}`, `|Ones(3)| == 3` verifies with an empty body, and `|Ones(n)| == n` for every `n` does not, even with the same fuel. Why? What does the general lemma need instead, and why is `{:induction false}` on it part of the question?

```dafny
module R14_RepeatProbe {
  function Ones(n: nat): seq<int>
  {
    if n == 0 then [] else [1] + Ones(n - 1)
  }

  lemma {:fuel Ones, 4} OnesThree()
    ensures |Ones(3)| == 3
  {
  }

  lemma {:fuel Ones, 4} {:induction false} OnesAny(n: nat)
    ensures |Ones(n)| == n
  {
  }
}
```

**Target insights**
- Fuel is the number of times a recursive definition is opened at a term. `Ones(3)` is opened to `[1] + Ones(2)`, then `Ones(1)`, `Ones(0)`, `[]`: four unfoldings reach the base, and the length follows.
- `Ones(n)` for an unknown `n` opens to `[1] + Ones(n - 1)` and then to `Ones(n - 2)`, … with no base in sight: every finite depth leaves an unknown `Ones(n - k)`. Only an induction (a recursive lemma call on `n - 1`) closes it.
- Without `{:induction false}`, Dafny's automatic induction would supply the recursive call itself; the lever keeps the question about fuel. This is P5's lesson (three Stars) and H2's (every power, by induction).

**Misconceptions & counter-moves**
- *"More fuel would do it."* → Ask for the fuel value that covers `n = 1000`, then `n` unknown.
- *"The general lemma is false."* → Ask for an `n` where `|Ones(n)| != n`.

**Verifier probe** (line 14 is `OnesAny`; `OnesThree` verifies)

### K5 [why] — a trigger the outside cannot see
**viva:** yes · **tags:** `triggers`, `fuel` · **backward-edge:** none

Two Verus definitions of "the sequence splits into even-length chunks", identical except for the trigger: `pairs_rec` triggers on the recursive call `pairs_rec(s.subrange(i, …))`, `pairs_sub` on the term `s.subrange(i, …)`. The same proof, the subrange equation and fuel 2, is given to both. One verifies. Which, and why does the other fail although its trigger "is the obvious one"? Why does Dafny's `MatchesV` get away with a trigger on its own recursive call?

```rust
use vstd::prelude::*;

verus! {

pub open spec fn pairs_rec(s: Seq<int>) -> bool
    decreases s.len(),
{
    s.len() == 0 || exists|i: int|
        0 < i <= s.len() && i % 2 == 0 && #[trigger] pairs_rec(s.subrange(i, s.len() as int))
}

proof fn lemma_two_rec()
    ensures
        pairs_rec(seq![7, 8]),
{
    assert(seq![7, 8].subrange(2, 2) =~= Seq::<int>::empty());
    reveal_with_fuel(pairs_rec, 2);
}

} // verus!
```
```rust
use vstd::prelude::*;

verus! {

pub open spec fn pairs_sub(s: Seq<int>) -> bool
    decreases s.len(),
{
    s.len() == 0 || exists|i: int|
        0 < i <= s.len() && i % 2 == 0 && pairs_sub(#[trigger] s.subrange(i, s.len() as int))
}

proof fn lemma_two_sub()
    ensures
        pairs_sub(seq![7, 8]),
{
    assert(seq![7, 8].subrange(2, 2) =~= Seq::<int>::empty());
    reveal_with_fuel(pairs_sub, 2);
}

} // verus!
```

**Target insights**
- Verus encodes a recursive spec function with fuel: the call inside the body is a call of the fuel-indexed copy, not of the function a proof outside refers to. A trigger on it names a term that no outside proof produces, so the quantifier is never instantiated from outside.
- A trigger on `s.subrange(i, s.len())` names an ordinary term: the proof's equation produces it, and the existential fires.
- Dafny's encoding lets a definition's existential trigger on the function itself (R14's `MatchesV` does), so the two languages' `MatchesV` have different triggers by necessity: C4dv. The trigger is part of a definition's interface.

**Misconceptions & counter-moves**
- *"More fuel would let `pairs_rec`'s trigger match."* → The probe has fuel 2; ask which term in the proof has the shape of the fuel-indexed copy.
- *"The two definitions mean different things."* → They are the same predicate; only the trigger annotation differs. Ask what a trigger changes about the meaning (nothing) and about the proofs (everything).

### K6 [predict] — the high bits of a code point
**viva:** yes (verifier-refereed predict) · **tags:** `bit-vector` · **backward-edge:** R09 (character classes over A2's `u32` code-point ranges; R03, which first builds them, is parked)

Two parts. (a) In Dafny, for the `bv32` value `c == 0x1F600`, what integer is `(c - 0x10000) >> 10`? Answer form: numeral. (b) In Verus, for a `u32` code point `c < 0x110000`, `c >> 16 <= 16` with an empty body: predict the verdict `V:<verified|failed>`, then say what the repair is.

```dafny
module R14_LowTenProbe {
  method {:test} LowTen()
  {
    var c: bv32 := 0x1F600;
    expect ((c - 0x10000) >> 10) as int == 61;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

proof fn lemma_high_bits(c: u32)
    requires
        c < 0x110000,
    ensures
        c >> 16u32 <= 16,
{
}

} // verus!
```

**Target insights**
- (a) `0x1F600 - 0x10000 = 0xF600 = 62976`, and shifting right by ten divides by 1024 and drops the rest: `61`. (In UTF-16 that is the high surrogate's offset, `0xD800 + 61`.)
- (b) Verus reasons about `u32` as integers in its main query and does not know what `>>` does to a bounded integer there; the fact is proved by the bit-vector theory: `assert(c >> 16u32 <= 16) by (bit_vector) requires c < 0x110000;`, a separate query that sees only its `requires`.
- In Dafny, `bv32` values are bit-vectors in the solver, so such facts are native; mixing `int` and `bv32` costs a conversion the solver handles badly (the battery's `bv-d` cell).

**Misconceptions & counter-moves**
- *"`>> 10` keeps the low ten bits."* → That is `& 0x3FF`; ask which bits a right shift keeps.
- *"Verus knows bit operations on u32."* → It knows them in the bit-vector query; show the follow-up.

### K8 [why] — eight small queries instead of one large one
**viva:** yes · **tags:** `proof-splitting`, `resource-limits` · **backward-edge:** R05 (`{:isolate_assertions}` and `spinoff_prover`, written there)

Take K7's lemma and add one attribute: `lemma {:isolate_assertions} Batch(…)`. Now all three seeds verify, each with about 3.1 million units in all. Why? What did the attribute change, and what did it not change about the eight statements?

**Target insights**
- `{:isolate_assertions}` makes each assertion its own verification task, with the facts before it assumed. Each task gets the whole resource budget; one cubic identity is cheap, so each fits, and the search no longer depends on how eight expansions interleave.
- Nothing about the statements changed, and nothing became more true. The facts before an isolated assertion are still assumed, so isolation can also hurt: a nonlinear fact assumed in every later task is more for the solver to search through. Here it helps: the attribute changes how the work is cut into queries, so it changes which budget each piece has. It is the same lever R05 had you write, here with its reason visible.
- In Verus the corresponding cut is a separate query per fact: one `by (nonlinear_arith)` assertion per identity rather than one for their conjunction (the battery's `iso-v` cell); `#[verifier::spinoff_prover]` gives a function its own solver process, not its own per-assertion budget.

**Misconceptions & counter-moves**
- *"Isolation gives the solver more resources."* → Per query, the same; in total, possibly more. Ask whether the limit was raised.
- *"Isolation hides facts the proof needs."* → Assertions before an isolated one are still assumed. Ask which fact an identity needed from another.

### K10 [transfer] — choosing a trigger for a new definition
**viva:** yes · **tags:** `triggers`, `quantifiers` · **backward-edge:** none

You define `HasNeg(s)`: some element of `s` is negative, with the trigger `s[i]`. Which proofs about `HasNeg` does this trigger make easy, and which hard? Prove `HasNeg(s + [-1])` with one assertion. Then: if the trigger were a helper predicate `IsNeg(s, i)` instead, what would every proof have to mention?

```dafny
module R14_NegProbe {
  ghost predicate HasNeg(s: seq<int>)
  {
    exists i {:trigger s[i]} | 0 <= i < |s| :: s[i] < 0
  }

  lemma AppendNeg(s: seq<int>)
    ensures HasNeg(s + [-1])
  {
    assert (s + [-1])[|s|] == -1;
  }
}
```

**Target insights**
- With the trigger `s[i]`, any proof that mentions an element `t[k]` of the sequence in question instantiates the existential at `k`. Appending is easy once the element `(s + [-1])[|s|]` is named; the assertion does it, and says what it is.
- A helper-predicate trigger such as `IsNeg(s, i)` would match only terms of that shape: every proof would have to mention `IsNeg(t, k)` explicitly, and facts about `t[k]` alone would not fire it. That is sometimes wanted (fewer accidental instances, no loops) and sometimes a burden.
- The choice is made once, in the definition, and is part of its interface: R14's `MatchesV` chose the left part's match (Dafny) or the left part's subrange (Verus), which is why H1 needs exactly the slice equation.

**Misconceptions & counter-moves**
- *"The trigger only affects performance."* → Show the empty body failing: it decides whether a true goal is proved at all.
- *"A trigger should be as general as possible."* → Ask what a trigger that matches every `int` term would do to K2's chain.

**Target insights**
- The done rule is a gate (three seeds, all must verify); a sweep is a description (ten runs, every one recorded). Neither substitutes for the other, as R12's profiler measurements never substitute for the gate.

### PP2 — parallel to R14.H3d and R14.H3v (an induction that ends in a product inequality)
