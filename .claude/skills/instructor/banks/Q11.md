### K1 [predict] — a function that reads a field
**viva:** yes (verifier-refereed predict) · **strand:** S6 · **tags:** `frames`, `false-friends` · **backward-edge:** Q05 (frames: what a function may read)

A class or struct `Tally` holds one number, `reading`, and a ghost function (Verus: a spec fn) returns twice the reading. Neither has any frame clause. Predict `scripts/vcheck --module Q11`'s verdict in each language (`D:<v> V:<v>`, each `ok`, `fail` or `err:<stage>`). Then: what does the failing one ask for, and why does the other need nothing?

**Target insights**
- A Dafny function's result may depend only on what its `reads` clause names; a function with no `reads` clause reads nothing on the heap, so reading `this.reading` fails: "insufficient reads clause". Adding `reads this` fixes it.
- The point of `reads` is the frame rule for functions: when a method writes the heap, the verifier keeps a function's value unchanged exactly when the write is outside what the function reads.
- Verus's spec fn takes `&self` as a value: a `Tally` is a plain struct, not a heap object, so there is nothing to frame. Who may change `self.reading` is settled by Rust's ownership, not by a clause.
- One concept, two mechanisms: Dafny frames by clauses over a shared heap, Verus by ownership.

**Misconceptions & counter-moves**
- *"A ghost function can read anything: it is never compiled."* → Probe: the Dafny file; ask: what does the error ask for?
- *"Verus needs `reads` too, it just infers it."* → Ask: where is `self.reading` stored, and who else could change it during the call?

### K2 [why] — what a loop may have changed
**viva:** yes · **strand:** S6 · **tags:** `frames` · **backward-edge:** Q05 (what a loop may change)

A Dafny method `modifies a` and fills `a[1..]` with a loop whose only invariant bounds `i`. After the loop, it asserts that `b[0]` (another array) and `a[0]` still hold their values from before the loop. One assertion verifies and one does not. Which, why, and what one invariant fixes it?

**Target insights**
- A loop with no frame clause of its own may change anything the method may modify: here, every element of `a`. After the loop the verifier knows only the invariant about `a`, so `a[0] == a0` fails, though the code never writes `a[0]`.
- `b` is not in the method's `modifies` clause, so the loop cannot have changed it: `b[0] == b0` survives without any invariant.
- The fix states what the loop keeps: `invariant a[0] == a0`. In H2d the same reasoning tells you why the other vector's contents survive the copy, and what the loop must say about the copied part.
- A frame is a promise about everything else: outside the frame, facts survive; inside it, only invariants do.

**Misconceptions & counter-moves**
- *"The loop starts at 1, so the verifier knows `a[0]` is untouched."* → Probe: the file; ask: what does the verifier assume about `a` at the top of each iteration?
- *"`b` survives because it is a different array."* → Ask: would it survive if `b` were in the `modifies` clause?

**Verifier probe**

```dafny
module ProbeK2 {

    modifies a

      a[i] := 7;
      i := i + 1;
    }
    assert b[0] == b0;
    assert a[0] == a0;
  }
}
```

### K3 [predict] — one object, passed twice
**viva:** yes (verifier-refereed predict) · **strand:** S6 · **tags:** `ownership-and-mut-ref`, `false-friends` · **backward-edge:** none

`Exchange(p, q)` swaps the numbers held by two objects, with `modifies p, q` (Verus: `exchange(p: &mut Crate2, q: &mut Crate2)`, with `final` in its `ensures`). A second method calls it with the same object twice: `Exchange(c, c)` (Verus `exchange(c, c)`). Predict the verdict of each file (`D:<v> V:<v>`). Then: is the aliased call meaningful, and which language lets you write it?

**Target insights**
- Dafny allows aliases: `p` and `q` may be the same object. With `p == q` the `ensures` says `c.n == old(c.n)`, which the swap establishes; the file verifies. The contract must hold for aliased arguments too, and here it does.
- Rust's borrow checker forbids two live `&mut` borrows of one object, so Verus refuses the call before verification, at resolve.
- In Dafny, aliasing is a case your specification must survive; in Verus it is a program you cannot write. A Dafny contract that is false for `p == q` would be refused at its body, not at the call.

**Misconceptions & counter-moves**
- *"Dafny rejects the aliased call."* → Probe: the Dafny file; ask: what does the `ensures` say when `p == q`?
- *"Verus's error is a verification failure."* → Probe: the Verus file; ask: which stage printed it?

**Verifier probe**
```dafny

    var n: nat

  method Exchange(p: Crate, q: Crate)
    modifies p, q
    ensures p.n == old(q.n) && q.n == old(p.n)
  {
    var t := p.n;
    p.n := q.n;
    q.n := t;
  }

  method SelfExchange(c: Crate)
    modifies c
  {
    Exchange(c, c);
  }
}
```

### K4 [reconstruct] — why a subset type needs a witness
**viva:** yes · **strand:** S7 · **tags:** `subset-types` · **backward-edge:** Q03 (subset types and their witnesses)

`type OddInt = n: int | n % 2 == 1` fails without a `witness` clause. Reconstruct why Dafny asks for one, what it tries by itself, and what `witness 1` establishes. Then: what does a function returning an `OddInt` (or H5d's `CanonSeq`) owe at each return?

**Target insights**
- Dafny requires every type to be inhabited unless declared possibly empty, because a variable of the type may be declared before it is assigned, and must hold some value of the type. With no clause it tries `0`, which is even, and fails.
- `witness 1` names a value that satisfies the constraint; the verifier checks it once, at the declaration. `witness *` would declare the type possibly empty instead.
- Every value produced as an `OddInt` must satisfy the constraint at that point: a function's return value is checked against the subset constraint as well as the `ensures`, which is H5d's double obligation.
- Verus has no subset types: the counterpart is a spec predicate in `requires`/`ensures`, or a type invariant on a struct with private fields.

**Misconceptions & counter-moves**
- *"The witness is the default value."* → Ask: where is the witness used, and is it ever computed at run time?
- *"The constraint is checked only when the type is declared."* → Ask: what does a function returning the type owe at each return?

**Verifier probe**

### K6 [connect] — backwards, not forwards
**viva:** yes · **strand:** S8 · **tags:** `wp-vc` · **backward-edge:** Q03 (weakest preconditions by hand)

The program `z := z * 2; z := z + 1` must end with `z > 9`. Q03 computed weakest preconditions by hand. One reader substitutes from the last statement back and gets `z * 2 + 1 > 9`; another substitutes in the order the statements run and gets `(z + 1) * 2 > 9`. Which is the weakest precondition, and how does a lemma decide it in one run?

**Target insights**
- The assignment rule substitutes into the formula that must hold *after* the assignment, so the last statement is substituted first: `z + 1 > 9` becomes, through `z := z * 2`, `z * 2 + 1 > 9`.
- Substituting forwards composes the expressions in the wrong order: `(z + 1) * 2` is the program `z := z + 1; z := z * 2`, a different program.
- A lemma `Pre(z) <==> Post(Run(z))` with an empty body checks a hand-computed precondition exactly, both directions at once: the backward formula verifies, the forward one fails. H7d's `Pre1Exact` is that check, and it sees meaning, not how you got there.

**Misconceptions & counter-moves**
- *"The order does not matter for two assignments."* → Probe: both lemmas; ask: which one fails?
- *"If the lemma verifies, the formula was computed correctly."* → Ask: what else, equivalent to the right formula, would also verify?

**Verifier probe**
```dafny
module ProbeK6 {
  // z := z * 2; z := z + 1
  function Run(z: int): int
  {
    var z1 := z * 2;
    z1 + 1
  }

  // Backwards: substitute z + 1, then z * 2, into z > 9.
  lemma Backward(z: int)
    ensures (z * 2 + 1 > 9) <==> Run(z) > 9
  {
  }

  // Forwards: substitute in the order the statements run.
  lemma Forward(z: int)
    ensures ((z + 1) * 2 > 9) <==> Run(z) > 9
  {
  }
}
```

### K7 [predict] — the branch where nothing happens
**viva:** yes (verifier-refereed predict) · **strand:** S8 · **tags:** `wp-vc` · **backward-edge:** none

`if w < 0 then w := 0 - w` (nothing happens otherwise), with the postcondition `w < 3`. One candidate precondition keeps only the branch that runs the assignment, `w < 0 ==> 0 - w < 3`; the other adds the branch in which nothing happens, `!(w < 0) ==> w < 3`. Each is checked against the program by an exactness lemma with an empty body, in both languages. Predict which lemmas verify (`D:<one> <two> V:<one> <two>`, each `ok` or `fail`).

**Target insights**
- A one-armed conditional still has two ways to go. When `w >= 0` nothing happens, so `w < 3` must already hold: the second implication is not optional.
- With only the first implication, every `w >= 3` satisfies the candidate and ends outside the postcondition: the one-implication lemmas fail in both languages; the two-implication lemmas verify.
- W2d's `Wp` builds exactly the two implications for `IfThen`, and H9d's soundness case splits on the same two ways.

**Misconceptions & counter-moves**
- *"If the condition is false, nothing happens, so there is nothing to require."* → Ask: what must be true of `w` at the end when nothing happened?
- *"The implication is vacuous when the condition is false."* → Ask: vacuous for which formula, the candidate or the postcondition?

**Verifier probe**

### K8 [transfer] — a permission per cell, a frame per method
**viva:** yes · **strand:** S8 · **tags:** `permissions`, `frames` · **backward-edge:** none

Verus: `glance(a, b, pa)` holds the permission of cell `a` and tries to read cell `b` with it. Dafny: `Glance(a, b)` reads `b.v` with no clause at all, and `Poke(a, b)` writes `b.v` under `modifies a`. Which of the three fail, and what does each verifier check where the other checks something else? Transfer the H10v idea: what plays the role of `PointsTo` in Dafny?

**Target insights**
- A `PCell`'s value is reachable only through its own `PointsTo`, matched by id: `b.read(Tracked(pa))` with `pa` for `a` fails `read`'s precondition. Reading through the right permission verifies.
- Dafny methods read the heap freely (no clause needed), so `Glance` verifies; writes need `modifies`, so `Poke`, writing `b` under `modifies a`, fails.
- The counterpart of a `PointsTo` in Dafny is the frame: `modifies` grants writes per method, and nothing per object grants reads to a method. Verus's permission is a value: it can be passed, split and returned, and it covers reads too.

**Misconceptions & counter-moves**
- *"The id check is a runtime check."* → Ask: where is `pa.id()` compared with `b.id()`, and what remains of it in the compiled program?
- *"Dafny needs `reads` in a method."* → Probe: `Glance` verifies; ask: where does Dafny need `reads`? (K1.)

**Verifier probe**
