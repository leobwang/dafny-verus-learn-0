### K1 [reconstruct] — where a refined value is checked
**viva:** yes · **tags:** `subset-types`, `verdict-reading` · **backward-edge:** none

Reconstruct, for a Dafny subset type and for a Verus struct with a type invariant, the one place where membership is checked, and what a value of the type gives its users afterwards. Then read the probes: `EvenBankR10` holds even numbers, and the first version of each function builds an odd one.

```dafny
module R10_BankEvenOdd {
  type EvenBankR10 = n: nat | n % 2 == 0 witness 0

  // The result type is a promise checked where the value is returned.
  method NextEvenBankR10(k: EvenBankR10) returns (out: EvenBankR10)
  {
    out := k + 1;
  }
}
```
```dafny
module R10_BankEvenTwo {
  type EvenBankR10 = n: nat | n % 2 == 0 witness 0

  method NextEvenBankR10(k: EvenBankR10) returns (out: EvenBankR10)
  {
    out := k + 2;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

pub struct EvenBankR10 {
    n: u64,
}

impl EvenBankR10 {
    #[verifier::type_invariant]
    spec fn even(&self) -> bool {
        self.n % 2 == 0 && self.n < 1000
    }

    // The struct expression is where the invariant is checked.
    fn next_bank_r10(&self) -> EvenBankR10 {
        proof {
            use_type_invariant(self);
        }
        let m = if self.n < 998 { self.n + 1 } else { 0 };
        EvenBankR10 { n: m }
    }
}

} // verus!
```
```rust
use vstd::prelude::*;

verus! {

pub struct EvenBankR10 {
    n: u64,
}

impl EvenBankR10 {
    #[verifier::type_invariant]
    spec fn even(&self) -> bool {
        self.n % 2 == 0 && self.n < 1000
    }

    fn next_bank_r10(&self) -> EvenBankR10 {
        proof {
            use_type_invariant(self);
        }
        let m = if self.n < 998 { self.n + 2 } else { 0 };
        EvenBankR10 { n: m }
    }
}

} // verus!
```

**Target insights**
- Membership is checked where a value enters the type: Dafny at the expression assigned to a variable or out-parameter of the subset type ("value does not satisfy the subset constraints"), Verus at the struct expression ("constructed value may fail to meet its declared type invariant"). Neither waits for a client to misuse the value.
- After that, every value of the type carries the predicate. A method that receives a `EvenBankR10` may assume it is even without any `requires`; the Verus method opens the invariant of `self` with `use_type_invariant` (K6) and uses it to keep `self.n + 2` in range.
- Both repairs keep the obligation and change the value. A cast, an `assume` or a weaker type would make the error disappear by deleting the promise, which is the opposite of what the boundary is for.

**Misconceptions & counter-moves**
- *"A subset type is checked at run time, like an assertion."* → Ask: where does the error appear in the output, at a run or at verification, and what does the compiled program hold for `out`?
- *"The invariant is checked when the object is read."* → Ask: which line does Verus name, the struct expression or a later use?

### K2 [predict] — three trees, one predicate
**viva:** yes (verifier-refereed predict) · **tags:** `subset-types`, `verdict-reading`, `fuel` · **backward-edge:** none

Three claims that a regex is normal under A4's predicate: [a] `Alt(Chr('x'), Alt(Chr('y'), Chr('x')))`; [b] `Cat(Chr('x'), Star(Eps))`; [c] `Star(Alt(Chr('x'), Chr('x')))`. Each is a lemma with an empty body (Verus: with enough fuel to unfold the predicate three times). Predict which labels fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>` (or `none`).

```dafny
  }

    ensures Normal(Cat(Chr('x'), Star(Eps)))
  {
  }

  // [c]
  lemma ShapeCBankR10()
    ensures Normal(Star(Alt(Chr('x'), Chr('x'))))
  {
  }
}
```

```rust
use rg_re_a4::*;

    Re::Chr('x')
}

// [a]

    ensures
        is_norm(Re::Alt(Box::new(x_bank_r10()), Box::new(Re::Alt(Box::new(Re::Chr('y')), Box::new(x_bank_r10()))))),

}

    ensures
        is_norm(Re::Star(Box::new(Re::Alt(Box::new(x_bank_r10()), Box::new(x_bank_r10()))))),
{
    reveal_with_fuel(is_norm, 3);
}

} // verus!
```

**Target insights**
- The predicate is checked at every node, not just the root. [a]'s outer `Alt` has two non-`Empty` branches that differ (`Chr('x')` is not the inner `Alt`), and the inner `Alt` has two different leaves: normal. Repeating a leaf deeper in the tree is not a duplicate branch.
- [b] fails one level down: the `Cat`'s operands are not `Empty` or `Eps`, but its right operand `Star(Eps)` is not normal (a star's body may not be `Eps`). [c] fails one level down too: the star's body is not `Eps`, `Empty` or a star, but `Alt(Chr('x'), Chr('x'))` has equal branches. The answer: `D:FAILS b c V:FAILS b c`.
- Dafny names the conjunct of A4's predicate it could not prove (the `related:` lines point into `RG_A4_Norm.dfy`, the `Cat` and `Star` cases); Verus reports only the `ensures` lines. A predicate that recurses needs one unfolding per level: Dafny unfolds literal arguments by itself, Verus needs `reveal_with_fuel`.

**Misconceptions & counter-moves**
- *"`Chr('x')` appears twice in [a], so [a] has a duplicate."* → Ask: which two branches does the `Alt` case compare, and are they equal trees?
- *"[b] is fine because `Star(Eps)` matches only the empty string, like `Eps`."* → Ask: is the predicate about languages or about trees?

### K3 [predict] — who proves the shape, and of which value
**viva:** yes (verifier-refereed predict) · **tags:** `subset-types`, `requires-ensures`, `verdict-reading` · **backward-edge:** none

`UseShapeBankR10` (Verus `use_shape_bank_r10`) takes a normal regex: a `NormRe` parameter. Three callers start from raw regexes: [a] tests `r` at run time and passes `r`; [b] tests `r` and passes another regex `t`; [c] passes the value inside the `Some` an optional validator returned. Predict which callers fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>` (or `none`).

```dafny
module R10_BankSpectrum {
  import opened RG_A1_Re
  import opened RG_A4_Norm

  method UseShapeBankR10(r: NormRe)
  {
  }

  datatype MaybeShapeBankR10 = NoneBankR10 | SomeBankR10(value: NormRe)

  function TryShapeBankR10(r: Re): MaybeShapeBankR10
  {
    if Normal(r) then SomeBankR10(r) else NoneBankR10
  }

  // [a] test the value, then call with it
  method CallerABankR10(r: Re)
  {
    if Normal(r) {
      UseShapeBankR10(r);
    }
  }

  // [b] test one value, call with another
  method CallerBBankR10(r: Re, t: Re)
  {
    if Normal(r) {
      UseShapeBankR10(t);
    }
  }

  // [c] call with what the optional validator returned
  method CallerCBankR10(r: Re)
  {
    var o := TryShapeBankR10(r);
    if o.SomeBankR10? {
      UseShapeBankR10(o.value);
    }
  }
}
```
```rust
use vstd::prelude::*;
use rg_re_a1::*;
use rg_re_a4::*;

verus! {

fn use_shape_bank_r10(r: NormRe) {
}

fn try_shape_bank_r10(r: Re) -> (o: Option<NormRe>)
    ensures
        match o {
            Some(n) => n.re() == r && is_norm(r),
            None => !is_norm(r),
        },
{
    if is_normal_exec_r10(&r) {
        Some(NormRe::from_normal_r10(r))
    } else {
        None
    }
}

// [a] test the value, then build from it
fn caller_a_bank_r10(r: Re) {
    if is_normal_exec_r10(&r) {
        use_shape_bank_r10(NormRe::from_normal_r10(r));
    }
}

// [b] test one value, build from another
fn caller_b_bank_r10(r: Re, t: Re) {
    if is_normal_exec_r10(&r) {
        use_shape_bank_r10(NormRe::from_normal_r10(t));
    }
}

// [c] call with what the optional validator returned
fn caller_c_bank_r10(r: Re) {
    let o = try_shape_bank_r10(r);
    match o {
        Some(n) => use_shape_bank_r10(n),
        None => {},
    }
}

} // verus!
```

**Target insights**
- The parameter type is a precondition the caller must prove at the call. In [a] the branch condition `Normal(r)` is exactly the subset predicate, so the call is justified; in [c] the validator's contract says the payload of `Some` is normal. Both stand on facts about the value actually passed.
- [b]'s test is about `r` and the call passes `t`: no fact about `t` is known, and the verifier reports the call (Dafny: the subset constraint at the argument; Verus: `from_normal_r10`'s precondition). The answer: `D:FAILS b V:FAILS b`.
- This is the spectrum of chapter §1.3 in miniature: a runtime predicate gives a fact for one branch and one value, an optional result packages the fact with the value, a precondition demands the fact from the caller, and the type carries it from then on.

**Misconceptions & counter-moves**
- *"A runtime check before the call is enough, whatever it checks."* → Ask: in [b], which value does the branch condition describe, and which value does the callee receive?
- *"The optional validator's `None` branch must also be handled to verify."* → Ask: which obligation would the `None` branch create, given that nothing is called there?

### K4 [predict] — ghost data in a proof and in a branch
**viva:** yes (verifier-refereed predict) · **tags:** `ghost-and-modes`, `erasure`, `tracked-ghost` · **backward-edge:** R02 (ghost and compiled: why `Matches` is a spec)

Each language has two probes over a word with a ghost size. In `x` the ghost value appears only in a proof (`assert`, a `proof` block); in `y` it decides which branch the compiled code takes. Predict the verdict of each probe. Answer form `D:<x>,<y> V:<x>,<y>`, each one of `ok`, `fail`, `timeout`, `err:<stage>`.

```dafny
// x: a ghost size used only in a proof

  datatype SizedBankR10 = SizedBankR10(word: seq<char>, ghost size: nat)

  type ExactBankR10 = p: SizedBankR10 | p.size == |p.word| witness SizedBankR10([], 0)

  method FirstBankR10(p: ExactBankR10) returns (c: char)

  {
    assert p.size > 0;
    c := p.word[0];
  }
}
```

### K6 [why] — why Verus asks you to open an invariant
**viva:** yes · **tags:** `subset-types`, `requires-ensures` · **backward-edge:** none

Both languages hold a pair whose denominator is positive: a Dafny subset type, a Verus struct with a type invariant. Each divides by the denominator. Dafny's method verifies with no extra step; Verus's [p] fails and [q], which calls `use_type_invariant(self)` first, verifies. Why does Verus need the call, and what does it cost to forget it?

```dafny

  datatype PairBankR10 = PairBankR10(num: int, den: int)

  type ProperBankR10 = p: PairBankR10 | p.den > 0 witness PairBankR10(0, 1)

  // The subset predicate is part of p's type: no step opens it.
  method QuotientBankR10(p: ProperBankR10) returns (q: int)
  {
    q := p.num / p.den;
  }
}
```

```rust
    num: u64,
    den: u64,

        self.den > 0
    }

        self.num / self.den
```

**Target insights**
- A Dafny subset type is part of the value's type: a parameter `p: ProperBankR10` carries `p.den > 0` into every expression that mentions `p`, with no statement required.

- *"The invariant is checked on entry to every method, so it is known there."* → Ask: in [p], which fact about `self.den` is in the context at the division?

### K11 [transfer] — the packet pattern on another invariant
**viva:** yes · **tags:** `subset-types`, `erasure`, `tracked-ghost` · **backward-edge:** none

Transfer R10's packet idea to a different invariant. In Dafny, `UniqueBankR10` is a word with no repeated character, carried with a ghost set of its characters; [x] extends it with a fresh character and rebuilds the ghost set, [y] keeps the old set. In Verus, a tracked permit allows one withdrawal; [x] spends it once, [y] twice. What does each report, and what do the two halves have in common?

```dafny
module R10_BankStock {
  // A different invariant in the packet pattern: a word with no repeated
  // character, carried with a ghost set of its characters.
  datatype CharsBankR10 = CharsBankR10(word: seq<char>, ghost seen: set<char>)

  type UniqueBankR10 = p: CharsBankR10 | (forall i, j :: 0 <= i < j < |p.word| ==> p.word[i] != p.word[j]) && p.seen == set i | 0 <= i < |p.word| :: p.word[i] witness CharsBankR10([], {})

  // [x] extend with a fresh character, rebuilding the ghost set from the old one
  method PushFreshBankR10(p: UniqueBankR10, c: char) returns (q: UniqueBankR10)
    requires c !in p.seen
  {
    ghost var s := p.seen + {c};
    var w := p.word + [c];
    assert forall i | 0 <= i < |p.word| :: p.word[i] in p.seen;
    assert forall i | 0 <= i < |p.word| :: w[i] == p.word[i] && w[i] != c;
    assert w[|p.word|] == c;
    assert (set i | 0 <= i < |w| :: w[i]) == s;
    q := CharsBankR10(w, s);
  }

  // [y] the same, with the ghost set left as it was
  method PushStaleBankR10(p: UniqueBankR10, c: char) returns (q: UniqueBankR10)
    requires c !in p.seen
  {
    assert forall i | 0 <= i < |p.word| :: p.word[i] in p.seen;
    q := CharsBankR10(p.word + [c], p.seen);
  }
}
```

**Target insights**
- A ghost cache is part of the type's promise, so it must be rebuilt whenever the value changes: [x] proves the new set equals the characters of the new word (and that the new character is fresh), [y] leaves a stale set and fails the subset constraint at construction. This is H2's obligation on a different object: rebuild the erased count from the operands, do not let it go stale.
- A tracked value is a proof object with ownership: passing it to `spend_bank_r10` moves it, and spending it again is a use of a moved value, refused at resolution. A `Ghost` value has no such discipline; it can be copied freely.
- Both are erased from the compiled program: the set and the permit cost nothing at run time. What they buy is a proof obligation that cannot be skipped: a stale cache cannot be built, and a permit cannot be used twice.

- *"The ghost set is only documentation, so a stale one is harmless."* → Ask: where is the subset predicate checked, and what does it say about `seen`?
- *"`Tracked` is a `Ghost` with a different name."* → Ask: which error does [y] produce, and could a `Ghost` produce it?
