### K1 [why] — a build that exits 0
**viva:** yes · **strand:** S9 · **tags:** `exit-codes-and-doors`, `fake-green` · **backward-edge:** Q01 (the doors: a build that exits 0 is not a verdict)

A contractor ships the delivery below and reports "built, exit 0". Both forms compile: the code type-checks and the build command finishes. Why is that report no evidence about the `ensures` clause, in either language, and which single command of the course is? What does the pinned command see that a build does not, and what would make even that command's green mean less (name one thing a gate must check besides its exit code)?

```rust
use vstd::prelude::*;

verus! {

// A delivery that compiles: its body type-checks and its build exits 0.
pub fn kite_half(x: u64) -> (r: u64)
    ensures
        r + r == x,
{
    x / 2
}

} // verus!
```

```dafny

  method KiteHalf(x: nat) returns (r: nat)
    ensures r + r == x
  {
    r := x / 2;
  }
}
```

**Target insights**
- A build compiles. In Verus, `cargo build` and `cargo test` never run the verifier and check no `ensures` (catalog row V20); in Dafny, `dafny build` verifies first unless verification is switched off (`--no-verify`, row G7), and a build with it switched off checks no postcondition. Such an exit 0 says the text compiles, nothing more.
- The course's verdict is the pinned command, `scripts/vcheck`, run fresh on the proof text: here it fails the postcondition in both languages (an odd `x` has no `r` with `r + r == x`).
- Even the pinned command's exit code is not enough alone: a gate reads its record (the stage, the verdict, the hole count, the whole crate covered, the pinned counts), so a skipped or partial run cannot pass for a full one.

**Misconceptions & counter-moves**
- *"It built, so it is fine up to the proofs."* → Probe: the two runs; ask: what did the build check that the verifier did not?
- *"Exit 0 from the verifier is the verdict."* → Ask: what does exit 0 look like for a run that verified part of the crate?

### K3 [predict] — six rows, one nonlinear step
**viva:** yes (verifier-refereed predict) · **strand:** S11 · **tags:** `brittleness` · **backward-edge:** Q09 (seed flips and the solver swap)

The lemma below proves casting out (BASE + 1)s, the alternating limb sum, with one nonlinear assertion and its induction call. You run `scripts/vcheck --module Q18 --brittleness --solvers` on it (seeds 1–3 under each bundled Z3). **Predict** the six rows' verdicts, the summary word, and whether the resource counts are flagged.

```dafny
module ElevenProbe {
  import opened QG_L1_BigNat

  // The alternating sum of the limbs, lowest first.
  function SignedDigits(s: seq<nat>): int
    decreases |s|
  {
    if |s| == 0 then 0 else s[0] - SignedDigits(s[1..])
  }

  // Casting out (BASE + 1)s, with one nonlinear step.
  lemma ElevenRule(s: seq<nat>)
    ensures ToNat(s) % (BASE + 1) == SignedDigits(s) % (BASE + 1)
    decreases |s|
  {
    if |s| > 0 {
      ElevenRule(s[1..]);
      var t := ToNat(s[1..]);
      assert BASE * t == (BASE + 1) * t - t;
    }
  }
}
```

**Target insights**
- All six rows verify: the summary says `stable`. The resource counts are flagged: the widest spread is about 0.39 M to 2.96 M on Z3 4.14.1 (CV 71.1%), more than half of the course's 5 M resource limit at its top.
- `stable` is the gate's word; the flag is advisory, never gating. A proof whose worst row uses more than half the limit, with a spread like that, is the shape of a proof the next solver or seed may push over: a stable verdict is evidence, not a margin.
- The step the solver finds on its own is the product's expansion; naming it (and the remainder facts) by library calls would shrink the spread. Q09's flips were seeds; here the swap is the second axis.

**Misconceptions & counter-moves**
- *"Stable means safe."* → Probe: the spread line; ask: how far is the top count from the limit?
- *"A flag fails the sweep."* → Ask: which word does the summary end with, and which line says advisory?

### K4 [why] — out of resources is not false
**viva:** yes · **strand:** S11 · **tags:** `resource-limits`, `brittleness` · **backward-edge:** Q06 (resource limits and verdict kinds)

Two one-step nonlinear proofs below: the first claims a true fact, the second a false one. The run reports an error for each. Why are the two errors different kinds of evidence, and which one tells you something about the claim itself? What does a sweep of the file report, and why does a seed sweep never turn a resource error into a refutation?

```rust
use vstd::prelude::*;

verus! {

// A true fact, left to one nonlinear step over a variable modulus.
pub proof fn lemma_beacon_true(m: int, t: int, l: int, d: int)
    requires
        m > 1,
        t % m == l % m,
    ensures
        (d + (m + 1) * t) % m == (d + l) % m,
{
    assert((d + (m + 1) * t) % m == (d + l) % m) by (nonlinear_arith)
        requires
            m > 1,
            t % m == l % m,
    ;
}

// A false fact, left to one nonlinear step.
pub proof fn lemma_beacon_false(m: int, t: int)
    requires
        m > 1,
        t > 0,
    ensures
        m * t == t,
{
    assert(m * t == t) by (nonlinear_arith)
        requires
            m > 1,
            t > 0,
    ;
}

} // verus!
```

**Target insights**
- The first error is `Resource limit (rlimit) exceeded`: the solver ran out of its budget without an answer. The fact is true; the solver could not find the proof within the limit. The second is `assertion failed`: the solver found that the fact can be false (here at once, a few hundred units).
- A resource error says "not found in budget", never "false": the course counts it as failing at the pin (it is not a proof), and it is no counterexample either. Only the second error refutes something.
- A sweep re-runs each seed: the file fails on every seed (the false fact fails each time); a true fact that runs out of resources on every seed is no more refuted for it. The repair of a resource error is a proof that states its facts (split, scoped, a library call), never a raised limit.

**Misconceptions & counter-moves**
- *"Both lemmas are false."* → Ask: evaluate the first at m = 3, t = 1, l = 4, d = 0.
- *"Raise the rlimit and it is proved."* → Ask: what does a raised limit prove about the next solver version?

### K5 [predict] — one clause more
**viva:** yes (verifier-refereed predict) · **strand:** S12 · **tags:** `frozen-statements`, `contract-allowlist` · **backward-edge:** Q07 (`specfreeze --against` in a contract's acceptance)

You committed the statement `HarborMax` (left, with no body). A co-developer delivers the file on the right: a body, and one `requires` clause more. The delivery verifies. **Predict** what `scripts/specfreeze --against <your committed file> <delivered file>` reports: no change, or a changed statement, and why.

```dafny
module HarborProbe {
  // The committed statement.
  method HarborMax(a: nat, b: nat) returns (r: nat)
    ensures r >= a && r >= b && (r == a || r == b)
}
```

```dafny
module HarborProbe {
  // The delivered file: a body, and one clause more.
  method HarborMax(a: nat, b: nat) returns (r: nat)
    requires a != b
    ensures r >= a && r >= b && (r == a || r == b)
  {
    if a > b {
      r := a;
    } else {
      r := b;
    }
  }
}
```

**Target insights**
- `freeze-changed — HarborProbe.HarborMax`: an added `requires` is a changed statement. The freeze compares the signature and every clause, so a clause added is as visible as a clause removed.
- The added clause makes the claim weaker for every caller: it says nothing when `a == b`, the case the body's `else` branch handles anyway. A contract that lets the co-developer prove a weaker statement has given away the statement, which is the learner's work.
- The delivery verifies: verification never notices a weakened statement. Only the comparison with the committed snapshot does, which is why the capstone commits its statements before any run.

**Misconceptions & counter-moves**
- *"A `requires` is only an assumption, not part of the claim."* → Ask: what does the delivered lemma promise a caller with `a == b`?
- *"It verifies, so the contract held."* → Probe: the freeze run; ask: which acceptance line fails?

### K6 [connect] — a statement no input meets
**viva:** yes · **strand:** S12 · **tags:** `vacuity`, `witnesses`, `gate-design` · **backward-edge:** Q03 (vacuity: a contradictory precondition proves anything)

The two lemmas below verify in both languages, the second one with `false` as its conclusion. Connect this to Q03: what makes them verify? Then to gate v2: which class of the cheat taxonomy is this, which instrument would decide it, and why does gate v2 answer `UNKNOWN` on it rather than `PASS`? module LanternProbe {

  lemma LanternBound(x: nat)
    requires x > 5 && x < 3
    ensures x == 100
  {
  }

  // The swap-to-false probe: the conclusion replaced by false.
  lemma LanternSwapped(x: nat)

  }

### K7 [transfer] — a gate that passed every control
**viva:** yes · **strand:** S13 · **tags:** `statistics`, `grader-inflation` · **backward-edge:** Q09 (a false-positive rate with its Wilson interval)

Your gate v2 fails none of the 4 controls of its adversarial set. A colleague writes "false-positive rate: 0%" in a report and moves on. Transfer Q09's lesson to Lab 3: what interval goes beside that 0%, what would 20 controls give, and how does the false-positive interval change what you may say about a cheat rate the same gate measured? What would one false positive among 4 do?

**Target insights**
- 0 of 4 gives the 95% Wilson interval [0, 0.49]: the data allow a gate that fails up to about half of all healthy deliveries. 0 of 20 gives [0, 0.16]. One of 4 gives about [0.05, 0.70].
- A cheat rate the gate measured is a count of FAILs among claims; with a false-positive rate that may be near half, part of that count may be healthy deliveries the gate failed: the cheat rate's upper end is inflated by up to the false-positive interval's upper end, so the pre-registration states it as a caveat.
- The interval is computed with `fvh.stats.wilson_interval`, never re-derived; more controls, not more confidence in the gate's design, shrink it.

**Misconceptions & counter-moves**
- *"No false positive means the gate has none."* → Probe: the first call; ask: what is the upper end?
- *"The cheat rate is exact, it is a count."* → Ask: which of those FAILs could be controls in disguise, and how many could the interval allow?

### PP1 — parallel to Q18.H1d (a remainder step named by the library)
**Isolates:** `brittleness`, `proof-splitting`

Casting out nines in base 10, with the two library modules Q18's Dafny file imports.

```dafny
module PP1 {
  import DivMod = Std.Arithmetic.DivMod
  import Mul = Std.Arithmetic.Mul

  // The value of decimal digits, lowest first.
  function TenValue(s: seq<nat>): nat
    decreases |s|
  {
    if |s| == 0 then 0 else s[0] + 10 * TenValue(s[1..])
  }

  // The plain sum of the digits.
  function TenSum(s: seq<nat>): nat
    decreases |s|
  {
    if |s| == 0 then 0 else s[0] + TenSum(s[1..])
  }

  // PP1: casting out nines. Prove it by induction, each step's facts named
  // and each one a library call or an assertion, stable under
  // `scripts/vcheck --module Q18 --brittleness --solvers <file>`.
  lemma NinesRule(s: seq<nat>)
    ensures TenValue(s) % 9 == TenSum(s) % 9
    decreases |s|
}
```

### PP2 — parallel to Q18.H1v (instances named, one at a time)
**Isolates:** `brittleness`, `proof-splitting`

The value modulo 9 of decimal digits, from the top digit down; the code and the invariant are given, the loop body's proof block is the hole.

```rust
use vstd::prelude::*;
use vstd::arithmetic::div_mod::*;

verus! {

/// The value of decimal digits, lowest first.
pub open spec fn ten_value(s: Seq<u8>) -> nat
    decreases s.len(),
{
    if s.len() == 0 { 0 } else { s[0] as nat + 10 * ten_value(s.drop_first()) }
}

/// PP2: the value modulo 9, from the top digit down. The code and the invariant are
/// given; write the loop body's proof block, each instance named (no `broadcast use`),
/// stable under `scripts/vcheck --module Q18 --brittleness <file>`.
pub fn nines_rem(v: &Vec<u8>) -> (r: u8)
    ensures
        r as nat == ten_value(v@) % 9,
{
    let n = v.len();
    let mut r: u8 = 0;
    let mut i: usize = n;
    while i > 0
        invariant
            i <= n,
            n == v@.len(),
            r < 9,
            r as nat == ten_value(v@.subrange(i as int, n as int)) % 9,
        decreases i,
    {
        i = i - 1;
        let x = v[i];
        let s: u16 = x as u16 + r as u16;
        let r2: u8 = (s % 9) as u8;
        proof {
            #[verifier::proof_note("PP2")] assume(false);  // write the proof here
        }
        r = r2;
    }
    proof {
        assert(v@.subrange(0, n as int) =~= v@);
    }
    r
}

} // verus!
```
**Done =** `scripts/vcheck --module Q18 <file>` prints `verified` with `0 holes, 0 errors`, and `scripts/vcheck --module Q18 --brittleness <file>` ends with `stable`, with no `broadcast use` and no `rlimit` attribute.

**Author-verified (2026-10-11, the course pins):** as shipped, the file verifies with exactly one hole (`hole assume PP2`); a proof block that names the suffix's unfolding and two library lemmas' instances verifies (3 verified, 0 holes) and is stable on seeds 1–3.

**Diagnostic.** If PP2 closes but H1v does not, compare the moduli: what does the remainder step need that is the same in both, and what is only a different constant? If PP2 times out, ask: which fact did you leave to a broadcast?
