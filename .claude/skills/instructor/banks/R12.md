### K1 [reconstruct] — four doors, one subject
**viva:** yes · **tags:** `exit-codes-and-doors`, `verdict-reading`, `json-verdicts` · **backward-edge:** R01 (a command names its target and its stage)

An editor shows a red squiggle under a postcondition, a terminal run of `scripts/vcheck` prints a summary line, a program receives a JSON record, and a language-server log holds a `publishDiagnostics` notification. Reconstruct what each of the four doors is bound to (which bytes, which options, which declarations), which fields each one carries that the others drop, and which of them can support the claim "this file is done". Use the run below: one false lemma, seen through two doors.

```dafny
module R12_BankDoors {
  // A claim that is false for n == 1.
  lemma DoorClaimBankR12(n: nat)
    requires n <= 1
    ensures n == 0
  {
  }
}
```

**Target insights**
- One verification subject, four views. The editor door is bound to a buffer and its document version, which can differ from the committed bytes; the command line names its target and options explicitly; JSON is the same native run with its fields kept as data; the language server reports per URI and version, incrementally. None of them is a second proof oracle.
- The summary line and the JSON record describe the same run: `failed`, 62 verified tasks (the given layers'), 0 holes, one error. The JSON keeps what the line drops: `stage` (`verify`), `exit_code`, the per-symbol status of the probe's own lemma (`failed`) among 61 entries (the other 60 are the given layers'), and each diagnostic with its severity (`error`, `related`), file, line and column.
- Only the full gate on the committed target supports "done": it checks every declaration, counts unfinished holes and audits trust. A green squiggle-free buffer, a selected symbol or a parsed JSON record each answers a smaller question.
- A program should read the JSON door, never search the summary text for the word `verified`: the line's words are for people, the fields are for code.

**Misconceptions & counter-moves**
- *"The editor and the terminal disagree, so one of them is wrong."* → Ask: which bytes did each one send, and were they the same file at the same version?
- *"`exit_code` 4 means four errors."* → Ask: where in the record is the number of errors, and what does the exit code report instead?
- *"62 verified means the lemma is nearly proved."* → Ask: whose declarations are the 62, and what does `per_symbol` say about `R12_BankDoors.DoorClaimBankR12`?

### K2 [predict] — three selections and one full run
**viva:** yes (verifier-refereed predict) · **tags:** `fast-channel`, `verdict-reading`, `requires-ensures` · **backward-edge:** R08 (a client of an interface knows only its contract)

The file below has a true lemma, a false lemma, and a lemma that calls the false one. Predict the verdict of each of four runs, in each language: `--symbol` on the true lemma, on the caller, on the false lemma, and the full file. Commit all eight before any run.

```dafny
module R12_BankScope {
  lemma SolidBankR12(n: nat)
    ensures n + 0 == n
  {
  }

  // False: n == 0 is a counterexample.
  lemma ShakyBankR12(n: nat)
    ensures n > 0
  {
  }

  // Relies on ShakyBankR12's contract only.
  lemma LeanerBankR12(n: nat)
    ensures n + 1 > 0
  {
    ShakyBankR12(n + 1);
  }
}
```

```rust
    ensures
        n + 1 > 0,
{

}

} // verus!
```

**Target insights**
- **Answer:** in both languages, the true lemma's selection verifies, the caller's selection verifies, the false lemma's selection fails, and the full run fails (Dafny: 64 verified, 1 error; Verus: 2 verified, 1 error).
- A selected run checks the selected declaration's own obligations. The caller's obligation is the callee's precondition (none) plus its own postcondition from the callee's ensures (`n + 1 > 0`): both hold whether or not the callee's proof does, so the caller is green on its own.
- The caller's green is real and narrow: it proves "if `ShakyBankR12` holds, so does mine". The full run is what reports that `ShakyBankR12` is false, and so that the caller's conclusion rests on an unproved fact.
- A profiler or a fast loop that records selected greens must record the selected symbol with each result; a report that drops it turns three greens into a false claim about the file.

**Misconceptions & counter-moves**
- *"The caller must fail, because it uses a false lemma."* → Ask: which obligations does the verifier generate for the caller, and does any of them mention the callee's body?
- *"The full run fails twice, once for each lemma that depends on the false one."* → Ask: how many errors does the full run print, and at which declaration?
- *"Three of four runs are green, so the file is mostly done."* → Ask: which single run covers the file, and what does it say?

### K3 [why] — null is not zero, and an empty stream is not success
**viva:** yes · **tags:** `json-verdicts`, `unavailable-not-zero`, `verdict-reading` · **backward-edge:** R05 (obligations are data, and an unavailable value is not a result)

The file below names a function that does not exist. Its JSON record reports `"verified_count": null`. Explain why a parser must keep that `null` rather than store `0`, why it must reject `true` where a count is expected even though Python accepts `True + 1`, and why an empty stream of results must not be reported as "every task succeeded". What goes wrong downstream in each case?

```dafny
module R12_BankCount {
  lemma CountClaimBankR12(n: nat)
    ensures UnknownBankR12(n) == n
  {
  }
}
```

**Target insights**
- The run stopped at resolution (`stage: resolve`, `exit_code` 2): no obligation was generated, so there is no count to report. `null` says "not measured"; `0` would say "measured, and nothing verified", a different and false statement about a run that never reached the solver.
- A consumer that averages or sums counts across a batch turns a stored `0` into a measurement: the run looks like a verified-nothing proof attempt, and a later comparison of search regimes counts it on the wrong side.
- `True` is an `int` in Python (`isinstance(True, int)`), so a careless check lets `true` through as the count 1. The schema says count, not flag; rejecting a Boolean keeps a malformed record from becoming a one-task success.
- An empty stream is an empty observation set. "No failure was reported" is not "every task succeeded": the tasks may never have run, the stream may have been truncated, or the writer may have crashed. A parser reports what it read, with its line numbers, and leaves acceptance to a separate consumer.

**Misconceptions & counter-moves**
- *"`null` and `0` are the same in a report; nobody verified anything either way."* → Ask: in which of the two runs did the solver run, and which question would a learner ask next in each case?
- *"Rejecting `true` is pedantic; it is obviously one."* → Ask: which program wrote `true` there, and what else might it have got wrong?
- *"If the stream is empty, nothing failed."* → Ask: how would the parser tell an empty batch from a writer that died before its first line?

### K4 [predict] — a decreases site at its placeholder
**viva:** yes (verifier-refereed predict) · **tags:** `hint-sites`, `termination-measure`, `verdict-reading` · **backward-edge:** R06 (a termination measure is part of an induction)

A `decreases` site (the D63 site kind) ships as `/*R12_DECREASES:<name>*/ (0 as int)`: a placeholder measure that the engine, or a learner, replaces with one expression. Below, the same recursive lemma twice, in each language: once with the site at its placeholder, once with the site filled with the parameter `n`. Predict both verdicts in each language, and for a failure the kind of error.

```dafny
module R12_BankMeasure {
  function HalvingsBankR12(n: nat): nat
  {
    if n == 0 then 0 else 1 + HalvingsBankR12(n / 2)
  }

  // A decreases site left at its placeholder.
  lemma HalvingsBoundBankR12(n: nat)
    ensures HalvingsBankR12(n) <= n
    decreases /*R12_DECREASES:m1*/ (0 as int)
  {
    if n > 0 {
      HalvingsBoundBankR12(n / 2);
    }
  }
}
```

**Target insights**
- **Answer:** the placeholder fails in both languages, at the recursive call (Dafny: `decreases clause might not decrease`; Verus: `could not prove termination`); the filled site verifies in both.
- The placeholder is a constant. A recursive call must make its measure strictly smaller, and `0` is never smaller than `0`, so the call's termination obligation fails whatever the body proves. That is by design: an unfilled `decreases` site fails at verification, never silently passes, so a search engine cannot score an unfilled candidate as solved.
- The postcondition is not the failing obligation. With the placeholder, the induction hypothesis the call provides is itself unjustified, which is why the verifier reports the call, not the `ensures`.
- The filled measure is the argument an induction rests on: `n / 2 < n` for `n > 0`. A lemma with a recursive call is an induction only when some measure goes down along the call; R06's manual inductions carried that measure implicitly in `decreases |s|` or the structure of the datatype.

**Misconceptions & counter-moves**
- *"The placeholder only matters at run time; a lemma does not run."* → Ask: what does the verifier have to prove about the recursive call before it can use the call's postcondition?
- *"Any expression that type-checks fills the site."* → Ask: which expression would make the call's obligation false again (`n + 1`, a constant)?
- *"The error should name the postcondition, because that is what is false."* → Ask: is the postcondition false?

### K6 [why] — stage before observe
**viva:** yes · **tags:** `agent-output-is-data`, `node-accounting` · **backward-edge:** R09 (consume or roll back: an attempt is recorded whether or not it succeeds)

The search engine stages a request (choosing a parent and recording a generated node) before the trusted executor applies it and observes the native outcome. Explain why the node is reserved first, what a malformed model output costs, what must happen when the transport fails between staging and observing, and why the only stopping condition called "solved" is a full original-task gate.

**Target insights**
- Staging consumes one width slot and records the generated node before any native work. A proposal is an expense the moment it is requested: if nodes were counted only on success, a regime that produces many malformed outputs would look cheaper than it is, and budgets would stop measuring work.
- Malformed output consumes its node and its model call, and makes no native tool call. It is recorded as malformed, not retried for free, not dropped.
- A transport failure keeps the staged request identifiable and propagates the frozen infrastructure status. Erasing it and staging a replacement would give that run an unrecorded extra attempt, which is exactly the best-of-many inflation a matched-budget comparison exists to prevent.
- Observation binds one pending proposal to one trusted outcome for one file revision; it refuses an observation with nothing pending, a second proposal while one is pending, or feedback about a different revision. The model never supplies a Result; the executor does.
- "Solved" is a full, zero-hole, zero-finding gate on the original task's statements and source binding. A heuristic score of zero obligations, a selected green or a model's claim is search guidance, never acceptance. This is R09's cursor discipline at the level of a search: the attempt is consumed, and only a checked success commits.

**Misconceptions & counter-moves**
- *"A malformed output never reached the verifier, so it should not count."* → Ask: what did it cost, and what would a regime that produced only malformed outputs look like in a table that did not count them?
- *"On a transport error, just try again."* → Ask: how many attempts does the run's record show afterwards, and how many did it make?
- *"If the obligation count reaches 0, the engine can stop."* → Ask: which instrument has not yet run, and what can it still reject (a hole, a finding, a changed statement)?

**Verifier probe** — none: this is the engine's accounting, examined in H4py's acceptance cases rather than by a toy proof. Ask the learner to trace one malformed output and one transport failure through the lifecycle diagram of §4 and to name the record each leaves.
