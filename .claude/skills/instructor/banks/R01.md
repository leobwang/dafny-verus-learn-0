### K1 [reconstruct] — who owes what at a call
**viva:** yes · **tags:** `requires-ensures`, `exec-overflow`, `verdict-reading` · **backward-edge:** none

Reconstruct, from one signature, the three facts a call involves: what the caller must establish, what the body may assume, and what the caller receives afterwards. Then read the probe. `StepDown` / `step_down` returns one less than a positive number. One caller keeps the precondition, one does not; a second file removes the precondition and keeps the body. Where does each language report the problem, and what does the location tell you about whose obligation it was?

```dafny
module R01_BankStepDown {
  // One less than a positive number.
  method StepDown(n: nat) returns (m: nat)
    requires n > 0
    ensures m + 1 == n
  {
    m := n - 1;
  }

  // A caller that keeps the precondition.
  method StepDownFive()
  {
    var m := StepDown(5);
    assert m == 4;
  }

  // A caller that does not.
  method StepDownZero()
  {
    var m := StepDown(0);
  }
}
```
```dafny
module R01_BankStepDownOpen {
  // The same body with the precondition removed.
  method StepDown(n: nat) returns (m: nat)
    ensures m + 1 == n
  {
    m := n - 1;
  }
}
```

```rust
    requires

fn step_down_five() {
    let m = step_down(5);
    assert(m == 4);
}

}
```


**Target insights**
- The precondition is the caller's obligation and the body's assumption. `StepDownZero` fails *at its call* (Dafny: "a precondition for this call could not be proved", with a `related:` line pointing back to the `requires`; Verus: "precondition not satisfied" at the call), not inside `StepDown`: the body is never blamed for a caller's argument.
- The postcondition is the body's obligation and the caller's fact. `StepDownFive` asserts `m == 4` with no view of the body: `m + 1 == 5` is enough, and that is everything the caller knows.
- Remove the `requires` and the obligation moves into the body: `n - 1` on a `nat` (Dafny) or a `u32` (Verus) is no longer justified for `n == 0`. Dafny reports a subset-constraint violation on `nat`, Verus a possible underflow. The same expression is safe or unsafe according to what the contract lets the body assume.

**Misconceptions & counter-moves**
- *"`requires` is a runtime check the function performs."* → Ask: which line of `StepDown`'s body tests `n > 0`, and where did the verifier report the bad call?
- *"A stronger precondition is always the safe fix."* → Ask: with `requires n > 5`, which given caller now fails, and who decided that 5 is no longer a legal argument?
- *"The caller knows `m == n - 1` because that is what the body does."* → Ask: point to the line that tells the caller anything; what would it know if the body were replaced by another one with the same `ensures`?

### K2 [predict] — four operations on a byte
**viva:** yes (verifier-refereed predict) · **tags:** `nat-vs-machine-int`, `exec-overflow`, `verdict-reading` · **backward-edge:** none

Four executable bodies over 8-bit values, one per label: Dafny over the bounded `newtype Octet` (0 to 255), Verus over `u8`. [a] the average `(x + y) / 2` with both inputs below 128; [b] `x * 2` with `x <= 128`; [c] `x - y` under `y <= x`; [d] `255 - x` with no precondition. No body has a postcondition: the only obligations are the range obligations of the operations. Predict which labels fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>` (or `none`).

```dafny
module R01_BankOctet {
  newtype Octet = x: int | 0 <= x < 256

  // [a] the average of two values below 128
  method OctetA(x: Octet, y: Octet) returns (r: Octet)
    requires x < 128 && y < 128
  {
    r := (x + y) / 2;
  }

  // [b] doubling a value up to 128
  method OctetB(x: Octet) returns (r: Octet)
    requires x <= 128
  {
    r := x * 2;
  }

  // [c] a difference under its guard
  method OctetC(x: Octet, y: Octet) returns (r: Octet)
    requires y <= x
  {
    r := x - y;
  }

  // [d] the complement, with no precondition
  method OctetD(x: Octet) returns (r: Octet)
  {
    r := 255 - x;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// [a] the average of two values below 128
fn octet_a(x: u8, y: u8) -> u8
    requires
        x < 128,
        y < 128,
{
    (x + y) / 2
}

// [b] doubling a value up to 128
fn octet_b(x: u8) -> u8
    requires
        x <= 128,
{
    x * 2
}

// [c] a difference under its guard
fn octet_c(x: u8, y: u8) -> u8
    requires
        y <= x,
{
    x - y
}

// [d] the complement, with no precondition
fn octet_d(x: u8) -> u8 {
    255 - x
}

} // verus!
```

**Target insights**
- Every intermediate result of a bounded operation must lie in the type's range, not just the final value. In [a] the intermediate `x + y` is at most 254, so it fits; in [b] `x * 2` reaches 256 at `x == 128`, one past the range, so the multiplication itself is the failing obligation.
- [c] is justified by its guard: `y <= x` keeps `x - y` at or above 0. [d] needs no guard at all: `255 - x` lies in 0..255 for every byte. A missing precondition is a problem only where some admitted input breaks an operation.
- Dafny phrases the obligation as a newtype constraint ("result of operation might violate newtype constraint for 'Octet'"), Verus as "possible arithmetic underflow/overflow". Both point at the operation, not at a return or a contract. The answer: `D:FAILS b V:FAILS b`.

**Misconceptions & counter-moves**
- *"Only the returned value has to fit."* → Ask: which operator in [b] produces 256, and does anything after it get a chance to bring it back into range?
- *"Dafny's integers are mathematical, so Dafny cannot overflow."* → Ask: what type do `x` and `x * 2` have in `OctetB`, and what does a `newtype` with a range add to every operation on it?
- *"[d] needs `requires x <= 255`."* → Ask: which values can an `Octet` (a `u8`) hold, and which of them makes `255 - x` negative?

**Verifier probe** (the answer: `D:FAILS b V:FAILS b`)
(Dafny 4.11.0; line 15 is [b]'s `x * 2`:)
```

instructor/scratch/probe.dfy:15:12: error: result of operation might violate newtype constraint for 'Octet'
```
(Verus 0.2026.09.27; line 19 is [b]'s `x * 2`:)
```
vcheck: instructor/scratch/probe.rs [verus, learner loop]: failed — 3 verified, 0 holes, 1 error
instructor/scratch/probe.rs:19:5: error: possible arithmetic underflow/overflow
```
Follow-up for a correct prediction: give two different repairs of [b], one that changes the contract and one that changes only the body's types, and say which one a caller of `OctetB` notices. (A stronger `requires x < 128` removes the call `OctetB(128)` from what callers may make; computing in a wider type keeps every caller but changes the result type, or needs its own bound on the way back.)

### K4 [predict] — which callers receive the fact
**viva:** yes (verifier-refereed predict) · **tags:** `lemma-call`, `induction-as-recursion` · **backward-edge:** none

`Spaced(s)` / `spaced(s)` puts a dash after every character, and `SpacedLength` proves its length is `2 * |s|` by recursion (Dafny prints `{:induction false}` on it). Three clients assert the length for an arbitrary `s`: [x] calls nothing; [y] calls the lemma on the tail `s[1..]` (`s.drop_first()`), for a non-empty `s`; [z] calls the lemma on `s` itself. Predict which clients fail. Answer form `D:FAILS <labels> V:FAILS <labels>` (or `none`).

```dafny
module R01_BankSpaced {
  // Every character followed by a dash.
  function Spaced(s: seq<char>): seq<char>
    decreases |s|
  {
    if |s| == 0 then [] else [s[0], '-'] + Spaced(s[1..])
  }

  lemma {:induction false} SpacedLength(s: seq<char>)
    ensures |Spaced(s)| == 2 * |s|
    decreases |s|
  {
    if |s| > 0 {
      SpacedLength(s[1..]);
    }
  }

  // [x] no call
  method SpacedClientX(s: seq<char>)
  {
    assert |Spaced(s)| == 2 * |s|;
  }

  // [y] a call on the tail
  method SpacedClientY(s: seq<char>)
    requires |s| > 0
  {
    SpacedLength(s[1..]);
    assert |Spaced(s)| == 2 * |s|;
  }

  // [z] a call on the argument itself
  method SpacedClientZ(s: seq<char>)
  {
    SpacedLength(s);
    assert |Spaced(s)| == 2 * |s|;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// Every character followed by a dash.
spec fn spaced(s: Seq<char>) -> Seq<char>
    decreases s.len(),
{
    if s.len() == 0 {
        Seq::<char>::empty()
    } else {
        seq![s[0], '-'] + spaced(s.drop_first())
    }
}

proof fn lemma_spaced_length(s: Seq<char>)
    ensures
        spaced(s).len() == 2 * s.len(),
    decreases s.len(),
{
```

### K9 [why] — why the Dafny hand proof ships a lever

`Dots(n)` / `dots(n)` is a row of `n` dots. Two Dafny copies of the same lemma, `|Dots(n)| == n`, both with empty bodies: one under R01's default induction, one with `{:induction false}` printed. ```dafny

```dafny
  // n dots in a row.
  function Dots(n: nat): seq<char>
    decreases n
  {
    if n == 0 then [] else ['.'] + Dots(n - 1)
  }

  // Default induction, empty body.
  lemma DotsLengthAuto(n: nat)
    ensures |Dots(n)| == n
  {
  }

  // The lever printed on the lemma, empty body.
  lemma {:induction false} DotsLengthManual(n: nat)
    ensures |Dots(n)| == n
    decreases n
  {
  }
}
```

```rust
// n dots in a row.

    decreases n,
{
    if n == 0 {
        Seq::<char>::empty()
    } else {
        seq!['.'] + dots((n - 1) as nat)
    }
}

// Empty body: Verus has no automatic induction.

    ensures
        dots(n).len() == n,
    decreases n,

}

```
```rust

verus! {

// n dots in a row.
spec fn dots(n: nat) -> Seq<char>
    decreases n,
{
    if n == 0 {
        Seq::<char>::empty()
    } else {
        seq!['.'] + dots((n - 1) as nat)
    }
}

// The call on the smaller argument is the induction hypothesis.
proof fn lemma_dots_length(n: nat)
    ensures
        dots(n).len() == n,
    decreases n,
{
    if n > 0 {
        lemma_dots_length((n - 1) as nat);
    }
}

} // verus!
```

**Target insights**
- Dafny tries induction on a lemma's arguments by itself: `DotsLengthAuto` verifies with an empty body, so the "proof" is the tool's, not the writer's. With the lever printed, the same empty body fails: the hypothesis must now be called.
- Verus never inducts: its empty body fails, and the call on `n - 1` (the hypothesis, legitimate by `decreases n`) closes it. The two languages ask for the same proof only when Dafny's automation is switched off.
- An exercise whose empty body verifies measures nothing. The course's admission check runs every hole's empty body at maximal automation and requires it to fail, or names the shipped lever that makes it fail. ### K11 [transfer] — an implication under a quantifier
**viva:** yes · **tags:** `false-friends`, `quantifiers` · **backward-edge:** none

On the string `['y', 'x']`, three bounded universal claims about positions: [p] every `'x'` sits after position 0 (`s[i] == 'x' ==> i > 0`); [q] every position holds an `'x'` after position 0 (`s[i] == 'x' && i > 0`); [r] no position holds a `'z'` (`s[i] == 'z' ==> false`). Read the two languages' syntax for the same three formulas, then the results. Transfer the reading to a specification you will write later: which connective does "every `'x'` is …" need, and what does an implication say about the positions where its premise is false?

```dafny
module R01_BankImplies {
  // [p] every 'x' sits after position 0
  lemma ImpliesP()
  {
    var s := ['y', 'x'];
    assert forall i | 0 <= i < |s| :: s[i] == 'x' ==> i > 0;
  }

  // [q] every position holds an 'x' after position 0
  lemma ImpliesQ()
  {
    var s := ['y', 'x'];
    assert forall i | 0 <= i < |s| :: s[i] == 'x' && i > 0;
  }

  // [r] an implication whose premise never holds
  lemma ImpliesR()
  {
    var s := ['y', 'x'];
    assert forall i | 0 <= i < |s| :: s[i] == 'z' ==> false;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// [p] every 'x' sits after position 0
proof fn implies_p() {
    let s = seq!['y', 'x'];
    assert(forall|i: int| 0 <= i < s.len() ==> (s[i] == 'x' ==> i > 0));
}

// [q] every position holds an 'x' after position 0
proof fn implies_q() {
    let s = seq!['y', 'x'];
    assert(forall|i: int| 0 <= i < s.len() ==> (s[i] == 'x' && i > 0));
}

// [r] an implication whose premise never holds
proof fn implies_r() {
    let s = seq!['y', 'x'];
    assert(forall|i: int| 0 <= i < s.len() ==> (s[i] == 'z' ==> false));
}

} // verus!
```

**Target insights**
- "Every `'x'` is after 0" is an implication under the quantifier: positions that hold no `'x'` satisfy it vacuously. [p] holds. Replacing `==>` by `&&` claims something about *every* position, and position 0 holds `'y'`, so [q] fails.
- An implication whose premise is false everywhere is true: [r] holds, and says only that no `'z'` occurs. A vacuous truth is still a truth, which is how a precondition that nothing can satisfy makes every postcondition true.
- The syntax differs while the meaning matches: Dafny writes the range after `|` and the body after `::`; Verus writes one `==>` for the range and parenthesises the body. The parentheses make the grouping explicit; read every formula by its grouping (which part is the premise, which the conclusion), never by the order in which its symbols appear.

**Misconceptions & counter-moves**
- *"`==>` and `&&` say the same thing when the premise is true."* → Ask: at position 0, what does each formula require?
- *"[r] should fail: `false` can never hold."* → Ask: at which position is `s[i] == 'z'` true, and what does an implication demand when its premise is false?
- *"A bounded `forall` checks the positions one by one at run time."* → Ask: is this assertion compiled? What did the verifier prove, and over how many positions?
