### K1 [reconstruct] — what `:-` and `?` need from a type
**viva:** yes · **tags:** `error-propagation`, `verdict-reading` · **backward-edge:** none

Reconstruct, from memory, what `var v :- x;` asks of the type of `x` in Dafny, and what `let v = x?;` asks of `x` and of the enclosing function in Rust. Then read the probes: in each language the first version is refused before any proof runs. Which member or which type is missing, and what does the second version add?

```dafny
module R09_BankStep {
  // A failure-compatible type needs all three members; this one lacks one.
  datatype StepBankR09 = Done(n: nat) | Stuck(at: nat)
  {
    predicate IsFailure()
    {
      Stuck?
    }

    function Extract(): nat
      requires Done?
    {
      n
    }
  }

  method TwiceBankR09(x: StepBankR09) returns (y: StepBankR09)
  {
    var v :- x;
    y := Done(2 * v);
  }
}
```
```dafny
module R09_BankStepFull {
  // The same type with the third member: :- now has a failure to return.
  datatype StepBankR09 = Done(n: nat) | Stuck(at: nat)
  {
    predicate IsFailure()
    {
      Stuck?
    }

    function PropagateFailure(): StepBankR09
      requires Stuck?
    {
      Stuck(at)
    }

    function Extract(): nat
      requires Done?
    {
      n
    }
  }

  method TwiceBankR09(x: StepBankR09) returns (y: StepBankR09)
    ensures x.Stuck? ==> y == x
    ensures x.Done? ==> y == Done(2 * x.n)
  {
    var v :- x;
    y := Done(2 * v);
  }
}
```
```rust

verus! {

// `?` on an Option inside a function that returns a Result.
fn twice_bank_r09(x: Option<u32>) -> (y: Result<u32, usize>)
    requires
        x is Some ==> x->Some_0 <= 1000,
{
    let v = x?;
    Ok(2 * v)
}

} // verus!
```
```rust
use vstd::prelude::*;

verus! {

// `?` on a Result whose error type is the function's own.
fn twice_bank_r09(x: Result<u32, usize>) -> (y: Result<u32, usize>)
    requires
        x is Ok ==> x->Ok_0 <= 1000,
    ensures
        x is Err ==> y == x,
        x is Ok ==> y == Ok::<u32, usize>((2 * x->Ok_0) as u32),
{
    let v = x?;
    Ok(2 * v)
}

} // verus!
```

**Target insights**
- Dafny's `:-` is a protocol, not a type: the right-hand side's type must declare `IsFailure()`, `PropagateFailure()` and `Extract()`. On a failure the method returns `x.PropagateFailure()` as its result; on a success `v` gets `x.Extract()`. A type with two of the three is refused at resolve: there is no failure value to return.
- Rust's `?` needs the operand's error type to convert into the enclosing function's: an `Option` cannot be propagated from a function that returns a `Result`. The refusal is again at the front end (`stage resolve`), so no obligation was checked.
- Once the protocol is complete, the propagation is an ordinary return path, and the full versions' `ensures` clauses are proved on it: the failure branch returns the input's failure unchanged (`y == x`), which is exactly what the contracts state.

**Misconceptions & counter-moves**
- *"`:-` works on any datatype with an error case."* → Ask: which value does the method return on the failing branch, and which member computes it?
- *"A `stage resolve` refusal means the proof failed."* → Ask: how many obligations did the run verify, and what would a failed proof report instead?

### K2 [predict] — the write before the exit
**viva:** yes (verifier-refereed predict) · **tags:** `error-propagation`, `requires-ensures`, `ownership-and-mut-ref` · **backward-edge:** none

A tally counts every call, successful or not, and returns its input unchanged. [a] counts the call and then propagates; [b] propagates and then counts. Predict which labels fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>` (or `none`).

```dafny
module R09_BankTally {
  import opened RG_A3_Syntax

  class TallyBankR09 {
    var calls: nat
  }

  // [a] count the call, then propagate
  method CountFirstBankR09(t: TallyBankR09, x: Res<nat>) returns (r: Res<nat>)
    modifies t
    ensures t.calls == old(t.calls) + 1
    ensures r == x
  {
    t.calls := t.calls + 1;
    var v :- x;
    r := Ok(v);
  }

  // [b] propagate, then count the call
  method CountAfterBankR09(t: TallyBankR09, x: Res<nat>) returns (r: Res<nat>)
    modifies t
    ensures t.calls == old(t.calls) + 1
    ensures r == x
  {
    var v :- x;
    t.calls := t.calls + 1;
    r := Ok(v);
  }
}
```
```rust
use vstd::prelude::*;

verus! {

pub struct TallyBankR09 {
    pub calls: u64,
}

// [a] count the call, then propagate
fn count_first_bank_r09(t: &mut TallyBankR09, x: Result<u32, usize>) -> (r: Result<u32, usize>)
    requires
        old(t).calls < 1000,
    ensures
        final(t).calls == old(t).calls + 1,
        r == x,
{
    t.calls = t.calls + 1;
    let v = x?;
    Ok(v)
}

// [b] propagate, then count the call
fn count_after_bank_r09(t: &mut TallyBankR09, x: Result<u32, usize>) -> (r: Result<u32, usize>)
    requires
        old(t).calls < 1000,
    ensures
        final(t).calls == old(t).calls + 1,
        r == x,
{
    let v = x?;
    t.calls = t.calls + 1;
    Ok(v)
}

} // verus!
```

**Target insights**
- `:-` and `?` leave the method at once on a failure: whatever is written after them has not happened on that path. The count promise is unconditional, so in [b] the failing path returns with `calls` unchanged and the postcondition fails on that path.
- In [a] the write precedes the propagation, so both paths have counted. The returned value is the same in both versions (`r == x` holds on either path), which is why only one clause fails: the failure is about state, not about the result.
- The answer: `D:FAILS b V:FAILS b`. Dafny names the return path itself (line 25, the `:-`); Verus names the failed clause (line 27).

**Misconceptions & counter-moves**
- *"The propagation returns the error, so the postcondition is about the error only."* → Ask: which of the two `ensures` clauses mentions `x`, and which mentions `t`?
- *"Order inside a method does not matter to the verifier."* → Ask: on the path where `x` is a failure, which statements of [b] execute?

### K3 [predict] — which test guards which read
**viva:** yes (verifier-refereed predict) · **tags:** `verdict-reading`, `false-friends` · **backward-edge:** none

Three functions ask whether an `x` directly followed by a `y` sits at position `i`, with no precondition on `i`. They differ only in the order and the content of their tests. Predict which labels fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>`.

```dafny
module R09_BankPair {
  // Is there an "x" directly followed by a "y" at position i?

  // [a] the length test first, then both reads
  method PairAtABankR09(s: seq<char>, i: nat) returns (b: bool)
  {
    b := i + 1 < |s| && s[i] == 'x' && s[i + 1] == 'y';
  }

  // [b] the first read before any length test
  method PairAtBBankR09(s: seq<char>, i: nat) returns (b: bool)
  {
    b := s[i] == 'x' && i + 1 < |s| && s[i + 1] == 'y';
  }

  // [c] a test of i only, then both reads
  method PairAtCBankR09(s: seq<char>, i: nat) returns (b: bool)
  {
    b := i < |s| && s[i] == 'x' && s[i + 1] == 'y';
  }
}
```
```rust

verus! {

// Is there an 'x' directly followed by a 'y' at position i?

// [a] the length test first, then both reads
fn pair_at_a_bank_r09(s: &Vec<char>, i: usize) -> bool {
    i < s.len() && i + 1 < s.len() && s[i] == 'x' && s[i + 1] == 'y'
}

// [b] the first read before any length test
fn pair_at_b_bank_r09(s: &Vec<char>, i: usize) -> bool {
    s[i] == 'x' && i < s.len() && i + 1 < s.len() && s[i + 1] == 'y'
}

// [c] a test of i only, then both reads
fn pair_at_c_bank_r09(s: &Vec<char>, i: usize) -> bool {
    i < s.len() && s[i] == 'x' && s[i + 1] == 'y'
}

} // verus!
```

**Target insights**
- `&&` is short-circuit in both languages, so a read is safe exactly when the tests to its left imply its index is in range. [b] reads `s[i]` before any test; [c] tests `i < |s|`, which guards `s[i]` and not `s[i + 1]`.
- The answer: `D:FAILS b c V:FAILS b c`, each at the unguarded read: Dafny's `index out of range` (13:11 is [b]'s `s[i]`, 19:37 is [c]'s `s[i + 1]`), Verus's `precondition not satisfied` of the indexing call.
- A false friend: Dafny's [a] tests only `i + 1 < |s|` (on `nat` no addition overflows), while Verus's [a] tests `i < s.len()` first, because `i + 1` on a `usize` would itself owe an overflow obligation. The same guard in the two languages is not the same text.

**Misconceptions & counter-moves**
- *"A test anywhere in the condition protects the reads."* → Ask: in [b], which test has run when `s[i]` is evaluated?
- *"`i < |s|` protects every read near `i`."* → Ask: which index does `s[i + 1]` read, and what bound does it need?

### K4 [predict] — the guard that overflows
**viva:** yes (verifier-refereed predict) · **tags:** `nat-vs-machine-int`, `exec-overflow`, `verdict-reading` · **backward-edge:** R01 (the midpoint's overflow obligation)

Three bounded functions decide whether `used + extra` fits within `cap`; the contract is stated over mathematical integers. [a] adds and compares; [b] subtracts only what is known to fit; [c] subtracts without the first test. Predict which labels fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>`.

```dafny
module R09_BankSpend {
  newtype SpendBankR09 = x: int | 0 <= x < 0x100000000

  // Does used + extra stay within cap? Three guards.

  // [a] add first, then compare
  method RoomABankR09(used: SpendBankR09, extra: SpendBankR09, cap: SpendBankR09) returns (ok: bool)
    ensures ok == ((used as int) + (extra as int) <= cap as int)
  {
    ok := used + extra <= cap;
  }

  // [b] subtract only what is known to fit
  method RoomBBankR09(used: SpendBankR09, extra: SpendBankR09, cap: SpendBankR09) returns (ok: bool)
    ensures ok == ((used as int) + (extra as int) <= cap as int)
  {
    ok := extra <= cap && used <= cap - extra;
  }

  // [c] subtract without the first test
  method RoomCBankR09(used: SpendBankR09, extra: SpendBankR09, cap: SpendBankR09) returns (ok: bool)
    ensures ok == ((used as int) + (extra as int) <= cap as int)
  {
    ok := used <= cap - extra;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// Does used + extra stay within cap? Three guards.

// [a] add first, then compare
fn room_a_bank_r09(used: u32, extra: u32, cap: u32) -> (ok: bool)
    ensures
        ok == ((used as int) + (extra as int) <= cap as int),
{
    used + extra <= cap
}

// [b] subtract only what is known to fit
fn room_b_bank_r09(used: u32, extra: u32, cap: u32) -> (ok: bool)
    ensures
        ok == ((used as int) + (extra as int) <= cap as int),
{
    extra <= cap && used <= cap - extra
}

// [c] subtract without the first test
fn room_c_bank_r09(used: u32, extra: u32, cap: u32) -> (ok: bool)
    ensures
        ok == ((used as int) + (extra as int) <= cap as int),
{
    used <= cap - extra
}

} // verus!
```

**Target insights**
- The contract's sum is mathematical, but every operation in the body computes a value of the bounded type and owes a range obligation. [a]'s `used + extra` can exceed the type; [c]'s `cap - extra` can go below zero. Each fails at the operation, not at the comparison.
- [b] tests `extra <= cap` first, so `cap - extra` is in range, and `used <= cap - extra` decides the mathematical question exactly. The answer: `D:FAILS a c V:FAILS a c`.
- Dafny reports the newtype constraint of the result (`SpendBankR09`'s range); Verus reports `possible arithmetic underflow/overflow` on `u32`. Same obligation, two vocabularies.

**Misconceptions & counter-moves**
- *"The comparison is all the contract talks about, so only the comparison is checked."* → Ask: what is the type of `used + extra` in [a], and what must hold for it to exist?

### K9 [why] — two statements that agree with each other
**viva:** yes · **tags:** `fidelity-audit`, `prose-to-spec`, `paper-cards` · **backward-edge:** none

```dafny
module R09_BankMirror {
  import opened RG_A3_Syntax

  predicate LetterBankR09(c: char)
  {
    'a' <= c <= 'z'
  }

  // The intent: a word of letters is accepted; otherwise the error is at
  // the first non-letter. Both statements below copy a wrong reading of it.
  ghost predicate OriginalBankR09(s: seq<char>, r: Res<nat>)
  {
    (r.Ok? ==> r.value == |s|) && (r.Err? ==> r.pos == 0)
  }

  ghost predicate MirrorBankR09(s: seq<char>, r: Res<nat>)
  {
    match r
    case Ok(n) => n == |s|
    case Err(p, _) => p < 1
  }

  lemma {:induction false} BothWaysBankR09(s: seq<char>, r: Res<nat>)
    ensures OriginalBankR09(s, r) <==> MirrorBankR09(s, r)
  {
  }

  // An implementation that meets both.
  method ScanBankR09(s: seq<char>) returns (r: Res<nat>)
    ensures OriginalBankR09(s, r) && MirrorBankR09(s, r)
  {
    var i := 0;
    while i < |s|
      invariant 0 <= i <= |s|
    {
      if !LetterBankR09(s[i]) {
        r := Err(0, "not a letter");
        BothWaysBankR09(s, r);
        return;
      }
      i := i + 1;
    }
    r := Ok(|s|);
    BothWaysBankR09(s, r);
  }

  // A use-site check written from the intent: the error of "ab1" is at 2.
  method IntentBankR09()
  {
    var r := ScanBankR09(['a', 'b', '1']);
    assert r.Err? ==> r.pos == 2;
  }
```

- An implication lemma between two statements proves that they agree, nothing about either and the intent. ### K10 [connect] — what an accumulating loop owes at every exit
**viva:** yes · **tags:** `loop-invariant`, `error-propagation`, `nat-vs-machine-int` · **backward-edge:** R06 (a loop invariant must be strong enough at every exit)

`SumAllBankR09` adds a list of bounded values with checked addition, leaving with `:-` (`?`) as soon as a partial sum exceeds `cap`. The probe below verifies. The second version deletes one line, the invariant `acc as int == TotalBankR09(xs[..i])` (Verus `acc as int == total_bank_r09(xs@.subrange(0, i as int))`), and fails twice. Which two return paths fail, and why does the early exit need that invariant too?

```dafny
module R09_BankTotal {
  newtype SumBankR09 = x: int | 0 <= x < 0x100000000

  datatype FitBankR09 = Fits(v: SumBankR09) | Over
  {
    predicate IsFailure()
    {
      Over?
    }

    function PropagateFailure(): FitBankR09
      requires Over?
    {
      Over
    }

    function Extract(): SumBankR09
      requires Fits?
    {
      v
    }
  }

  // The mathematical total, summed from the back.
  ghost function TotalBankR09(xs: seq<SumBankR09>): int
  {
    if |xs| == 0 then 0 else TotalBankR09(xs[..|xs| - 1]) + xs[|xs| - 1] as int
  }

  lemma PrefixBelowBankR09(xs: seq<SumBankR09>, i: nat)
    requires i <= |xs|
    ensures TotalBankR09(xs[..i]) <= TotalBankR09(xs)
    decreases |xs|
  {
    if i < |xs| {
      assert xs[..|xs| - 1][..i] == xs[..i];
      PrefixBelowBankR09(xs[..|xs| - 1], i);
    } else {
      assert xs[..i] == xs;
    }
  }

  method AddBankR09(a: SumBankR09, b: SumBankR09, cap: SumBankR09) returns (r: FitBankR09)
    ensures r.Fits? ==> r.v <= cap && r.v as int == a as int + b as int
    ensures r.Over? ==> a as int + b as int > cap as int
  {
    if a > cap || b > cap - a {
      r := Over;
    } else {
      r := Fits(a + b);
    }
  }

  method SumAllBankR09(xs: seq<SumBankR09>, cap: SumBankR09) returns (r: FitBankR09)
    ensures r.Fits? ==> r.v <= cap && r.v as int == TotalBankR09(xs)
    ensures r.Over? ==> TotalBankR09(xs) > cap as int
  {
    var acc: SumBankR09 := 0;
    var i := 0;
    while i < |xs|
      invariant i <= |xs| && acc <= cap
      invariant acc as int == TotalBankR09(xs[..i])
    {
      assert xs[..i + 1][..i] == xs[..i];
      PrefixBelowBankR09(xs, i + 1);
      acc :- AddBankR09(acc, xs[i], cap);
      i := i + 1;
    }
    assert xs[..i] == xs;
    r := Fits(acc);
  }
}
```

### K11 [transfer] — roll back when the second step fails
**viva:** yes · **tags:** `error-propagation`, `ownership-and-mut-ref`, `frames` · **backward-edge:** R05 (read which return path an obligation names before repairing)

A given step takes one letter and moves the reader only on success. A pair reader must take two letters, and on any failure leave the reader where it started. [a] propagates both steps; [b] propagates the first and handles the second by hand. Transfer R09's transaction policy: which version keeps the promise, and why can `:-` (`?`) not express the repair?

```dafny
module R09_BankTwoStep {
  import opened RG_A3_Syntax

  class ReaderBankR09 {
    var src: seq<char>
    var at: nat
  }

  // Given: take one letter; the reader moves only on success.
  method LetterBankR09(rd: ReaderBankR09) returns (r: Res<char>)
    modifies rd
    ensures rd.src == old(rd.src)
    ensures r.Ok? ==> old(rd.at) < |rd.src| && rd.at == old(rd.at) + 1 && r.value == rd.src[old(rd.at)]
    ensures r.Err? ==> rd.at == old(rd.at) && r.pos == old(rd.at)
  {
    if rd.at < |rd.src| && 'a' <= rd.src[rd.at] <= 'z' {
      r := Ok(rd.src[rd.at]);
      rd.at := rd.at + 1;
    } else {
      r := Err(rd.at, "expected a letter");
    }
  }

  // [a] two propagations
  method PairABankR09(rd: ReaderBankR09) returns (r: Res<(char, char)>)
    modifies rd
    ensures rd.src == old(rd.src)
    ensures r.Err? ==> rd.at == old(rd.at)
  {
    var x :- LetterBankR09(rd);
    var y :- LetterBankR09(rd);
    r := Ok((x, y));
  }

  // [b] the second failure handled by hand
  method PairBBankR09(rd: ReaderBankR09) returns (r: Res<(char, char)>)
    modifies rd
    ensures rd.src == old(rd.src)
    ensures r.Err? ==> rd.at == old(rd.at)
  {
    var start := rd.at;
    var x :- LetterBankR09(rd);
    var second := LetterBankR09(rd);
    if second.Err? {
      rd.at := start;
      r := Err(second.pos, second.msg);
      return;
    }
    r := Ok((x, second.value));
  }
}
```
