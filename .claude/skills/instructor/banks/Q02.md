### K1 [reconstruct] — the three obligations of a loop invariant
**viva:** yes · **strand:** S4 · **tags:** `loop-invariant`, `verdict-reading`, `assume-after-failure` · **backward-edge:** none

Reconstruct, in both languages, every obligation that a `while` loop with an invariant hands the verifier, and what the verifier knows on the first line after the loop. Then read the probe's two errors: which obligation does each name, why is neither method's postcondition reported, and what one-line change removes each error?

**Target insights**
- Three obligations: the invariant holds **on entry** (before the first guard test); **maintained**: one arbitrary pass that starts where the invariant and the guard hold ends where the invariant holds; **at exit**: the code after the loop knows the invariant and the negated guard, and nothing else from the loop.
- The verifier never runs the loop: maintenance is the induction step over passes, proved once for an arbitrary pass.
- The messages name the obligation: Dafny "could not be proved on entry" / "could not be proved to be maintained by the loop"; Verus "invariant not satisfied before loop" / "invariant not satisfied at end of loop body". A weak invariant at the exit shows up later, at the postcondition or an `assert`.
- A failed obligation is assumed afterwards, so the postconditions that the broken invariant would have given are not reported again: one error per broken obligation.
- Repairs, one line each: start `d` at 0 (`DoubleEntry`, on entry); add 2 per pass, not 3 (`DoubleKept`, maintained).

**Misconceptions & counter-moves**
- *"The verifier tries a few iterations."* → Probe: `DoubleKept` fails with no concrete `m` anywhere; ask: what exactly was checked, and for which state?
- *"If the invariant fails on entry, the postcondition must fail too."* → Probe: `DoubleEntry` ends with `d == 2 * m + 1`, yet only the entry error appears; ask: what does the verifier assume after an obligation fails?

**Verifier probe**
```dafny
module Probe {
  // Three loops that double m. The first verifies; each other one breaks one obligation.
  method DoubleOk(m: nat) returns (d: nat)
    ensures d == 2 * m
  {
    var k := 0;
    d := 0;
    while k < m
      invariant k <= m && d == 2 * k
      decreases m - k
    {
      k := k + 1;
      d := d + 2;
    }
  }

  method DoubleEntry(m: nat) returns (d: nat)
    ensures d == 2 * m
  {
    var k := 0;
    d := 1;
    while k < m
      invariant k <= m && d == 2 * k
      decreases m - k
    {
      k := k + 1;
      d := d + 2;
    }
  }

  method DoubleKept(m: nat) returns (d: nat)
    ensures d == 2 * m
  {
    var k := 0;
    d := 0;
    while k < m
      invariant k <= m && d == 2 * k

}
```

### K2 [predict] — the invariant that forgot its bound
**viva:** yes (verifier-refereed predict) · **strand:** S4 · **tags:** `loop-invariant`, `verdict-reading` · **backward-edge:** Q01 (reading a verdict: which obligation failed, and where)

Each program triples `m` with a loop whose invariant is only `t == 3 * k` (the Verus one also keeps `m < 1000`, for the arithmetic). Predict both verdicts as `D:<v> V:<v>` (`ok`, `fail`, `timeout`, `err:<stage>`) and, for a failure, the obligation: on entry, maintained, or at the exit.

**Target insights**
- `D:fail V:fail`, both at the postcondition: Dafny reports the return path with a `related` line on the `ensures`, Verus the `ensures` clause itself.
- The invariant is inductive: it holds on entry and every pass keeps it. At the exit the verifier knows `t == 3 * k` and `!(k < m)`, that is `k >= m`, not `k == m`: the invariant never states the bound `k <= m`.
- A loop forgets every fact its invariant does not state, including facts that are obviously true of every run.
- Adding `k <= m` closes it (K1's `DoubleOk` has that shape).

**Misconceptions & counter-moves**
- *"The guard bounds `k`, so the verifier knows `k == m` after the loop."* → ask: what does the negated guard say on its own? Then run the probe with `k <= m` added beside `t == 3 * k`.
- *"A weak invariant shows up as an invariant error."* → the probe: the only error is at the postcondition; ask which of K1's three obligations failed.

### K3 [why] — what survives an `assert … by`
**viva:** yes · **strand:** S3 · **tags:** `assert-by`, `lemma-call` · **backward-edge:** none

In the probe, `UseScoped` calls the length lemma inside an `assert … by` block and `UseTop` calls it at the top level. Why does only the second verify its last line, and why would you still choose the scoped form in a longer proof?

**Target insights**
- A `by` block proves its own assertion with the steps inside it; after the block, only the asserted proposition is in context, not the postcondition of a lemma called inside. The same holds in Dafny and Verus.
- A top-level call puts the lemma's postcondition in context for the rest of the body.
- Scoping keeps the context small (the solver considers fewer facts, the proof is cheaper and steadier) and shows the reader which fact each step uses. A fact needed later is asserted itself, or the call is made at the top level.

**Misconceptions & counter-moves**
- *"A lemma call proves its fact for the whole body, wherever it is written."* → Probe: `UseScoped` fails on its last line (Dafny line 21, Verus line 32).
- *"Scoping is only style."* → ask: in each version, which facts does the solver hold while it proves the rest of the body?

**Verifier probe**
```dafny
module Probe {
  function Ones(n: nat): seq<nat>
    decreases n
  {
    if n == 0 then [] else [1] + Ones(n - 1)
  }

  lemma {:induction false} OnesLen(n: nat)
    ensures |Ones(n)| == n
    decreases n
  {
    if n > 0 {
      OnesLen(n - 1);
    }
  }

  lemma UseScoped(k: nat)
    requires k >= 1
  {
    assert |Ones(k)| >= 1 by { OnesLen(k); }
    assert |Ones(k)| == k;
  }

  lemma UseTop(k: nat)
    requires k >= 1
  {
    OnesLen(k);
    assert |Ones(k)| >= 1;
    assert |Ones(k)| == k;
  }
}
```

**Target insights**

### K5 [predict] — a measure that is not bounded below
**viva:** yes (verifier-refereed predict) · **strand:** S4 · **tags:** `termination-measure` · **backward-edge:** none

`StepDown(x: int)` (Verus `step_down`) recurses on `x - 1` until `x == 0`, with `decreases x`. Predict `D:<v> V:<v>` for the first function of each probe, and say whether the verifier is right about it.

**Target insights**
- `D:fail V:fail`, at the recursive call: Dafny "decreases expression must be bounded below by 0", Verus "could not prove termination".
- A measure must strictly decrease **and** stay bounded below (0 for an `int`) at every call. For a negative `x` the argument keeps shrinking and never meets the base case: `StepDown(-1)` does not terminate, so the verifier is right.
- Repairs: a base case that covers every `x <= 0` (the second function, which verifies), or a domain where the measure cannot go negative (`nat`, or a `requires`).

**Misconceptions & counter-moves**
- *"`x` drops by one per call, so the recursion ends."* → ask: trace `StepDown(-1)` for three calls.
- *"Any decreasing integer is a valid measure."* → Probe: the error names the bound, not the decrease.

**Verifier probe**

### K6 [why] — an existential needs a term
**viva:** yes · **strand:** S2 · **tags:** `quantifiers` · **backward-edge:** none

The `requires` says that every one of the three limbs is zero; the `ensures` says that some limb is zero. Why does the empty proof fail, and why does asserting one limb make it verify?

**Target insights**
- A solver proves `exists i :: P(i)` by finding a term `t` with `P(t)` among the terms it already holds; quantifiers are instantiated through terms that match their triggers (here `s[…]`).
- A `forall` in the `requires` supplies no term of its own: it is used only when a matching term appears. With no `s[c]` anywhere, neither quantifier is instantiated.
- `assert s[0] == 0` adds the term `s[0]`: the `forall` instantiates at 0, and the existential has its witness. Naming a witness is the repair (the Rosetta card C9dv).
- The mechanism is the same in Dafny and Verus.

**Misconceptions & counter-moves**
- *"The `forall` already covers `s[0]`, so the solver sees it."* → Probe: the bare lemma fails; ask which term the solver would have to invent.
- *"Any extra `assert` helps by giving the solver more to work with."* → ask: what new term does this particular `assert` add, and what would `assert |s| == 3` add?

**Verifier probe**

```dafny
    requires |s| == 3 && forall j :: 0 <= j < |s| ==> s[j] == 0
    ensures exists i :: 0 <= i < |s| && s[i] == 0

    assert s[0] == 0;
  }
}
```
