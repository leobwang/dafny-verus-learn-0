### K1 [reconstruct] — five rungs on one clamp
**viva:** yes · **tags:** `escalation-ladder`, `hole-contract` · **backward-edge:** R01 (a test runs code; a proof covers inputs)

Reconstruct, without the chapter, the five rungs of the escalation ladder in order; for each, name the fault class it is the first to catch and what it leaves open, and say where statement review sits. Then place the probe on the ladder. `ClampR15` / `clamp_r15` keeps an input inside `[lo, hi]`. Three fixed checks state expected answers on chosen inputs; the contract states the property for every input. Which declarations verify, which rung does each exercise, and what input would a fourth fixed check need in order to catch the fault?

```dafny
module R15_ClampProbe {
  // The contract: the result lies in [lo, hi], and an input already there is kept.
  function ClampR15(x: int, lo: int, hi: int): (y: int)
    requires lo <= hi
    ensures lo <= y <= hi
    ensures lo <= x <= hi ==> y == x
  {
    if x < lo then lo else if x >= hi then hi - 1 else x
  }

  // Fixed checks: the expected answers on three chosen inputs.
  lemma ClampSamplesR15()
    ensures ClampR15(5, 0, 10) == 5
    ensures ClampR15(-3, 0, 10) == 0
    ensures ClampR15(7, 2, 9) == 7
  {
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// The body under test.
pub open spec fn clamp_r15(x: int, lo: int, hi: int) -> int {
    if x < lo {
        lo
    } else if x >= hi {
        hi - 1
    } else {
        x
    }
}

// The contract: the result lies in [lo, hi], and an input already there is kept.
proof fn lemma_clamp_contract_r15(x: int, lo: int, hi: int)
    requires
        lo <= hi,
    ensures
        lo <= clamp_r15(x, lo, hi) <= hi,
        lo <= x <= hi ==> clamp_r15(x, lo, hi) == x,
{
}

// Fixed checks: the expected answers on three chosen inputs.
proof fn lemma_clamp_samples_r15()
    ensures
        clamp_r15(5, 0, 10) == 5,
        clamp_r15(-3, 0, 10) == 0,
        clamp_r15(7, 2, 9) == 7,
{
}

} // verus!
```

**Target insights**
- The rungs: (1) run once on a chosen input, first to catch a crash or a visibly wrong answer; (2) executable checks on listed inputs (`expect` in a `{:test}` method, `assert!` in a `#[test]`), a wrong answer on a listed input; (3) a property test against an independent oracle, a wrong answer nobody listed, inside the generator's range; (4) a proof of the stated contract, a wrong answer on any admitted input, relative to the statement, the assumptions and the trusted base; (5) the audit, `scripts/vaudit` for assumptions and escape hatches and `scripts/specfreeze` for changed statements. Statement review sits beside the ladder: every rung is relative to the statement, so none catches a contract that says the wrong thing.
- The sample lemma verifies in both languages: each check is a concrete evaluation, and all three inputs sit away from the upper end. The contract fails twice in each language. The `hi - 1` branch breaks `lo <= y` when `lo == hi` (`ClampR15(4, 4, 4)` is 3) and breaks "an input in range is kept" at `x == hi` (`ClampR15(10, 0, 10)` is 9). Dafny names the branch (line 8) with each failed `ensures` (lines 5 and 6) as related; Verus names the two contract clauses (lines 21 and 22).
- The samples are rung 2: their reach is exactly three inputs, chosen by the mind that wrote `>=`. A fourth check catches the fault only at `x == hi` or at `lo == hi`, an input someone has to think of. The contract is rung 4 and finds both without anyone thinking of them. That is R01's sentence at ladder scale: a test runs code on its inputs; a proof covers every input the `requires` admits.
- In this toy the checks are assertions the verifier evaluates, because a module probe cannot run `--test`; a compiled `expect` or `#[test]` on the same three inputs would pass the same way, by running instead of evaluating.

**Misconceptions & counter-moves**
- *"The samples verified, so the function is right near them."* → Ask which of the three inputs equals `hi`, and which has `lo == hi`.
- *"The contract failed, so the samples must be wrong too."* → Ask what each sample claims and whether the body meets it on that input.
- *"Rung 4 passed once the contract is green; nothing above it matters."* → Show the follow-up: a green run that proves nothing, and ask which rung reports it.

### K2 [predict] — every sequence has a sorted slice
**viva:** yes (verifier-refereed predict) · **tags:** `anchoring`, `witnesses`, `quantifiers` · **backward-edge:** R04 (the empty slice is a slice)

`HasSortedSliceR15` / `has_sorted_slice_r15` asks whether some slice `a[i..j]` of `a`, the empty slices included, is sorted, and answers `true` without looking. Predict each verdict: `D:<v> V:<v>`, each `verified` or `failed`. Then say what the statement's author probably meant, and whether the verdict changes your review of the statement.

```dafny
module R15_SortedSliceProbe {
  ghost predicate SortedR15(t: seq<int>)
  {
    forall k, l | 0 <= k < l < |t| :: t[k] <= t[l]
  }

  // Is some slice of a sorted? The body answers yes without looking.
  method HasSortedSliceR15(a: seq<int>) returns (b: bool)
    ensures b == exists i, j | 0 <= i <= j <= |a| :: SortedR15(a[i..j])
  {
    b := true;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

pub open spec fn sorted_r15(t: Seq<i64>) -> bool {
    forall|k: int, l: int| 0 <= k < l < t.len() ==> t[k] <= t[l]
}

// Is some slice of a sorted? The body answers yes without looking.
fn has_sorted_slice_r15(a: &Vec<i64>) -> (b: bool)
    ensures
        b == exists|i: int, j: int| 0 <= i <= j <= a.len() && #[trigger] sorted_r15(a@.subrange(i, j)),
{
    true
}

} // verus!
```

**Target insights**
- The statement is true for every `a`: the empty slice `a[0..0]` is sorted, and so is every one-element slice. Proving an `exists`, though, needs a term to instantiate it with. Nothing in the body mentions a slice, so the solver has no candidate and the postcondition is not proved in either language. A true postcondition is not a proved one until its witness is named.
- The repair is one line that names the witness, `assert SortedR15(a[0..0]);` / `assert(sorted_r15(a@.subrange(0, 0)));`, and then both verify (the follow-up). The empty slice is both the witness and the defect.
- Each language needs the term in its own trigger's shape: Dafny's `exists` is matched through `SortedR15(a[i..j])`, Verus's through the marked `sorted_r15(a@.subrange(i, j))`, so the witness line names exactly that term (`a[0..0]`, `a@.subrange(0, 0)`).
- As a statement, it is degenerate: the answer is `true` on every input, so it demands nothing of a body. Its author probably meant a sorted run of length at least 2 (`i + 2 <= j`), or a longest-run question. This is the empty-slice trap turned around: §4's empty-string candidate lost cases by excluding empty slices; here including them makes the question trivial. R04 §1.2 planted the convention that the empty slice is a slice; reviewing a search statement means asking what that convention does to it.

**Misconceptions & counter-moves**
- *"`D:verified V:verified`: the statement is true, so the constant body meets it."* → Ask which term the solver would use to instantiate the `exists`.
- *"It fails because `true` is wrong on some input."* → Ask for that input; then ask what `a[0..0]` is.
- *"Once it verifies, the statement is fine."* → Ask what a body has to do to meet it, and what its author wanted to know.
- *"The empty slice is a technicality; reviewers can ignore it."* → Ask what requiring `i + 2 <= j` would change in the answer on `[3, 1]`, and on `[]`.

### K3 [why] — what the passed positions ruled out
**viva:** yes · **tags:** `loop-invariant`, `verdict-reading` · **backward-edge:** R11 (searching with an exclusion invariant)

`HasRepeatR15` / `has_repeat_r15` looks for two equal neighbours. Its loop carries only a bound. Read the failure: which path fails, and why do the bound and the exit condition not give it? Then write the missing invariant clause in both languages, and say which of the chapter's two kinds of clause it is. Why does the `return true` path verify without it?

```dafny
module R15_RepeatProbe {
  // Do two equal values stand next to each other somewhere in a?
  method HasRepeatR15(a: seq<int>) returns (b: bool)
    ensures b == exists p | 0 <= p && p + 1 < |a| :: a[p] == a[p + 1]
  {
    if |a| < 2 {
      return false;
    }
    var p := 0;
    while p + 1 < |a|
      invariant 0 <= p && p + 1 <= |a|
    {
      if a[p] == a[p + 1] {
        return true;
      }
      p := p + 1;
    }
    return false;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// Do two equal values stand next to each other somewhere in a?
fn has_repeat_r15(a: &Vec<i64>) -> (b: bool)
    ensures
        b == exists|p: int| 0 <= p && p + 1 < a.len() && #[trigger] a@[p] == a@[p + 1],
{
    if a.len() < 2 {
        return false;
    }
    let mut p: usize = 0;
    while p + 1 < a.len()
        invariant
            p + 1 <= a.len(),
        decreases a.len() - p,
    {
        if a[p] == a[p + 1] {
            return true;
        }
        p = p + 1;
    }
    false
}

} // verus!
```

**Target insights**
- Dafny fails on the `return false` path (line 18, with the `ensures` at line 4 related); Verus fails at the postcondition (line 8). At the exit the loop knows `p + 1 >= |a|` and the bound, and nothing about the positions it passed, so "no two equal neighbours anywhere" does not follow.
- The missing clause is an exclusion: Dafny `invariant forall q | 0 <= q < p :: a[q] != a[q + 1]`, Verus `forall|q: int| 0 <= q < p ==> #[trigger] a@[q] != a@[q + 1]`. It holds before the loop (an empty range), and each step grows it by one, because reaching `p := p + 1` means `a[p] != a[p + 1]`. It is the first kind, what the passed positions ruled out; together with the exit condition it gives the `false` half. Both repaired files verify (below).
- The `true` path needs only a witness, and the witness `p` is in hand with `a[p] == a[p + 1]` in context. The two halves of `b == exists …` need different things: a witness for `true`, an exclusion of every candidate for `false`. R11 §5.2 said it for split positions: progress through positions is not enough; the invariant must state the exclusion, and the exclusion is what proves the no-match clause.
- This loop needs no clause of the second kind, because its state is the position alone. Write the clause on top of a bound that keeps `a[q + 1]` in range: an invariant must be well-formed under the invariants before it, and in Dafny an exclusion over `0 <= p` alone is itself refused as an index out of range.

**Misconceptions & counter-moves**
- *"The missing clause is a tighter bound on `p`."* → Ask what any bound says about `a[0]` and `a[1]` once `p` is 5.
- *"The invariant should say `b == false`."* → Ask what `b` records and whether it says anything about positions.
- *"The `true` path needs the invariant too."* → Ask what the `exists` needs, and which `p` is in hand at the `return`.

### K4 [predict] — what the inner loop's body knows
**viva:** yes (verifier-refereed predict) · **tags:** `loop-invariant`, `verdict-reading` · **backward-edge:** none

`HasEchoR15` / `has_echo_r15` asks whether some value repeats an earlier one. The outer loop runs `p` over the positions; the inner loop runs `q` over the positions before `p`.
```dafny
module R15_EchoProbe {
  // Does some value repeat an earlier one: positions q < p with a[q] == a[p]?
  method HasEchoR15(a: seq<int>) returns (b: bool)
    ensures b == exists q, p | 0 <= q < p < |a| :: a[q] == a[p]
  {
    var p := 0;
    while p < |a|
      invariant 0 <= p <= |a|
      invariant forall q1, p1 | 0 <= q1 < p1 < p :: a[q1] != a[p1]
    {
      var q := 0;
      while q < p
        invariant 0 <= q <= p
        invariant forall q1 | 0 <= q1 < q :: a[q1] != a[p]
      {
        if a[q] == a[p] {
          return true;
        }
        q := q + 1;
      }
      p := p + 1;
    }
    return false;
  }
}
```

### K5 [transfer] — six statements for a low slice
**viva:** yes · **tags:** `spec-strength`, `vacuity`, `anchoring`, `witnesses` · **backward-edge:** R06 (a counterexample is a proof too)

Transfer §4's review to integers. The task `HasLowSliceR15(a: seq<int>, t: int) returns (b: bool)` asks whether some slice of `a`, the empty slices included, has a total of at most `t`, where `SumR15` totals a sequence by peeling its last element. Classify each candidate as faithful, weak, vacuous, over-strong, anchoring error or empty-string error, and give a witness that separates each defective one from the faithful one:

- [a] `ensures b == exists i, j | 0 <= i <= j <= |a| :: SumR15(a[i..j]) <= t`
- [b] `ensures b == exists j | 0 <= j <= |a| :: SumR15(a[..j]) <= t`
- [c] `ensures b ==> exists i, j | 0 <= i <= j <= |a| :: SumR15(a[i..j]) <= t`
- [d] [a]'s `ensures` under `requires forall i, j | 0 <= i <= j <= |a| :: SumR15(a[i..j]) != 0` (its author meant: no slice totals zero)
- [e] `ensures b == (exists i, j | 0 <= i <= j <= |a| :: SumR15(a[i..j]) <= t) && (b ==> SumR15(a) <= t)`
- [f] `ensures b == exists i, j | 0 <= i < j <= |a| :: SumR15(a[i..j]) <= t`

```dafny
module R15_LowSliceReview {
  // The sum of a sequence, peeling the last element.
  function SumR15(t: seq<int>): int
  {
    if |t| == 0 then 0 else SumR15(t[..|t| - 1]) + t[|t| - 1]
  }

  // Anchoring witness: on [5, -1] with t = -1, a slice reaches the bound and no prefix does.
  lemma PrefixMissesR15(a: seq<int>)
    requires a == [5, -1]
    ensures exists i, j | 0 <= i <= j <= |a| :: SumR15(a[i..j]) <= -1
    ensures !exists j | 0 <= j <= |a| :: SumR15(a[..j]) <= -1
  {
    assert a[1..2] == [-1];
    assert SumR15(a[1..2]) == -1;
    forall j | 0 <= j <= |a|
      ensures SumR15(a[..j]) > -1
    {
      if j == 1 {
        assert a[..1] == [5];
      } else if j == 2 {
        assert a[..2] == a;
        assert a[..1] == [5];
      }
    }
  }

  // Vacuity witness: the slice from 0 to 0 breaks the requires for every a.
  lemma NoAdmittedInputR15(a: seq<int>)
    requires forall i, j | 0 <= i <= j <= |a| :: SumR15(a[i..j]) != 0
    ensures false
  {
    assert SumR15(a[0..0]) != 0;
  }

    }
  }
```

```rust
pub open spec fn sum_r15(t: Seq<int>) -> int
    decreases t.len(),
{
    if t.len() == 0 {
        0
    } else {
        sum_r15(t.subrange(0, t.len() - 1)) + t[t.len() - 1]
    }
}

// Anchoring witness: on [5, -1] with t = -1, a slice reaches the bound and no prefix does.
proof fn prefix_misses_r15(a: Seq<int>)
    requires
        a == seq![5int, -1],
    ensures
        exists|i: int, j: int| 0 <= i <= j <= a.len() && #[trigger] sum_r15(a.subrange(i, j)) <= -1,
        !exists|j: int| 0 <= j <= a.len() && #[trigger] sum_r15(a.subrange(0, j)) <= -1,

    assert(a.subrange(1, 2) =~= seq![-1int]);

    assert forall|j: int| 0 <= j <= a.len() implies #[trigger] sum_r15(a.subrange(0, j)) > -1 by {
        assert(a.subrange(0, 1) =~= seq![5int]);
        assert(a.subrange(0, 2) =~= a);
    }
}

        forall|i: int, j: int| 0 <= i <= j <= a.len() ==> #[trigger] sum_r15(a.subrange(i, j)) != 0,

}

        a == seq![3int],

        a == seq![5int, -1],
```

**Target insights**
- [a] is faithful. [b] is the anchoring error, prefixes only: on `([5, -1], -1)` the slice `[-1]` reaches the bound, while the prefixes total 0, 5 and 4. [c] is weak: `b := false` meets it on every input. [d] is vacuous: `i = j = 0` gives `SumR15([]) == 0`, so no input is admitted and every body is correct. [e] is over-strong: on `([5, -1], -1)` the `exists` forces `b`, and `SumR15(a)` is 4, so no output satisfies it and no body can. [f] is the empty-string error: on `([3], 0)` only the empty slice reaches the bound.

Each is a proof of a separation: an existential with its term named (`a[1..2]`, `a[0..0]`) and, for the negative half, a finite exclusion of every candidate. That is R06 §5.1's point, a refutation is a proof with R04's shape; the review's witnesses are claims the verifier checked, not sentences. `NoAdmittedInputR15` is a witness of unsatisfiability (`ensures false` from the `requires`); for a satisfiable `requires` the review asks for the opposite, one concrete input that meets it.

That is why the review asks for a witness per candidate rather than a few test cases.

The subject `CountRecR15` and the oracle `CountLoopR15` both call `IsNegR15`, which counts zero as negative. Their agreement is not sampled: it is proved for every input. The intent is written separately, as `CountNegR15`. Read the probe. What does the proved agreement establish and what does it not; what two kinds of thing can an oracle share with its subject? Then apply that to rung 3 for the search: what must the `regex`-crate oracle's wrapper get right, and what does §3's in-course differential test leave untested?

```dafny
module R15_SharedHelper {
  // The helper both implementations call, with a planted fault at zero.
  function IsNegR15(x: int): bool
  {
    x <= 0
  }

  // Implementation 1, a recursion: the subject.
  function CountRecR15(s: seq<int>): nat
  {
    if |s| == 0 then 0 else (if IsNegR15(s[0]) then 1 else 0) + CountRecR15(s[1..])
  }

  // Implementation 2, a loop: the oracle. Their agreement is proved for every input.
  method CountLoopR15(s: seq<int>) returns (n: nat)
    ensures n == CountRecR15(s)
  {
    n := 0;
    var i := 0;
    while i < |s|
      invariant 0 <= i <= |s|
      invariant n + CountRecR15(s[i..]) == CountRecR15(s)
    {
      assert s[i..][1..] == s[i + 1..];
      if IsNegR15(s[i]) {
        n := n + 1;
      }
      i := i + 1;
    }
  }

  // The intent, written without the helper: count the negative values.
  function CountNegR15(s: seq<int>): nat
  {
    if |s| == 0 then 0 else (if s[0] < 0 then 1 else 0) + CountNegR15(s[1..])
  }

  // The subject against the intent.
  lemma RecMeetsIntentR15(s: seq<int>)
    ensures CountRecR15(s) == CountNegR15(s)
  {
  }
}
```

### K12 [why] — 83 % agreement, κ below zero
**viva:** yes · **tags:** `statistics`, `pre-registration`, `contamination`, `nonlinear-arith` · **backward-edge:** R12 (the unit of uncertainty is the cluster)

Lab β's primary estimand is Cohen's κ between the two oracles' binary verdicts. Take two tables over 24 units, with `ff` both faithful, `fd` only oracle 1 faithful, `df` only oracle 2 faithful and `dd` neither: Table 1 is (10, 2, 4, 8), Table 2 is (20, 2, 2, 0). The probe computes κ's numerator and denominator, both multiplied by `n²`. Why is κ, not the fraction of units that agree, the primary estimand? Why is its interval a bootstrap over cards rather than over units? And which rules protect the later comparison with the hidden verdicts?

```dafny
module R15_KappaArith {
  // Two oracles' binary verdicts on n units: both faithful (ff), only oracle 1 (fd),
  // only oracle 2 (df), neither (dd). kappa = num / den, both scaled by n * n.
  function ChanceR15(ff: int, fd: int, df: int, dd: int): int
  {
    (ff + fd) * (ff + df) + (df + dd) * (fd + dd)
  }

  function KappaNumR15(ff: int, fd: int, df: int, dd: int): int
  {
    (ff + fd + df + dd) * (ff + dd) - ChanceR15(ff, fd, df, dd)
  }

  function KappaDenR15(ff: int, fd: int, df: int, dd: int): int
  {
    (ff + fd + df + dd) * (ff + fd + df + dd) - ChanceR15(ff, fd, df, dd)
  }

  // Table 1: 18 of 24 agree.
  lemma TableOneR15()
    ensures KappaNumR15(10, 2, 4, 8) == 144
    ensures KappaDenR15(10, 2, 4, 8) == 288
  {
  }

  // Table 2: 20 of 24 agree.
  lemma TableTwoR15()
    ensures KappaNumR15(20, 2, 2, 0) == -8
    ensures KappaDenR15(20, 2, 2, 0) == 88
  {
  }
}
```

**Target insights**
- With `n` units, the observed agreement is `p_o = (ff + dd) / n`, the chance agreement from each oracle's own rate of *faithful* is `p_e = C / n²` with `C = (ff + fd)(ff + df) + (df + dd)(fd + dd)`, and `κ = (p_o − p_e) / (1 − p_e) = (n(ff + dd) − C) / (n² − C)`. Table 1: 144 / 288 = 0.5, at `p_o` = 0.75. Table 2: −8 / 88 ≈ −0.09, at `p_o` ≈ 0.83. In Table 2 both oracles call almost everything faithful, so chance alone would agree on about 85 % of units and the observed 83 % is below it. Raw agreement rewards two oracles that both say yes.
- The cluster is the card: a card's four variants in two languages share a task, a vocabulary and an author, so their verdicts are correlated, and resampling the 192 units would treat them as independent. Resample the 24 cards with replacement 10,000 times, recompute κ, and report the 2.5th and 97.5th percentiles. R12's Lab α made the same choice: repeats and arms stay inside their cluster. With 24 clusters there is no useful test to power, so the pre-registration fixes a simulated interval half-width instead, and says plainly that 24 clusters cannot separate κ = 0.4 from κ = 0.6.
- κ compares the oracles with each other; their error rates against the hidden verdicts are the secondary confusion matrices. Those stay valid only if the hidden verdicts stay out of every loop (delivery loops see verifier output only, the oracles run after the batch, the comparison runs only in the grader container), and if the cards resist recall (post-cutoff authorship, a novelty review, a renamed perturbation probe per card, a fresh context for every run). The pre-registration's hash is committed before any run, and the report discloses that Claude grades the method and is a subject of one arm.
- The arithmetic differs by language: Dafny evaluates the literal products alone; Verus proves one of the four clauses alone and the rest with `by (compute)` (the last Verus run below). That is R14's nonlinear arithmetic, met in a place that looks like plain counting.

**Misconceptions & counter-moves**
- *"83 % agreement is good agreement."* → Ask what two oracles that always answer *faithful* would score.
- *"192 units give a tight interval."* → Ask what the variants of one card share.
- *"Showing `roundtrip` a few hidden verdicts would only improve it."* → Ask what the lab would then measure.
- *"An interval for κ above zero shows both oracles are right."* → Ask what κ compares the oracles with.

### PP2 — parallel to R15.H1py and R15.H2py (the checks `spectest` renders, decided by hand)
