### K1 [predict] — what a run record makes of two unfinished files
**viva:** yes (verifier-refereed predict) · **strand:** S9 · **tags:** `exit-codes-and-doors`, `json-verdicts`, `hole-contract` · **backward-edge:** Q03 (a `verified` run with a hole in it; done = verified and zero tool-counted holes)

Two files per language, each checked alone with `scripts/vcheck --json`: [a] a lemma whose `ensures` is false for odd `x`; [b] the same kind of lemma, true, left as a hole.

```dafny
lemma HalvesBack(x: nat)
  ensures x / 2 + x / 2 == x
{
}
```
```dafny
lemma HalvesBelow(x: nat)
  ensures x / 2 + x / 2 <= x
```
```rust
use vstd::prelude::*;

verus! {

proof fn lemma_halves_back(x: nat)
    ensures
        x / 2 + x / 2 == x,
{
}

} // verus!
```
```rust
use vstd::prelude::*;

verus! {

proof fn lemma_halves_below(x: nat)
    ensures
        x / 2 + x / 2 <= x,
{
    #[verifier::proof_note("K1")] assume(false);
}

} // verus!
```
For each file predict: the exit code of `scripts/vcheck --json` itself, the document's `verdict`, the number of entries in its `holes` list, and whether a `RunRecord` built from the document has `success` (`fvh.records`: `verdict == "verified" and holes == 0`). Answer form, per language: `a:<exit>/<verdict>/<holes>/<yes|no> b:<exit>/<verdict>/<holes>/<yes|no>`.

**Target insights**
- A hole does not make the run fail: the learner loop checks the obligations it can and counts holes separately, so [b] exits 0 with `"verdict": "verified"` and one entry in `holes`. Only `success`, which also needs zero holes, says the file is unfinished.
- [a] is `failed` with exit 1: a refuted obligation, no hole. Neither file is a success, for two different reasons, and a harness that reads only the exit code (or only `verdict`) files [b] as solved.
- The document's own `exit_code` is the verifier's, not `scripts/vcheck`'s: Dafny's 4 for [a], and Verus's 1 for both files (under `--no-cheating` Verus rejects the `assume` of [b] and exits 1; the wrapper counts it as the hole and reports `verified`). A harness reads `verdict` and `holes`, never that field.
- Fields differ by language: `count_unit` is `tasks` for Dafny and `verified` for Verus, and Verus's `verified_count` is `null` when the run printed no count, as in [b].

**Misconceptions & counter-moves**
- *"A hole is an error, so `scripts/vcheck` exits non-zero."* → Probe: [b] below; ask: which field of the document shows the hole, and which would a harness that reads only the exit code miss?
- *"The `exit_code` field is the exit code of the run I made."* → Probe: Verus [b]; ask: what does the field say, what did `scripts/vcheck` exit with, and whose exit code is each?
- *"`verified` means the lemma is proved."* → Ask: what does `success` add to `verdict`, and why does the course define done with both?

### K2 [reconstruct] — the inventory behind a green run
**viva:** yes · **strand:** S10 · **tags:** `tcb`, `trust-ledger`, `standard-library` · **backward-edge:** Q03 (the pipeline and the trusted base)

For each language, reconstruct the trusted base of a green `scripts/vcheck` run on your Q06 unit, row by row: front end, solver, standard library, course wrappers, given layers. For each row, name one concrete way it could make a green run wrong without a line of your file changing. Then say which rows `scripts/vaudit` examines in each language, and what a report of 0 findings therefore licenses.

**Target insights**
- The rows, with their pinned versions: Dafny 4.11.0 through Boogie, Z3 4.12.1, `Std`, the wrappers and the generated `dfyconfig.toml`s, L1–L3; Verus 0.2026.09.27.3cf1832 on rustc 1.98.1 through VIR and AIR, Z3 4.16.0, `vstd`, the wrappers with `--no-cheating` and the pinned `--rlimit`, L1–L3.
- One failure per row, each invisible from your file: a solver that answers "unsat" to everything, or a wrong translation; a trusted library specification that is false (a Dafny `{:axiom}`, a Verus `external_body` or `assume_specification`); a wrapper bug (a flag dropped, a verdict misparsed); a given lemma whose statement does not say what its name says.
- `scripts/vaudit` examines your files: your holes and assumptions (the probe's own hole, in both languages), and your resource attributes. It does not report the libraries: Dafny's audit counts the standard library's rows against a pin and hides them, and Verus's never examines `vstd`. The library calls in the probe add no finding.
- So 0 findings means "nothing trusted in what I wrote", never "nothing trusted": `TRUST.md` lists the library, solver, front-end and wrapper rows by hand, each with the reason a green run could still be wrong.

**Misconceptions & counter-moves**
- *"The audit is clean, so the run trusts nothing."* → Probe: the files below; ask: which declaration does the audit report, and what about the library lemma the other declaration calls?

- *"The given layers are the course's, so they are trusted for free."* → Ask: what would make a given lemma wrong for your proof even if it verifies? (Its statement says less, or something else, than its name.)

### K3 [predict] — which terms switch a quantified fact on
**viva:** yes (verifier-refereed predict) · **strand:** S11 · **tags:** `triggers`, `lemma-call` · **backward-edge:** Q04 (the `forall` statement, whose triggers Q04 gave you)

Four lemmas share a hypothesis that bounds every element of `s` by `Cap(i)`, triggered on `Cap(i)`. `Cap` is an ordinary (transparent) function, and `CapTwo` is a helper lemma about it. Which lemmas fail, in each language?

```dafny
function Cap(i: nat): nat
{
  3 * i
}

lemma CapTwo()
  ensures Cap(2) == 6
{
}

// [a]
lemma SampleA(s: seq<nat>)
  requires |s| > 2
  requires forall i {:trigger Cap(i)} | 0 <= i < |s| :: s[i] <= Cap(i)
  ensures s[2] <= 6
{
}

// [b]
lemma SampleB(s: seq<nat>)
  requires |s| > 2
  requires forall i {:trigger Cap(i)} | 0 <= i < |s| :: s[i] <= Cap(i)
  ensures s[2] <= 6
{
  assert s[2] <= Cap(2);
}

// [c]
lemma SampleC(s: seq<nat>)
  requires |s| > 2
  requires forall i {:trigger Cap(i)} | 0 <= i < |s| :: s[i] <= Cap(i)
  ensures s[2] <= Cap(2)
{
}

// [d]
lemma SampleD(s: seq<nat>)
  requires |s| > 2
  requires forall i {:trigger Cap(i)} | 0 <= i < |s| :: s[i] <= Cap(i)
  ensures s[2] <= 6
{
  CapTwo();
}
```
```rust
use vstd::prelude::*;

verus! {

pub open spec fn cap(i: nat) -> nat {
    3 * i
}

proof fn lemma_cap_two()
    ensures
        cap(2) == 6,
{
}

// [a]
proof fn lemma_sample_a(s: Seq<nat>)
    requires
        s.len() > 2,
        forall|i: nat| i < s.len() ==> s[i as int] <= #[trigger] cap(i),
    ensures
        s[2] <= 6,
{
}

// [b]
proof fn lemma_sample_b(s: Seq<nat>)
    requires
        s.len() > 2,
        forall|i: nat| i < s.len() ==> s[i as int] <= #[trigger] cap(i),
    ensures
        s[2] <= 6,
{
    assert(s[2] <= cap(2));
}

// [c]
proof fn lemma_sample_c(s: Seq<nat>)
    requires
        s.len() > 2,
        forall|i: nat| i < s.len() ==> s[i as int] <= #[trigger] cap(i),
    ensures
        s[2] <= cap(2),
{
}

// [d]
proof fn lemma_sample_d(s: Seq<nat>)
    requires
        s.len() > 2,
        forall|i: nat| i < s.len() ==> s[i as int] <= #[trigger] cap(i),
    ensures
        s[2] <= 6,
{
    lemma_cap_two();
}

} // verus!
```
Answer form: `D:FAILS <labels> V:FAILS <labels>` (labels in order, or `none`).

**Target insights**
- A quantified hypothesis is used only through instances, and an instance is created when a term of the trigger's shape, here `Cap(t)`, appears among the facts of the proof. The goal of [a] mentions `s[2]` and `6`, which match nothing, so the hypothesis never fires: [a] fails in both languages.
- The trigger term may come from anywhere in the proof's context: an assertion ([b] names `Cap(2)`), the goal itself ([c]), or a called lemma's `ensures` ([d] puts `Cap(2) == 6` in context, at the call's argument). Each creates the instance at `i = 2`, and since `Cap` is transparent its value follows.
- "Could not be proved" is the only message: no tool says that no trigger matched. When a quantified hypothesis should close a goal, ask which term would fire it.
- Contrast with an opaque function (K4, P4v): the instance a trigger yields is only as useful as the definitions the solver can see.

**Misconceptions & counter-moves**
- *"The hypothesis covers every `i`, so `s[2] <= Cap(2)` is known from the start."* → Probe: [a]; ask: which term in [a]'s proof has the shape `Cap(…)`?
- *"Only an `assert` that names the trigger term fires it."* → Probe: [d]; ask: where did the term `Cap(2)` come from there?
- *"The goal has to be stated with the trigger term."* → Probe: [b] and [d] against [c]; ask: which of the three states its goal that way, and which still verify?

### K4 [predict] — a reveal behind a helper lemma
**viva:** yes (verifier-refereed predict) · **strand:** S11 · **tags:** `opacity`, `lemma-call` · **backward-edge:** none

`Treble` is opaque. [a] reveals it at the top of its own body; [b], [c] and [d] never reveal it. Which lemmas fail, in each language?

```dafny
opaque function Treble(x: nat): nat
{
  3 * x
}

// [a]
lemma TrebleTwo()
  ensures Treble(2) == 6
{
  reveal Treble();
}

// [b]
lemma AfterCall()
  ensures Treble(2) + 1 == 7
{
  TrebleTwo();
}

// [c]
lemma NoCall()
  ensures Treble(2) + 1 == 7
{
}

// [d]
lemma OtherArgument()
  ensures Treble(3) == 9
{
  TrebleTwo();
}
```
```rust
use vstd::prelude::*;

verus! {

#[verifier::opaque]
pub open spec fn treble(x: nat) -> nat {
    3 * x
}

// [a]
proof fn lemma_treble_two()
    ensures
        treble(2) == 6,
{
    reveal(treble);
}

// [b]
proof fn lemma_after_call()
    ensures
        treble(2) + 1 == 7,
{
    lemma_treble_two();
}

// [c]
proof fn lemma_no_call()
    ensures
        treble(2) + 1 == 7,
{
}

// [d]
proof fn lemma_other_argument()
    ensures
        treble(3) == 9,
{
    lemma_treble_two();
}

} // verus!
```
Answer form: `D:FAILS <labels> V:FAILS <labels>` (labels in order, or `none`).

**Target insights**
- A `reveal` lasts to the end of its block: in [a] that block is [a]'s body, so [a] verifies and nothing outside it sees `Treble`'s body.
- What leaves [a] is its `ensures`, at the call's arguments: [b] calls it and gets `Treble(2) == 6`, which is enough; [c] has neither the body nor the fact, so it fails.
- [d] calls the helper too, but the fact it exports is about `Treble(2)`, not `Treble(3)`: an exported fact is an instance, never the definition. [d] fails. Answer `D:FAILS c d V:FAILS c d`.

### K8 [transfer] — a claim from ten tasks
**viva:** yes · **strand:** S13 · **tags:** `statistics`, `eval-reporting` · **backward-edge:** none

A summary reads: "Prover X closed all 10 tasks of the held-out set, prover Y only 7: X is perfect and clearly better." The 3 tasks Y missed are among X's, and no task was solved by Y alone. Every count is a first attempt. Using `fvh.stats` (from the checkout root), work out what the data support: each prover's 95 % Wilson interval and the paired test. Then write the sentence you would put in an `EVAL.md` claim, and say what would have to change before "clearly better" is licensed.

**Target insights**
- 10 of 10 is a fact about these ten tasks. The Wilson interval does not collapse at `k = n` (a Wald interval would have width zero): it runs from about 0.72 to 1, so "perfect" is not supported. Y's 7 of 10 runs from about 0.40 to 0.89, and the two intervals overlap.
- The comparison is paired (same tasks), so only the discordant tasks count: `b = 3` (X only), `c = 0` (Y only). McNemar's exact test gives `p = 0.25`: three discordant tasks cannot reach 0.05 even when all go one way, since the smallest possible p-value is `2 · (1/2)^3`. It takes six one-way discordant tasks (`p = 0.03125`; five give `0.0625`).
- An honest claim states the population, `n`, the rates with their intervals, the paired test and its counts, and that only first attempts entered: for example, "X 10/10 (95 % Wilson 0.72–1.00), Y 7/10 (0.40–0.89); 3 discordant tasks, all X's, McNemar p = 0.25: no evidence of a difference at n = 10".
- Licensing "clearly better" needs more tasks (more discordant pairs), fixed before the run, not more adjectives; the n to aim for is a pre-registration question (Q09's minimum detectable effect).

**Misconceptions & counter-moves**
- *"10/10 means the rate is 100 %."* → Probe: the interval below; ask: what range of true rates is consistent with ten successes?
- *"Three wins to none is decisive."* → Probe: `stats.mcnemar(3, 0)`; ask: how surprising is a 3–0 split of three fair coins?
- *"Compare the two intervals; if they overlap there is no difference."* → Ask: which test uses the pairing, and why is it the right one here? (Overlap is not a test; the paired test is.)
