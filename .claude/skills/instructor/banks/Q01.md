### K1 [reconstruct] — the contract and who proves which half
**viva:** no (survey bank) · **strand:** S2 · **tags:** `requires-ensures` · **backward-edge:** none

A method (or exec fn) has one `requires` and one `ensures`. Say who must prove each clause, where the verifier checks it, and what a caller knows about the result after the call, in Dafny and in Verus.

**Target insights**
- `requires` is an obligation of every caller, checked at each call site, and an assumption inside the body; `ensures` is an obligation of the body, checked on every return path, and the caller's only knowledge of the result.
- Verification is modular: a caller sees the callee's contract, never its body, and the verifier proves each body once, for all inputs that meet its `requires`, without running it.

**Misconceptions & counter-moves**
- *"The callee checks its own precondition, as a runtime check or an error inside the body."* → Probe K1; ask: on which line is the error, and which declaration verified?
- *"After the call the caller knows what the body computed."* → Ask: in the probe, what may a caller of `HalfOf(6)` assume about `h` besides `h + h == 6`? (Nothing: the body is invisible to it.)

**Verifier probe** (`instructor/scratch/q01_k1.dfy`, `instructor/scratch/q01_k1.rs`)
```dafny
method HalfOf(n: nat) returns (h: nat)
  requires n % 2 == 0
  ensures h + h == n
{
  h := n / 2;
}

method UseHalfOf()
{
  var h := HalfOf(7);
}
```
```rust
use vstd::prelude::*;

verus! {

fn half_of(n: u64) -> (h: u64)
    requires
        n % 2 == 0,
    ensures
        h + h == n,
{
    n / 2
}

fn use_half_of() {
    let h = half_of(7);
}

} // verus!
```

### K2 [predict] — the lemma call before or after the assertion
**viva:** no (survey bank) · **strand:** S3 · **tags:** `lemma-call`, `verdict-reading` · **backward-edge:** none

In each language the probe below defines a recursive sequence, proves a lemma about its length, and then has two declarations that differ only in order: [a] asserts the length and then calls the lemma; [b] calls the lemma and then asserts. Which of [a] and [b] fail, in each language? Commit to an answer (`D:<labels> V:<labels>`, or `none`) before the probe runs.

**Target insights**
- A lemma call puts the lemma's `ensures` into what the verifier knows from the call onwards, never before it: [a] fails and [b] verifies, in both languages.
- Without the call the fact must be proved from the definition alone, and a recursive definition at a symbolic argument needs induction, which an `assert` does not do.

**Misconceptions & counter-moves**
- *"A proved lemma is known everywhere in the file."* → Run the probe; ask: which declarations verified, and what differs between [a] and [b]?
- *"[a] fails because the lemma is wrong."* → Ask the learner to count the verified declarations in the summary line; the lemma is among them.

**Verifier probe** (`instructor/scratch/q01_k2.dfy`, `instructor/scratch/q01_k2.rs`)
```dafny
function Ones(n: nat): seq<int>
  decreases n
{
  if n == 0 then [] else [1] + Ones(n - 1)
}

lemma OnesLength(n: nat)
  ensures |Ones(n)| == n
  decreases n
{
  if n > 0 {
    OnesLength(n - 1);
  }
}

method AssertThenCall(k: nat)
{
  assert |Ones(k)| == k;   // [a]
  OnesLength(k);
}

method CallThenAssert(k: nat)
{
  OnesLength(k);
  assert |Ones(k)| == k;   // [b]
}
```
```rust
use vstd::prelude::*;

verus! {

spec fn ones(n: nat) -> Seq<int>
    decreases n,
{
    if n == 0 {
        Seq::empty()
    } else {
        seq![1int] + ones((n - 1) as nat)
    }
}

proof fn lemma_ones_length(n: nat)
    ensures
        ones(n).len() == n,
    decreases n,
{
    if n > 0 {
        lemma_ones_length((n - 1) as nat);
    }
}

proof fn assert_then_call(k: nat) {
    assert(ones(k).len() == k);  // [a]
    lemma_ones_length(k);
}

proof fn call_then_assert(k: nat) {
    lemma_ones_length(k);
    assert(ones(k).len() == k);  // [b]
}

} // verus!
```

### K3 [why] — the same `+`, two kinds of arithmetic
**viva:** no (survey bank) · **strand:** S1 · **tags:** `nat-vs-machine-int`, `spec-vs-exec` · **backward-edge:** none

Why does `a + b` on two `u64` values raise an obligation in a Verus exec fn but not in a Verus spec fn, and why does the same addition on `nat` raise none in a Dafny method?

**Target insights**
- Verus exec code is Rust and runs on fixed-width integers: every arithmetic operation carries an obligation that its result stays in range (no silent wrap-around).
- Verus spec code is mathematics: `u64` operands are read as integers, so the sum is an unbounded `int` and there is nothing to overflow.
- Dafny's `nat` and `int` are mathematical in compiled code too (arbitrary-precision at run time): addition raises no obligation, while a result that must stay a `nat` (a subtraction) does.

**Misconceptions & counter-moves**
- *"Verus wraps around like a Rust release build."* → Probe K3 (Verus); ask: what does the error on line 6 ask you to prove?
- *"Spec arithmetic on `u64` overflows too."* → Same probe; ask: why did `plus_spec_past_u64` verify?
- *"Dafny's `nat` is a machine word."* → Probe K3 (Dafny); ask: what would make this method fail?

**Verifier probe** (`instructor/scratch/q01_k3.rs`, `instructor/scratch/q01_k3.dfy`)
```rust

proof fn plus_spec_past_u64() {
```

### K5 [why] — why "verified" is not "done"
**viva:** no (survey bank) · **strand:** S12 · **tags:** `hole-contract`, `exit-codes-and-doors` · **backward-edge:** none

The learner loop reports both Q01 units `verified` while six holes remain. Why is that not done, why does the course count holes with a tool rather than by searching the text, and what must agree before a file counts as finished?

**Target insights**
- A hole is a typed placeholder where a proof or a body is assumed rather than checked; the verdict covers what was checked, so a file can verify with holes in it.
- The hole forms differ by language and some contain no telltale word (a Dafny lemma with no body), so only a tool that knows the forms counts them; a text search both misses forms and counts comments.
- A raw tool run may not mention a hole at all; the course's wrapper runs each tool so that holes are reported.
- Done is three instruments agreeing: the done gate (`scripts/vcheck --gate`, which refuses holes and warnings), the audit with no finding, and the strict first-try report.

**Misconceptions & counter-moves**
- *"Searching for `assume` finds every hole."* → Ask the learner to search the Dafny exercise file for `assume` and compare the count with the holes listed by `scripts/vcheck Q01`.
- *"Exit code 0 means finished."* → Ask: what does the learner loop exit with on the shipped files, and what does the gate add?

### K8 [transfer] — a sort that sorts nothing
**viva:** no (survey bank) · **strand:** S13 · **tags:** `spec-strength` · **backward-edge:** none

A verified function promises only that its result is sorted. Name a wrong body that verifies against that promise, the clause that would rule it out, and one concrete check that would catch the wrong body.

**Target insights**
- An empty result (or any constant sequence) is sorted, so a body that returns it meets the promise: verified, and wrong.
- The missing clause relates the output to the input: the same elements with the same multiplicities (a permutation), which also fixes the length.
- A use-site check on one concrete input (sorting `[3, 1, 2]` must give `[1, 2, 3]`) fails on the wrong body: it pins the result where the specification does not.

**Misconceptions & counter-moves**
- *"The verifier would notice that the body throws the data away."* → Probe K8; ask: what did the verifier prove about `r`, and what did it never look at?
