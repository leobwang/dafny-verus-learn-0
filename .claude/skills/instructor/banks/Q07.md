### K1 [predict] — a ground term and a symbolic one
**viva:** yes (verifier-refereed predict) · **strand:** S4 · **tags:** `fuel`, `prover-choice`, `false-friends` · **backward-edge:** Q04 (prover choice: `compute` evaluates a closed term)

`Doubling(n)` is 2 to the power `n`, defined by recursion. With empty bodies: [a] `Doubling(5) == 32`, a ground term; [b] `Doubling(n + 3) == 8 * Doubling(n)`, a symbolic argument three levels down; and in Verus only, [c] the ground term by `compute_only`. Predict `scripts/vcheck --module Q07`'s verdict on each, in each language (`D:<a> <b> V:<a> <b> <c>`, each `ok` or `fail`). Then: what closes each failing one, and why does Verus's [a] need more unfoldings than [b]?

**Target insights**
- Dafny unfolds a recursive function freely when its arguments are literals: [a] verifies with an empty body, by evaluation. A symbolic argument unfolds only to the default depth, short of three levels, so [b] fails; `{:fuel Doubling, 3}` on the lemma closes it.
- Verus unfolds a recursive spec fn once by default, whatever its argument: [a] and [b] both fail. `reveal_with_fuel` raises the depth for one proof. [b] closes at `doubling(n)` after three levels; [a] has nothing symbolic to stop at, so it needs every level down to the base case: fuel 5 still fails, 6 verifies.
- `compute_only` hands a closed term to Verus's interpreter: [c] needs no unfolding by the solver at all. It is the tool for ground terms, and useless with a variable in the term (Q04's prover choice; P3v's [c]).
- The same lemma text, two verifiers, two outcomes: count the levels a goal needs, and know which verifier evaluates literals for you.

**Misconceptions & counter-moves**
- *"Both verifiers unfold the same way, so the verdicts match."* → Probe: [a] in each language; ask: what does Dafny do with literal arguments that Verus does not?
- *"The fuel a ground term needs is its argument."* → Probe: Verus [a] with fuel 5, then 6; ask: which level does the fifth unfolding stop at, and what does the goal still need there?
- *"`compute` would close [b] too."* → Ask: what does the interpreter do with `n`? (P3v's [c] printed its warning.)

### K2 [reconstruct] — what a reveal gives, and what fuel gives
**viva:** yes · **strand:** S4 · **tags:** `opacity`, `fuel` · **backward-edge:** Q06 (opacity: what a `reveal` lets the solver see, and where)

In each language, reconstruct what an opaque recursive definition looks like to the solver, what `reveal` changes, and what fuel changes. Then read the probe: one goal, three levels down, proved [a] with neither, [b] with a reveal only, [c] with fuel only (Dafny) and [d] with both. Which verify, and what does each failure tell you?

**Target insights**
- An opaque definition is known by its signature only: no unfolding happens at all, so [a] fails whatever the depth.
- A `reveal` (Dafny `reveal Stairs();`, Verus `reveal(stairs)`) makes the body visible in that proof, at the default depth: one or two levels, not three, so [b] still fails.
- Fuel sets the depth but reveals nothing: Dafny's `{:fuel Stairs, 3}` on an opaque function without the `reveal` leaves [c] failing. Verus folds the two into one call: `reveal_with_fuel(stairs, 3)` reveals and sets the depth.
- So the two settings answer two questions: "may the solver see the body?" and "how many times may it unfold it?". A failure reads as a plain postcondition failure in every case; only the cause differs.

**Misconceptions & counter-moves**
- *"A reveal unfolds the definition completely."* → Probe: [b]; ask: how many levels does the goal need, and how many does the default give?
- *"Enough fuel makes the reveal unnecessary."* → Probe: Dafny's [c]; ask: what can fuel unfold if the body is hidden?
- *"The error message will say which one is missing."* → Probe: the three Dafny failures; ask: how do their messages differ? (They do not.)

### K4 [why] — a call refused at its precondition
**viva:** yes · **strand:** S5 · **tags:** `standard-library`, `lemma-call` · **backward-edge:** Q04 (a library call's `requires` is checked at the call)

A positive number should not shrink when it is scaled by `k`. The proof is one library call, the library's fact that scaling a positive number by a positive factor does not shrink it, in each language. Both runs fail at the call's precondition, not at the postcondition. Why, and what is the right fix: a different call, an extra assertion, or a change to the statement?

**Target insights**
- The call's `requires` asks for `0 < k`; the statement gives only `0 <= k`. The verifier checks a callee's `requires` at the call, so the call is refused there, and the lemma's own postcondition is then not reached.
- The precondition is not a technicality: at `k == 0` the product is 0, below any positive `y`, and the statement itself is false. The test exhibits it (`k, y := 0, 3`).
- So the fix is to the statement (`0 < k`), after which the same call verifies in both languages. Searching for a stronger library lemma, or asserting `0 < k`, would hunt for a proof of a false claim.
- Read a library lemma's `requires` before its `ensures`: a refused call is often the counterexample, pointed at.

**Misconceptions & counter-moves**
- *"The call needs a different lemma."* → Probe: the `@Test`; ask: is the statement true at `k == 0`?
- *"Add `assert 0 < k;` before the call."* → Ask: what will the verifier say about that assertion, and why?
- *"The error is in the library."* → Probe: the Dafny `related:` line; ask: whose `requires` is it, and who must establish it?

### K8 [transfer] — porting a midpoint
**viva:** yes · **strand:** S1 · **tags:** `fidelity-audit`, `exec-overflow`, `false-friends` · **backward-edge:** none

The source is a Dafny function on `int`: the midpoint of `[lo, hi]`, rounded down, `lo + (hi - lo) / 2`, with a lemma that it lies in the interval. Port it to Verus code on `i32`, keeping both promises. Run the first port; explain its error and give a sample input that shows it. Then a mutant computes the sum halved, `(lo + hi) / 2`: which contract kills it in each language, and what does that say about a port's contract?

**Target insights**
- The source has no overflow obligation: `int` is unbounded. The port's `hi - lo` on `i32` can overflow (with `lo` near the minimum and `hi` near the maximum, the difference needs 32 bits unsigned): Verus's obligation is the port's, not the source's. Widening to `i64` (or a `requires` on the range, which changes the contract) discharges it.
- The mutant agrees with the source in Dafny: `/` on `int` is Euclidean, which on any integer sum is the floor, so `(lo + hi) / 2 == lo + (hi - lo) / 2` for every `lo <= hi`, and the Dafny method verifies. In Verus code `/` truncates toward zero, so for a negative odd sum (`lo = -3`, `hi = 0`) the mutant returns `-1` where the contract's `lo + (hi - lo) / 2`, computed in the specification, is `-2`: the Verus contract kills it. One mutant, two verdicts: a fidelity finding, from the two meanings of `/` (C7dv).
- Mutant-kill parity is a test of the two contracts, not of the code: with only `lo <= r <= hi` in its `ensures`, the Verus mutant verifies too (the probe below), and so it would in Dafny.
- The differential sample needs the edge rows: the extreme `i32` interval (overflow) and a negative odd sum (rounding); a sample of small positive intervals passes every port above.

**Misconceptions & counter-moves**
- *"The port is the same expression, so it inherits the source's proof."* → Probe: the first port; ask: which operation has an obligation in Rust that it lacks on `int`?
- *"`(lo + hi) / 2` is the same midpoint."* → Probe: the Dafny mutant against the Verus one; ask: at which inputs do the two `/` disagree?
- *"`lo <= r <= hi` pins the midpoint."* → Ask: which outputs does it accept at `lo = -3`, `hi = 0`?
