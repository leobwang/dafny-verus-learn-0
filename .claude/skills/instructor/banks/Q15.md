### K1 [why] — a header that counts bytes
**viva:** yes · **strand:** S9 · **tags:** `lsp` · **backward-edge:** Q09 (the editor's door: a hint, not a verdict)

Every Language Server Protocol message is a `Content-Length: <n>` header, a blank line, then the body. Your client frames a `didOpen` whose text holds the character `≤`. Why does the header count the body's bytes and not its characters? With Python's default `json.dumps`, and with `ensure_ascii=False`, which length would a client that counted characters get wrong, and why must the reader count bytes whatever the client does? Then: once the framing is right, why is your client's report still not a verdict on the file?

**Target insights**
- The stream has no other boundary: the reader takes exactly `n` bytes as the body and reads the next header after them. A count that is short by two leaves two bytes of this body to be read as the start of the next header, and every message after it is misread; a count that is long waits for bytes that never come.
- `json.dumps` escapes non-ASCII by default (`≤`), so that body is pure ASCII: 90 characters, 90 bytes, and a client that counts characters gets this message right by luck. With `ensure_ascii=False` the body is 85 characters and 87 bytes (`≤` is three bytes of UTF-8): a header counting characters says 85 and is two bytes short.
- Nothing obliges the other side to escape, so the reader counts bytes, reads exactly that many, and decodes the UTF-8 afterwards; a short read is an ended stream, not a body.
- Framing right is not judging right. The server's per-symbol status says whether each body met its contract, as the server checked it under its own state and options; it counts no hole and leaves no document a third party can re-run (Q09's editor's door, and P1d's answer in the chapter). The client's report is a hint; `scripts/vcheck --gate` is the verdict.

**Misconceptions & counter-moves**
- *"`len(json.dumps(msg))` is the length."* → Probe: the four numbers; ask: which pair differs, and what made the default pair equal?
- *"The server would tell me if the count were wrong."* → Ask: where does the server think your next message starts?
- *"All `correct` means the file is done."* → Ask: what does the server check for a lemma with no body, and which instrument counts it?

**Verifier probe**
```
$ python3 -c '
import json
m = {"jsonrpc": "2.0", "method": "textDocument/didOpen", "params": {"text": "// ≤ BASE"}}
a = json.dumps(m)
b = json.dumps(m, ensure_ascii=False)
print(len(a), len(a.encode("utf-8")), len(b), len(b.encode("utf-8")))
'

```

### K3 [predict] — a trigger written into a statement

The toolsmith's CONTRACT allows trigger changes only, and forbids writing a statement line. A goal ships with an unannotated quantifier in its first `requires` (`goal.dfy`, `goal.rs`). Three Dafny deliveries: [a] writes `{:trigger Glows(k)}` into that `requires`; [b] leaves the statement alone and adds a quantified step with its own trigger in the body; [c] adds a `requires` clause.     true

  }

**Target insights**
- All four verify. Dafny: [a] `freeze-changed`, [b] no finding, [c] `freeze-changed`. Verus: [a] `freeze-changed`.
- A trigger written into a `requires` or an `ensures` changes where the quantifier is instantiated wherever it is assumed (inside the lemma's proof for a `requires`, in every caller's proof for an `ensures`), so it is part of what the clause states. Both freezes keep it: Dafny's statement comparison drops a declaration's attributes but keeps a clause's `{:trigger}`, and Verus's `#[trigger]` stays among the clause's tokens. [a] is a statement change in both languages, although it verifies.
- [b] changes no statement: its trigger sits on a proof step, so no freeze reports it, and only `diff -u` against the shipped goal shows the added line. So the CONTRACT's line "never writes a statement line" is checked by `specfreeze --against`, while "triggers only" (no proof line added beside them) is an audit line, read in the diff. [c] is the change every freeze catches.

**Misconceptions & counter-moves**
- *"A trigger is an attribute, and the freeze drops attributes, so [a] is no change."* → Probe: [a] in Dafny; ask: what does the trigger change for a proof that assumes this `requires`?
- *"A trigger is only a performance hint, so it cannot matter in a statement."* → Ask: which terms must a proof that assumes this quantifier hold before it says anything, with each trigger?
- *"`specfreeze --against` reports no change, so the tool only changed triggers."* → Probe: [b]; ask: which line did the delivery add, and which check would show it?

### K4 [reconstruct] — two lemmas and five verdicts
**viva:** yes · **strand:** S13 · **tags:** `spec-oracles`, `spec-strength`, `vacuity` · **backward-edge:** Q13 (the prose item's hidden equivalence check)

A task `Gap(a: int, b: int) returns (d: int)` has the reference `ensures d == if a >= b then a - b else b - a` and no `requires`. Reconstruct the two implication lemmas `implication` writes for a candidate: what each assumes, what each proves, and which failure each one exhibits. Then, for the candidates C1–C4 below and C5 (`requires a < b && b < a`), say which lemmas verify and the verdict `classify` gives. Why is C3 neither `WEAK` nor `STRONG`, and why does a failed lemma here not prove the implication false?

```dafny
module ProbeK4 {
  // The reference ensures of a task Gap(a: int, b: int) returns (d: int), no requires:
  //   d == if a >= b then a - b else b - a
  // Four candidate ensures, each checked by the two implication lemmas.

  // C1: ensures d >= 0 && (d == a - b || d == b - a)
  lemma GapC1_SpecImpliesRef(a: int, b: int, d: int)
    requires d >= 0 && (d == a - b || d == b - a)
    ensures d == if a >= b then a - b else b - a
  {
  }

  lemma GapC1_RefImpliesSpec(a: int, b: int, d: int)
    requires d == if a >= b then a - b else b - a
    ensures d >= 0 && (d == a - b || d == b - a)
  {
  }

  // C2: ensures d >= 0
  lemma GapC2_SpecImpliesRef(a: int, b: int, d: int)
    requires d >= 0
    ensures d == if a >= b then a - b else b - a
  {
  }

  lemma GapC2_RefImpliesSpec(a: int, b: int, d: int)
    requires d == if a >= b then a - b else b - a
    ensures d >= 0
  {
  }

  // C3: ensures d == a - b
  lemma GapC3_SpecImpliesRef(a: int, b: int, d: int)
    requires d == a - b
    ensures d == if a >= b then a - b else b - a
  {
  }

  lemma GapC3_RefImpliesSpec(a: int, b: int, d: int)
    requires d == if a >= b then a - b else b - a
    ensures d == a - b
  {
  }

  // C4: ensures d > 0 && (d == a - b || d == b - a)
  lemma GapC4_SpecImpliesRef(a: int, b: int, d: int)
    requires d > 0 && (d == a - b || d == b - a)
    ensures d == if a >= b then a - b else b - a
  {
  }

  lemma GapC4_RefImpliesSpec(a: int, b: int, d: int)
    requires d == if a >= b then a - b else b - a
    ensures d > 0 && (d == a - b || d == b - a)
  {
  }

  // C5: requires a < b && b < a, ensures d == 0; its vacuity lemma
  lemma GapC5_Vacuity(a: int, b: int)
    requires a < b && b < a
    ensures false
  {
  }
}
```

**Target insights**
- `SpecImpliesRef` assumes the candidate and proves the reference: if it fails, the candidate allows an output the reference forbids (too weak). `RefImpliesSpec` assumes the reference and proves the candidate: if it fails, the candidate forbids an output the reference allows (too strong). Q13's hidden check is the same pair, run by the grader.
- C1 both verify: `FAITHFUL`, though it reads nothing like the reference (`d >= 0` rules out the wrong sign). C2 only `RefImpliesSpec` verifies: `WEAK`. C4 only `SpecImpliesRef` verifies (at `a == b` the reference gives 0 and C4 demands `d > 0`): `STRONG`. C3 both fail: it is wrong whenever `a < b` and says nothing the reference does not, so it is neither weaker nor stronger, just different: `UNDECIDED`, counted as unfaithful. C5's vacuity lemma verifies: `VACUOUS`, checked before the two implications.
- A failed lemma is "could not be proved", never a counterexample: a true implication the solver cannot prove (a product, a missing unfolding) also fails. `classify` turns every such case into an unfaithful verdict, so the oracle errs only towards calling a faithful specification unfaithful, never the reverse; Lab 2's agreement with the hidden verdicts measures how often.

**Misconceptions & counter-moves**
- *"A specification that looks different from the reference is not faithful."* → Probe: C1.
- *"Failing one direction means failing the other."* → Probe: C2 and C4; ask: which direction does each failure point to?
- *"Both lemmas failed, so the candidate is false."* → Ask: false against what? Name an input where C3 is right.

### K5 [predict] — four true repairs and one client
**viva:** yes (verifier-refereed predict) · **strand:** S12 · **tags:** `refute-repair-prove`, `vacuity` · **backward-edge:** Q03 (vacuity: a contradictory precondition proves anything)

The claim `(a + b) / 2 == a / 2 + b / 2` for naturals ships with no `requires`. Its refutation at `a = b = 1` is given. Four repairs each add one `requires`: A `a % 2 == 0`; B `a % 2 == 0 && b % 2 == 0`; C `false`; D `a % 2 == 0 || b % 2 == 0`. ### K8 [connect] — agreement beyond chance
**viva:** yes · **strand:** S13 · **tags:** `statistics`, `pre-registration` · **backward-edge:** Q09 (a rate with its Wilson interval)

Lab 2 judges your oracles by their agreement with the hidden verdicts. Collapse the verdicts to faithful and unfaithful, and take 30 specifications of which the hidden verdicts call 24 faithful. Oracle A says `FAITHFUL` to all 30. Oracle B agrees on 22 of the 24 faithful ones and on 4 of the 6 unfaithful ones. Compute raw agreement and Cohen's κ for each, and say why the pre-registration's metric is κ. Then: Q09 reported a gate's false-positive rate with its Wilson interval; what does the interval of a verified-but-unfaithful rate of 4 in 20 say about what Lab 2 can claim?

**Target insights**
- A: agreement 0.8, κ = 0. B: agreement 0.867, κ = 0.583. A has learned nothing and still agrees 80% of the time, because most specifications are faithful; κ subtracts the agreement the two sets of margins give by chance.
- So agreement alone rewards the oracle that always says the majority verdict; κ is zero for it whatever the majority, which is why the plan names κ (on the full five-class table, with an interval over tasks) and keeps the confusion matrix beside it.
- Q09's Wilson interval was the honest form of a small-sample rate, and here it is wide: 4 in 20 gives about 0.08 to 0.42. At Lab 2's sizes every rate is a range, the plan states it before the run, and the report scores its prediction intervals against it.

**Misconceptions & counter-moves**
- *"80% agreement is good."* → Probe: oracle A's κ.
- *"κ needs a large sample to mean anything, so agreement is better here."* → Ask: which of the two numbers moves when the oracle learns nothing?
- *"4 in 20 means 20%."* → Probe: the Wilson call.
