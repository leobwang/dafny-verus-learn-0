### K1 [reconstruct] — a name, a contract and a body
**viva:** yes · **tags:** `module-visibility`, `requires-ensures`, `verdict-reading` · **backward-edge:** R01 (callers see the contract, not the body)

Reconstruct, without the chapter, the three separate things a declaration can send across a module boundary, and say which Dafny and Verus construct controls each. Then read the probe: the body of `ScaleR03` / `scale_r03` computes `3 * x`, the API exports a contract `y >= x` (Verus: a lemma stating it) and a lemma `ScaleTripleR03` / `lemma_scale_triple_r03`. The client calls the lemma and states [a], [b] and [c]. Which clause fails in each language, and which sentence of R01 does that verdict repeat at module scale?

```dafny
module R03_ScaleApi {
  export provides ScaleR03, ScaleTripleR03

  // The body computes 3 * x; the contract promises less.
  function ScaleR03(x: nat): (y: nat)
    ensures y >= x
  {
    3 * x
  }

  // A fact about the body, proved here and exported as a statement.
  lemma ScaleTripleR03(x: nat)
    ensures ScaleR03(x) % 3 == 0
  {
  }
}

module R03_ScaleClient {
  import S = R03_ScaleApi

  lemma UseScaleR03()
    ensures S.ScaleR03(2) >= 2      // [a]
    ensures S.ScaleR03(2) % 3 == 0  // [b]
    ensures S.ScaleR03(2) == 6      // [c]
  {
    S.ScaleTripleR03(2);
  }
}
```
```rust
use vstd::prelude::*;

verus! {

mod scale_api {
    use vstd::prelude::*;

    // The body is 3 * x; outside this module only the name crosses.
    pub closed spec fn scale_r03(x: nat) -> nat {
        3 * x
    }

    pub proof fn lemma_scale_ge_r03(x: nat)
        ensures
            scale_r03(x) >= x,
    {
    }

    // A fact about the body, proved here and exported as a statement.
    pub proof fn lemma_scale_triple_r03(x: nat)
        ensures
            scale_r03(x) % 3 == 0,
    {
    }
}

use scale_api::*;

proof fn use_scale_r03()
    ensures
        scale_r03(2) >= 2,  // [a]
        scale_r03(2) % 3 == 0,  // [b]
        scale_r03(2) == 6,  // [c]
{
    lemma_scale_ge_r03(2);
    lemma_scale_triple_r03(2);
}

} // verus!
```

**Target insights**
- Three facts cross separately: the name (it resolves: `provides`, `pub`), the contract (signature, `requires`, `ensures`, and exported lemmas' statements), and the defining equation (Dafny `reveals`, Verus `open`). A name that resolves brings no body with it.
- [a] comes from the `ensures` (Verus: `lemma_scale_ge_r03`), [b] from the exported lemma, called in the client; both verify. [c] needs `ScaleR03(2) == 6`, which only the body says; `y >= 2 && y % 3 == 0` admits 3, 9, … So [c] fails, at line 24 (Dafny) and line 33 (Verus), in the client.
- R01's §2.3 said a caller works from the `ensures`; it also noted that a Dafny `function`'s body is visible to callers. The export set is what removes that visibility: through `provides` a Dafny function is as closed as a Verus `closed spec fn`. A body fact a client needs must be exported as a statement (a stronger `ensures` or a lemma), proved inside the module.

**Misconceptions & counter-moves**
- *"Dafny functions are transparent, so [c] verifies."* → Ask which export keyword names `ScaleR03`, and what `provides` sends.
- *"[b] is also unprovable: the client cannot see `3 * x`."* → Ask what the call `S.ScaleTripleR03(2)` puts in the client's context.
- *"The client should read the body; the fix is `reveals`."* → Ask which fact the client actually needs, and whether a stronger exported statement would serve it without exposing the body.

### K2 [predict] — an exported body over a hidden field
**viva:** yes (verifier-refereed predict) · **tags:** `module-visibility`, `pipeline-stages` · **backward-edge:** none

The Dafny API provides the datatype `GaugeR03` (its constructor and field stay hidden) and reveals `ShallowR03`, whose body reads `g.depth`. The Verus API makes `shallow_r03` a `pub open spec fn` whose body reads the private field `depth`. A client asserts that a fresh gauge is shallow, which the factory's `ensures` states. Predict each verdict: `D:<v> V:<v>`, each `ok`, `fail` or `err:<stage>`.

```dafny
module R03_GaugeApi {
  export
    provides GaugeR03, MakeGaugeR03
    reveals ShallowR03

  datatype GaugeR03 = GaugeR03(depth: int)

  // Revealed, and its body reads the field of a provided-only type.
  predicate ShallowR03(g: GaugeR03)
  {
    g.depth < 5
  }

  function MakeGaugeR03(): (g: GaugeR03)
    ensures ShallowR03(g)
  {
    GaugeR03(1)
  }
}

module R03_GaugeClient {
  import G = R03_GaugeApi

  lemma FreshIsShallowR03()
  {
    assert G.ShallowR03(G.MakeGaugeR03());
  }
}
```
```rust
use vstd::prelude::*;

verus! {

mod gauge_api {
    use vstd::prelude::*;

    pub struct GaugeR03 {
        depth: u32,
    }

    impl GaugeR03 {
        // Public, open, and its body reads the private field.
        pub open spec fn shallow_r03(&self) -> bool {
            self.depth < 5
        }

        pub fn make_gauge_r03() -> (g: GaugeR03)
            ensures
                g.shallow_r03(),
        {
            GaugeR03 { depth: 1 }
        }
    }
}

use gauge_api::GaugeR03;

fn fresh_is_shallow_r03() {
    let g = GaugeR03::make_gauge_r03();
    assert(g.shallow_r03());
}

} // verus!
```

**Target insights**
- Both are refused at resolution, before any proof: the client's assertion is never examined. A revealed or open definition crosses the boundary, so it must make sense on the client's side of it, and there `depth` does not exist (Dafny: "member 'depth' does not exist in abstract type", raised while checking the export set; Verus: "field expression for an opaque datatype").
- The repair is the one §3 names for H6v and H7v: keep the definition public and its body private (`provides` / `closed`). The client then sees the name and the factory's `ensures`, which is all its assertion needs.
- The failure is about the definition, not the assertion. A learner who reads it as "the proof failed" has misread the stage.

**Misconceptions & counter-moves**
- *"`D:ok`: Dafny exports what you ask for."* → Ask what `g.depth` would mean in a module that sees `GaugeR03` as an abstract type.
- *"`V:fail` at the client's assert."* → Point at the stage on the summary line; ask which line the error names.
- *"Make the field `pub` and the problem is solved."* → Ask what that does to the representation the API meant to hide.

### K3 [predict] — an opaque contract inside its own module
**viva:** yes (verifier-refereed predict) · **tags:** `opacity`, `requires-ensures` · **backward-edge:** none

`StampR03` is `opaque`, its body appends `0`, and its contract says only that the result is longer. Both lemmas sit in the same module as `StampR03`. In Verus, `stamp_r03` is an executable function with the same contract, called from the same file. Predict, per language, which of [a] (the length is at least 3) and [b] (the element at index 2 is 0) verify: `D:a:<v>,b:<v> V:a:<v>,b:<v>`.

```dafny
module R03_StampProbe {
  // Opaque: even this module sees the contract, not the body.
  opaque function StampR03(s: seq<int>): (r: seq<int>)
    ensures |r| > |s|
  {
    s + [0]
  }

  // [a]
  lemma StampGrowsR03()
    ensures |StampR03([4, 5])| >= 3
  {
  }

  // [b]
  lemma StampEndsR03()
    ensures StampR03([4, 5])[2] == 0
  {
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// An executable function: every caller, in this module too, sees its ensures only.
fn stamp_r03(v: Vec<i64>) -> (r: Vec<i64>)
    ensures
        r@.len() > v@.len(),
{
    let mut r = v;
    r.push(0);
    r
}

// [a]
fn stamp_grows_r03() {
    let mut v: Vec<i64> = Vec::new();
    v.push(4);
    v.push(5);
    let r = stamp_r03(v);
    assert(r@.len() >= 3);
}

// [b]
fn stamp_ends_r03() {
    let mut v: Vec<i64> = Vec::new();
    v.push(4);
    v.push(5);
    let r = stamp_r03(v);
    assert(r@[2] == 0);
}

} // verus!
```

**Target insights**
- [a] is an instance of the contract (`|r| > 2`, so `|r| >= 3`) and verifies; [b] needs the body (`s + [0]`) and fails, in both languages. Being in the same module gives no exemption: `opaque` hides the body from every caller that does not reveal it, and a Verus `fn`'s body is hidden from every caller, full stop.
- This is H2's situation exactly: the given insertion's contract states membership and validity, not the number of ranges, so a promise about the range count cannot be met by calling it. The honest moves are a stronger contract or building the value yourself; a Dafny `reveal` inside the lemma is the third, local move.
- The well-formedness of [b]'s index is proved from the contract (`|r| > 2`); only the value is missing. That is why the error is a postcondition, not an index out of range.

**Misconceptions & counter-moves**
- *"Opacity is a module boundary, so code in the same module sees the body."* → Point at [b]'s verdict; ask where `StampR03` is revealed.
- *"[b] fails because index 2 may be out of range."* → Ask what the contract says about the length and what the error message names.
- *"Verus needs `#[verifier::opaque]` to hide `stamp_r03`."* → Ask what a Verus caller ever sees of an exec function.

### K4 [why] — partiality moved into a requires
**viva:** yes · **tags:** `requires-ensures`, `spec-strength`, `verdict-reading` · **backward-edge:** R01 (`requires`: what the caller owes)

The API offers two ways to read the first element: `FirstR03` / `first_r03`, total (an empty input gives `NoPickR03` / `None`), and `FirstStrictR03` / `first_strict_r03`, which `requires` a non-empty input. A client with an unrestricted parameter calls both. Explain the verdicts, and say why §8 calls the second design an interface change rather than a proof aid.

```dafny
module R03_FirstApi {
  datatype PickR03 = NoPickR03 | PickedR03(v: int)

  // Total: the empty sequence has an answer too.
  function FirstR03(s: seq<int>): (r: PickR03)
    ensures s == [] <==> r == NoPickR03
    ensures s != [] ==> r == PickedR03(s[0])
  {
    if s == [] then NoPickR03 else PickedR03(s[0])
  }

  // Partial: the empty case is moved into the requires.
  function FirstStrictR03(s: seq<int>): (r: int)
    requires s != []
    ensures r == s[0]
  {
    s[0]
  }
}

module R03_FirstClient {
  import opened R03_FirstApi

  method PeekR03(s: seq<int>) returns (a: PickR03, b: int)
  {
    a := FirstR03(s);        // [a]
    b := FirstStrictR03(s);  // [b]
  }
}
```
```rust
use vstd::prelude::*;

verus! {

mod first_api {
    use vstd::prelude::*;

    // Total: the empty vector has an answer too.
    pub fn first_r03(v: &Vec<i64>) -> (r: Option<i64>)
        ensures
            v@.len() == 0 ==> r == None::<i64>,
            v@.len() > 0 ==> r == Some(v@[0]),
    {
        if v.len() == 0 {
            None
        } else {
            Some(v[0])
        }
    }

    // Partial: the empty case is moved into the requires.
    pub fn first_strict_r03(v: &Vec<i64>) -> (r: i64)
        requires
            v@.len() > 0,
        ensures
            r == v@[0],
    {
        v[0]
    }
}

use first_api::*;

fn peek_r03(v: &Vec<i64>) {
    let a = first_r03(v);  // [a]
    let b = first_strict_r03(v);  // [b]
}

} // verus!
```

**Target insights**
- [a] verifies, [b] fails its precondition at the call: the client's `s` / `v` may be empty, and nothing in the client's context says otherwise. Dafny relates the failure to the `requires` (line 14); the error itself sits in the client.
- Both functions verify inside the API. The strict one is not wrong; it is a different interface: the empty case has been moved from the implementer's proof onto every caller, who must now prove non-emptiness or not call. That is the meaning of "total relative to the stated domain".
- R01's §2.2: a `requires` is what the caller owes. A stronger `requires` is never free; in R03 the domains are fixed by the statements (valid classes, any endpoints with reversed ones meaning empty), and a requirement that a class be non-empty or that two inputs differ is exactly what the API review looks for.

**Misconceptions & counter-moves**
- *"The strict version is fine; an empty input is a caller bug."* → Ask who must prove that, at how many call sites, and what the statement printed in the exercise admits.
- *"[b] fails inside `FirstStrictR03`."* → Ask which line the error names and which line is only related.
- *"Adding `requires s != []` to `PeekR03` fixes it."* → Ask what that does to `PeekR03`'s own callers: the same move, one level up.

### K5 [why] — two representations, one meaning
**viva:** yes · **tags:** `module-visibility`, `sequences-and-views` · **backward-edge:** none

`NetR03` stores two counters; its meaning (`NetViewR03`, Verus `@`) is their difference, and its validity says the first is at least the second. `NetShiftR03` adds one to both. A client proves [a], that a shifted value means the same as the original, and tries [b], that the two values are different. Explain why [a] verifies and [b] does not although [b] is true, and connect it to the client checks in R03's file that compare a split pair of ranges with one range across the surrogate block.


### PP1 — parallel to R03.H2d and R03.H2v (a total constructor proved through its witness)
**Isolates:** `witnesses`, `requires-ensures`

`StockOneR03` (Verus `stock_one_r03`) builds the stock of `n` units of item `k` as at most one row, with no `requires`: `n == 0` gives the empty stock, since every stored row must have a positive count.
```dafny
module R03_PP1 {
  // A stock: rows of (item, count).
  datatype StockR03 = StockR03(rows: seq<(int, nat)>)

  // Every row has a positive count.
  predicate StockValidR03(s: StockR03)
  {
    forall i | 0 <= i < |s.rows| :: s.rows[i].1 > 0
  }

  // Some row holds item k.
  ghost predicate HasItemR03(s: StockR03, k: int)
```

### PP2 — parallel to R03.H5d and R03.H5v (a model built by a client through the API only)
**Isolates:** `module-visibility`, `loop-invariant`

`BagOfR03` (Verus `bag_of_r03`) builds the bag of a sequence in a client module, using only what the bag API exports: the empty bag and `BagPutR03` / `bag_put_r03`, with their contracts. The representation is hidden. Write the body (Dafny: a recursion; Verus: a loop is natural) and prove its contract.

```dafny
module R03_PP2 {
  module BagApiR03 {
    export provides BagR03, InBagR03, BagNoneR03, BagPutR03

    datatype BagR03 = BagR03(items: seq<int>)

    ghost predicate InBagR03(b: BagR03, x: int)
    {
      x in b.items
    }

    function BagNoneR03(): (b: BagR03)
      ensures forall x :: !InBagR03(b, x)
    {
      BagR03([])
    }

    function BagPutR03(b: BagR03, x: int): (r: BagR03)
      ensures forall y :: InBagR03(r, y) <==> InBagR03(b, y) || y == x
    {
      BagR03([x] + b.items)
    }
  }

  module BagClientR03 {
    import opened BagApiR03

    // PP2: the bag of a sequence, built through the exported API only.
    function BagOfR03(xs: seq<int>): (b: BagR03)
      ensures forall y :: InBagR03(b, y) <==> y in xs
      decreases |xs|
  }
}
```

```rust
    pub struct BagR03 {
        items: Vec<i64>,
    }

    impl BagR03 {
        // The meaning: the set of stored values.
        pub closed spec fn bag_set_r03(&self) -> ISet<i64> {
            ISet::new(|x: i64| self.items@.contains(x))
        }

        pub fn bag_none_r03() -> (b: BagR03)
            ensures
                b.bag_set_r03() == ISet::<i64>::empty(),
        {
            let b = BagR03 { items: Vec::new() };
            proof {
                assert(b.bag_set_r03() =~= ISet::<i64>::empty());
            }
            b
        }

        pub fn bag_put_r03(self, x: i64) -> (r: BagR03)
            ensures
                r.bag_set_r03() == self.bag_set_r03().insert(x),
        {
            let ghost old_items = self.items@;
            let mut items = self.items;
            items.push(x);

                assert forall|y: i64| r.bag_set_r03().contains(y) <==> self.bag_set_r03().insert(x).contains(y) by {

                    assert(r.items@[old_items.len() as int] == x);

            }
            r
        }
```
