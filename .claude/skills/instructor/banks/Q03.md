### K1 [reconstruct] — ghost code: where it may go, and what runs
**viva:** yes · **strand:** S7 · **tags:** `ghost-and-modes`, `erasure` · **backward-edge:** Q01 (functions and methods, spec fns and fns: what may call what)

In each language, reconstruct the rules for a ghost variable: where it may be declared and assigned, what may read it, and what of it is left in the compiled program. Then write one line in each language that the tool rejects for breaking those rules, and name the rule it breaks.

**Target insights**
- A ghost variable (Dafny `ghost var`; Verus `let ghost`, or a value carried as `Ghost<T>`) exists for the verifier only: specifications, assertions and other ghost code may use it, and it is erased from the compiled program.
- Information flows one way: ghost code may read executable values, but executable code may never depend on a ghost value, neither by assignment nor by branching on it.
- Where ghost state changes: in Dafny by a ghost assignment statement; in Verus only inside a `proof { }` block.
- The rule exists because of erasure: what runs must not depend on what was erased.

**Misconceptions & counter-moves**
- *"A ghost variable is like a debug-only variable that exists in some builds."* → Probe: the Dafny `Sign` below; ask: if `big` existed at run time, why would the tool refuse to let `r` depend on it?
- *"A Verus `let ghost mut` is assigned like any `let mut`."* → Probe: the Verus `nudge` below; ask: which line is rejected, and where must that assignment go instead?
- *"Then ghost code cannot read exec values either."* → Probe: the repaired versions below verify; ask: in which direction does each repaired line move information?

**Verifier probe**
```dafny
method Sign(n: int) returns (r: int)
{
  ghost var big := n > 100;
  if big {
    r := 1;
  } else {
    r := 0;
  }
}
```

### K2 [predict] — the precondition that is one short
**viva:** yes (verifier-refereed predict) · **strand:** S8 · **tags:** `wp-vc` · **backward-edge:** none

Each file holds two routines with the same body and postcondition and different preconditions. Before running anything, compute the weakest precondition of the body for the postcondition by hand, then predict the verdict of each routine: verified, or an error, and at which line.

```dafny
method ClampA(x: int) returns (y: int)
  requires x >= 3
  ensures y >= 3
{
  y := x - 1;
  if y < 0 {
    y := 0;
  }
}

method ClampB(x: int) returns (y: int)
  requires x >= 4
  ensures y >= 3
{
  y := x - 1;
  if y < 0 {
    y := 0;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

proof fn clamp_a(x: int) -> (y: int)
    requires
        x >= 3,
    ensures
        y >= 3,
{
    let y = x - 1;
    if y < 0 { 0 } else { y }
}

proof fn clamp_b(x: int) -> (y: int)
    requires
        x >= 4,
    ensures
        y >= 3,
{
    let y = x - 1;
    if y < 0 { 0 } else { y }
}

} // verus!
```
Answer form, per language: each routine `verified` or `error at line <n>`.

**Target insights**
- The wp is computed backwards: one implication per branch of the conditional (the branch condition implies that branch's wp), then the assignment `y := x - 1` substitutes into both; then simplify over the integers.
- A routine verifies exactly when its `requires` implies that wp; the check is about every integer the `requires` admits, so one admitted value outside the wp is enough to fail.
- A failed check is reported at the postcondition (in Dafny on the return path, with the `ensures` as related location), never at the `requires` line that is too weak: the message names the obligation, not the fix.

**Misconceptions & counter-moves**
- *"The clamp keeps `y` non-negative, so the postcondition follows from the requires."* → Ask: which branch runs for the smallest `x` each `requires` admits, and what is `y` there? Then run the probe.
- *"An error means the requires is wrong somewhere; the tool will point at it."* → Probe: the recorded locations; ask: which line does each tool name, and why that one?

**Verifier probe** (the code above, one file per language)
(Dafny 4.11.0, `scripts/vcheck instructor/scratch/probe.dfy`:)
```

instructor/scratch/probe.dfy:4:1: error: a postcondition could not be proved on this return path
instructor/scratch/probe.dfy:3:13: related: this is the postcondition that could not be proved
```
(Verus 0.2026.09.27, `scripts/vcheck instructor/scratch/probe.rs`:)

### K3 [why] — `verified` with a hole in it
**viva:** yes · **strand:** S9 · **tags:** `hole-contract`, `exit-codes-and-doors` · **backward-edge:** Q01 (done = verified and zero holes, tool-counted)

In the learner loop, `scripts/vcheck` prints `verified` for a file that still holds a hole, and `--gate` fails the same file. Why is `verified` the right verdict for the loop and the wrong signal to grade by? Name three further things the done gate or the done line checks that the verdict word does not, and what each would let through if nobody checked it.

**Target insights**
- The learner loop reports whether the obligations it checked hold, and lists holes separately, counted by the tool, so that you can work one hole at a time; the verdict word alone says nothing about holes.
- A grader that reads only the verdict word (or the exit code of the loop) accepts unfinished work: that is a naive signal.
- The gate adds zero tool-counted holes and, in Dafny, no warnings; a positive verified count and the module's count pin (a deleted or filtered declaration would otherwise pass); done also needs `scripts/vaudit` (assumptions the hole counter does not count) and `scripts/firsttry.sh <ID> --report --strict` (slots, first tries, commented or deleted checks).

**Misconceptions & counter-moves**
- *"If the summary says verified and 0 errors, the file is done."* → Probe: the files below in the learner loop, then with `--gate`; ask: which number on the summary line differs from what done needs?
- *"Grep for `assume` and bodyless lemmas and you have the hole count."* → Ask: what does the course count holes with, and why never grep? (A comment that mentions a hole is not one; a hole the wrapper counts is one whatever its text.)

### K4 [reconstruct] — from source to a running program, and what you trust
**viva:** yes · **strand:** S10 · **tags:** `pipeline-stages`, `tcb`, `erasure` · **backward-edge:** none

For each language, reconstruct the path from your source file to a verdict and to a running program: the stages in order, the point where ghost code leaves, and what you must trust for `verified` to mean "the compiled program meets its `ensures` on every input".

**Target insights**
- Dafny: parse, resolve (names, types, the ghost and compiled rules), verify (a translation to Boogie, then Z3), compile (to the target language, ghost code erased), run. Verus: the Rust front end and Verus's own type and mode checking, verify (VIR to AIR, then Z3), then `rustc` compiles the executable part with ghost code erased, and it runs.
- The trusted base: the verifier and its translations, the solver, the compiler and runtime of the target, the specifications themselves (yours and the given layers'), and every construct the verifier assumes without proof (assumptions, axioms, external bodies, an `expect` outside a test); `scripts/vaudit` lists the last group.
- A runtime check and a proof are different stages: a check that runs can stop a bad run, but the verifier only assumes it, so it proves nothing about inputs that reach it.

**Misconceptions & counter-moves**
- *"A runtime check such as `expect` is as good as a proof: the verifier accepts the code after it."* → Probe: `Ratio` below verifies, the audit lists the `expect`, and the compiled test fails at it; ask: what did the verifier prove about `Ratio(0)`?
- *"Verified code cannot fail at run time."* → Same probe; ask: which stage reported the failure, and which part of the trusted base did the program rest on?

**Verifier probe**

```dafny
}
```

### K5 [predict] — where the error points
**viva:** yes (verifier-refereed predict) · **strand:** S11 · **tags:** `verdict-reading`, `no-goal-state` · **backward-edge:** Q02 (no goal display: bisecting with `assert`)

Each routine's three steps leave `y` one short of its postcondition. Predict, for each tool, which line or lines its error names: the `ensures` line, the start of the body (the return path), or one of the three steps.

```dafny
method AddTwo(x: int) returns (y: int)
  ensures y == x + 2
{
  y := x + 1;
  y := y - 1;
  y := y + 1;
}
```
```rust
use vstd::prelude::*;

verus! {

proof fn add_two(x: int) -> (y: int)
    ensures
        y == x + 2,
{
    let a = x + 1;
    let b = a - 1;
    let c = b + 1;
    c
}

} // verus!
```
Answer form: `D:<line numbers> V:<line numbers>`.

**Target insights**
- A failure message names the obligation that could not be proved and where it is checked (the postcondition, on a return path), not the statement to change: the tool does not know which step you meant differently.
- "Could not be proved" is a statement about the obligation and the facts available; which step is wrong depends on intent, which only you hold.
- Without a goal display, you find the first step that disagrees with your intent by bisecting with `assert`: state what you believe after each step; the first `assert` that fails brackets the step.

**Misconceptions & counter-moves**
- *"The error line is the buggy line."* → Probe: the recorded locations below; ask: is any of the three steps named?
- *"Then the message is useless."* → Probe: the Dafny bisection below; ask: what did the two asserts tell you that the first run did not?

### K7 [connect] — a witness call against a proof of nothing
**viva:** yes · **strand:** S13 · **tags:** `witnesses`, `vacuity` · **backward-edge:** Q02 (`exists` and `forall` in specifications)

In Q02 you proved postconditions with `exists` by naming a term. Connect that to vacuity: a lemma whose premises contradict each other proves any conclusion. How does calling a lemma on concrete arguments (a witness call) tell a vacuous lemma from a useful one in each language, what kind of verdict does a failing witness call give, and what would confirm vacuity outright?

**Target insights**
- An `exists` is proved by exhibiting a term; non-vacuity of premises is proved the same way: exhibit arguments that satisfy them, by calling the lemma on them.
- The witness call on a vacuous lemma fails at the call's precondition. That is an error verdict (kind 2): on its own it says only that these arguments were not shown to satisfy the premises.
- Vacuity is confirmed by a verified refutation: a lemma whose conclusion is the negation of the premises, for all arguments, verifies (kind 1).

**Misconceptions & counter-moves**
- *"It verified, so the lemma is useful."* → Probe: `FirstIsBig` verifies as written; ask: which input could ever satisfy its `requires`?
- *"The failed witness call proves the premises are contradictory."* → Ask: which verdict kind is it, and what would a verified one look like? Then run the refutation probe.

**Verifier probe**

**Target insights**

- A v0 rule such as "acceptance includes the shipped checks that pin outputs, and no check may be edited" is verifier-class once the checks exist; "the spec says what I meant" stays reader-class.

### PP2 — parallel to Q03.H1v (a loop invariant that feeds a given lifting lemma)
**Isolates:** `loop-invariant`, `ghost-and-modes`

Count the elements of a vector above a bound. The code, the ghost history `h` and its updates, the `decreases`, the first invariant and the final call of the given `lemma_count_lift` are given: write the rest of the loop invariant. ```rust

```rust
verus! {

// The number of elements of s above b, counted from the front.
pub open spec fn count_above(s: Seq<u64>, b: u64) -> nat
    decreases s.len(),
{
    if s.len() == 0 {
        0
    } else {
        (if s[0] > b { 1nat } else { 0nat }) + count_above(s.drop_first(), b)
    }
}

// Given (proved): a history h whose every step adds the count of one element
// ends at its start plus the count of the whole sequence.
pub proof fn lemma_count_lift(s: Seq<u64>, b: u64, h: Seq<nat>)
    requires
        h.len() == s.len() + 1,
        forall|j: int|
            0 <= j < s.len() ==> h[j + 1] == h[j] + (if #[trigger] s[j] > b { 1nat } else { 0nat }),
    ensures
        h[s.len() as int] == h[0] + count_above(s, b),
    decreases s.len(),
{
    if s.len() > 0 {
        let s2 = s.drop_first();
        let h2 = h.drop_first();
        assert forall|j: int| 0 <= j < s2.len() implies h2[j + 1] == h2[j] + (if #[trigger] s2[j]
            > b { 1nat } else { 0nat }) by {
            assert(s2[j] == s[j + 1]);
        }
        lemma_count_lift(s2, b, h2);
    }
}

// updates, the decreases, the first invariant and the final lift call are
// given; write the rest of the loop invariant.
pub fn count_above_exec(v: &Vec<u64>, b: u64) -> (r: u64)

        r == count_above(v@, b),
{
```
