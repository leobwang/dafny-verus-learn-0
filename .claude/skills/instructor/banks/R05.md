### K1 [reconstruct] — what a failure names
**viva:** yes · **tags:** `verdict-reading`, `no-goal-state` · **backward-edge:** R01 (reading a verdict: its stage and its obligation)

Neither verifier shows a goal state, so the failure message is all the evidence you get. Reconstruct what each line of a failure names: the location of the error, a "related" location, and the kind of obligation. Then read the probe. `PairPQ` / `lemma_pair_pq` claims, truly, that `Cat(Chr('p'), Chr('q'))` matches `['p', 'q']`, and its body names no split. What does each language say, and what does each line point at?

**Target insights**
- Dafny gives three locations: the return path that could not establish the postcondition (line 7, the closing of the body), the postcondition itself (line 6), and a related location inside A1 (`RG_A1_Re.dfy:21`, the `Cat` case of `Matches`): the proposition there, the existential over split points, is the conjunct it could not prove. That third line is the nearest thing to a goal: it names the fact the solver lacked.
- Verus gives one location, the `ensures` clause, with "postcondition not satisfied": it does not point into `matches`. The missing fact is the same (no split was named), but the reader must find it from the definition.
- A failure on a true claim is not a counterexample; it says this body did not establish this obligation. The repair is to name what the solver lacked (here a split), not to change the claim.

**Misconceptions & counter-moves**
- *"The related line in A1 means A1 is wrong."* → Ask: which proposition sits on line 21 of the given file, and whose obligation was it to supply a witness for it?
- *"Verus said less, so it checked less."* → Ask: which obligation failed in each language? Is it the same claim?
- *"A failed postcondition means the statement is false."* → Ask: is `['p', 'q']` matched by `Cat(Chr('p'), Chr('q'))`? Which split shows it?
- *"The same message twice means no progress."* → Ask: which assertion would you insert to find out how far the second Verus attempt got?

### K2 [predict] — what a by-block exports
**viva:** yes (verifier-refereed predict) · **tags:** `assert-by`, `lemma-call` · **backward-edge:** R01 (a lemma call supplies a fact on its arguments, at that point)

`Hundreds(n)` is opaque (its definition `n > 100` is hidden), and `HundredsFrom(n)` proves it for `n > 200`. Three lemmas use the helper: [a] calls it inside the `by` block of an unrelated assertion, then asserts `Hundreds(n)` after the block; [b] calls it the same way, then asserts the block's own claim again; [c] calls it outside any block, then asserts `Hundreds(n)`. Predict which labels fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>` (or `none`).

```dafny
module R05_BankScope {
  opaque predicate Hundreds(n: int)
  {
    n > 100
  }

  lemma HundredsFrom(n: int)
    requires n > 200
    ensures Hundreds(n)
  {
    reveal Hundreds();
  }

  // [a] the helper's fact is used after the by-block that called it
  lemma ScopeA(n: int)
    requires n > 200
  {
    assert n + 1 > 1 by {
      HundredsFrom(n);
    }
    assert Hundreds(n);
  }

  // [b] the by-block's own assertion is used after it
  lemma ScopeB(n: int)
    requires n > 200
  {
    assert n + 1 > 1 by {
      HundredsFrom(n);
    }
    assert n + 1 > 1;
  }

  // [c] the helper is called outside any by-block
  lemma ScopeC(n: int)
    requires n > 200
  {
    HundredsFrom(n);
    assert Hundreds(n);
  }
}
```
```rust
use vstd::prelude::*;

verus! {

#[verifier::opaque]
spec fn hundreds(n: int) -> bool {
    n > 100
}

proof fn hundreds_from(n: int)
    requires
        n > 200,
    ensures
        hundreds(n),
{
    reveal(hundreds);
}

// [a] the helper's fact is used after the by-block that called it
proof fn scope_a(n: int)
    requires
        n > 200,
{
    assert(n + 1 > 1) by {
        hundreds_from(n);
    }
    assert(hundreds(n));
}

// [b] the by-block's own assertion is used after it
proof fn scope_b(n: int)
    requires
        n > 200,
{
    assert(n + 1 > 1) by {
        hundreds_from(n);
    }
    assert(n + 1 > 1);
}

// [c] the helper is called outside any by-block
proof fn scope_c(n: int)
    requires
        n > 200,
{
    hundreds_from(n);
    assert(hundreds(n));
}

} // verus!
```

**Target insights**
- `assert P by { … }` proves `P` using the block and exports `P` only. Every fact established inside the block, the helper's postcondition included, stays inside it. So [a] fails: after the block the context knows `n + 1 > 1` and nothing about `Hundreds(n)`.
- [b] verifies: the exported fact is exactly the asserted one. [c] verifies: a call outside any block puts the helper's postcondition into the enclosing context, as any lemma call does.
- The answer: `D:FAILS a V:FAILS a`. Scoping is a tool for keeping a large proof's context small; it is also a way to lose a fact you meant to keep.

**Misconceptions & counter-moves**
- *"Anything proved earlier in the method is known later."* → Ask: where was `Hundreds(n)` established, and where is the block's closing brace?
- *"A by-block is just grouping."* → Probe: move the call out of the block in [a] and rerun; ask what changed in the context.
- *"[b] fails because the helper did nothing for the arithmetic."* → Ask: what does `n + 1 > 1` need, given `n > 200`?

**Verifier probe** (the answer: `D:FAILS a V:FAILS a`)
(Dafny 4.11.0; line 21 is [a]:)
```
vcheck: instructor/scratch/probe.dfy [dafny, learner loop]: failed — 8 verified, 0 holes, 1 error
instructor/scratch/probe.dfy:21:5: error: assertion might not hold
```
(Verus 0.2026.09.27; line 27 is [a]:)
```
vcheck: instructor/scratch/probe.rs [verus, learner loop]: failed — 3 verified, 0 holes, 1 error
instructor/scratch/probe.rs:27:12: error: assertion failed
```
Follow-up for a correct prediction: what is the smallest edit to [a] that keeps the call inside the block and still lets the later assertion verify? (Make `Hundreds(n)` the block's asserted claim, `assert Hundreds(n) by { HundredsFrom(n); }`, so that it is the fact exported.)

**Reread:** §3.1 "`assert … by` keeps its facts local"

### K3 [predict] — five facts about a join
**viva:** yes (verifier-refereed predict) · **tags:** `sequences-and-views`, `verdict-reading` · **backward-edge:** R02 (a split is two slices of one string)

A lemma about `s + t`, with `|t| > 0` and no other fact, states five things in order: [a] the length of the join; [b] the join at index `|s|` is `t[0]`; [c] the join's prefix of length `|s|` is `s`; [d] the rest is `t`; [e] the join's first element is `s[0]`. The Verus file states [c] and [d] with plain `==` on sequences. Predict which labels fail in each language. Answer form `D:FAILS <labels> V:FAILS <labels>`.

```dafny
module R05_BankJoin {
  // Five facts about a concatenation, with no lemma call.
  lemma JoinFacts(s: seq<char>, t: seq<char>)
    requires |t| > 0
  {
    assert |s + t| == |s| + |t|;  // [a]
    assert (s + t)[|s|] == t[0];  // [b]
    assert (s + t)[..|s|] == s;  // [c]
    assert (s + t)[|s|..] == t;  // [d]
    assert (s + t)[0] == s[0];  // [e]
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// Five facts about a concatenation, with no lemma call.
proof fn lemma_join_facts(s: Seq<char>, t: Seq<char>)
    requires
        t.len() > 0,
{
    assert((s + t).len() == s.len() + t.len());  // [a]
    assert((s + t)[s.len() as int] == t[0]);  // [b]
    assert((s + t).subrange(0, s.len() as int) == s);  // [c]
    assert((s + t).subrange(s.len() as int, (s + t).len() as int) == t);  // [d]
    assert((s + t)[0] == s[0]);  // [e]
}

} // verus!
```

**Target insights**
- [a]–[d] are facts the sequence axioms give directly about a concatenation; both tools prove them, Verus's [c] and [d] included (its extensionality for these two shapes needs no `=~=` here; when it does, `=~=` is the step to add).
- [e] is not a fact: when `s` is empty, `s[0]` does not exist. Dafny reports it twice on one line: the assertion might not hold, and the index `s[0]` is out of range, a well-formedness obligation of the expression itself. Verus reports only the assertion: its spec indexing outside the bounds is not an error, just an unknown value.
- The answer: `D:FAILS e V:FAILS e`. One label, two Dafny errors: count obligations, not lines, and read each error's kind.

**Misconceptions & counter-moves**
- *"Five errors would appear if the chain broke at [a]."* → Ask: does a failed assertion stop the verifier from checking the next one? (No: each is checked under the earlier ones.)
- *"Index out of range is a runtime error."* → Ask: which tool reported it, at which stage, and was anything run?
- *"[e] fails because the chain needs a lemma."* → Ask: which input makes [e]'s two sides meaningless?

### K4 [predict] — a fast-channel green that leans on a red lemma
**viva:** yes (verifier-refereed predict) · **tags:** `fast-channel`, `lemma-call` · **backward-edge:** R01 (a caller receives the contract, not the body)

`Overclaim(n)` promises `n * 0 == 1` and has an empty body: its own proof fails. `DependsOnOverclaim(n)` promises `0 == 1` and its body only calls `Overclaim(n)`. The whole file fails, at `Overclaim`. What does the fast channel report for the second lemma alone (`scripts/vcheck --symbol R05_BankLean.DependsOnOverclaim`, Verus `--symbol depends_on_overclaim`)? Answer form `D:<v> V:<v>`, `v` one of `ok`, `fail`, `timeout`, `err:<stage>`.

```dafny
module R05_BankLean {
  // A lemma whose own proof fails: its contract is false.
  lemma Overclaim(n: int)
    ensures n * 0 == 1
  {
  }

  // A lemma that relies on Overclaim's contract.
  lemma DependsOnOverclaim(n: int)
    ensures 0 == 1
  {
    Overclaim(n);
  }
}
```
```rust

verus! {

// A lemma whose own proof fails: its contract is false.
proof fn overclaim(n: int)
    ensures
        n * 0 == 1,
{
}

// A lemma that relies on overclaim's contract.
proof fn depends_on_overclaim(n: int)
    ensures
        0 == 1,
{
    overclaim(n);
}

} // verus!
```

**Target insights**
- The fast channel checks the selected symbol's obligations under every other declaration's contract as stated. `DependsOnOverclaim` calls a lemma whose postcondition, `n * 0 == 1`, is false; the caller receives it anyway, and from a false fact everything follows, `0 == 1` included. So it verifies: `D:ok V:ok`.
- The whole-file run tells the truth: `Overclaim` fails. The fast channel's green is conditional on the contracts it leaned on, proved or not; that is why the done rule is one full gate, not a collection of symbol greens.
- A callee's contract is a promise to its callers (R01 §2); the verifier checks the promise in the callee's own obligation, never at the call.

**Misconceptions & counter-moves**
- *"A green symbol is a proved symbol."* → Ask: which other symbol did its proof use, and what is that symbol's verdict?
- *"The verifier would notice the call uses a false lemma."* → Ask: where is `Overclaim`'s contract checked, and is that obligation in the selected symbol?
- *"The whole-file run would also pass `DependsOnOverclaim`."* → Ask: it does pass it; which line of the whole-file output fails, and what does that say about trusting the caller's green?

```python
sys.path.insert(0, "/home/leobwang/code/learn/dafny-verus/dafny-verus-learn-0-authoring/harness")
from fvh import stats

walls = [1.02, 0.98, 1.10, 1.01, 0.99, 1.31, 0.97, 1.00, 1.04, 0.98,
         1.12, 0.99, 1.01, 1.27, 1.00, 0.96, 1.03, 1.05, 0.99, 1.08]
for n in (5, 20):
    sample = walls[:n]
    lo, hi = stats.bootstrap_ci(sample, statistics.median, seed=11)
    inside = sum(1 for w in sample if lo <= w <= hi)
    print(f"n={n:2d} median={statistics.median(sample):.3f} interval=({lo:.3f}, {hi:.3f}) runs inside: {inside} of {n}")
```

**Target insights**
- A bootstrap interval of a centre (here the median) estimates where that centre of the sampled runs lies, under the resampling assumptions. It narrows as the sample grows (`(0.980, 1.100)` at n = 5, `(0.990, 1.045)` at n = 20) because the centre is better determined, not because the runs became less variable.
- It is not a prediction interval: at n = 20 only 10 of the 20 observed runs lie inside it, and the next run is no more likely to. "95 %" is about the centre, not about individual runs. The values here are typed in, not captured; with a captured log, the same reading applies.
- The R01 lesson carries over: a sample of runs describes those runs (this proof, this host, this order, this seed). A claim about another proof, another workflow or the next run needs its own design.
- Consecutive runs are not independent draws: a warm cache, another job on the host or the order of the runs can move every value together, and the bootstrap assumes the values are exchangeable. The two long runs in the list (1.31 and 1.27) are the kind of value to keep and explain, not to delete because they widen an interval; if a run is excluded, the rule is stated before the runs, and the full log is kept beside the summary.

**Misconceptions & counter-moves**
- *"95 % of future runs will fall in the interval."* → Ask: how many of the twenty observed runs fall in it?
- *"More runs shrink the spread."* → Ask: compare the interval width and the range of the values at n = 5 and n = 20; which one shrank?
- *"The interval shows the proof is stable."* → Ask: stable in what sense, and would a different seed or a changed proof be covered?
- *"Changing the bootstrap seed is a new sample."* → Ask: which numbers were resampled under seed 12, and were any new runs made?

**Verifier probe**

At this precision the endpoints do not move: the seed makes the interval reproducible for one input, and a different seed is a check that the number of resamples is large enough, not a new experiment on the proof.

Follow-up: which statistic would answer "how much does one run vary", and why is it not an interval of the centre? (A spread measure, such as the sample standard deviation or the coefficient of variation; an interval of the centre answers where the centre is.)

### K11 [transfer] — `assert false` as a probe
**viva:** yes · **tags:** `vacuity`, `assertion-repair` · **backward-edge:** R04 (vacuity and the non-vacuity witness)

`Strong(n)` requires `n > 5 && n < 3` and ensures `n * n == n + 1`, with an empty body, and verifies. Transfer the bisection habit: put `assert false;` at the start of the body. What does it mean if that verifies? Compare a sound lemma with the same probe.

```dafny
module R05_BankHollow {
  // A green lemma; is it about anything?
  lemma Strong(n: int)
    requires n > 5 && n < 3
    ensures n * n == n + 1
  {
  }

  // The same lemma with a probe: assert false where the proof starts.
  lemma StrongProbed(n: int)
    requires n > 5 && n < 3
    ensures n * n == n + 1
  {
    assert false;
  }

  // A sound lemma with the same probe.
  lemma SoundProbed(n: int)
    requires n > 5
    ensures n * n > n
  {
    assert false;
  }
}
```
```rust
use vstd::prelude::*;

verus! {

// A green lemma; is it about anything?
proof fn lemma_strong(n: int)
    requires
        n > 5 && n < 3,
    ensures
        n * n == n + 1,
{
}

// The same lemma with a probe: assert false where the proof starts.
proof fn lemma_strong_probed(n: int)
    requires
        n > 5 && n < 3,
    ensures
        n * n == n + 1,
{
    assert(false);
}

// A sound lemma with the same probe.
proof fn lemma_sound_probed(n: int)
    requires
        n > 5,
    ensures
        n * n > n,
{
    assert(false);
}

} // verus!
```

**Target insights**
- `assert false` verifies exactly when the context at that point is contradictory. At the start of a body, the context is the precondition, so a verified `assert false` there proves that no input satisfies the `requires`: the lemma is vacuous (R04 §3.1), and its green says nothing.
- In the sound lemma the same probe fails: some `n > 5` exists, so the context is consistent. Here the failure is the good news.
- Placed later in a body, the same probe asks whether a branch is reachable, or whether facts collected so far contradict each other. It is a bisection probe for inconsistency; it must never stay in a delivered file (it is an assertion that fails on consistent contexts, and a vacuous green is caught only this way or by a non-vacuity witness).

**Misconceptions & counter-moves**
- *"`assert false` verifying means the verifier is broken."* → Ask: what was assumed at that line?
- *"A green lemma is a useful lemma."* → Ask: give an input that meets `Strong`'s precondition.
- *"The probe proves the postcondition is false."* → Ask: what would `assert false` say about `n * n == n + 1` if the precondition were `n == 0`?

### PP2 — parallel to R05.H4d/H4v (bisect and repair)
**Isolates:** `assertion-repair`, `no-goal-state`

A `Star` match of `a` is a `Star` match of `Cat(Eps, a)`. The case split, the choice of the first chunk and the recursive call are given; the facts the solver lacks are not. Find them by bisection and replace the labelled hole with them, keeping every given line.

```dafny
module R05_PP2 {
  import opened RG_A1_Re

  // PP2: a Star match of a is a Star match of a preceded by Eps.
  // The case split, the choice of the first chunk and the recursive call are given.
  lemma StarPadded(a: Re, s: seq<char>)
    requires Matches(Star(a), s)
    ensures Matches(Star(Cat(Eps, a)), s)
    decreases |s|
  {
    if s == [] {
    } else {
      var i :| 0 < i <= |s| && Matches(a, s[..i]) && Matches(Star(a), s[i..]);
      StarPadded(a, s[i..]);
      assume false;  // HOLE: replace this line with the facts the solver lacks
    }
  }
}
```
