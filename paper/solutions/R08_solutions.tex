\section*{Problem B1}\label{ans:B1}
\begin{answer}
\textbf{Task shape:} A 183-page survey of proof engineering across interactive theorem provers meeting the de Bruijn criterion, including Coq, Isabelle/HOL, HOL Light and Agda. It covers foundations, automation, organization, reuse and evolution. The unit is a synthesis of existing work, not a newly executed common task suite.

\textbf{Oracle:} The surveyed ITPs check proof objects with a kernel. The LCF example protects an abstract theorem type while tactics transform goals into subgoals and a proof. The survey does not define one agent acceptance harness or a new uniform oracle across the cited corpora.

\textbf{Trust:} The foundation, kernel and surrounding checking pipeline of each system must be identified. A small checking kernel and a sound abstract theorem interface support the stated criterion; the reported 23 documented critical Coq soundness bugs caution against declaring an implementation infallible. Dafny-style program verifiers are outside this survey summary's scope.

\textbf{Cheat surface:} Information hiding and refinement can protect clients from representation changes; structural tactics avoid dependence on unstable generated names. A repair that changes the theorem may be formally checked yet change the intended claim. Eligibility of artifacts, preserved statements and maintenance intent therefore require separate review; no agent reward-hacking experiment is reported here.

\textbf{Metric:} The cited figures have different denominators: CompCert code versus specification/proof is 13 versus 87 percent of about 35,000 lines; seL4 has about 480,000 proof lines and 20 person-years; hammer results refer to their own corpora. They are second-hand heterogeneous observations, not entries in a pooled ranking or a measured course success rate.

\textbf{Budget:} The summary gives some project engineering scales but no common per-task token, runtime, dollar or sampling budget for an agent experiment. About 20 person-years for seL4 is project effort, not a budget for one repair. Mark the unavailable common budget as unavailable.

\textbf{Variance:} The summary says empirical data on real proof changes and processes is scarce. Its pre-LLM 2019 scope and Coq/Isabelle emphasis limit transfer. The several cited percentages and speedups are different experimental settings; they supply no shared repeated-run variance estimate or confidence interval.

\textbf{Artifact:} Ringer, Palmskog, Sergey, Gligoric and Tatlock, Foundations and Trends in Programming Languages 5(2--3), 2019, arXiv 2003.06458. Retain the exact local line range and digest. The excerpt does not supply an immutable implementation commit, a universal reproduction manifest or a new agent benchmark artifact.
\end{answer}
\section*{Problem B2}\label{ans:B2}
\begin{answer}
(a) \emph{StartLaw}: $\mathit{Matches}(p, w) \iff \mathit{Matches}(p, w)$;
discharged by the engine with an empty proof, checked by verification.
\emph{FeedLaw}: $\mathit{Matches}(\mathit{Trim}(\mathit{Deriv}(st, c)), w)
\iff \mathit{Matches}(st, [c] + w)$; discharged by the engine, from A2's
\emph{DerivCorrect} and a lemma of its own that $\mathit{Trim}$ keeps the
language (the engine must state and prove it in an ordinary lemma, since a
refining lemma inherits the interface's decreases clause). \emph{FinalLaw}:
$\mathit{Nullable}(st) \iff \mathit{Matches}(st, [\,])$; discharged by A1b's
\emph{NullableCorrect}. \texttt{MatchWord}'s postcondition
$b = \mathit{Lang}(p, w)$ is discharged once, by the interface, from the three
laws' statements; a client's postcondition is discharged by
\texttt{MatchWord}'s if and only if the client needs exactly $\mathit{Lang}$.
All are checked by verification; the statements (and $\mathit{Lang}$) by the
specification freeze.

(b) \emph{FeedLaw} fails, because $\mathit{Star}(\mathit{Empty})$ accepts the
empty word and $\mathit{Empty}$ accepts nothing. Take
$st = \mathit{Cat}(\mathit{Chr}(a), \mathit{Star}(\mathit{Empty}))$, $c = a$
and $w = [\,]$. The derivative is
$\mathit{Cat}(\mathit{Eps}, \mathit{Star}(\mathit{Empty}))$, which
$\mathit{Trim}$ rewrites to $\mathit{Cat}(\mathit{Eps}, \mathit{Empty})$: the
left side, $\mathit{Matches}(\mathit{Cat}(\mathit{Eps}, \mathit{Empty}), [\,])$,
is false. The right side, $\mathit{Matches}(st, [a])$, is true: $a$ matches
$\mathit{Chr}(a)$ and the empty rest matches the star. The verifier reports
the engine's own lemma that $\mathit{Trim}$ keeps the language (or, if the
engine has none, \emph{FeedLaw}'s return path) against a postcondition: the
lemma's own, or \emph{FeedLaw}'s, which is stated in the given interface file
\texttt{dafny/given/R/RG\_A2\_MatcherStatement.dfy} (Verus: the trait in
\texttt{rg\_re\_a2/src/step\_matcher.rs}).

(c) $\mathit{Lang}$ is the engine's semantic binding: the interface lets each
engine choose it, so an engine consistent with its own $\mathit{Trim}$ can be
made to verify by redefining what it matches. That proves a different task
(a client wanting $\mathit{Matches}(p, w)$ still fails, as P5 shows), and the
specification freeze (\texttt{scripts/specfreeze --against} the original
snapshot) refuses a delivery whose $\mathit{Lang}$ differs from the shipped
one, whatever the gate says.

(d) A refinement may add a postcondition: Dafny re-verifies the inherited
body of \texttt{MatchWord} against it, Verus checks an implementation's own
body; a client that knows the concrete engine may then use it. It may not add
a precondition: Dafny refuses at resolution (``a refining method is not
allowed to add preconditions''), Verus refuses any \texttt{requires} on a
trait method's implementation. A client of the interface calls
\texttt{MatchWord} on every pattern and word, so a stronger precondition
would break it; a stronger promise gives it more, never less.
\end{answer}
