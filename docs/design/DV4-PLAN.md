*Status: **DV4 plan, 2026-10-06, revised the same day after the plan review** (the DV4 planning lane of the DV3b/DV4 planning workflow). Nothing in this plan is built. It plans the rest of the research harness that Q07's sandboxed Qwen replay, Q09's gate core and the labs (Q12, Q15, Q18; R12, R15, R16) need: the policy protocol and its backends, the instrument runners and the corpus view that the gates compose, budgets, apparatus pinning, the per-run sandbox, `scripts/contract_local.sh`, the benchmark fetcher, and the guard rows, CI coverage and calendar rules that go with them. The `fvh` core that Q06 needed (`fvh.stats`, `fvh.records`, `fvh.holes`, the Python adapter and the `harness` CI job) was built in DV3a (DELTAS Δ134, Δ136) and is not changed here: DV4 extends the core and never changes one of its signatures. `docs/design/DELTAS.md` is authoritative over this plan, as over the design and the spec. Where this plan proposes to amend or supersede an entry (Δ60's fallback, Δ61, Δ63, Δ64, Δ65, Δ75, design D6 and §13.3 item 2), §14 says so; until the orchestrator adopts a proposal as a new entry, the entry stands. §15 lists what the review changed and what it did not.*

> **Predictions first.** This file is in `docs/design/`, which is on the README's *Predictions first* list. It describes apparatus (how model runs are made, bounded, recorded and contained, and how course instruments are run for a gate), never an answer: it names no hole, slot, prediction or exit answer of any module, and no verifier behaviour that a prediction asks about. ## 0. How to read this plan

**Evidence tags.** *[probed 2026-10-06]*: a read-only command this planning lane ran on this host (no container started, no network created, no model called); the captures are lane scratch under `/tmp/dvl0-plan3b4-dv4/`, not archived, and the DV4 build lane re-captures every one it relies on into the author probe archive under `dv4/`. *[DV0]*, *[VERSIONS]*: an earlier archived row (`docs/design/DV0-REPORT.md`, `VERSIONS.md`). *[string]*: evidence from help text or from strings in a binary, never behaviour. *[probe]*: a question the build lane must answer on the pins before relying on it. *[A]*: an assumption with a number, to be calibrated.

**Words.** A *policy* proposes typed actions and never acts (design §11.1 engine 2; spec §5.6). The *executor* is the harness code that validates and performs those actions; it is the only executor. *Policy mode*: a tool-less model call returns actions. *Harness-executed run*: a policy-mode loop whose actions the executor performs, with every verification in a per-run container. *Agent mode*: a tool-using agent CLI (opencode with a local Qwen, or Claude Code under design D6) runs its own tool loop inside a per-run container. A *run* is one task attempt sequence under one arm; a *batch* is the runs of one lab session or one `contract_local.sh` call. An *instrument* is one course tool invocation that a gate reads (`vcheck --gate`, `vaudit`, `specfreeze`, the witness and swap runs). A target's *provenance* is where its text came from: `course` (a course-authored file), `learner` (the learner's own file in the checkout) or `agent` (anything a model wrote, and anything whose origin the harness cannot establish).

**Laws this plan keeps.** No usage-billed API, ever: Claude only through the subscription CLI, with overage checked off on every call (§4.4); Qwen only through the host's Ollama. CI never calls a model, never starts a container and never opens a connection outside its own fakes (§9). Agent output is data (design N2): it is returned to `research/runs/`, judged in a network-less verification container and never executed on the host or merged; every instrument run on an `agent` target goes to that container, whatever code asks for it (§3.7); a `contract_local.sh` patch is applied only by the learner, after reading it. No course script calls `sudo` (§5.1). Every quoted tool output is real (spec §9.3). The memory rules of `CLAUDE.md` §Resources bind containers too (§10). The guard stays a tripwire against accidental exposure; the sandbox exists for research validity (the agent under test sees only its task), not as an anti-spoiler layer (design §13.3).

### 3.2 The protocol (frozen from its first build)

`propose(state, ctx, budget) -> list[Action]` (design §10.3; spec §5.6). Actions are pure data; a policy holds no tool and touches no file.

| type | fields | executor's rule |
|---|---|---|
| `Read` | `path`, `start: int \| None`, `end: int \| None` | `path` must be in `ctx.readable`; returns at most `ctx.read_limit` bytes [A: 64 KiB] |
| `Edit` | `path`, `old`, `new` | `path` must be in `ctx.editable`; `old` must occur exactly once; `new` at most 64 KiB [A]; the edit is applied to the run's work copy, never to the learner tree |
| `Verify` | `mode: "loop" \| "gate"` | runs the task's pinned gate on the work copy in the verification container (§5.9) through `fvh.tools`' `ContainerRunner`; returns the same JSON document that `scripts/vcheck --json` prints |
| `Stop` | `reason: "done" \| "give-up"`, `note` (at most 2 KiB) | ends the run |

- `State` (frozen): `task_id`, `step`, `files` (path → sha256 of the work copy), `last_verify` (the last verifier document or `None`), `history` (the earlier proposals and their observations).
- `Context` (frozen): `task_id`, `lang`, `statement`, `editable`, `readable`, `target`, `max_actions` [A: 8 per proposal], `read_limit`, and `material` (the task's prompt material, as the pre-registration fixes it).
- `Budget` (frozen snapshot): `calls_left`, `tokens_left`, `wall_s_left`, `gpu_s_left`, and `exhausted`.
- `Observation`: `kind`, `ok`, `text` (truncated, with the cut stated), `verdict` (for `Verify`).
- `ACTION_SCHEMA` is the JSON schema of one proposal, `{"actions": [...]}`; `--json-schema` passes it to Claude, and every model reply is validated against it. A reply that does not validate is the attempt's outcome `malformed` (it counts as a call and ends the run); it is never repaired by the harness.

### 3.3 The CI-safe policies

- **`MockPolicy(fn)`**: a deterministic function of `(state, ctx, budget)`. Used for the executor's and the ledger's tests.
- **`ScriptedPolicy(proposals)`**: returns the n-th proposal at step n; raises when the script runs out.
- **`ReplayPolicy(run_dir)`**: replays a recorded run's `actions.jsonl` proposal by proposal and checks, at each step, that the state's file digests equal the recorded ones; a difference stops it with `replay-diverged`. `fvh report` uses it to re-derive outcomes from logs (design §11.1, acceptance: "`fvh report` reproduces every table from logs").

### 3.4 The model backends (policy mode)

Both transports return a `Completion` (the reply text or structured output, token usage, turn count, wall-clock seconds, and the apparatus facts of the call). `ModelPolicy(transport, render, parse)` turns one into a `Policy`; the rendering of a state into a prompt is the policy author's (§14 Q7). A transport is built from the apparatus file only; with `FVH_NO_MODEL=1` in its environment, building one raises before anything is executed (§9).

**Claude (`fvh.backends.claude`).** The argv is Δ63's, as probed on 2.1.288 [DV0] and re-checked against 2.1.289's help [string]:

```
<pinned version file> -p --safe-mode --tools "" --strict-mcp-config --no-session-persistence
    --output-format stream-json --verbose --json-schema <ACTION_SCHEMA> --model <pinned>
    --effort <pinned> --system-prompt <prompt> --max-turns 2 <message>
```

- **The binary** is the pinned version file, written in the apparatus file relative to `HOME` (`~/.local/share/claude/versions/<version>`) with its sha256, never the `claude` link, so an auto-update cannot change the apparatus under a batch. `fvh` checks the sha256 before every exec.
- **The environment** is built from nothing: a minimal `PATH`, `HOME` and `CLAUDE_CONFIG_DIR` set to the run's state directory (§5.7 says what credentials it holds), `LANG=C.UTF-8`, `TERM=dumb`, and `DISABLE_AUTOUPDATER=1`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, `DISABLE_TELEMETRY=1`, `DISABLE_ERROR_REPORTING=1` [string; their effect is a probe]. No `ANTHROPIC_*` variable and no `CLAUDE_CODE_OAUTH_TOKEN`; the parent session's `CLAUDE*` identity variables and `CI` are removed (as `tests/acceptance/guard_doors.py` does). Never `--bare`, never `--mcp-config`, never a tool.
- **The working directory** is a fresh empty directory made by `mktemp -d` under `/tmp` (a name that names no task, module, `Solutions`, repo or session, Δ63), checked empty after the call and removed. Records say "system prompt replaced; environment context still injected" (Δ63).
- **Init assertions**, every call: `tools == ["StructuredOutput"]`, `mcp_servers == []`, `model` equals the pin, `apiKeySource == "none"`, `claude_code_version` equals the pin, `cwd` equals the run's directory, and `plugins` and `skills` empty under the isolated config [probe: Δ63 saw plugins listed under `--safe-mode` with the user's config]. A failed assertion discards the reply unread, stops the batch with `apparatus-mismatch`, and counts as an infrastructure failure, never as an attempt.
- **Overage assertions**, every call (§4.4): the call's `rate_limit_event` must show `isUsingOverage == false` and an `overageStatus` in the apparatus file's allowed list (today `["rejected"]`, from DV0's record). A failure stops the batch as `apparatus-mismatch` before the next call, and the record keeps the call's event.
- **Result checks:** `is_error` false, `num_turns` at most the cap, `structured_output` validates. Kept in the record: `usage`, `modelUsage`, `num_turns`, `permission_denials`, the `rate_limit_event`; `total_cost_usd` is recorded as notional and is never a budget unit.
- **Open probes (DV0-REPORT §8 item 23):** whether `--max-turns` is enforced beyond 2, how much environment context `--system-prompt` keeps besides the cwd, whether the isolated config removes the listed plugins, and whether every call emits a `rate_limit_event` (if not, a call without one inherits the batch's last event, and a batch whose first call has none stops).

**opencode (`fvh.backends.opencode`), on the host, tool-less.** Δ64's recipe, pinned:

- argv `<pinned opencode> run --pure --format json -m ollama/<tag> <message>`, from a fresh `mktemp -d` directory under `/tmp` (outside `$HOME`); the binary path and sha256 come from the apparatus file, as for Claude;
- `env -i` with `HOME` and every `XDG_*` directory in the run's state directory, `OPENCODE_CONFIG` pointing at the run's config, and the eight variables `OPENCODE_DISABLE_{CLAUDE_CODE, EXTERNAL_SKILLS, PROJECT_CONFIG, AUTOUPDATE, MODELS_FETCH, LSP_DOWNLOAD, SHARE, DEFAULT_PLUGINS}=1`;
- the config `{"permission": {"*": "deny"}, "tools": {"*": false}, "mcp": {}, "autoupdate": false, "share": "disabled"}` plus one provider whose base URL is this run's Ollama gate address (§5.6.3), never `127.0.0.1:11434`, and whose model entry states the pinned `num_ctx` as its context limit, so that opencode compacts before Ollama truncates [probe];
- **a per-run gate before the first call, without a model call:** `opencode debug agent build --pure` must show every tool false and no `external_directory` rule outside the run directory, and `opencode debug config --pure` must show the gate's address as the only provider URL;
- the reply: `<think>` blocks are stripped (design §11.1), and the rest must be exactly one JSON value that validates against `ACTION_SCHEMA`.
- **Open probes:** whether opencode 1.18.25 needs to fetch its provider package at run time (if so, the package is pinned by sha256 and pre-seeded into the run's cache directory, and a run never fetches); which request options it sends (the gate pins them either way, §5.6.3); and whether it makes requests beyond the agent's turns (session titles, compaction), which the gate counts as calls either way (§6).

**Where Qwen requests go.** Every Qwen request of every mode passes the Ollama gate, which pins the model tag and the request options and counts calls, tokens and GPU time (§5.6.3). Δ65's rule ("every request sets temperature, seed and `num_predict`") is therefore enforced in one place, whatever the client sends. A direct Ollama transport (`fvh.backends.ollama`) is an alternative to opencode for policy mode; §14 Q3 leaves the choice to the orchestrator after the probes.

### 3.5 Agent mode and harness-executed runs

- **opencode agent (Qwen), in a container** (`contract_local.sh`, Q07's replay; Q18's and R16's Qwen agent runs). The same isolation variables and pinned binary as policy mode, inside the agent image (§5.2), with an agent config that enables the read, list, glob, grep, edit, write and bash tools, allows edits only under `/work`, denies every web tool and every `external_directory` path, and sets `mcp {}`. The per-run gate (`opencode debug agent build`) checks that config inside the container before the agent starts. The provider URL is the in-container relay's loopback address (§5.6.2). The course tools inside run in `container-agent` mode (§5.9).
  - **As built for batches** (the user's decision D8; DELTAS Δ219, Δ223): `fvh.batch`'s plan construct `"agent"` (Qwen only, no policy; turns = rounds = the gate's call cap, at most 200; caps `wall_s`, 120–14,400 s, and `gpu_s` only) composes Lab 3's Qwen arm (R16's later). `open()` preflights every agent arm × task: each session's manifest is built (`mksandbox-run --build-agent`, `dvl.sandbox.build_agent`) and self-tested, and an unattested card refuses the batch. Each attempt stages its task by `src` (a file, or a crate's `src/**/*.rs` editable and its other files read-only), and each session runs live through `mksandbox-run --agent-session` with the attempt's derived seeds and the batch's GPU calendar fd. The frozen `fvh.backends.agent` reaches the sandbox only through `scripts/mksandbox-run`. The returned work copy is judged in a fresh verification container: for a lab plan, the lab gate with its lever check and the assumption audit (D24). Arm G's stop is its `Verify` (D17): a failed gate refuses the stop, and a new session continues from the returned work copy with the rest of the attempt's caps.
- **Harness-executed Claude runs: the default, and the only Claude route for agent tasks until step 4c's decision** (design D6's fallback; DV0-REPORT §6). Claude runs in policy mode on the host (§3.4). The executor applies its reads and edits to the run's work copy (text in the run directory, never executed) and runs each `Verify` in a fresh verification container (§5.9). No credential enters a container, and no agent process runs in one.
- **Claude Code agent, in a container (design D6), only in §5.7's form and only after step 4c passes.** `--tools "Read,Edit,Write,Bash,Glob,Grep"` (no web tool, no subagent tool), `--disallowedTools WebFetch,WebSearch`, `--strict-mcp-config`, `--no-session-persistence`, `--max-turns <pinned>`, `--output-format stream-json --verbose`, `--settings sandbox/claude/agent-settings.json` (deny rules for the web tools and for reads of the credentials path), `HTTPS_PROXY` set to the in-container relay of the egress proxy, and §5.7's credential form. Whether `--restricted` belongs on this line is a probe.

| `actions.jsonl`, `observations.jsonl` | every proposal and its observations (policy and harness-executed modes) |

`research/runs/<ID>/ledger.jsonl` is the module's or lab's budget ledger, anchored in `research/ledger-heads.jsonl` (§4.2).

**`RunMeta`** (frozen dataclass, validated like `RunRecord`): `run_id`, `module`, `lab` (or empty), `arm`, `task_id`, `attempt`, `repeat`, `mode` (`policy`, `harness-executed`, `agent`), `backend`, `outcome` (below), `ended_by` (what ended the run: `stop`, `turn-cap`, `call-cap`, `wall-clock`, `malformed`, or a truncation cause), `verify` (the verdict document), `usage` (calls, input and output tokens, turns, wall-clock seconds, GPU-seconds, and the proxy's or gate's own counts beside the client's), `apparatus` (below), `course_commit` and `course_dirty` (the checkout's `HEAD` and whether tracked files differed, at batch start), `inputs_sha256`, `manifest_sha256`, `selftest`, `return_summary`, `secret_scan`, `findings` (run findings such as `ctx-saturated` or `unattributed-calls`), `prereg_sha256`, `ledger_seq`, timestamps.

**From a run's outcome to a `RunRecord`.** `runlog.to_run_record(meta)` derives the frozen `RunRecord` that `fvh.stats` composes, so Q06's types stay as built (Δ134); `runlog.split(metas)` returns the records and the exclusions, which the disclosure block lists per arm.

| `RunMeta.outcome` | scored | `RunRecord` |
|---|---|---|
| a verifier verdict from `verify.json` (one of `fvh.records.VERDICTS`) | yes | that verdict, with `holes`, `errors` and `verified_count` from the document |
| `malformed` (a reply that does not validate) | yes | verdict `error`, `holes` 0, `errors` 1, `verified_count` 0; the work copy's own verdict stays in `RunMeta.verify` |
| `truncated:<cause>` (§4.3 rule 2) | yes, never re-issued | verdict `inconclusive`, counts from the last verification document or 0; the disclosure's sensitivity line recomputes each rate without these attempts |
| `infra-failed`, `apparatus-mismatch` (no model output) | no; re-issuable (§4.3 rule 3) | none; counted per arm in the disclosure |
| `replay-diverged` | no (a report-time finding) | none; `fvh report` fails for that run and says so |
| `planned`, `deferred` | no | none |

**Apparatus** (design §11.1: "records carry CLI version, model id, prompt hash, Ollama digest and sandbox manifest"). Pinned in `sandbox/apparatus.toml` (2g) and collected into every record:

- the Claude CLI version, version-file path and sha256; the model id and effort; the init assertions' results; the allowed overage statuses; "system prompt replaced; environment context still injected";
- the opencode version and binary sha256, and the sha256 of its run config;
- the Ollama version, the model tag and full digest (from `/api/tags`), the unit's `OLLAMA_CONTEXT_LENGTH`, `OLLAMA_KV_CACHE_TYPE`, `OLLAMA_NUM_PARALLEL` and `OLLAMA_FLASH_ATTENTION` (recorded as unset when unset, with the effective value from the server's start-up log when the probe finds one), the GPU driver and CUDA versions, the models resident beside the pinned one (`/api/ps` at batch start and after each request), and the request options the gate pinned (temperature, seed, `num_predict`, `num_ctx`, top-k, top-p);
- the prompt hash: sha256 over the system prompt, the rendered message, the action schema and the policy module's own source;
- the image digests (§5.2), the sandbox manifest's sha256, the toolchain pins (`scripts/dvl/pins.toml`, the `get_toolchain.sh --check` digests), the course commit and dirty flag, and the git tree hash of `harness/fvh` with its own dirty flag;
- the registry budget of the module and the pre-registration hash, for lab runs.

`fvh apparatus --check` compares the host with the pins before every batch. Any difference refuses the batch (exit 3) with the field and both values, and says what to re-probe: an auto-updated CLI, for example, means re-running the policy probes of `VERSIONS.md` §2.3 and re-pinning, never running on the new version silently.

**Re-verification.** `fvh report --reverify <run>` (Docker needed) re-materializes a run's inputs from `inputs.tar.gz` and from `git show <course_commit>:<path>` for the trusted files, checks them against `inputs.sha256`, lays `returned/` over them and re-runs the verification container; a different verdict is a report finding.

### 3.7 Instruments for the gates: `fvh.verdicts`, `fvh.corpus`, `fvh.tools`

Q09's gate core (QPLAN §17.7), Q18's gate v2 and the lab gates compose these; their frozen tests and the Q09 fixtures are DV3b's. DV4 builds the modules, their core tests and the recorder at step 1a, before Q09 is armed.

**`fvh.verdicts`** (plain data): `PASS`, `FAIL`, `UNKNOWN` and `GATE_WORDS`; `XCLASSES`, spec §5.6's ids X01–X18 with their titles; `GRADER_ONLY`, the classes spec §5.6 and `tests/corpus/README.md` mark as needing an oracle the learner never sees (X07, X08, X14).

**`fvh.corpus`** (read-only view of `tests/corpus/<lang>/<ID>/manifest.toml`): each fixture is loaded as two parts kept apart, `Delivery(id, lang, half, target, files)` and `Label(xclass, kind, title, expects)` with `Expect(tool, outcome, kinds)`. `load_half(lang, half, *, root=None) -> tuple[Fixture, ...]`, where `Fixture` holds one `Delivery` and one `Label`. A CI test checks the loader against `scripts/test_corpus.py`'s own (same ids, classes, kinds, targets) on every fixture, so the two cannot drift.

**`fvh.tools`** (one interface for every instrument run, host or container):

- `INSTRUMENTS`: the wrapper instruments of `tests/corpus/README.md`'s table, by the same names (`vcheck --gate`, `vaudit`, `specfreeze --check`, `witness`, `swap-to-false`, `seed-rerun`). `fvh.tools` builds each argv itself from the table; a caller names an instrument and a target, never an argv or an option, so no caller can pass an option the course tools would refuse.
- `ToolResult` (frozen): `instrument`, `target`, `document` (the tool's own `--json` document where it has one, otherwise `{"exit_code", "lines"}` from its normalized text, paths redacted as `scripts/pins.py` does), `exit_code` (or `None`), `killed` (`None`, `"memory"` or `"wall-clock"`), `runner`, `provenance`, `output_sha256`. A kill or a time-out is returned as such and never carries a document that reads as a pass (Δ57, Δ58).
- `Runner`: `execute(instrument, target, *, timeout_s) -> ToolResult`. Three runners: `HostRunner` (the course tool as a subprocess from the course root, under the tool's own caps, with a process-group kill at the time-out), `ContainerRunner` (one verification container per call through `scripts/mksandbox-run`, §5.9), and `ReplayRunner(fixtures_dir)` (the recorded documents; no solver, no Docker). The executor's `Verify` uses the same `ContainerRunner` and `ReplayRunner`.
- **The provenance rule.** `run(instrument, target, *, root=None, timeout_s=None, runner=None) -> ToolResult` resolves the target's real path and gives it a provenance: `course` for files under `tests/corpus/`, `harness/tests/q/fixtures/` and the registry's declared exercise, agentic, given and check paths; `learner` for the learner's own files among those; `agent` for everything else, including every path under `research/` and under the sandbox's run directories. A caller may raise a provenance to `agent` and never lower it. An `agent` target is always run by `ContainerRunner`; asking `HostRunner` to run one raises `ProvenanceError`. So a gate written once runs on the host for the corpus and in the verification container for a delivery, and no later gate can run an instrument on agent output on the host.
- `replay(fixture_id, instrument, *, root=None) -> ToolResult`: the recorded result of one instrument on one fixture, from `harness/tests/q/fixtures/q09/<lang>/<ID>/<instrument>.json` (the instrument's name in a file-safe spelling). The recorded files hold instrument results only, never a fixture's label.
- **The recorder** `python -m fvh.tools.record --half Q [--lang L] [--only ID…]`: author-only (it refuses, exit 3, unless `CI=true` or Δ103's three-condition test holds, like `test_corpus.py --update`). It runs every instrument a fixture's manifest lists through `HostRunner`, one solver job at a time under the caps, and writes the normalized results. The Q09 lane runs it; DV4 tests it on throwaway roots.

## 4. Budgets

### 4.1 Units and where the caps come from

Budgets are counted in **calls, tokens (input and output), turns, wall-clock seconds and GPU-seconds** (spec §5.6). Three levels of cap, each enforced before the call that would cross it:

1. **Per run:** from the lab's pre-registration, or from `sandbox/apparatus.toml`'s defaults for a non-lab run (Q07's replay: turns, calls, wall-clock and GPU-seconds [A: 40 turns, 40 calls, 45 min, 3,600 GPU-s]).
2. **Per module or lab:** the registry's `budget` (`claude_calls`, `claude_runs`, `qwen_calls`, `qwen_runs`, `gpu_hours`; Δ73, Δ75). `fvh` reads it; the registry's checker already holds `gpu_hours` to ≤ 10 per module and ≤ 45 in all.
3. **Rolling windows:** the subscription's own windows for Claude, and the GPU calendar for Qwen (§4.4, §10).

**Which count is the budget's.** Calls and tokens are counted where the request leaves the sandbox: by the Ollama gate for Qwen, by the egress proxy for Claude in agent mode, and by `fvh` for Claude policy calls. A client's own count (opencode's turns, the CLI's stream) is recorded beside it; a model request the client did not report (a title or compaction request, or a request from a tool process) still counts.

### 4.2 The attempt plan, the ledger and its anchors

- **The plan.** Before a lab batch, `fvh run` enumerates every attempt id, `<arm>/<task>/<repeat>/<attempt>`, from the pre-registered arithmetic (calls = tasks × attempts × rounds × arms × repeats, design §11.1), and refuses a plan whose total exceeds the registry budget. No id is added after the plan is fixed. A non-lab batch (Q07's replay) has a one-id plan.
- **The ledger** `research/runs/<ID>/ledger.jsonl` is append-only and hash-chained: each line carries the sha256 of the previous line, and `fvh report` re-checks the chain. Each attempt id moves `planned → running → scored`, or to `infra-failed` or `deferred`. `scored` is write-once.
- **The anchors.** A chain detects edits but not deletion, truncation or a fresh clone. So at each batch's start and end `fvh` appends a line to `research/ledger-heads.jsonl` (tracked; `fvh` refuses to run when git reports it ignored, and `scripts/ci.sh`'s static job fails a `.gitignore` that matches it): `module`, `event` (`open` or `close`), `seq`, `head` (the sha256 of the ledger line at `seq`), `planned`, `date`, `course_commit`. `fvh run`, `resume` and `report` refuse (exit 3, naming the line) when a module has anchors but its ledger is missing, shorter than an anchored `seq`, or hashes differently there; `fvh run` refuses a new batch while the module's last anchor is an `open` (the earlier batch must be resumed). The learner commits the heads file after a batch; `fvh report` lists an uncommitted heads file as a disclosure item. Resetting a budget therefore takes a visible edit of a tracked file, never an accidental `git clean`.
- **Who writes them.** Only `fvh`. `/contract` refuses `research/runs/**` and `research/ledger-heads.jsonl` as allowed files (§8), so no contractor session can write them either.

### 4.3 Checkpoint and resume, so that a limit never becomes best-of-n

1. An attempt that produced any model output and ended for a reason inside the run is scored with that outcome: a malformed reply, a turn, call, token or GPU cap, the wall clock (`inconclusive`, Δ58), a memory kill (`killed(memory)`, never a verdict, Δ57), a verification failure or time-out.
2. An attempt that produced model output and was then cut by a cause outside the run is scored `truncated:<cause>`, with `<cause>` one of `rate-limit` (a window or limit reached mid-run), `auth` (a credential rejected mid-run), `cli-crash` (the CLI's own failure, as its stream or exit shows), `gate`, `proxy`, `docker` and `host-memory` (the run aborted because the host ran short, §10). It is never re-issued; the report counts it per arm, and the disclosure carries a sensitivity line: each rate with these attempts counted as failures and with them excluded. Which of the two is primary is the pre-registration's choice; the default is "counted as failures".
3. An attempt that produced no model output (a rate limit before the first token, a CLI or network failure, an apparatus mismatch, a sandbox that failed its self-test) is `infra-failed`, stays in the ledger, and may be re-issued under the **same id, with the same prompt hash and the same seed**, at most a pre-registered number of times [A: 3].
4. `fvh resume <run>` re-issues only `planned`, `deferred` and re-issuable `infra-failed` ids, in plan order; a `scored` id is never re-run.
5. The report counts infrastructure failures and truncations per arm. A difference between arms beyond the pre-registered bound is flagged as a disclosure item.
6. A batch stops cleanly (`deferred`, never `failed`) when a window or a cap is reached between attempts, and its checkpoint is the ledger itself.

### 4.4 Rolling windows and overage

- **Claude.** After every call `fvh` reads `rate_limit_event.rate_limit_info` (`status`, `unifiedWindows`, `resetsAt`, `overageStatus`, `isUsingOverage`) [DV0 key names]. It stops the batch as `apparatus-mismatch` when `isUsingOverage` is not `false` or `overageStatus` is not in the apparatus file's allowed list (§3.4). It defers the batch when the status is not the allowed one, or when a window's utilization passes the thresholds that protect the study reserve (design §15.3's 25% reserve) [A: 0.8 of the five-hour window, 0.6 of the seven-day window]. A per-window call cap is the second line [A: 60 policy calls per five hours]. Resumption is by hand or at `resetsAt`.
- **Before a batch.** `fvh` keeps the newest event of any batch in `research/runs/claude-window.json`. A batch starts only when that event is younger than one five-hour window and shows an allowed overage status and utilization under the thresholds. Otherwise the batch's first call is a sentinel: one fixed neutral prompt through the same pinned argv, recorded in the ledger as `sentinel`, counted against `claude_calls`, never an attempt; its event decides whether the batch proceeds. No cheaper read-only source of the overage state is known (`claude auth status --json` carries none, §2); step 4a looks for one.
- **Qwen.** A per-run GPU-second cap from the gate's count (§5.6.3), the module's or lab's `gpu_hours`, and the calendar lock of §10.

### 4.5 The pre-registration gate (Δ91, as built in the skills)

For a lab run, `fvh.prereg` recomputes the sha256 of the lines from `% PREREG-BEGIN` to `% PREREG-END` of `paper/<ID>_answers.tex` (refusing missing or repeated markers), finds the module's `prereg` rows in `instructor/gradebook.md` (`| date | ID | prereg | <min> sha256 <first 16 hex> | … |`), and runs only when the newest row's hash prefix equals the recomputed one and its minimum is at least 3. Otherwise exit 3, naming the row and the two hashes. The full hash goes into every record of the batch.

## 5. The sandbox

### 5.1 Docker access

`scripts/mksandbox-run` calls plain `docker` and nothing else (Δ60's decision), and no course script calls `sudo`. Its first step, and its `--check-access` mode, is a read-only check (`docker version` with a short timeout). When that is refused it prints a diagnosis and exits 3, and never escalates:

- the account is listed in `getent group docker` but this login predates the change: "log in again (or start a shell with `newgrp docker`) and re-run";
- the account is not listed: "Δ60's host action is not done: the human runs `sudo usermod -aG docker <user>` and logs in again".

The diagnosis reads only `id` and `getent`; it never tries `sg` or `sudo`. `sg docker` is not a route on this host (Δ60). Rootless Docker stays optional (H2) and needs the `uidmap` package. (The first draft of this plan had a human-only override variable naming another client command; the review's alignment with "no `sudo` from scripts" removed it, §15.)

### 5.2 Images, by digest

| image | content | built by |
|---|---|---|
| `dvl-toolchain` | `ubuntu:24.04` by digest; Python 3 from the base's packages (version recorded); `tar` (used by the input and return streams, §5.8); the pinned Dafny 4.11.0 and Verus `0.2026.09.27.3cf1832` trees exactly as `get_toolchain.sh --check` verifies them (tree digests checked inside the image at build time); the Rust 1.98.1 minimal toolchain; a user `agent` (uid 1000, matching the host user); the in-container relay (§5.6.2) | `sandbox/build-images.sh`, from a staged build context that holds only these inputs (never the checkout as a context) |
| `dvl-agent` | `dvl-toolchain` plus the pinned opencode binary (sha256 checked) and, once step 4c passes, the pinned Claude Code version file, plus any provider package the opencode probe shows it needs | the same script |
| `dvl-netfilter` | **only if Route A is chosen (§5.6.2):** `ubuntu:24.04` by digest with `iptables` and `ip6tables`; run once per run, with `NET_ADMIN` in the holder's namespace only, and never with a mount | the same script |

The digests go into `sandbox/images.lock` (2g) and `VERSIONS.md` §1.4 (its sandbox row, blank since DV0, DV0-REPORT §8 item 26); every manifest names its image by digest, and `mksandbox-run` refuses one that is not in the lock. Image size: about 0.6 GB of Rust toolchain, 0.15 GB of Dafny and 1.6 GB of Verus over the base [probed 2026-10-06, `du`]. Reproducibility of the package layer (a dated package snapshot) is a probe.

### 5.3 The manifest: task-only contents

`scripts/mksandbox-run <manifest>` takes a TOML or JSON manifest (schema 1) and nothing else that can change what a run sees: no flag or variable weakens isolation, and the schema has no field for a host network, a socket mount other than the run's own relay sockets, a device, a capability or a privileged mode.

| key | meaning |
|---|---|
| `schema`, `run_id`, `module`, `kind` | `kind` is `agent` (a container running an agent CLI over the editable files) or `verify` (the verification container); a harness-executed run materializes its run directory once (`--materialize`, with the self-test) and then makes one `verify` run per `Verify` action |
| `image` | a digest from `sandbox/images.lock` |
| `network` | `none`, `ollama` or `anthropic` (§5.6); `verify` runs are always `none` |
| `[limits]` | `mem_gb`, `cpus`, `pids`, `wall_clock_s`, `work_mb` (the `/work` tmpfs), `tmp_mb` (§5.10) |
| `[[file]]` | `src` (course-relative), `dst` (under `/work`), `role` (below), `sha256`, and for a `snapshot` or an `editable` staged from history, `rev` (the commit it was read from) |
| `[[return]]` | the paths that may come back (§5.8) |
| `[agent]` | `cli` (`opencode` or `claude`), the model tag (one the apparatus file pins), the turn cap (agent runs only) |

**Roles.** `editable` (the files the run may change; they live on the `/work` tmpfs), and the read-only roles, each bound read-only: `task` (a stripped task statement), `given` (the module's given layers), `project` (the generated `dfyconfig.toml`, the module crate's `Cargo.toml` with `build = false` and no new dependency, the workspace pins), `tool` (the trusted course tools), `expected` (the module's pins a CONTRACT names), `snapshot` (a committed snapshot a CONTRACT names, §6), and `contract` (the contract text).

**What may enter.** The editable files (a learner's own agentic file for `contract_local.sh`, staged from history, §6; a benchmark task from `bench/**/tasks/`; an attested lab task card's stripped form, §5.4); the given layers of the module's chain; the trusted project copies; trusted copies of the course tools the in-container verifier runs (`scripts/vcheck`, `scripts/vaudit`, `scripts/specfreeze`, `scripts/dvl/`, `scripts/course_items.py`, `MODULES.toml`); the module's `expected/<ID>.counts`, `expected/<ID>.freeze` and any `expected/*.audit` file a CONTRACT acceptance line names; a snapshot a CONTRACT names; the contract text. The toolchain image supplies the standard library and vstd sources.

**What never enters**, refused by source class before anything is copied: the reference set (`Solutions/`, `paper/solutions/`, `tests/instructor/leak_patterns/`, the grader calibration fixtures, `~/.cache/dafny-verus-learn-0/`), the hidden lab truth, `instructor/`, `.claude/`, `.git` and any history, `bench/**/answers/`, `research/` (earlier runs included; the one exception is the single `snapshot` path a CONTRACT names, read from a commit, §6), chapters, banks, rubrics, other modules' files, finished exercises other than the task's own editable files, and every path that is not a regular file (no symlink, no device). The classes are the guard's (`class_of` in the hook, `is_reference` in the checker); the library imports one table and a CI test keeps the three in step.

The run directory lives under `$XDG_RUNTIME_DIR/dvl-runs/<random>/` (a per-user tmpfs, mode 0700; 13 GB and RAM-backed on this host [probed 2026-10-06, `df`]): `in/` (the materialized inputs, never written after the self-test; the read-only roles are bound from here), `work/` (harness-executed runs only: the executor's text work copy, never mounted writable into a container), `out/`, and `state/` (the relay sockets and, in Claude agent mode, the proxy's per-run CA, §5.7). It is removed after the return path has finished, whatever the outcome; what the record needs is in `research/runs/` by then (§3.6).

### 5.4 The pre-run self-test

`mksandbox-run` runs it on the materialized tree before any container starts, and again inside the container (the containment controls, below). Its report and the manifest's sha256 go into the record. Any failure stops the run before the agent starts, as `infra-failed` (§4.3).

1. **Closure.** Every file under `in/` is in the manifest with its sha256 and an allowed role; nothing else is there.
2. **Canaries.** Each reference tree, each answer tree and the hidden truth carry a canary file whose token is `DVLCANARY-` followed by a random suffix; `sandbox/canaries.sha256` (2g) lists the sha256 of each full token and the tree it marks. The self-test refuses any sandbox file that contains the public prefix, and names the tree by the token's hash. No secret is needed in study mode, and no tree is read to check.
3. **Attested task cards.** A lab task card enters only when its stripped form's sha256 is in `sandbox/attested.toml` (2g). The author writes that list once per card with `mksandbox-run --author --attest <card>`, which runs the reference fingerprints and leak patterns on it (item 5); a sealed stratum's cards (Lab 3's) are attested from the archive decrypted into memory (`attest_data`, which records a `source`). Each entry records the scan's rule (`scan`, now `"DV6"`), the public pool files it read (`pools`: their count and sha256) and the sealed reference twins it read (`refs`: their count and sha256; an entry is current only while all three match); attesting a card whose entry names an earlier rule scans it again, rewriting the entry on a pass and withdrawing it on a failure. A study-mode run checks the hash only. **As built** (DELTAS Δ221; the user's decisions D25 and D31, Δ228, Δ237): all 88 lab card files (Lab 1's 22, Lab 2's 20 local and 10 public cards, Lab 3's 36) are attested under `"DV6"`; `mksandbox-run --author --attest-rescan` re-scans every entry once (78 re-attested before the public cards were added; 88 of 88 current at the fix round's re-scan, Δ239).
4. **Public answers.** No sandbox file equals a file under `bench/public/**/answers/` or the learner's `bench/local/**/answers/` (both readable in study mode; they are never mounted), or shares with one at least [A: 3] distinct normalized windows of [A: 24] tokens, counting only windows that occur in none of the module's given layers, the task's shipped form or the matching public task file. The window and the threshold are calibrated at step 1b so that no shipped file of Q01–Q06 and no public task form is flagged.
5. **Author context only** (`--author`, self-gated like every author-only mode, Δ103): the reference twins' answer-region fingerprints and the leak patterns of `tests/instructor/leak_patterns/` are checked too. A study-mode run never reads them, and its record says the check was skipped and why. This departs from design §13.3 item 2 for every run that carries the learner's own work, for the reason in §14 P6. **The fingerprint scan as built** (`author_scan`, `ScanIndex`, `scripts/dvl/sandbox.py`; DELTAS Δ221, D25): the twins' answer spans (each a minimal run of whole consecutive answer lines, those a twin holds and its learner file does not, of at least `SPAN_TOKENS` = 10 tokens; the lab cards' references in `Solutions/bench/local/` are twins) hit a file **whole** (every 7-token shingle of the span is in it) or **renamed** (the span's form with each non-keyword identifier replaced by its first-occurrence index, in one variant with the given layers' declared names kept, occurs as a contiguous run of the file's tokens). Generic structure never counts: text (or, for the renamed test, a form) any learner-visible course code file shows; a shingle or renamed form found in at least `POOL_COMMON` = 2 installed public benchmark files; and, for the renamed test, a span of declaration headers, brackets and comments only. Without the pools installed the scan is stricter, never looser. **Under DV6** (the user's decision D31, Δ237): Lab 2's sealed reference programs and statements and Lab 3's sealed reference deliveries are twins too, read into memory only (`sealed_reference_twins`; a source that cannot be read refuses the attestation and changes nothing), and a sealed twin's exact copy counts even when the public pools show its shape (Lab 2's public cards come from those pools). Known limits: an answer line under 10 tokens is caught only inside a longer copied run (one Lab 3 reference differs from its task form only below the span length; its counted stub holes and the lab gate remain).
6. **Containment controls, inside the container, before the agent starts:** the effective capability set is empty and the user is not root; the root file system is read-only, every bound input is read-only, and only the `/work` tmpfs, `/tmp` and the home tmpfs are writable; no container-runtime socket is reachable; for `network = "none"`, no interface but loopback; for the model networks, only the run's relay answers, a public address does not (IPv4 and IPv6), an external name does not resolve, and none of the host's own listening ports answers on any of its addresses (`mksandbox-run` passes the list it reads from `ss -ltn` and `ss -ltn -6` at run start). The full list of controls, as neutral regression checks, is the by-hand acceptance script `tests/acceptance/sandbox_doors.py` (§9).

### 5.5 Container flags

Every container: `--rm`, a name and label `dvl.run=<run_id>`, `--user 1000:1000`, `--read-only`, `--tmpfs /tmp` and a home tmpfs (size-capped), `--mount type=tmpfs,destination=/work,tmpfs-size=<work_mb>m`, each read-only role bound read-only from `in/` at its path under `/work` (never from the checkout), `--cap-drop ALL`, `--security-opt no-new-privileges`, `--sysctl net.ipv6.conf.all.disable_ipv6=1` (on the holder in Route A), `--pids-limit`, `--memory` equal to `--memory-swap`, `--cpus`, `--ulimit nofile`, `--init`, and the image by digest. Editable files enter and leave `/work` only as a tar stream (§5.8). Never: `--privileged`, `--network host`, `--pid host`, `--ipc host`, a device, `--gpus` (Ollama runs on the host), the Docker socket, `~/.claude`, or any path of the checkout. That Docker mounts the binds over the `/work` tmpfs in path order is checked at step 2b.

### 5.6 Networks

#### 5.6.1 `none`

Every verification container (and so every step of a harness-executed run that runs code), and any run without a model in the container.

#### 5.6.2 `ollama` and `anthropic`: the route to the host

Δ61's probed pattern (a per-run `--internal` network and a host-side process bound to its gateway) has two hazards found while planning:

1. **The gateway address is the host.** A container on the internal network can reach every host port that listens on all addresses (on this host today 22, 3002 and 902, on IPv4 and IPv6 [probed 2026-10-06]), not only the forwarder's, and the gateway also answers containers of other bridges. DV0's probe did not test this.
2. **A plain forwarder exposes all of Ollama's API**, including the endpoints that pull, push, create, copy and delete models: a pull reaches the internet, and a delete removes the user's models. So the forwarder is HTTP-aware: the Ollama gate below.

**Route B (plan of record, subject to step 2c): no network at all.** The container runs with `--network none`. The host-side gate (or, in Claude agent mode, the egress proxy) listens on a Unix socket in the run's `state/` directory (mode 0600, owner uid 1000), bind-mounted at `/run/dvl/`; the image's entry starts a small standard-library relay on `127.0.0.1` inside the container that forwards to the socket, then starts the agent. There is no route, no DNS, no host port and no per-run network object; a process that kills the relay gains nothing. The probe: a bind-mounted Unix socket accepts connections under the docker-default AppArmor profile with `--cap-drop ALL`.

**Route A (fallback, only if Route B fails its probe): Δ61 with the gateway closed.** A holder container joins the per-run internal network; a short-lived `dvl-netfilter` container with `NET_ADMIN`, sharing only that namespace, sets the IPv4 and IPv6 output policies to drop and admits loopback and the gate's address and port; the agent joins the namespace with no capability (`--network container:<holder>`); the holder disables IPv6. The gate admits only connections whose source address is the holder's. Docker's embedded resolver is loopback traffic in the namespace, so the run passes an unreachable resolver and control C8 checks resolution.

§14 P2 proposes the entry that records the gateway exposure and supersedes Δ61's network half with Route B (or amends it with Route A's filter), whichever step 2c keeps.

#### 5.6.3 The Ollama gate (`sandbox/hostside/ollama_gate.py`)

A host-side HTTP proxy (standard library), one per run, listening on the run's socket (Route B), on the internal network's gateway (Route A) or on an ephemeral `127.0.0.1` port (host policy runs). Its upstream is the apparatus file's Ollama address. For every request it:

- admits only the inference endpoints (`/api/chat`, `/api/generate`, `/v1/chat/completions`) and `/api/version`, and answers 403 to everything else (model management in particular), logging the refusal;
- admits only the run's pinned model tag;
- sets the pinned options on every request (temperature, seed, `num_predict` or `max_tokens`, `num_ctx`, top-k, top-p) and records any value it overrode;
- counts calls and tokens (Ollama's own counts where the endpoint reports them) and the request's busy seconds as GPU-seconds, and answers 429 once the run's caps are reached (§4);
- flags `ctx-saturated` when a request's prompt token count reaches `num_ctx` less a margin [A: 512 tokens], since Ollama then cuts the prompt without an error;
- reads `/api/ps` after each request and records any other resident model;
- logs each request and response, with the prompt and reply, to `gate.log` in the run directory.

The probes: which endpoint and options opencode sends; that streamed responses pass through unchanged; and the GPU-second definition against `/api/ps` (a model partly offloaded to the CPU is recorded with its `size_vram`).

#### 5.6.4 `anthropic` (Claude Code agent mode only, design D6, after step 4c)

The egress proxy (`sandbox/hostside/egress_proxy.py`) in place of the gate, on the same route. It is not the first draft's pass-through `CONNECT` proxy: a pass-through proxy cannot tell the CLI's calls from a tool process's, so tool processes could make subscription calls `fvh` never counts and could reach server-side tools through the one allowed host. The proxy:

- terminates TLS with a per-run CA made by the host's `openssl` (version recorded), whose certificate reaches the container through `NODE_EXTRA_CA_CERTS` and whose key stays in the run's `state/` [string: the CLI names the variable; that it honours it is a probe];
- admits only the requests the probe records for an agent run (inference: `POST /v1/messages` on `api.anthropic.com`), refuses a request whose tools include any server-side tool type or that names remote MCP servers, and refuses every other host and path, logging each refusal;
- counts calls and tokens from the responses (the budget's count, §4.1) and reconciles them with the CLI's stream: an excess is the run finding `unattributed-calls`;
- in the preferred credential form, supplies the access token itself (§5.7);
- logs every request line and response status to `egress.log`, without the authorization header.

### 5.7 Credentials (design D6)

**The rule:** no process outside the user's own Claude Code configuration ever holds the refresh token, and no tool process in a container can read a usable access token.

- **Host policy mode (the default route).** For each call, `fvh` writes a **derived snapshot** of the user's current credentials file into the call's `CLAUDE_CONFIG_DIR` (mode 0600): the access token, its expiry, the scopes and the subscription type, without the refresh token. Because it is rebuilt before each call, a refresh by the user's own sessions between calls is picked up. `fvh` refuses to start a call when the access token's remaining life is shorter than the call's wall-clock cap plus a margin [A: 30 min]; the batch is deferred (§4.4). Policy mode has no tool process to misuse the snapshot.
- **Claude agent mode, preferred form: no token in the container** [probe, step 4c]. The container's `CLAUDE_CONFIG_DIR` (a tmpfs) holds a placeholder credentials file: the same keys, a fixed non-secret placeholder token, and an expiry in the future. The egress proxy (§5.6.4) replaces the placeholder in each admitted request's authorization header with the access token it reads from the user's credentials file at that moment; it never refreshes. A tool process that reads the credentials path finds only the placeholder, a host-side refresh mid-run is absorbed, and nothing needs rotating after a batch. The probe: the CLI starts and runs with the placeholder, makes no authenticated request the proxy does not see, and does not try to refresh while the placeholder's expiry is in the future.
- **Fallback form, only if the preferred form fails its probe:** the read-only derived snapshot bind-mounted at the credentials path, as the first draft planned, and then only together with confinement of tool processes by Claude Code's command sandbox (reads of the credentials path and all network denied for commands) [string: its settings names are in the binary; whether it runs inside the container, where `enableWeakerNestedSandbox` suggests a weaker nested mode, is a probe]. In this form a run must fit the access token's remaining life, and control C23 decides whether a host-side refresh ends a run (`truncated:auth`).
- **If neither form passes, Claude never enters a container**: harness-executed runs (§3.5) stay the only Claude route for agent tasks (Q18's ≤ 24 runs, R16's), as design D6 and DV0-REPORT §6 make them the default today.
- **Secret scan.** Every returned file, transcript and log is scanned before it reaches `research/runs/` for the credential formats and, in the fallback form, for the exact token value the run was given (built: `dvl.sandbox.live_run(exact_secrets=…)` scans the returned files, the event stream, `gate.log` and each command's output, Δ222; the Claude transport's run-directory scan, Δ215); a hit withholds that file (its name, size and sha256 are recorded, never its content), marks the run, and asks the human to rotate (`claude auth logout`, then `claude auth login`).
- **The D6 probe (step 4c), with the user's consent** (DV0-REPORT §8 items 20 and 21; author notes §1.3): (a) does a derived snapshot work for a policy call; (b) does the preferred form work for a short agent run; (c) which hosts and paths does the CLI request, with the switches of §3.4 set; (d) the containment controls C21–C25 (author notes §2.2): a tool process reading the credentials path, a tool process sending a request to the allowed host, a server-side tool type in a request, the proxy's count against the stream's, and an access token issued before a host refresh used after it. If (a) fails, host policy mode uses a `CLAUDE_CONFIG_DIR` whose credentials file is a link to the user's own [probe: whether a refresh writes through the link].

### 5.8 The return path

After the agent or executor finishes, the container's entry process keeps it alive, and `mksandbox-run` reads `/work` as a tar stream (`docker exec <container> /usr/bin/tar --create --one-file-system -C /work .`, so the read-only binds are not in it). The host parses the stream with Python's `tarfile` in stream mode and never extracts it, never creates a link and never opens a path the container wrote:

| found in the stream | what happens |
|---|---|
| a `[[return]]` path, a regular file, changed | its content goes to `returned/`, and its diff against the staged input to `patch.diff` |
| a `[[return]]` path, absent | recorded as a deletion in `patch.diff` |
| any other regular file, new or changed | rejected: name, size and sha256 (computed from the stream) recorded, content not kept |
| a member that is neither a regular file nor a directory (a symlink, hard link, device or FIFO), a path that leaves `/work` or repeats, a returned file over the size cap [A: 1 MiB] or not valid UTF-8 | rejected the same way, before any byte of it is kept |

Then the container is removed, then the secret scan (§5.7), then verification (§5.9). Nothing from the container is executed on the host, and nothing is written into the learner tree outside `research/runs/`. The read-only roles never come back: the verification container gets the trusted copies from `in/`. Editable files enter the same way, as a tar stream into `/work` before the agent starts. (The review suggested `docker cp`; a stream through `docker exec` is used instead, because whether `docker cp` reaches a tmpfs mount is uncertain (not tried here) and the stream lets the host check every member before keeping it, §15.)

### 5.9 The verification container

Image `dvl-toolchain`, `network = "none"`, no checkout mount. Its `/work` is a fresh tmpfs with the read-only roles bound from `in/` and only the returned files streamed in over the staged editable files. It runs the course's own gate on the target, `scripts/vcheck --gate --json` from the trusted copy, so the verdict document has the same keys as on the host, and writes it to `out/verify.json`; for a contract it then runs the acceptance lines that `contract_local.sh` checks (§6). Dafny tests (`--target py`), Verus `--compile` tests and Python acceptance tests, which run agent-written code, run only here. `fvh.tools`' `ContainerRunner` uses this container for every instrument on an `agent` target (§3.7).

**`run_capped` in containers.** A container's processes run under the Docker daemon's cgroup, so `systemd-run --user --scope` is not available inside. `scripts/dvl/common.run_capped` gains two container modes, selected by `DVL_CAP`, which `mksandbox-run` sets:

| mode | where | it runs a job when | concurrency |
|---|---|---|---|
| `container-verify` | verification containers | `/sys/fs/cgroup/memory.max` is set and at most the job's pinned cap + 1 GB + the container's tmpfs caps | the pool's pinned jobs |
| `container-agent` | agent containers | `memory.max` is set and at most the job's pinned cap + the agent allowance [A: 4 GB] + 1 GB + the tmpfs caps | one solver job at a time across all pools, held by an `flock` inside the container |

The allowance and the margins are read from the read-only pins (`scripts/dvl/pins.toml`, `[container]`), never from the environment. In either mode a job whose exit is 137 while the cgroup's `memory.events` `oom_kill` count rose is `killed(memory)` (Δ57); the wall-clock net and the exit map stay as built (Δ100). Both modes are tested against fake cgroup files in `tests/sandbox/`.

**Parity acceptance** (once, and after any image change): for every armed unit of Q01–Q06, the in-container gate's verdict, counts and holes equal the host's, in both container modes.

### 5.10 Lifecycle, memory and cleanup

- **Memory.** `--memory` (equal to `--memory-swap`) is the only cap on a container, and tmpfs pages count against it. Verification containers: the pinned job cap + 1 GB + the tmpfs caps (Dafny 8 + 1 + 2.5 = 11.5 GB, Verus 16 + 1 + 2.5 = 19.5 GB [A: `/work` 0.5 GB, `/tmp` 1.5 GB, home 0.5 GB]). Agent containers add the agent allowance (Dafny 15.5 GB, Verus 23.5 GB) [A]. A container killed for memory (`docker inspect` reports `OOMKilled`) is `killed(memory)`, never a verdict (Δ57).
- **Wall clock.** `mksandbox-run` kills the container at the run's `wall_clock_s` (exit 124, inconclusive, Δ58).
- **No orphans.** A detached watcher, as `dvl.common`'s lifeline (Δ100), kills the run's labelled containers and removes any network it made if `mksandbox-run` dies; `mksandbox-run --reap` removes anything labelled `dvl.run` that has no live owner.
- **Concurrency.** One sandbox container at a time by default (`FVH_SANDBOX_JOBS=1`), counted in §10's budget.
- **Agent-mode batch sessions** (§3.5; DELTAS Δ219, Δ223). The session's child process gets SIGKILL when the runner dies (`PR_SET_PDEATHSIG`), and its watcher removes the container and the gate. A session writes its gate counts into its `seg-<k>/` directory, so `fvh resume` settles a killed runner's attempt from them; a session that returns without the sandbox's record has its spend read from `gate-counts.json`, and exit 137/143 or a signal is `killed-memory`: after output the attempt is `truncated:host-memory` (another failure `truncated:container`), scored and never re-issued; before output `infra-failed`. `load_plan` refuses `wall_s` under 120 s, and an attempt with no room for a session is `deferred` (the batch stops).

## 6. `scripts/contract_local.sh`

**Purpose** (design §12; N2): from Q07 on, replay a module's contract under opencode and a local Qwen in a per-run container, from the same starting state the learner's `/contract` run had, and return a patch that the learner reads before deciding whether to apply it.

**Usage.** `scripts/contract_local.sh <ID> [--file <agentic path>] [--model <tag>] [--from <rev>] [--available]`. It is a thin front end: it resolves the module, then runs `uv run --offline --frozen --directory harness python -m fvh contract-local …`, so the ledger, the run log and the sandbox are the same as every other run. `--model` accepts only a tag the apparatus file pins (today `qwen3.8:latest`); any other refuses.

**Steps.**

1. Refuse (exit 3, one line each) a planned or solo module, an empty `agentic` list, a module whose `engines` lacks `agent`, an exhausted `qwen_runs` or `gpu_hours`, a failed `fvh apparatus --check`, a ledger that disagrees with its anchors (§4.2), and no Docker access (§5.1). `--available` runs only these checks and reports.
2. Parse the agentic file's CONTRACT header (line 1; exactly `goal:`, `allowed-files:`, `acceptance:`) and validate every allowed path by `/contract`'s rules (`.claude/skills/contract/SKILL.md` §2: in the module's own `agentic` list, never a solo, frozen, guard or reference path, never `research/runs/**` or the ledger anchors). A malformed header refuses, as `/contract` does.
3. **Find the starting state.** The replay must start where the learner's `/contract` run started, never from the learner's tree as it stands after that run (which would hand the replay another agent's answer to its own task). The starting state is the commit that last changed the snapshot the CONTRACT names in a `scripts/specfreeze --against <snapshot> <file>` acceptance line, or the commit `--from <rev>` names. Refuse (exit 3) when the CONTRACT names no snapshot and no `--from` is given, when the snapshot is missing, untracked or differs from `git show HEAD:<snapshot>`, or when an allowed file did not exist at that commit. Every allowed file is staged as `git show <rev>:<path>` (role `editable`, `rev` recorded), and the snapshot as `git show <rev>:<snapshot>` (role `snapshot`, read-only, at its course path so the acceptance line works unchanged inside).
4. Build the rest of the manifest (§5.3): the `[[return]]` set (the allowed files), the module's given layers, the trusted project and tool copies (`scripts/specfreeze` included), the module's `expected/<ID>.counts` and `.freeze` and every `expected/*.audit` file an acceptance line names, and the instructions: the parsed contract, `CLAUDE.md` §Contractor contract's fallback rules, and the learner's own contract sections (`Q-vN`, `R-vN`) copied verbatim. Nothing else of `CLAUDE.md`, and no chapter.
5. Run the opencode agent (§3.5) in the container with `network = "ollama"`, under the run caps (§4.1). Inside, the contract's own commands work unchanged in `container-agent` mode (§5.9): the agent can run every acceptance line that `contract_local.sh` checks.
6. Return path (§5.8), secret scan, then the verification container, which checks the acceptance lines of the forms below. Every other line, and every transcript discipline ("re-verify after every edit", "one full gate run, last"), is listed for the learner's audit with the transcript.
7. Print the run directory, the patch's path and line counts, one line per checked acceptance line (met or not), and one verdict line. **Never apply the patch.** The learner reads `patch.diff` and applies it by hand (`git apply`), or not; a later `/contract` or `/review-code` session sees only what the learner applied.

**Acceptance-line forms `contract_local.sh` checks** (the parser in `fvh.contract`; a CONTRACT that uses other wording loses only the machine check, never the run):

| form in the `acceptance:` line | checked |
|---|---|
| `` `scripts/vcheck --gate <file>` exits 0 `` (optionally "and prints only the summary line") | in the verification container, on the patched copy |
| "zero holes" | from the same run's document |
| `` `scripts/specfreeze --against <snapshot> <file>` reports no change `` | in the verification container, against the read-only snapshot |
| `` `scripts/vaudit <file>` reports no finding `` and `` `scripts/vaudit --compare expected/<name>.audit <file>` reports no difference `` | in the verification container, with the trusted pin |
| a `git diff` line ("`git diff` against the committed snapshot changes …") | not run in a container (no `.git` enters): `patch.diff` is exactly that diff, so it is shown as this line's evidence and the line goes to the learner's audit list |

**Exit codes:** 0 the run completed (whatever the verdict), 1 the run failed (self-test, containment, agent crash), 2 usage, 3 refused. An infrastructure failure before model output does not use up `qwen_runs` (§4.3 rule 3); a truncation after model output does (rule 2).

**Calls and turns.** The registry's `qwen_calls` is counted by the gate and includes any request opencode makes besides the agent's turns; the turn cap is opencode's own step limit and is set no higher than the call cap. Step 3a measures how many requests one turn costs (session titles, compaction) and disables the extra ones in the run config if opencode allows; if it does not, the turn cap drops until the two agree, before Q07's replay is armed.

## 7. Benchmarks: `scripts/get_bench.sh` and `bench/`

### 7.1 The manifest and the layout

**Answers never enter a sandbox:** `bench/**/answers/` is a refused source class (§5.3), and the public answers are checked against every sandbox (§5.4 item 4).

### 7.2 `scripts/get_bench.sh`

- `get_bench.sh <set>`: `git fetch` of the pinned commit only (never a branch), a check that the fetched tree's commit equals the pin, normalization into `tasks/` and `answers/` by the layout map, the upstream licence and notice files copied verbatim, and the tree digest against the manifest; any difference refuses (exit 3) and installs nothing. Idempotent.
- `--check`: offline; re-computes the digest of an installed set, and refuses a set whose licence or notice files are missing or differ from the manifest's sha256.
- `--list`: the sets, their licences, upstream licences and modes, and whether each is installed.
- `--validate <set> [--only …]`: the re-validation on the course pins (design §6.5). Each task's answer through `scripts/vcheck --gate --json` in a scratch copy, one solver job at a time under the caps, and the task form must not verify as shipped. Writes `validation.jsonl` (per task: verdict, holes, the resource count, time). A lab's pool is the tasks that validate (DV5). A benchmark's trusted declarations go into a per-benchmark trust allowlist (design §6.5) [probe, per set]. **As built** (DELTAS Δ221): `--validate SET [--only NAME…] [--sample N --seed S] [--workers N --mem-gb SHARE] [--restart]`. The pool rule, stricter than above: the answer passes the done check (`vcheck --gate`, verified with 0 holes, and `vaudit`, no finding) and, as a delivery for its task form, the lab gate's static half (`specfreeze --lab`, 0 findings); the task form fails `vcheck --gate` as shipped at the verify stage; an answer equal to its task form is no task. A job killed by memory (137/143), stopped by the net (124) or without JSON is never a verdict: the next invocation re-runs its row. Resumable (`validation.partial.jsonl`; another selection, set digest or tool pins needs `--restart`) and stoppable (SIGINT/SIGTERM keep the finished rows); `--workers` 1..4 (default 1) within `--mem-gb` (workers × cap ≤ the share; MemAvailable ≥ share + 15 GB at the start and cap + 15 GB before each job, else it waits); `--sample N --seed S` is a pre-registered, seeded, stratified sample for a set projected over 6 h. `validation.jsonl` (schema 3) opens with a header row: the set digest, the pins digest, the selection, the wall time and the counts by reason and stratum. `DVL_BENCH_TMP` places the temporary trees.
- `--pin-pool SET…`: author-only (rule 1b, like `--pin`; `scripts/dvl/bench.py --pin-pool` the same): records a finished validation's pool in `bench/public/POOLS.toml` (§7.1), keeping the file's `[[draw]]` records; `--check` then compares an installed `validation.jsonl` with its entry.
- `--pin`: author-only (Δ103's three-condition test; rule 1b): writes `sha256` into the manifest.
- **The licence rule** (design §11.1): `vendor` only when the repository's licence is MIT or Apache-2.0, **and** every upstream source of the subset is too (recorded in `upstream`), **and** `leak_scan` names DV5's scan of the set's answers against every twin's answer lines (author notes §2.4). Everything else is `fetch`. `get_bench.sh` refuses to vendor a set whose manifest says otherwise. **Every set starts as `fetch`**; a set moves to `vendor` only in the entry that records its scan.

## 10. Memory and GPU calendar

- **One budget.** Containers count in `CLAUDE.md` §Resources' 48 GB solver budget at their `--memory` cap (§5.10), which includes their tmpfs. Before a container starts, `MemAvailable` must hold its cap plus 15 GB; otherwise the run is deferred, never started. A run aborted because the host ran short mid-run is `truncated:host-memory` (§4.3).
- **One sandbox job at a time** by default; two only when both caps plus 15 GB are available and no solver sweep runs beside them.
- **Qwen.** One model resident at a time: the gate admits only the pinned tag and records any other resident model. `qwen3.8:latest` (17.7 GB of weights) is the agent and policy workhorse (Δ65); requests pin `num_ctx` well below the unit's 262,144 [A: 32,768] to bound the KV cache, the gate flags a saturated context (§5.6.3), and the probe records `/api/ps`'s `size_vram` at that setting. After a batch, the last request sets `keep_alive` to 0 so the model leaves the GPU.
- **flash-next.** `UD-Q4_K_XL` (112.2 GB) cannot fit the 97,887 MiB GPU, so it needs CPU offload into host RAM; `UD-IQ4_XS` (94.6 GB) is at the limit before any KV cache. Either runs only in an exclusive window: no solver lane, no sandbox job, no other GPU user, the host-RAM share checked first. Whether its tool calls work through Ollama is a probe (§2: the two endpoints disagree on its capabilities); until then agent mode stays on `qwen3.8:latest` (Δ65).
- **The calendar lock.** A per-user lock (`flock` on a file under `$XDG_RUNTIME_DIR`) is held by every Qwen batch and every flash-next window; the GPU is also shared with the Lean course's par runs (design §11.1), which the human schedules around.
- **GPU-hour split.** The registry's split (Δ75: Q07 1, Q12 and R12 10, Q15 and R15 3, Q18 and R16 9) is an assumption until the throughput probe of §11 step 3d (DV0 measured one sample, 121.7 tok/s); DV4 revises it with that probe in a new entry, as Δ75 asks.
